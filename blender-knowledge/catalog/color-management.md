### AgX — the 4.0 default view transform · `✅ solid` · Blender 4.0+
**AgX replaced Filmic as the default view transform in Blender 4.0. It is a sigmoid-driven, scene-referred, filmic tone mapper with 16.5 stops of dynamic range. Bright/saturated colors desaturate toward white as they clip, mimicking how physical film handles overexposure. This is a deliberate design — it prevents harsh clipping and produces natural highlight rolloff. The tradeoff is that it intentionally desaturates highly-saturated or dark, richly-colored subjects.**
- **How:** In the Properties panel → Render → Color Management, View Transform defaults to 'AgX' in all new.blend files created with Blender 4.0+. In bpy: `bpy.context.scene.view_settings.view_transform = 'AgX'`. No further action needed for photorealistic or PBR work — it is the correct default.
- **Gotchas:** Any .blend file created in Blender 3.x still defaults to Filmic. When opened in 4.x the saved view transform persists — it does NOT auto-upgrade to AgX. Headless scripts that load old .blend files must explicitly set view_transform.; AgX desaturates highly-saturated, dark, or vivid colors more aggressively than Filmic did. Stylized/painterly/toon art with punchy colors will look muted compared to the artist's intent.; The 'Look' setting under AgX offers only three options: None, Punchy, and Greyscale. The full contrast range (Very Low / Low / Medium / High / Very High) belongs to Filmic and is stale/irrelevant under AgX.; EXR, HDR, and DPX output formats bypass the view transform entirely — they store scene-linear values. PNG/JPEG/BMP/TIFF bake in the view transform. For a sprite pipeline outputting PNG the chosen view transform is load-bearing.
- **For Studio:** For the TRELLIS → GLB → headless sprite pipeline: if the goal is painterly / saturated / stylized sprite art with vivid colors, AgX is the WRONG default. See recipe 'standard-for-stylized-sprites'. Use AgX only if the output aesthetic intentionally targets photorealistic desaturated film look.

### Exposure, Gamma, and Look — per-render tuning knobs · `✅ solid` · Blender 4.0+
**These three parameters adjust the final display image on top of the chosen view transform. Exposure shifts the overall brightness in EV stops before tone mapping is applied (formula: output = render_value × 2^exposure). Gamma applies a power curve to the output after tone mapping. Look applies a pre-baked contrast/color LUT on top of the view transform. These are scene-level render settings, not compositing — they affect every output PNG baked through the color management pipeline.**
- **How:** ```python
scene = bpy.context.scene
# Exposure: +1.0 = twice as bright, -1.0 = half as bright
scene.view_settings.exposure = 0.0
# Gamma: >1.0 brightens midtones, <1.0 darkens midtones
scene.view_settings.gamma = 1.0
# Look: 'None' is clean baseline; other values depend on view_transform
scene.view_settings.look = 'None'
```
For headless sprite rendering, setting all three explicitly prevents inheriting saved values from the.blend file.
- **Gotchas:** Exposure and gamma are both present in old 3.x files. When loading a 3.x file headless, the saved exposure (e.g., 0.5 or -0.5) will persist unless explicitly reset.; Look values available depend on the view_transform. Under AgX: None, Punchy, Greyscale. Under Filmic: None + 7 contrast presets. Under Standard and Khronos PBR Neutral: effectively only None. Setting a Look value that doesn't exist for the current view_transform silently falls back to None.; Exposure shifts happen before tone mapping — raising exposure with AgX will push more values into the desaturation zone. If using AgX and colors look washed, lower exposure first before switching view transforms.; Gamma correction here is on top of the view transform's built-in gamma encoding. Do not double-apply: if display_device is sRGB (standard), that already handles the 2.2 display gamma. The gamma knob here is a creative offset, not the display gamma — keep it at 1.0 unless you need a specific stylistic correction.; EXR output ignores all three settings — exposure, gamma, and look are only baked into formats that apply view transform (PNG, JPEG, TIFF).
- **For Studio:** For the headless sprite pipeline: set exposure=0.0, gamma=1.0, look='None' as the clean baseline. Any brightness correction should come from scene lighting (light energy values), not the exposure knob — that keeps the pipeline deterministic. Only adjust these if a specific batch of GLBs renders consistently too bright or too dark across the board.
- **Verify (solid):** Exposure formula (output = render × 2^exposure) confirmed by Blender API docs and search results. Look options per transform confirmed by search result citing AgX-specific Looks (None/Punchy/Greyscale) vs Filmic's wider range. | cross-family (deepseek-v3.1): confirmed — All three parameters (exposure, gamma, look) are valid ColorManagedViewSettings properties that work with all view transforms. [confirmed by 1 of 1 juror(s) [confirmed]]
- **Sources:** [Blender Python API — ColorManagedViewSettings](https://docs.blender.org/api/current/bpy.types.ColorManagedViewSettings.html) — exposure, gamma, look, and view_transform are all properties of bpy.types.ColorManagedViewSettings, accessible via scene.view_settings. ; [SuperRenders — Blender Render Settings Guide](https://superrendersfarm.com/article/blender-render-settings-optimization-guide) — Use the Exposure slider instead of cranking up light intensities; Look = 'None' is neutral; 'High Contrast' adds punch but risks blown highlights. ; [Blender 4.0 developer forum — AgX Look options](https://projects.blender.org/blender/blender/pulls/111099) — AgX supports seven contrast Looks operating in AgX Log at 0.18 middle grey pivot, plus Punchy and Greyscale; the contrast range Looks were designed for Filmic.

### Filmic — legacy view transform (Blender 3.x default) · `✅ solid` · Blender Available in 4.x, was default in 2.79–3.6
**Filmic was the default view transform from Blender 2.79 through 3.6. It is a sigmoid-based tone mapper with a wider effective dynamic range than Standard and a filmic S-curve that softens both shadows and highlights. It offers 7 contrast Look presets (Very Low / Low / Medium / High / Very High Contrast, plus Punchy and Greyscale). It remains available in 4.x but is no longer the default.**
- **How:** `bpy.context.scene.view_settings.view_transform = 'Filmic'`. Set Look via `scene.view_settings.look = 'High Contrast'` (or other values). Exposure and gamma work identically to AgX.
- **Gotchas:** Any .blend file from 3.x opened in 4.x retains Filmic as the stored view transform. Headless scripts must override explicitly if AgX output is desired.; Filmic has a lower effective dynamic range than AgX and handles wide-gamut inputs less well — documented weakness in the 4.0 release notes.; The Filmic contrast Looks (Very Low, Low, Medium, High, Very High) are the ones designed for Filmic. Under AgX, only Punchy and Greyscale are meaningful.; For new projects in 4.x, Filmic is legacy. It is kept for backward compatibility and specific artistic looks that matched old Filmic output.
- **For Studio:** Do NOT use Filmic for new sprite renders — it is superseded. The pipeline should explicitly set view_transform to either 'Standard' (stylized/painterly sprites) or 'AgX' (photorealistic renders) in every headless script to avoid inheriting stale Filmic from opened.blend files.

**A complete, copy-pasteable bpy color management block for the TRELLIS → GLB → headless sprite render pipeline. Sets all four color management properties explicitly so the output is deterministic regardless of which.blend file is loaded, whether it was created in Blender 3.x or 4.x, and whether the user had changed any settings interactively.**
- **How:** ```python
import bpy def configure_color_management_for_sprite_render(scene=None): """Configure Blender color management for stylized 2D sprite output. For saturated / painterly / stylized art: - view_transform = 'Standard' (no filmic desaturation) For photorealistic / PBR-accurate output: - view_transform = 'AgX' (Blender 4.0+ default) For PBR base-color fidelity (Blender 4.2+ only): - view_transform = 'Khronos PBR Neutral' """ if scene is None: scene = bpy.context.scene # Display device: sRGB is correct for PNG/JPEG sprite output scene.display_settings.display_device = 'sRGB' # View transform: 'Standard' for stylized art, 'AgX' for photorealistic scene.view_settings.view_transform = 'Standard' # <-- change to 'AgX' for PBR # Exposure in EV stops (0.0 = no shift); adjust scene lighting instead scene.view_settings.exposure = 0.0 # Gamma creative offset (1.0 = no correction; display gamma handled by OCIO) scene.view_settings.gamma = 1.0 # Look: artistic LUT on top of view transform; 'None' = clean baseline scene.view_settings.look = 'None' # Ensure film alpha for transparent sprite renders scene.render.film_transparent = True # Call before render
configure_color_management_for_sprite_render()
bpy.ops.render.render(write_still=True)
```

If a custom OCIO env var is set, these strings may be different.; 'Khronos PBR Neutral' requires Blender 4.2+. Attempting to set it on 4.0/4.1 raises a ValueError. Add a version check: `if bpy.app.version >= (4, 2, 0)` before using it.; scene.view_settings.look = 'None' must be the string 'None', not Python None. Setting it to Python None will raise a TypeError.; display_settings.display_device must be set BEFORE view_transform — the view transform options available depend on the display device.; This block must run after the scene is loaded and before `bpy.ops.render.render()`. If called before `bpy.ops.wm.open_mainfile()`, settings will be overwritten by the loaded file.
- **For Studio:** Drop this function into every headless `--python` render script in the TRELLIS → GLB pipeline. The choice between 'Standard' and 'AgX' is the single most impactful color decision for stylized sprite output — Standard for saturated stylized characters, AgX only if PBR realism is the target for a specific batch.

### Khronos PBR Neutral — albedo-faithful tone mapper (added Blender 4.2) · `✅ solid` · Blender 4.2+
**The Khronos PBR Neutral tone mapper was added in Blender 4.2 as a fourth view transform option. Its design goal is strict sRGB base-color fidelity: under grayscale (neutral) lighting, the sRGB base color of a PBR material should read through in the output render without saturation loss or hue skew. It maps colors 1:1 up to a ceiling value, then compresses the remaining headroom for highlight rolloff. Unlike AgX (which deliberately desaturates highlights for a film look), PBR Neutral preserves albedo chroma. Unlike Standard (which clips hard), PBR Neutral has gentle highlight compression.**
- **How:** `bpy.context.scene.view_settings.view_transform = 'Khronos PBR Neutral'`. Available only in Blender 4.2+. No additional Look presets — only 'None' applies.
- **Gotchas:** Only available in Blender 4.2 and later. Scripts targeting 4.0 or 4.1 will fail with an invalid enum error if this value is set.; Designed for well-exposed scenes with grayscale / neutral lighting. Under strongly colored or HDR lighting it can produce oversaturated results compared to AgX.; Positioned for product visualization and e-commerce (CAD, architecture, glTF web viewers). Its albedo-fidelity guarantee is strongest under controlled neutral-light conditions.; For stylized sprite art with colored scene lighting (neon, atmospheric tints), PBR Neutral may oversaturate highlights. Standard with exposure=0 is safer in that case.; Adopted by Three.js, Filament, Babylon.js, PlayCanvas — a common baseline for glTF web rendering interoperability.
- **For Studio:** Potentially useful for sprite turnaround renders where the reference GLB has carefully calibrated PBR materials and the studio wants the output PNG colors to match the base-color values in the texture files. Requires Blender 4.2+. Compare against Standard on the same test render — whichever better matches the hand-painted texture palette wins. Not a replacement for Standard when scene lighting is strongly colored.

### OpenColorIO config — custom OCIO and headless env setup · `✅ solid` · Blender 4.0+
**Blender's entire color management system is built on OpenColorIO (OCIO). The active config is the bundle shipped with Blender (at `blender/datafiles/colormanagement/config.ocio`). This config defines all available view transforms, looks, colorspaces, and display devices. For pipelines that need ACEScg, custom Looks (LUTs), or additional display devices (Display P3, BT.1886), a custom OCIO config can be swapped in. The display device is set via `scene.display_settings.display_device` and controls which output colorspace is targeted (typically 'sRGB').**
- **How:** Setting a custom OCIO config:
```bash
# Method 1: env var (affects ALL OCIO-aware software on the system)
export OCIO=/path/to/custom/config.ocio
blender --background --python render.py # Method 2: bat file (Windows — Blender-specific, safer)
SET OCIO=E:\AI\ocio\config.ocio
"C:\Program Files\Blender Foundation\Blender 4.4\blender.exe" --background --python render.py
```
In bpy, set display device:
```python
bpy.context.scene.display_settings.display_device = 'sRGB'
```
Available display devices depend on the active OCIO config.
- **Gotchas:** The OCIO environment variable affects ALL OCIO-aware software running on the system (Nuke, Houdini, etc.). Use a bat/shell wrapper to scope it to Blender only, as recommended by the OCIO community.; Blender 4.x ships an OCIOv2-compatible config. Some legacy OCIO v1 configs (e.g., old Filmic Blender releases from sobotka.github.io) may not load cleanly under 4.x — the default Blender config is the safest baseline.; Known issue (developer.blender.org T85084): with custom OCIO configs, color transforms may NOT be applied to viewport renders — everything renders to scene linear regardless of output format. This affects headless viewport renders but not full Cycles/EEVEE renders via `bpy.ops.render.render()`.; The display_device 'sRGB' is the correct target for PNG/JPEG sprite output destined for web or game engine import. Use 'Display P3' only if the target display and workflow are P3-aware.; A Blender 5.0 redesign of the color management system is in discussion (devtalk.blender.org) — expect the OCIO config structure to change in 5.0. The 4.x config and bpy API are stable for the current pipeline.
- **For Studio:** For the headless sprite pipeline: use the DEFAULT Blender OCIO config (no OCIO env var). The default config provides sRGB, AgX, Standard, Filmic, and Khronos PBR Neutral — all that is needed. Custom OCIO adds complexity and introduces the viewport render color-transform bug. Set `display_device = 'sRGB'` explicitly in every headless script.

### Texture color space: sRGB vs Non-Color — import correctness · `✅ solid` · Blender 4.0+
**Every texture imported as an Image Texture node must have its color space set correctly or the render will be wrong. Rule: color textures (Base Color / Albedo / Diffuse / Emission color maps) must be tagged sRGB — Blender converts them to linear for rendering. Data textures (Normal Maps, Roughness, Metallic, Occlusion, Height/Displacement) must be tagged Non-Color — Blender copies raw values without any gamma decode. Getting this wrong produces incorrect normals, incorrect roughness response, and washed/dark albedo.**
- **How:** In bpy when loading textures programmatically:
```python
import bpy
# For albedo / color maps:
tex_node = mat.node_tree.nodes.new('ShaderNodeTexImage')
tex_node.image = bpy.data.images.load('/path/to/albedo.png')
tex_node.image.colorspace_settings.name = 'sRGB' # For normal / roughness / metallic / AO maps:
tex_node2 = mat.node_tree.nodes.new('ShaderNodeTexImage')
tex_node2.image = bpy.data.images.load('/path/to/normal.png')
tex_node2.image.colorspace_settings.name = 'Non-Color'
```
Blender auto-detects based on filename conventions (_normal, _roughness, etc.) when using the Principled BSDF drag-and-drop, but headless scripts that load images explicitly must set this manually.
- **Gotchas:** Blender 4.1 had a reported bug where baked Non-Color images could have improper sRGB compression applied during image-view display (issue #121635). This is a display artifact, not a render artifact — renders were correct.; PNG files with embedded ICC profiles can confuse Blender's auto-detection. When loading TRELLIS-output GLBs with bundled textures, verify that the albedo texture is tagged sRGB and normal/roughness are Non-Color in the loaded material.; EXR textures loaded into Blender are assumed scene-linear regardless of the colorspace_settings tag — do not tag EXR as sRGB.; The colorspace_settings.name string must match an OCIO colorspace name in the active config. In Blender's default config the valid values include 'sRGB', 'Non-Color', 'Linear', 'Filmic Log', 'Raw'. 'Linear Rec.709' is available in some configs.; If a Normal Map texture is accidentally left as sRGB, the rendered normal response will be incorrect: the gamma decode shifts the 0.5-centered normal values, producing subtle shading errors that are hard to diagnose.
- **For Studio:** For TRELLIS GLB → headless render: GLB files from TRELLIS embed PBR textures. When loading via the Blender glTF importer (`bpy.ops.import_scene.gltf`), the importer sets color spaces correctly per glTF spec (base color = sRGB, normal/roughness/metallic = Non-Color). Verify post-import if using custom material setups.
- **Verify (solid):** Color-texture = sRGB / data-texture = Non-Color is a well-established Blender convention confirmed by multiple sources. Blender issue #121635 confirms the 4.1 display (not render) bug. | cross-family (deepseek-v3.1): confirmed — Correct distinction between sRGB for color textures and Non-Color for data textures is essential for proper rendering. [confirmed by 1 of 1 juror(s) [confirmed]]

### Standard view transform — preserving saturation for stylized sprite art · `▸ plausible` · Blender 4.0+
**The 'Standard' view transform applies only the display transfer function (sRGB gamma encode) with no tone mapping, no filmic rolloff, no desaturation. Colors are rendered with full saturation and the contrast that comes directly from the scene lighting — clipping hard at display white rather than rolling off. For stylized, painterly, or toon game sprites with saturated palettes (the painterly stylized visual canon), this is the correct choice. It prevents AgX from washing out dark, richly-saturated skin tones, neon accents, or hand-painted texture hues.**
- **How:** Set in bpy (headless script):
```python
import bpy
scene = bpy.context.scene
scene.view_settings.view_transform = 'Standard'
scene.view_settings.exposure = 0.0
scene.view_settings.gamma = 1.0
scene.view_settings.look = 'None'
scene.display_settings.display_device = 'sRGB'
```
All four lines are required in headless mode to guarantee a clean state independent of the loaded.blend file's saved settings.
- **Gotchas:** Standard hard-clips highlights — any surface value above 1.0 scene-linear clips to pure white with no rolloff. This is fine for baked/stylized diffuse sprites but wrong for photorealistic speculars or HDR environment maps.; Standard does NOT apply a Look — the Look dropdown has no effect under Standard in 4.x.; Because Standard simply gamma-encodes, the output is sensitive to scene exposure.
