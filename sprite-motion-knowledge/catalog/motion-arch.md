### Godot 4 consumption pattern (AnimatedSprite2D + Skeleton2D / Spine runtime) · `recommended` · ▸ reproduced
**Godot 4 offers two paths for consuming character animation — flat sprite-sheet via AnimatedSprite2D/SpriteFrames for pure frame-flip, and Skeleton2D/Bone2D or Spine-Godot extension for rig-driven deformation — and the pipeline must target one explicitly per character.**
Path A (frame-flip, recommended for this studio): AnimatedSprite2D node + SpriteFrames resource. Import atlas PNG, set hframes/vframes, assign frames per animation name, set loop mode (LOOP_LINEAR for idle/walk, LOOP_NONE for attack/hurt/death), set FPS per animation. call play('walk') at runtime. Signals: animation_finished for oneshots, frame_changed for hitbox/event sync. AnimationPlayer can drive the same Sprite2D frame property for events (hitbox enable on frame N). Path B (rig-driven): Skeleton2D + Bone2D hierarchy inside Godot 4 natively, or Spine-Godot GDExtension for characters animated in Spine. Spine exports.skel/.spine-json +.atlas +.png; the spine-godot extension loads these as SpineSkeletonDataResource on a SpineSprite node with multi-track animation mixing. Path A is correct for the studio's Blender-rendered painterly 2.5D sprite output. Path B is suitable if a Spine rig intermediate is used for AI-polish-lane idle animations.
- **For the pipeline:** The studio's primary output (Blender 8-view renders → AI-repainted PNGs) maps directly to Path A. Only add Path B (Spine runtime) if the idle/breath animations are built in Spine rather than rendered frame-by-frame — adding the Spine GDExtension dependency for only one animation type is not worth it.

### Motion cage rendered per direction (8-view orthographic batch) · `recommended` · ▸ reproduced
**Rendering the animated 3D proxy from 8 fixed orthographic camera angles in a single Blender batch pass guarantees consistent silhouette, proportions, and weapon position across all directions without re-generating 80 independent images.**
In Blender, parent the 3D proxy mesh to a root object. Set one orthographic camera facing the character's front. Animate the root object rotating 0°→315° in 8 keyframes (45° steps) and set Render Animation — Blender renders one frame per direction per animation pose. All 8 views share identical lighting, scale, and geometry so weapon tip, foot contact, and head position are spatially consistent by construction. This is categorically different from generating 8 separate AI images, which drift in proportions and costume detail between directions. Output: per-direction PNG sequences, one sequence per animation.
- **For the pipeline:** This is the studio-proven path for rigid-weapon consistency (TRELLIS.2-4B mesh → 8-view Blender render). The open gap is repaint to painterly, which is handled by the AI-polish lane (ControlNet/Qwen-Image-Edit), not by re-generating from scratch.

### Per-character animation contract (manifest) · `recommended` · ▸ reproduced
**A small per-character YAML/JSON manifest (views, animations+frame-counts+loop flags, anchors, layers) converts 'make a cool animation' into a verifiable pipeline target with zero ambiguity.**
Author one manifest per character specifying: 8 views (N, NE, E, SE, S, SW, W, NW); animations with frame count + loop flag — idle(6,loop), walk(8,loop), run(8,loop), attack_slash(10,oneshot), attack_cast(12,oneshot), hurt(4,oneshot), death(12,oneshot), block(6,loop); anchors — root/head/left_hand/right_hand/weapon_grip/weapon_tip/front_foot/back_foot; layers — body/weapon/shadow/fx. Every downstream stage (rig, Blender render, AI repaint, sheet pack, engine import, QA) targets the same spec. The verifier script checks rendered frame counts and presence of each anchor export against the manifest.
- **For the pipeline:** Without this contract the studio generates arbitrary frame counts per pass and cannot automate QA. One manifest per character unlocks motion-verify automation and makes resumable pipeline runs safe (skip complete = spec-complete).

### Sprite-sheet packing and atlas layout (JSON-hash / row-per-animation) · `recommended` · ▸ reproduced
**Packing per-direction animation frames into a consistent atlas layout (one row per animation, direction-named keys, JSON-hash metadata) is what lets Godot 4 AnimatedSprite2D and UE5 Paper2D consume sprites without bespoke importer code.**
The standard layout: each animation-direction combination occupies one horizontal strip in the atlas PNG (e.g., idle_S row, walk_S row, attack_S row, then repeat for SW, W, NW, N, mirrored directions). The accompanying JSON-hash metadata file maps sprite name keys (e.g., 'walk_S_03') to atlas coordinates (x, y, w, h), plus trim offsets and pivot points. Godot 4 imports via SpriteFrames panel (hframes × vframes grid or individual frame add). UE5 Paper2D imports via JSON-formatted sprite sheet auto-importing sprites and auto-generating flipbooks. TexturePacker (commercial) and free alternatives (FreeTexturePacker, ToolBuddy) produce both layouts from a folder of PNGs.
- **For the pipeline:** Use a single atlas per character per direction-group (e.g., all combat animations for South direction in one atlas). Separate body/weapon/shadow atlases if layer-compositing is needed at runtime (see layer-separation recipe). Consistent naming walk_S_00..walk_S_07 enables Godot auto-slice and UE5 alphabetical-order flipbook auto-generation.

### UE5 Paper2D consumption pattern (Sprites + Flipbooks) · `recommended` · ▸ reproduced
**UE5 Paper2D consumes 2D character animation as Sprite assets extracted from an atlas PNG plus Flipbook assets that sequence those sprites at a specified FPS — the output format the studio's atlas-pack step must produce.**
Enable the Paper2D plugin (Edit → Plugins). Import the atlas PNG; use the Sprite Editor to extract individual frames (or use JSON sprite sheet import for automatic extraction). Create Flipbook assets either manually (add sprites, set duration per keyframe, set overall FPS) or via right-click → Create Flipbook on selected sprites in alphabetical order. Attach a Flipbook Component to the character Blueprint; set Source Flipbook, Play Rate, and Sprite Color. Switch flipbooks at runtime (SetFlipbook()) to transition between idle, walk, attack states. Paper2D does not have a built-in state machine — a separate Animation Blueprint or simple Enum switch drives flipbook selection.
- **For the pipeline:** UE5 Paper2D is lower-level than Godot's AnimatedSprite2D (no per-animation loop mode — loop is set on the Flipbook asset itself). The studio must produce one Flipbook asset per animation-direction combination (e.g., walk_S, walk_SW…). JSON sprite sheet import from the atlas pack step saves manual sprite extraction.

### 3-lane production model (rig-proxy / AI-polish / manual-keyframe) · `recommended` · · community
**Separating motion generation into three lanes — rig/proxy for combat, AI for life/idle, manual for hit frames — matches tool strength to animation type and avoids over-applying diffusion where it drifts.**
Lane A (rig/proxy): combat animations where weapon rigidity and hitbox accuracy are required — drive via 3D proxy/mesh (TRELLIS.2-4B or Step1X-3D), render 8 views in Blender with orthographic camera, get rigid weapon across frames. Lane B (AI-polish): idle breathing, blink, cloth-flutter, ambient wind — low-motion passes where diffusion inbetweening or ControlNet-guided repaint poses no continuity risk. Lane C (manual keyframe): anticipation + impact frames in attack animations where feel > automated smoothness — a human artist places the 2-4 hit frames directly. The Spine spine-json intermediate is the handoff format between all three lanes.
- **For the pipeline:** Using diffusion on Lane A animations (combat) produces weapon drift and face mutation; the studio weapon-drift finding (canon) confirms this. Lane C is non-negotiable for combat juiciness — automated motion always produces mushy hits.

### 8-direction consistency strategy (5 unique + 3 mirrored) · `recommended` · · community
**For symmetrical characters, drawing 5 unique direction sets (S, SW, W, NW, N) and mirroring SW→SE, W→E, NW→NE cuts per-character animation work by ~37% while maintaining visual fidelity for symmetrical equipment.**
The standard JRPG 8-direction approach uses 5 unique view passes: South (front), Southwest, West (side), Northwest, North (back). Southeast, East, and Northeast are horizontal mirrors of SW, W, NW respectively. This works cleanly for symmetrically-equipped characters. Asymmetric equipment (single-shoulder pauldron, off-hand shield, asymmetric hairstyle) requires unique frames for all 8 views. The manifest flags each character's symmetry class so the pipeline knows which directions to render vs. mirror. For the AI-repaint pass on Blender renders, mirrored directions can reuse the painted left-side texture flipped — ensuring paint style is identical.
- **For the pipeline:** Most JRPG characters can use 5-unique + 3-mirrored, cutting a significant share of Blender render + AI-repaint cost. The manifest must declare symmetry_class (symmetric | asymmetric) and list which directions are mirrors of which source directions.

### JRPG frame budget table (idle/walk/attack/hurt/death) · `recommended` · · community
**Standard JRPG 2D character animation budgets — idle 4-8 frames, walk 6-8 frames, attack 8-12 frames (anticipation+strike+recovery), hurt 3-5 frames, death 8-15 frames — set the contract ceiling for every animation in the manifest.**
Validated ranges per animation type for high-fidelity (32px+ sprite, Sea of Stars / Octopath production tier): idle 4-8 frames at 6-8 FPS (loop); walk 6-8 frames at 8-10 FPS (loop); run 6-8 frames at 10-12 FPS (loop); attack_slash 8-12 frames at 12-16 FPS structured as anticipation(2-3) + strike(1-2) + recovery(3-4) (oneshot); attack_cast 10-14 frames (oneshot); hurt 3-5 frames at 10-12 FPS (oneshot); block 4-6 frames (loop or oneshot); death 8-15 frames at 8-10 FPS starting fast (oneshot). The critical frame-timing principle: slow anticipation → fast strike → slow recovery. Frame-count targets drive Blender render frame counts and the AI-repaint budget per character.
- **For the pipeline:** These ceilings prevent pipeline over-production (32-frame idles) and under-production (2-frame attacks that feel unresponsive). The manifest should encode the exact targets, not just minimums, so the verifier can flag under-delivery.

### Layer separation strategy (body / weapon / shadow / fx) · `recommended` · · community
**Rendering and storing body, weapon, shadow, and FX as separate sprite layers — rather than a single flat composite — allows runtime weapon swapping, dynamic shadows, and hit-flash fx without re-baking the full sheet.**
In the Blender render pass, use separate render layers or compositor output nodes for: body (character without weapon or shadow), weapon (the prop alone with transparency), shadow (ground-contact shadow blob), fx (particle/glow overlays baked as separate channel). Each layer is packed into its own atlas with identical frame layout to the body atlas — same frame count, same dimensions. At runtime in Godot 4, multiple AnimatedSprite2D nodes (or CanvasItem Z-order children) composite the layers in draw order: shadow → body → weapon → fx. This enables swap-in of different weapon sprites at runtime without re-baking character animation, matching the studio manifest weapon_grip/weapon_tip anchor export.
- **For the pipeline:** The weapon-drift canon finding means weapons should ALWAYS be a separate layer, never baked into body renders. The Blender mesh-render path makes this trivially achievable: hide body mesh, render weapon mesh alone against transparency, same 8-view batch.
