# midly with strict: what the law's parser rejects, compiled — generator packet

Written by `kimi-k2.6:cloud` through `scripts/openrouter_lane.py`; unverified until the wave's verification record says otherwise.

midly 0.5.3 strict rejects malformed SMF data that alloc-only silently masks or ignores: out-of-range restricted integers (e.g., u4 > 0x0F in a MidiChannel meta-event), truncated MTrk chunks, and track count mismatches. These become ErrorKind::Malformed. The strict configuration compiles and runs inside a wasm32-unknown-unknown cdylib export, returning u64 status codes for Ok (0), Invalid (1), Malformed (2), and SMPTE refusal (3), never panicking. 1) A header claiming two tracks with only one present parses Ok under alloc-only and fails under strict (Malformed). 2) An MTrk chunk whose declared length exceeds file bytes parses Ok under alloc-only (uses remainder) and fails under strict (Malformed). 3) A MidiChannel meta-event with data 0xFF parses Ok under alloc-only (masked to u4) and fails under strict (Malformed). 4) A wasm32 cdylib export maps midly ErrorKind::Invalid to status 1 and ErrorKind::Malformed to status 2. 5) SMPTE timing (header word with bit 15 set, e.g., 0xE800) is parsed as Timing::Timecode; the law refuses it with status 3.
