### Borrow stack data in worker threads with thread::scope (1.63); thread::spawn needs move and 'static
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust 1.63+ for thread::scope and Builder::spawn_scoped; thread::spawn any

**std::thread::spawn requires F: FnOnce() -> T + Send + 'static, so a closure borrowing a local is E0373, while std::thread::scope (stable 1.63.0) joins every scoped thread before returning, so workers can borrow slices and write disjoint chunks without Arc.**

- **How:** For a detached or long-lived worker use `thread::spawn(move || ...)` and get the result back with `JoinHandle::join()`, which returns `Err(payload)` when that thread panicked (under panic = unwind only that thread unwinds). For fork-join work over data you own, use `thread::scope(|s| { for (src, dst) in input.chunks(n).zip(out.chunks_mut(n)) { s.spawn(move || ...); } })`: shared `&[T]` reads and disjoint `&mut [T]` writes, no Arc and no 'static. Join a `ScopedJoinHandle` inside the scope when a worker's panic should become a value; otherwise `scope` re-raises it after joining. Use `thread::Builder::new().spawn(..)` (or `spawn_scoped`, 1.63.0) when a failure to create a thread must be an `io::Result`, not a panic.
- **Gotchas:** Adding `move` to silence E0373 moves the Vec into one thread, so a second worker cannot use it; scoped threads share it without Arc. Dropping a JoinHandle detaches the thread, and when main returns the process ends and detached threads are shut down. `thread::scope` panics in the caller if an un-joined scoped thread panicked (exit 101 below), which kills a sweep that meant to record the failure. Thread-local destructors of scoped threads may still be running after `scope` returns.
- **In si-rpg-engine:** The offline tools around the law (Phase 2 T5 nightly replay corpus, T6 reachability sweep) can fan work out with scoped threads, but not by calling one native law from several threads: the solver keeps its world in process-global `static mut` state (lib.rs `BODIES` / `COLLIDERS`, rapier_law.rs `SOLVER`). Run one law per process.

### Hand results between threads over mpsc or crossbeam channels and sort by a tag: arrival order is scheduling
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any; Sender: Sync 1.72+; std::sync::mpmc unstable on 1.98.1; crossbeam-channel 0.5.17

**std::sync::mpsc offers an unbounded channel() and a bounded sync_channel(n) (n = 0 is a rendezvous); iterating the Receiver ends only after every Sender is dropped; with several producers the arrival order depends on scheduling, so tag each message and sort before the data reaches a hash or a report.**

- **How:** `let (tx, rx) = mpsc::channel();` clone `tx` per producer, `drop(tx)` the original, then `for msg in rx` or `rx.iter().collect()`. Send `(index, value)` and `sort_by_key(|&(i, _)| i)` before folding or hashing. Use `sync_channel(k)` for back-pressure: senders block when k messages are queued and `try_send` returns `TrySendError::Full(v)`; `sync_channel(0)` hands a value over only when a receiver is waiting. Disconnection is a value, not a panic: send fails once the receiver is gone, recv fails once all senders are gone. Since 1.67.0 std's mpsc is built on crossbeam-channel, and Sender is Sync since 1.72.0. For several consumers or `select!` over channels and timers, use crossbeam-channel 0.5.17 (`bounded`, `unbounded`, zero-capacity, `select!`, `after` / `tick`), because `std::sync::mpmc` is still unstable on 1.98.1 (E0658, feature `mpmc_channel`).
- **Gotchas:** Forgetting `drop(tx)` makes `for msg in rx` block forever. That is a hang, not an error. FIFO holds per channel in send order, not in the order the producers were spawned. `Ok` from `send` does not mean the value was received. Reaching for std's mpmc on stable fails to compile.
- **In si-rpg-engine:** Tools that spread runs of the law across workers (T5 nightly replay corpus, T6 reachability sweep) should send `(run_index, trace_hash)` and sort by run_index before writing the report. The report is then byte-stable and diffable like the golden hashes it summarises.

### Let the compiler infer Send and Sync: they turn data races into E0277/E0499, not race conditions or deadlocks
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any; the disjoint-field closure capture in the gotcha is edition 2021+

**Send and Sync are unsafe auto traits derived from a type's fields. An Rc or raw-pointer field stops a value moving to another thread and a Cell field stops it being shared (both E0277), and two threads writing one variable fail with E0499. A check-then-act on atomics still loses updates.**

- **How:** Read Send as 'ownership may move to another thread' and Sync as '&T may be shared' (T: Sync exactly when &T: Send). The compiler implements both for a struct, enum, tuple or closure when every field or capture has them. The usual non-thread-safe leaves: Rc (neither), Cell / RefCell / UnsafeCell (Send when T: Send, never Sync, so &Cell<T> is not Send), *const T / *mut T (neither), NonNull (not Send), MutexGuard (not Send). Answer E0277 'cannot be sent/shared between threads safely' by changing the type: Rc -> Arc, Cell / RefCell -> an atomic, Mutex or RwLock, a raw-pointer view -> an owned buffer or an index. `unsafe impl Send` is a promise you prove (the Rustonomicon's Carton shows the reasoning), and `impl !Send` is nightly-only. The compiler does not catch race conditions: make each check-then-act one atomic read-modify-write (fetch_add, compare_exchange) or hold one lock across it.
- **Gotchas:** Edition 2021 closures capture disjoint fields: `move || v.len` captures only the usize, so a struct holding a *mut f64 crosses a thread boundary while only Send fields are used and fails E0277 the day an edit touches the pointer (both checks below). E0277's headline names the leaf type (`*mut f64`, `&Cell<u32>`); only the notes below it walk back to your struct. 'Safe Rust has no data races' does not mean 'no races': the Rustonomicon calls race conditions and deadlocks safe; the forced interleaving below loses an update with nothing but atomics.
- **In si-rpg-engine:** solver/src/lib.rs exports raw `*mut f64` from `bodies_ptr()` and `colliders_ptr()`. Any Rust-side host wrapper that stores those pointers is automatically neither Send nor Sync. That is the compiler enforcing one-thread use of the static buffers, so keep it rather than adding `unsafe impl Send`.

### Make parallel float reductions bit-reproducible: fixed chunks, per-chunk partials, combined in index order
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any; rayon claims per rayon 1.12.0 / rayon-core 1.13.0

**Float addition is not associative, so a parallel sum's bits depend on where the input is split and how the partials are combined. rayon's sum, reduce and fold leave that order unspecified (fold's docs call its break points nondeterministic), so results can change between runs and thread counts. A chunk size fixed in the code, with partials folded sequentially in chunk order, gives the same bits for any thread count.**

- **How:** Treat the reduction tree as part of the computation: a constant chunk size (never derived from the thread count or `available_parallelism()`), a sequential sum inside each chunk, each partial stored at its chunk index, then one sequential fold over the partials in index order. With std: `thread::scope` plus `partials.chunks_mut(per_thread)`. With rayon 1.12.0: fixed-size `par_chunks(CHUNK)` / `fold_chunks` producing partials that you combine yourself in index order; do not call `.sum()` or `.reduce()` on floats and expect stable bits. This is the pattern Rapier 0.35.3 uses in its parallel body-update pass (`par_chunks(256)`, results combined in order). rayon's reduce contract asks for an associative op; float `+` is not one, while wrapping integer addition is.
- **Gotchas:** The fixed-chunk result is reproducible across thread counts but is generally not the bits of the plain sequential sum (the check prints false), so changing CHUNK changes the result and must be treated like any other change to the computation. 'Same input on the same machine' is not enough under rayon: its docs call fold's break points nondeterministic, and join runs on work stealing. On wasm32-unknown-unknown rayon quietly falls back to a single-threaded mode, so a parallel float reduction there can give different bits from the same code on a native host.
- **In si-rpg-engine:** Inside the wasm law nothing is reduced in parallel: Rapier runs its staged solver with one worker when `parallel` is off. The rule binds tools that aggregate floats across runs (T5 corpus statistics, T6 sweep metrics) and any future native build that turns rapier's `parallel` on.

### Pick Mutex, RwLock or Condvar by job, and decide what a poisoned lock means before a panic decides for you
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any; Condvar::wait_while 1.42+, Mutex::clear_poison 1.77+

**Mutex<T> hands one thread &mut T at a time; RwLock<T> allows many readers or one writer under an OS-dependent priority policy; Condvar::wait_while sleeps until a predicate over the guarded state holds; a panic while holding a Mutex (or an RwLock in write mode) poisons it, and poisoning is only advisory.**

- **How:** Mutex for state every user mutates; RwLock only for read-mostly state, and never re-lock it on the thread that holds it; Condvar for 'wait until the state says X', always `cv.wait_while(lock.lock().unwrap(), |s| !ready(s))` (1.42.0), never a bare `wait`, because wakeups can be spurious and notify_one / notify_all are not buffered. Keep each guard in the smallest block, never call unknown code while holding one, and take several locks in one fixed global order. Decide poisoning per lock: `match m.lock() { Ok(g) => .., Err(p) => refuse or repair via p.into_inner() }`, then `m.clear_poison()` (1.77.0) once the invariant is restored. Detect a same-thread relock with `try_lock()`: it returns `TryLockError::WouldBlock` where `lock()` would never return.
- **Gotchas:** `.lock().unwrap()` everywhere turns one panic into a panic in every thread that touches the lock; the docs describe that propagation as the default intent, so choose it deliberately. Relocking a Mutex on the holding thread is unspecified and never returns (panic or deadlock). A waiting writer may block new readers, so a recursive `read()` can deadlock. A reader's panic does not poison an RwLock. Unsafe code cannot rely on poisoning for soundness: some panics (a second panic inside Drop, foreign exceptions) leave a mutex unpoisoned. On 1.98.1 the non-poisoning locks (`std::sync::nonpoison`) are still experimental. Under panic = "abort" a panic ends the process, so no survivor ever sees a poisoned lock.
- **In si-rpg-engine:** If a native host puts the law behind a Mutex (see the native-call recipe), a poisoned law lock means the world may be half-stepped. Refuse the call and return 0, as the exports already do for NaN, instead of stepping on from `into_inner()`. The solver's release profile (`panic = "abort"` in solver/Cargo.toml) ends the process on a panic, so poisoning only arises in unwind builds such as tests.

### Publish data across threads with a Release store and an Acquire load; keep Relaxed for counters
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any

**Rust atomics follow the C++20 model: a Release store paired with an Acquire load of the same atomic makes every earlier write visible after the load, Relaxed only makes each operation atomic, SeqCst adds one total order, and an ordering an operation cannot take is a deny-by-default lint (or a run-time panic when it arrives in a variable).**

- **How:** Message passing: the writer does `DATA.store(x, Relaxed); READY.store(true, Release);` and the reader does `while !READY.load(Acquire) { std::hint::spin_loop() }` then `DATA.load(Relaxed)`. Counters and statistics: `fetch_add(1, Relaxed)` never loses an increment. A busy flag: `compare_exchange(false, true, Acquire, Relaxed)` to enter and `store(false, Release)` to leave (the check runs it as a wasm32-unknown-unknown export, where atomics build without the `atomics` feature). Use SeqCst when several flags must be seen in one global order, or whenever you are unsure. Loads cannot be Release or AcqRel, stores cannot be Acquire or AcqRel, fences cannot be Relaxed, and a compare-exchange failure ordering cannot be Release or AcqRel: `invalid_atomic_ordering` rejects literals. std has no AtomicF64 (E0432): keep an f64 in an `AtomicU64` via `to_bits` / `f64::from_bits`.
- **Gotchas:** x86 is strongly ordered, so a Relaxed-where-Acquire-was-needed bug usually passes tests there; the Rustonomicon says to test concurrent algorithms on weakly-ordered hardware (ARM). Release on a read-modify-write gives a Relaxed load half, so use AcqRel when the RMW both publishes and consumes. An ordering passed through a variable escapes the lint and panics at run time. A data race (conflicting non-synchronized accesses, at least one non-atomic) is undefined behaviour even when the output looks right.

### Treat a future as an inert, pinned state machine: nothing runs until polled, and dropping it cancels it
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust 1.85+ for Waker::noop; pin! 1.68+; async/await edition 2018+

**Calling an async fn only builds a future, a compiler-generated state machine that stores every local alive across an .await. Nothing runs until an executor polls it through Pin<&mut Self>; async-block futures are !Unpin and must be pinned (pin!, 1.68, or Box::pin). Dropping a pending future runs its destructors, and the code after its current .await never executes.**

- **How:** Always `.await` or hand the future to an executor: a bare `step();` is only an `unused_must_use` warning ('futures do nothing unless you `.await` or poll them'), and the body never runs. Rust ships no runtime. Use tokio (or another executor) in programs; in tests, a 10-line `block_on` with `pin!(fut)` and `Context::from_waker(Waker::noop())` (1.85) is enough for futures that finish without waiting on I/O. `Pin::new(&mut fut)` on an async block is E0277 'cannot be unpinned'; the compiler's note says to use `pin!`, or `Box::pin` when the pinned future must outlive the scope. Keep big temporaries out of the state machine by ending their scope before the .await (a 4 KiB buffer held across an await makes the future at least 4096 bytes). Cancellation is drop: tokio's `select!` cancels the losing branches, and a future is cancellation-safe when dropping and recreating it is a no-op. Put cleanup in Drop guards, not after an .await.
- **Gotchas:** A `Waker::noop` busy-poll loop is for tests only: it discards wake-ups, so a future waiting on I/O would spin. Polling a future again after it returned Ready may panic or block. Code after an .await is not guaranteed to run, because an executor, a timeout or `select!` may drop the future at that point (the drop check shows 'after await' never printed).
- **In si-rpg-engine:** The law's exports (`step`, `solver_load`, `solver_step`, `solver_clear_warmstart`) are synchronous and CPU-bound, driven by the JS tick at 1/64 s. A quantum has no I/O to wait on, so the law gains nothing from async. Async belongs, if anywhere, in host and tool I/O around the law.

### Keep the wasm law single-threaded: no threads on wasm32-unknown-unknown, rapier3d-f64's parallel left off
`▸ plausible` · ✓ verified · ✔ compiles as claimed · Rust 1.98.1 on wasm32-unknown-unknown; rapier3d-f64 0.35.3

**On wasm32-unknown-unknown, std::thread::spawn panics (Builder::spawn returns Err) and available_parallelism errs. Shared-memory threads need the unstable `atomics` target feature plus a core and std rebuilt with it (nightly -Zbuild-std): stable 1.98.1's shipped core and std refuse --shared-memory at link time. Rapier 0.35.3 declares no conflict between `parallel` and `enhanced-determinism`, and its changelog says they 'can now be combined' with bitwise-identical results for any pool size.**

- **How:** Probe a target instead of assuming: `std::thread::Builder::new().spawn(..).is_err()`, `std::thread::available_parallelism().is_err()` and `cfg!(target_feature = "atomics")` are 1, 1 and 0 on wasm32-unknown-unknown (checks). Threaded wasm needs `-C target-feature=+atomics,+bulk-memory,+mutable-globals` with `cargo +nightly build -Z build-std=panic_abort,std`, or the experimental wasm32-wasip1-threads target (wasi-threads; links with --shared-memory, --import-memory and --export-memory). For Rapier, read the feature table at the pinned version: at 0.35.3 `parallel = ["dep:rayon", "std", "parry3d-f64/parallel"]`, `enhanced-determinism = ["simba/libm_force", "parry3d-f64/enhanced-determinism"]`, and the only compile_error! pairs `simd8` (an f32-only feature that rapier3d-f64 does not declare) with enhanced-determinism. With `parallel` off, `rapier3d_f64::rayon` and `PhysicsPipeline::configure_thread_pool` do not exist (checks). Rapier's `PhysicsHooks` and `EventHandler` require Sync even with `parallel` off (unless `unsync-callbacks`): hook state goes in atomics, not Cell. Features unify across a build graph, so any crate enabling `rapier3d-f64/parallel` turns it on for everyone; watch it with `cargo tree -e features -i rapier3d-f64`.
- **Gotchas:** Stale advice: 'enhanced-determinism is incompatible with parallel'. Rapier's v0.35.0-beta.0 changelog says the two 'can now be combined' with bitwise-identical results for any thread-pool size, and its current user guide (labelled 0.36) says the same. That is the vendor's claim, not measured here, and the same release's notes say multithreaded trajectories may shift within solver tolerance after the solver rewrite. On stable, `+atomics` only earns the warning 'unstable feature specified for `-Ctarget-feature`: `atomics`' and then a link error, even for a `#![no_std]` module, because core itself was not compiled with atomics. rayon on this target silently runs single-threaded, and its `spawn` may never run.
- **In si-rpg-engine:** solver/Cargo.toml turns on only `enhanced-determinism` for rapier3d-f64 0.35.3 (defaults dim3, f64, std, block-solver; `parallel` off, as solver/FLAGS.md records). Keep it off in the wasm law: the target has no threads to use, and the feature compiles rayon and the parallel code paths into the module whose bytes fixtures/solver.sha256 pins. If a native Godot or Unreal build ever turns `parallel` on, re-measure the golden hash at several thread-pool sizes before trusting Rapier's bitwise claim, and add a CI feature guard (owned by ci-reproducible-builds).
