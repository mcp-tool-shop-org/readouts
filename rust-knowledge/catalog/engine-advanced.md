## [Advanced traits & the type system](traits-advanced.md)

- ✓ **Apply the whole orphan rule: a local type before any uncovered type parameter, and no overlapping impls** — Conversions between the solver's stride-17 body records (solver/src/lib.rs) and Rapier values must go through a local type: `impl From<[f64; 17]> for Vector` is E0117, `impl From<&BodyRecord> for Vector` with a local `BodyRecord` compiles and converts (the BodyRecord check prints `0 1.5 0`).
- ✓ **Choose associated types for one-impl-per-type outputs; enforce associated consts and GATs at compile time** — If the solver grows a Law trait, `const STRIDE: usize` plus an assert-const is how BODY_STRIDE = 17 and COLLIDER_STRIDE = 10 (solver/src/lib.rs) become per-law compile-time facts. A concrete path still sizes the static buffers (`[f64; 64 * <BoxLaw as Law>::STRIDE]` is 1088 elements), but code generic over `L: Law` cannot declare `[f64; L::STRIDE]` on stable, so the buffers stay concrete arrays.
- ✓ **Control what impl Trait captures: RPITIT/async fn in traits (1.75), use<..> (1.82; traits 1.87), 2024 rules** — solver/Cargo.toml pins `edition = "2021"`: any `-> impl Iterator` helper added to solver/src (for example over body records for T2's restore) follows the 2021 capture rules, and moving the crate to 2024 changes borrow behaviour at call sites; run the edition migration and let the pinned golden hash and fixtures/solver.sha256 digest checks decide whether the bump is clean.
- ✓ **Encode solver states as zero-sized type parameters, seal traits privately, and import extension traits** — Engine hook, typestate vs `loaded: Option<Loaded>`: the JS host can call the exports in any order (`solver_step` loads lazily through `ensure`, `solver_clear_warmstart` returns 0 when nothing is loaded), and a type parameter cannot cross `extern "C"`, so the `Option` checks in `ensure`, `solver_step` and `solver_clear_warmstart` (solver/src/rapier_law.rs) stay at the export boundary. Inside, the code already has the typestate shape: `integrate(loaded: &mut Loaded)` and `rebuild_snapshot(loaded: &Loaded, ..)` cannot run without a loaded world. For T2's `solver_restore` (docs/dispatch-t2-restore.md: refuse and change nothing on a bad length, a NaN, a non-unit quaternion or a pair-count mismatch after the collision pass), build a complete `Loaded` from the bytes first and assign it to `SOLVER.loaded` only after every check passes; the boundary check shows the shape (`0 1 1 0 42`: step before load refused, bad restore refused, state kept).
- ✓ **Keep a trait dyn compatible or fence methods with `where Self: Sized`; a &dyn is two words: data + vtable** — rapier3d-f64 0.35.3 puts dynamic dispatch on the solver's path: `PhysicsWorld::step()` is `self.step_with_events(&(), &())` with parameters `hooks: &dyn PhysicsHooks, events: &dyn EventHandler`, and `warm_broadphase` in solver/src/rapier_law.rs passes `&(), &()` to `CollisionPipeline::step`, with `()` as the no-op implementor. The solver's own `step` and `resolve_pair` (solver/src/lib.rs) use no trait objects; on wasm32 each fat pointer is two 32-bit words.
- ✓ **Let auto traits follow the fields, steer them with PhantomData, and know a Drop impl drives drop check** — rapier3d-f64 0.35.3 declares `pub trait EventHandler: crate::utils::MaybeSync`, and `MaybeSync: Sync` unless the crate's `unsync-callbacks` feature is enabled, which solver/Cargo.toml does not do. A solver-side collision log therefore must be Sync: a `RefCell<u32>` counter is E0277 ('required for `Log` to implement `MaybeSync`'), an `AtomicU32` compiles (the AtomicU32 check drops a box onto a slab for 64 quanta at dt = 1/64 with `step_with_events(&(), &log)` and counts 1 started collision). Typed `Handle<T>` wrappers over the body and collider indices would keep the stride-17 and stride-10 buffers apart at zero bytes.
- ✓ **Put the box and product laws behind a Law trait only when Rust code drives both; keep every export monomorphic** — Engine hook, Law trait with static dispatch: solver/src/lib.rs exports the box law as `step` over `BODIES`/`COLLIDERS`; solver/src/rapier_law.rs exports the product law as `solver_load`/`solver_step`/`solver_clear_warmstart` over `SOLVER`. They share constants and buffers, not code, and the law is chosen on the JS side (docs/dispatch-t2-restore.md gives the reference and box laws a records-only save). Introduce `Law` when a Rust-side driver needs both, such as a Rust replay of T2's restore-then-rerun or the host bindings (Godot, then Unreal) planned after Phase 2; until then the two export families are the simpler design.

## [Memory, smart pointers & layout](memory-layout.md)

- ✓ **Budget pointer widths: Box<T> is one word, Box<[T]> and &dyn Trait carry metadata, ZSTs take no space** — The ABI buffers (BODIES and COLLIDERS in lib.rs, HEIGHTS in rapier_law.rs) are statics, neither stack nor heap: all references and raw pointers to a static refer to the same allocation, so their addresses never change. The heap holds the Rapier world, SOLVER.snapshot and the per-quantum scratch Vecs in integrate(). If an ABI buffer ever needs a length chosen at load time, a Box<[f64]> made once with into_boxed_slice keeps the fixed address that a growing Vec lacks.
- ✓ **Count on Option's niche only for std-listed types; give boundary enums #[repr(u8)] and explicit values** — rapier_law.rs keeps `handles: Vec<Option<RigidBodyHandle>>`; RigidBodyHandle is #[repr(transparent)] over rapier's Index { index: u32, generation: u32 }, which has no invalid bit pattern, so each slot costs 12 bytes (measured), harmless at 64 bodies. The body mode travels as the f64 in slot DRIVEN (16) and is tested with == 1.0 / 2.0 / 3.0; if it becomes a Rust enum, #[repr(u8)] plus a TryFrom<f64> keeps a stray 7.0 from JS an error instead of an invalid value.
- ✓ **Keep entities in a generational arena keyed by (index, generation); insertion order hands out the ids** — rapier_law.rs build_world inserts the fixed colliders first, then the heightfield, then each non-carried body, so a record index i is not its RigidBodyHandle index; hence `handles: Vec<Option<RigidBodyHandle>>`. rebuild_snapshot sorts contact pairs by `(collider1.into_raw_parts(), collider2.into_raw_parts())` and writes each index and generation into the hashed bytes, so the hash depends on insertion order (the subject of T3's insertion-order test) and on generations. Today every world is built fresh and nothing is removed, so every generation is 0; once any path removes a body or collider, the generations of everything inserted later shift, and T2's rebuild from bytes would reproduce the snapshot only by replaying the same removals.
- ✓ **Mutate through & only via UnsafeCell-based types; a &T-to-&mut T cast is UB even where the lint is silent** — rapier_law.rs solver_clear_warmstart() collects `core::ptr::from_ref(pair) as *mut ContactPair` for each &ContactPair that `narrow_phase.contact_pairs()` yields, then writes the manifold points through `&mut *ptr`. rapier3d-f64 0.35.3 offers no &mut path: every NarrowPhase accessor (contact_pairs, contact_pair, contact_graph) takes &self and returns shared references, and ContactPair's manifolds and solver_clusters are plain Vec<ContactManifold>, not cells. rustc denies this cast when it is written inline and accepts it once the pointer goes through a Vec (the first two checks), so the export compiles cleanly but sits outside what the std docs and the lint text permit. T2's solver_restore must write warm-start impulses into the same points: build it, and the clear, on a sound path (rebuild the world from the bytes, or a &mut accessor in a pinned rapier patch) rather than on this cast. What Miri's aliasing models say about it is the unsafe-ffi lane's question.
- ✓ **Point Rc/Arc edges one way (strong down, Weak back) or a strong cycle leaks and its destructors never run** — rapier_law.rs builds a fresh parry SharedShape (`pub struct SharedShape(pub Arc<dyn Shape>)`) on every character_shape() call in integrate(): once per non-lifted driven body for move_shape and once per plan for the impulse pass, so each quantum makes one or two new Arc allocations per driven body. Building it once per body in build_world and keeping it in Loaded would make each later use a count bump (a clone shares the allocation, per the check). The shape's numbers are identical, so results should not move; confirm with the golden hash.
- ✓ **Predict destructors: fields drop in declaration order, locals in reverse, statics and forgotten values never** — `static mut SOLVER` in rapier_law.rs is a static, so it is never dropped: its snapshot buffer and loaded Rapier world live as long as the wasm instance. The one release point is replacement: `solver.loaded = Some(loaded)` in ensure() drops the previous Loaded (fields in declaration order, the PhysicsWorld first) before the new one moves in. A T2 solver_restore that rebuilds the world inherits that same drop point.
- ✓ **Put ABI buffers in flat arrays or #[repr(C)]: default repr(Rust) promises no field order or size** — lib.rs exposes `static mut BODIES: [f64; MAX_BODIES * BODY_STRIDE]` (64 x 17) and COLLIDERS (64 x 10), rapier_law.rs HEIGHTS ([f64; 256]); build.mjs indexes a Float64Array at `bodies_ptr() / 8 + i * 17 + slot`. That is the guaranteed case: array element n sits at n*8 bytes, and the wasm check below returns 800 (f64 8-aligned, the static's address a multiple of 8). Keep the ABI as flat arrays or #[repr(C)]; a plain `struct Body { .. }` would give JS no fixed offsets. The coupling no compiler checks is the stride: build.mjs hard-codes 17 and 10 while Rust owns BODY_STRIDE and COLLIDER_STRIDE, so exporting the strides or generating the JS constants would turn a stride change into a loud failure.
- ✓ **Re-read a Vec's pointer after any call that can grow it: growth reallocates and kills raw pointers into it** — rapier_law.rs keeps the snapshot in `static mut SOLVER`'s `snapshot: Vec<u8>`; rebuild_snapshot() clears and refills it every quantum, so capacity persists and the buffer moves only when a quantum's snapshot is longer than every earlier one (more contact pairs or points). snapshot_ptr() and snapshot_len() are valid only until the next solver_* call; build.mjs's snapshotBytes() reads both after the call and copies with .slice(), which is right. The same rule binds T2's restore_ptr(): if the input buffer is a Vec sized to len, JS must take the pointer after the sizing call, never before.
- ✓ **Return Cow when a function usually passes its input through and only sometimes rewrites it** — rapier_law.rs canonicalises signed zero one value at a time (canon() inside push_f64 and write_body), which needs no Cow. The pattern fits a whole-buffer canonicalising or validating pass that usually finds nothing to change, like the check's signed-zero canonicaliser.
- ✓ **Store indices or offsets instead of self-references; use Pin only where an API such as Future::poll needs it** — Nothing in the solver needs Pin: world state sits in `static mut SOLVER`, bodies are named by Rapier handles (indices), body records by position in BODIES, and the snapshot is a byte string. That is what lets T2's solver_restore rebuild a world from bytes: every cross-reference is an index that means the same thing after the rebuild, which a stored address would not.

## [Unsafe Rust, UB & FFI](unsafe-ffi.md)

- ✓ **Choose extern "C" (a panic aborts, 1.81+) or extern "C-unwind" (a panic unwinds) for every boundary fn** — Every solver export is extern "C", the release profile sets panic = "abort", and wasm32-unknown-unknown defaults to panic=abort (measured below), so a panic inside an export (for example the .unwrap() on the plan lookup in rapier_law.rs) aborts inside the module and never unwinds into JS; "C-unwind" would add nothing. Refusals already travel as u32 0 (the errors-panics lane owns that policy; wasm-raw-abi owns what the JS caller sees on an abort). A future native Godot or Unreal build compiled with panic=unwind must keep "C" or wrap each export body in catch_unwind and return 0.
- ✓ **Cross the C ABI only with repr(C) types, scalars and raw pointers; pass strings as &CStr, c"" or CString** — The solver's exports pass only u32, f64, *mut f64 and *const u8, all FFI-safe, which is why the crate is lint-clean; no strings cross. The body, collider and height buffers are f64 arrays addressed by index constants (BODY_STRIDE 17, COLLIDER_STRIDE 10), not repr(C) structs. If a C-header host binding (Unreal, host-embedding lane) wants a struct view, add #[repr(C)] structs whose size matches the stride and assert it at compile time (macros-const lane).
- ✓ **Make raw pointers with &raw const / &raw mut, move bytes with std::ptr, and change addresses with map_addr** — The solver's release profile keeps debug assertions off, so these precondition checks never run in the wasm; a native dev-profile test of the law gets them. T2's `solver_restore` will parse snapshot bytes that `push_f64` wrote with to_le_bytes: read each value back with f64::from_le_bytes on an 8-byte slice (safe, no alignment question), not by casting a pointer into the Vec<u8> to *const f64, which is misaligned unless the offset happens to be a multiple of 8 from an 8-aligned base.
- ✓ **Never write through a pointer cast from &T: the solver's warm-start clear does, and rustc's lint misses it** — solver/src/rapier_law.rs `solver_clear_warmstart`: `core::ptr::from_ref(pair) as *mut ContactPair` for each pair of `loaded.world.narrow_phase.contact_pairs()`, pushed into a Vec<*mut ContactPair>, then `&mut *ptr` and `zero_manifolds` on `manifolds` and `solver_clusters`. T2's `solver_restore` needs the same kind of write (docs/rust-kb-requests.md, request 1). At 0.35.3 docs.rs lists only &self accessors, `contact_pairs_mut` is E0599 and the `contact_graph` field is E0616, so both jobs need a &mut route from outside today's public API; which warm-start fields must be written is the restore-internals lane's question.
- ✓ **Probe UB with const evaluation, which rejects invalid values and bad accesses with E0080; runtime is unchecked** — Every ABI slot of the solver is an f64, and floats are only required to be initialized, so whatever bits JS writes into the Float64Array views over BODIES / COLLIDERS / HEIGHTS (NaN included) are valid values: the NaN refusals in `step` and `write_body` are law rules, not UB guards. Keep flags such as DRIVEN as f64 compared with `!= 0.0`, as lib.rs does; a future u8 / bool / enum field decoded from shared memory must go through a match on the integer, never a transmute or a pointer cast to bool or an enum.
- ✓ **Put each unsafe operation in its own unsafe block under a // SAFETY: line, even inside an unsafe fn** — The solver has no unsafe fn, and none of its unsafe blocks carries a // SAFETY: line: lib.rs `bodies_ptr`, `colliders_ptr`, `step`; rapier_law.rs `heights_ptr`, `body_at`, `collider_at`, `write_body`, `signature`, `build_world`, `ensure`, `solver_step`, `snapshot_ptr`, `snapshot_len`, `solver_clear_warmstart`. The last one argues its safety in a prose comment, and that argument is the one the aliasing recipe shows to be insufficient. Write the SAFETY lines with the static-mut rewrite and gate them with undocumented_unsafe_blocks in the solver's CI (the job itself is the ci-reproducible-builds lane's).
- ✓ **Read unsafe as a short list of unlocked operations, never as a switch that turns the borrow checker off** — solver/src/lib.rs `step` wraps its whole ~120-line body in one unsafe block although only the `&mut BODIES` / `&COLLIDERS` borrows need it. After the static-mut rewrite (next recipes) the unsafe shrinks to those two borrows, and the integration, face selection, pair resolution and NaN refusal become ordinary checked Rust.
- ✓ **Replace every reference to a static mut with &raw mut before edition 2024 turns static_mut_refs into deny** — solver/src/lib.rs: `bodies_ptr` (BODIES.as_mut_ptr()), `colliders_ptr` (COLLIDERS.as_mut_ptr()) and `step` (`let bodies = &mut BODIES; let colliders = &COLLIDERS;`); solver/src/rapier_law.rs: `heights_ptr` (HEIGHTS.as_mut_ptr()), `snapshot_ptr` and `snapshot_len` (SOLVER.snapshot.as_ptr() / .len()). These shapes, compiled as extracted snippets (the crate itself was not built here), are static_mut_refs warnings under edition 2021 on 1.98.1 and errors under 2024. `ensure`, `solver_step` and `solver_clear_warmstart` already use `&mut *core::ptr::addr_of_mut!(SOLVER)`, and `body_at` / `collider_at` / `write_body` index the statics directly; the lint accepts both. The rewrite compiles clean under 2021, so it can land before the edition bump; re-pin fixtures/solver.sha256 if the bytes move and require the golden hash unchanged.
- ✓ **Run Miri on the law natively: Stacked Borrows is its default aliasing model, Tree Borrows is opt-in** — Miri's README promises tier-1 targets and warns that targets on other operating systems might fail before reaching main; it never mentions wasm, and wasm32-unknown-unknown's OS is `unknown`. So check the law on the host: unit tests of `canon`, `canon_quat`, `mix_f64`, `js_min` / `js_max` and `write_body`'s NaN refusal, plus one small product world that calls `solver_step` and `solver_clear_warmstart` so Miri executes the static-mut paths and the &ContactPair-to-*mut cast from the aliasing recipe. Full Rapier worlds are slow to interpret: mark them #[cfg_attr(miri, ignore)]. Where those tests live in a cdylib-only crate is the testing-tooling lane's call; the pinned-nightly CI job is ci-reproducible-builds'.
- ✓ **Write #[unsafe(no_mangle)], #[unsafe(export_name)], #[unsafe(link_section)] and unsafe extern blocks now** — All ten exports use a bare #[no_mangle]: lib.rs `bodies_ptr`, `colliders_ptr`, `step`; rapier_law.rs `heights_ptr`, `canon_zero`, `solver_load`, `solver_step`, `snapshot_ptr`, `snapshot_len`, `solver_clear_warmstart`. The crate's edition 2021 accepts that; each becomes a hard error at the edition bump. #[unsafe(no_mangle)] compiles clean under 2021 on 1.98.1 and keeps the export names, so switch now. The solver declares no extern blocks (the module imports nothing), so unsafe extern first matters for host bindings; a law-version custom section through #[unsafe(link_section)] is wasm-raw-abi's topic.

## [Concurrency, parallelism & async](concurrency-async.md)

- ✓ **Borrow stack data in worker threads with thread::scope (1.63); thread::spawn needs move and 'static** — The offline tools around the law (Phase 2 T5 nightly replay corpus, T6 reachability sweep) can fan work out with scoped threads, but not by calling one native law from several threads: the solver keeps its world in process-global `static mut` state (lib.rs `BODIES` / `COLLIDERS`, rapier_law.rs `SOLVER`). Run one law per process.
- ✓ **Hand results between threads over mpsc or crossbeam channels and sort by a tag: arrival order is scheduling** — Tools that spread runs of the law across workers (T5 nightly replay corpus, T6 reachability sweep) should send `(run_index, trace_hash)` and sort by run_index before writing the report. The report is then byte-stable and diffable like the golden hashes it summarises.
- ✓ **Keep the wasm law single-threaded: no threads on wasm32-unknown-unknown, rapier3d-f64's parallel left off** — solver/Cargo.toml turns on only `enhanced-determinism` for rapier3d-f64 0.35.3 (defaults dim3, f64, std, block-solver; `parallel` off, as solver/FLAGS.md records). Keep it off in the wasm law: the target has no threads to use, and the feature compiles rayon and the parallel code paths into the module whose bytes fixtures/solver.sha256 pins. If a native Godot or Unreal build ever turns `parallel` on, re-measure the golden hash at several thread-pool sizes before trusting Rapier's bitwise claim, and add a CI feature guard (owned by ci-reproducible-builds).
- ✓ **Let the compiler infer Send and Sync: they turn data races into E0277/E0499, not race conditions or deadlocks** — solver/src/lib.rs exports raw `*mut f64` from `bodies_ptr()` and `colliders_ptr()`. Any Rust-side host wrapper that stores those pointers is automatically neither Send nor Sync. That is the compiler enforcing one-thread use of the static buffers, so keep it rather than adding `unsafe impl Send`.
- ✓ **Make parallel float reductions bit-reproducible: fixed chunks, per-chunk partials, combined in index order** — Inside the wasm law nothing is reduced in parallel: Rapier runs its staged solver with one worker when `parallel` is off. The rule binds tools that aggregate floats across runs (T5 corpus statistics, T6 sweep metrics) and any future native build that turns rapier's `parallel` on.
- ✓ **Pick Mutex, RwLock or Condvar by job, and decide what a poisoned lock means before a panic decides for you** — If a native host puts the law behind a Mutex (see the native-call recipe), a poisoned law lock means the world may be half-stepped. Refuse the call and return 0, as the exports already do for NaN, instead of stepping on from `into_inner()`. The solver's release profile (`panic = "abort"` in solver/Cargo.toml) ends the process on a panic, so poisoning only arises in unwind builds such as tests.
- ✓ **Publish data across threads with a Release store and an Acquire load; keep Relaxed for counters** — The law needs no atomics: one thread, and wasm32-unknown-unknown without the `atomics` feature. Host or tool code that uses them should also run its tests on the Phase-2 T3 ARM64 lane, where a too-weak ordering can show up that x86 hides.
- ✓ **Serialize native calls into the law: static needs Sync, static mut skips the check, a Mutex restores it** — solver/src/lib.rs holds `static mut BODIES` and `COLLIDERS` (f64 arrays); solver/src/rapier_law.rs holds `static mut HEIGHTS` and `static mut SOLVER: Solver` (the loaded PhysicsWorld, controller and snapshot Vec). The types are Sync (f64 arrays trivially, PhysicsWorld per the check). What two host threads would break is the unsynchronized mutation that `static mut` allows: a data race, which is UB. `solver_clear_warmstart` even notes 'The world is ours alone on this thread', which nothing enforces. In the wasm module the JS host calls exports one at a time. Compiled natively for a Godot or Unreal host, two threads calling `solver_step` would race. Move the state into one `static LAW: Mutex<Option<Loaded>>` (or a host-owned handle) and have each export try_lock and return 0 on WouldBlock or Poisoned.
- ✓ **Spawn only Send + 'static futures: no std MutexGuard or Rc across .await, CPU-bound work to spawn_blocking** — A tokio-based host or tool (a replay service, an asset server) should call the law through `spawn_blocking` or one dedicated law thread fed by a channel, because the law is CPU-bound and process-global. It must never hold the law's std MutexGuard across an .await.
- ✓ **Treat a future as an inert, pinned state machine: nothing runs until polled, and dropping it cancels it** — The law's exports (`step`, `solver_load`, `solver_step`, `solver_clear_warmstart`) are synchronous and CPU-bound, driven by the JS tick at 1/64 s. A quantum has no I/O to wait on, so the law gains nothing from async. Async belongs, if anywhere, in host and tool I/O around the law.

## [Macros, const evaluation & build scripts](macros-const.md)

- ✓ **Compute tables in const fn with while, match and &mut; expect E0015 on for-loops, trait calls and formatting** — lib.rs's `step` and `resolve_pair` already use index while loops, a const-compatible style. The realistic const work in the solver is proofs and tables over the ABI constants (see 'Pin the solver ABI with const _ assertions...'); the step itself reads `static mut` buffers at run time and stays an ordinary fn.
- ✓ **Embed build inputs with include_bytes!, include_str!, env! and concat!, and know which of them fail the build** — build.mjs embeds the pinned wasm into JS as a Uint8Array literal. A native Rust host shell (the Godot or Unreal bindings slice) would embed it with include_bytes!(".../si_solver.wasm") and can refuse to compile against any other module with a const-fn digest check over those bytes; the pin itself stays the SHA-256 in fixtures/solver.sha256, and FNV-1a here only demonstrates compile-time hashing.
- ✓ **Emit cargo:: lines from build.rs, pair rustc-cfg with rustc-check-cfg, and read the target from CARGO_CFG_*** — The solver has no build.rs; its generator is node (solver/build.mjs), outside Cargo. A build.rs that generated the ABI table could write only the Rust half into OUT_DIR, so build.mjs would still have to read the same data file itself; that is why the macro table in 'Pin the solver ABI with const _ assertions...' is the smaller change. If one is ever added, it must test CARGO_CFG_TARGET_FAMILY (wasm), never cfg! (the Linux or Windows host), and every clean build gains a compile and a run unit.
- ✓ **Gate wasm code on target_family = "wasm" and turn a forbidden target feature into compile_error!** — solver/.cargo/config.toml and solver/build.mjs both pass `-C target-feature=-relaxed-simd` because RUSTFLAGS replaces the config's rustflags (build.mjs says so). Two lines in lib.rs, `#[cfg(target_feature = "relaxed-simd")] compile_error!(...)`, make the source refuse that configuration however the flags arrive, e.g. a `RUSTFLAGS="-C target-cpu=bleeding-edge"` build that forgot the disable. T3's opcode lint stays the check on the bytes. Measured on a scratch copy of solver/ at e5fbcb9: appended to the end of lib.rs, the guard left si_solver.wasm byte-identical, and a RUSTFLAGS='-C target-cpu=bleeding-edge' build then failed with the guard's message.
- ✓ **Keep const generics to standalone integer, bool and char params; size nested arrays, never N * STRIDE** — lib.rs's `[f64; MAX_BODIES * BODY_STRIDE]` compiles because MAX_BODIES and BODY_STRIDE are const items, not generic parameters. Making the body count generic would force `[[f64; BODY_STRIDE]; N]` (the same 64 x 136 bytes, flattened with as_flattened) and buys nothing while the ABI is fixed at 64 x 17.
- ✓ **Pin the solver ABI with const _ assertions and generate the JS strides from one Rust table, not by hand** — lib.rs declares BODY_STRIDE = 17, HX = 13, HY = 14, HZ = 15, DRIVEN = 16, COLLIDER_STRIDE = 10 and rapier_law.rs QX = 6 .. WZ = 12 (slots 0-5 are bare literals), while the module build.mjs generates hard-codes `i * 17` four times, `j * 10` twice and `view[at + 13..16]` eight times (e5fbcb9). Step one costs no bytes, measured: the 17-slot SLOTS proof appended to the end of rapier_law.rs, which already sees both sets of constants, compiled under the crate's edition 2021 and left si_solver.wasm unchanged. Step two removes the JS copy: build.mjs reads abi_word(i) from the module it has just built and emits the offsets; that export is new code, so the digest pin moves once, in the same commit.
- ✓ **Trust const f64 bits for + - * /, but keep d * PI / 180.0: to_radians() differs on 93 of 361 integer degrees** — rapier_law.rs: CLIMB_ANGLE = FRAC_PI_4 (0x3fe921fb54442d18) and SLIDE_ANGLE = 50.0 * PI / 180.0 (0x3febecde5da115a9) are produced by the compiler's soft-float, independent of the build host, and equal to what V8 computes at run time in wasm from the same expression. For T4's 44 deg / 46 deg climb course, build angles as `d * PI / 180.0` in Rust and `d * Math.PI / 180` in JS: `46f64.to_radians()` is one ulp away from both.
- ✓ **Use a derive proc macro only when code must read a type's definition; count its syn builds in build time** — The solver's own code uses no proc macro, yet every clean wasm build compiles four proc-macro crates from solver/Cargo.lock: nalgebra-macros, num-derive and profiling-procmacros on syn 2.0.119, thiserror-impl on syn 3.0.6. serde_derive 1.0.229 in the same lockfile also depends on syn 3.0.6, so a serde derive for world files would not add a third syn. If the stride-17 buffer is ever redesigned, a `#[derive(Pod)] #[repr(C)] struct Body` is the typed alternative to hand indices, proven padding-free at compile time.
- ✓ **Use const for values, static for one address, const { } for non-Copy repeats and generic compile-time asserts** — BODIES, COLLIDERS and HEIGHTS must stay statics: bodies_ptr(), colliders_ptr() and heights_ptr() hand JS one address that its Float64Array views index. Their lengths (MAX_BODIES * BODY_STRIDE, MAX_COLLIDERS * COLLIDER_STRIDE, MAX_HEIGHTS) and the SOLVER initializer (`Solver { loaded: None, snapshot: Vec::new() }`) are const contexts. DT, G, the strides and the angles are rightly consts.
- ✓ **Write macro_rules! with fragment follow-sets, $crate paths and edition 2024's wider expr (expr_2021) in mind** — solver/src/lib.rs and rapier_law.rs (e5fbcb9) contain no macro_rules! today. The first one that earns its place is the ABI table (see 'Pin the solver ABI with const _ assertions...'): one invocation declaring BODY_STRIDE, HX..DRIVEN and COLLIDER_STRIDE plus their stringify!'d names. The solver crate is edition 2021, so write `$v:literal` (or `expr_2021`) there: an `expr` fragment written today would widen on a 2024 migration.

## [Performance & profiling](performance.md)

- ✓ **Benchmark before tuning: criterion or divan with harness = false, black_box on every input and output** — The solver has no bench today and its crate-type is cdylib only. In a scratch copy with crate-type ["cdylib", "rlib"], an example linked the law, called `step` and `bodies_ptr` directly, and reached the rapier_law exports through an `extern "C"` block because `mod rapier_law` is private. Baseline on this rig (pinned profile, V8 in node 22.22.3): 17.6 ms per 400 quanta of `solver_step` for a 13-body scene, 203 us per 400 quanta of the box law `step`.
- ✓ **Choose release-profile knobs by measurement: opt-level sets speed; lto, codegen-units, strip, debug move bytes** — solver/Cargo.toml's profile (opt-level 3, lto = false, codegen-units 1, panic = "abort", overflow-checks = false) is at the fast end of every variant measured. Its lto = false means no LTO at all at codegen-units 1, and panic = "abort" restates the target default (`rustc --print cfg --target wasm32-unknown-unknown` prints panic="abort"), so that line only matters for a native host build of the law. The 182,205-byte name section is 12% of the artifact and is what gives V8 profiles readable frames (profiling recipe).
- ✓ **Get SIMD on stable from auto-vectorization, std::arch and #[target_feature]; std::simd is still nightly-only** — The solver builds with no SIMD feature and -relaxed-simd (FLAGS.md). A +simd128 build of the scratch copy gave identical results on the scene, 1,478,802 bytes (-3.0%), a target_features section of 157 instead of 148 bytes, and 0.95x V8 time (inside the +-10% noise). The small change is consistent with glam 0.33.10 (the version glamx 0.3.1 uses) keeping its simd128 paths in f32 and bool types (0 target_feature cfgs under src/f64). SIMD is not worth a new digest today.
- ✓ **Keep target-cpu=native, PGO and BOLT out of the pinned artifact: they tie codegen to a machine or a profile** — The wasm artifact is untouched by the builder's CPU today (native is ignored for wasm32 on 1.98.1) and cannot be PGO-instrumented. The real exposure is the planned native host bindings (Godot, then Unreal), where native or +fma flips cfg(target_feature) paths. In the pinned graph those sit in wide (reached through simba 0.10.2) and in glam's f32 types; rapier3d-f64 0.35.3, parry3d-f64 0.30.2, glamx 0.3.1, nalgebra 0.35.0 and simba 0.10.2 have 0 such cfg lines. aarch64-unknown-linux-gnu enables neon by default, so an ARM64 native build selects wide's fused path wherever it is reached. A native law must pin its CPU baseline and match the wasm golden.
- ✓ **Lay out hot data by access: struct-of-arrays when loops read few fields, rows sized against cache lines** — The solver ABI is array-of-structs: BODIES is [f64; 64 x 17] = 8,704 bytes, 136 bytes per body (2.125 64-byte lines, so rows straddle lines), and build.mjs hard-codes the stride 17 and every offset. rapier_law.rs `body_at` returns [f64; 17] = 136 bytes by value, just over the perf book's 128-byte memcpy size. The V8 profile of the scene put 65% of wasm samples in parry and Rapier and 4.0% in the law's own code, so there is no measured case for changing the ABI layout.
- ✓ **Leave inlining to rustc: #[inline] for cross-crate calls, #[cold] on refusal paths, static dispatch when hot** — lib.rs's helpers (field, body_at, js_min, js_max, rank, resolve_pair) are private and share one crate at codegen-units 1. Measured: the optimized box-law module defines only bodies_ptr, colliders_ptr and step, and step's remaining calls are LLVM intrinsics (llvm.is.fpclass, llvm.sqrt, lifetime markers). No attribute is needed. The law has no dyn of its own; parry3d-f64 0.30.2's SharedShape is `pub struct SharedShape(pub Arc<dyn Shape>)`, so narrow-phase shape dispatch is dynamic inside the dependency (DefaultQueryDispatcher was a top V8 frame), outside the engine's control.
- ✓ **Profile the law natively (samply, perf, VTune, Superluminal), then confirm hot spots with node --cpu-prof** — Profile natively from a scratch or bench build of solver/ with crate-type ["cdylib", "rlib"], never from the pinned profile, replaying input bits dumped from the JS run so the native run computes the same record (identical here). Then confirm with node --cpu-prof on build.mjs's artifact. Measured V8 split (100 us sampling, 1,192 wasm samples): parry3d_f64 34.9%, rapier3d_f64 30.3%, libm 13.9% (sqrt), __multi3 8.4% (called only from libm's sqrt), nalgebra 4.6%, the law's own code 4.0%, dlmalloc 0.7%. The software sqrt comes from `enhanced-determinism` (rapier: simba/libm_force; parry: simba/libm_force, glamx/libm, glamx/scalar-math); whether the wasm f64.sqrt instruction could replace it without moving results is for the float-determinism lane, not a flag to flip here.
- ✓ **Prove indices once: an entry guard, chunks_exact_mut or as_chunks_mut removes per-iteration bounds checks** — lib.rs `step` checks `n_bodies > MAX_BODIES // n_colliders > MAX_COLLIDERS` before touching the fixed-length statics, and that single guard lets LLVM prove every `field(bodies, i, slot)` and `colliders[j * COLLIDER_STRIDE + k]` index. Keep a guard like it first in every new export (T2's solver_restore included). rapier_law.rs `body_at` / `collider_at` copy rows with an index loop; `as_chunks::<BODY_STRIDE>()` would express a row directly, but that is a code change the golden hash must confirm, not a measured win.
- ✓ **Reuse per-quantum buffers: clear() keeps capacity, with_capacity sizes once, SmallVec/ArrayVec for small lists** — rapier_law.rs `rebuild_snapshot` already reuses `SOLVER.snapshot` with `out.clear()`, so the snapshot stops allocating after its largest contact set. Allocations left per quantum: `integrate` builds `plans` and a `collisions` Vec per driven body, `rebuild_snapshot` collects `pairs`, and `solver_clear_warmstart` builds `ptrs`. Measured: in a V8 profile of the scene (100 us sampling, 1,192 wasm samples) the allocator (dlmalloc) took 0.7% and the law's own code 4.0%, so reusing these buffers would be tidiness, not a speed lever, and would still move the digest.
- ✓ **Split profile knobs into digest-only and result-changing before editing the solver's pinned release profile** — solver/Cargo.toml [profile.release] and fixtures/solver.sha256: any profile edit, even lto = false -> "off" (no more LTO than today), moves every crate's -C metadata and therefore the digest; the golden hash is the invariant that must not move, so rerun the golden suite and re-pin the Linux digest together. Keep overflow-checks and debug-assertions off in the artifact (turning them on changes the law's failure mode, not only its bytes), and keep the target-feature set pinned (-relaxed-simd; +simd128 kept this scene's results but is another artifact). rapier_law.rs refuses NaN in poses and velocities (write_body, bad) and mix_u64 uses wrapping_mul/wrapping_add, so neither NaN payloads nor the overflow-checks knob reaches those paths.

## [What changed in Rust 1.80 → 1.98](rust-currency.md)

- ✓ **Expect 1.86-1.98 lint escalations to break old unsafe and macro code on a toolchain bump** — On 1.98.1 the solver builds with its 7 static_mut_refs warnings and no other lint (measured), and rapier_law.rs's `unsafe { &mut *core::ptr::addr_of_mut!(SOLVER) }` is already the explicit form these lints accept. Build the next bump with CARGO_BUILD_WARNINGS=deny (see the Cargo recipe) so a newly escalated lint stops CI instead of scrolling past.
- ✓ **Expect edition 2024 to drop if-let scrutinee and tail-expression temporaries earlier** — cargo fix --edition on the solver copy reported no if_let_rescope or tail_expr_drop_order site (measured): `ensure()` in rapier_law.rs uses `if let Some(loaded) = solver.loaded.as_ref()` with no else, and the other matches are let-else. The rules start to matter in the planned host bindings (Godot, then Unreal), where a wrapper may hold a lock guard or RefCell borrow over the solver's static state across an if-let.
- ✓ **Expect wasm32 undefined symbols to fail the link since 1.96 and the standard C ABI since 1.89** — The solver declares no extern block and imports nothing (build.mjs instantiates with `new WebAssembly.Instance(module)` and no import object), so on 1.96+ an accidental undefined symbol fails `cargo build` instead of the JS instantiation. Its ten exports take u32/f64 and return u32/f64/pointers, the class the C ABI post says is unaffected. Keep T3's no-imports check as a second gate, and give T2's restore exports the same scalar/pointer signatures.
- ✓ **Gate solver CI with Cargo's build.warnings (1.97), not RUSTFLAGS, and keep --locked across resolver 3** — solver/Cargo.toml (edition 2021, so resolver 2), solver/.cargo/config.toml (target rustflags that build.mjs's RUSTFLAGS replaces - the reason build.mjs repeats -relaxed-simd), solver/build.mjs, and the digest job in .github/workflows/ci.yml.
- ✓ **Keep 1.98's f64::algebraic_* methods out of the law: the std docs allow different results per run** — rapier_law.rs computes CLIMB_ANGLE and SLIDE_ANGLE as consts; `bad` rejects NaN before `mix_f64` hashes `to_bits()`, and `canon_zero` passes NaN through untouched - the discipline the NaN notes require. Add `algebraic_` to the source lints that accompany T3's relaxed-SIMD opcode lint, and grep the Cargo.lock diff's crates for it on every dependency bump.
- ✓ **Know which edition-2024 changes cargo fix --edition migrates and which stay manual** — The solver has no extern blocks, unsafe fns, macros, RPIT returns, `gen` identifiers or boxed slices, so of this list only the unsafe attributes touch it (measured: cargo fix changed nothing else). The rustfmt style edition is the one item that can move the digest with no semantic change, because a reformat shifts panic-location line numbers (see the solver migration recipe).
- ✓ **Move si-solver to edition 2024: cargo fix rewrites 10 #[no_mangle], hand-fix 7 static_mut_refs** — The 10 attribute sites are the exports in solver/src/lib.rs (bodies_ptr, colliders_ptr, step) and solver/src/rapier_law.rs (heights_ptr, canon_zero, solver_load, solver_step, snapshot_ptr, snapshot_len, solver_clear_warmstart); the 7 static_mut_refs sites are lib.rs:28, 33, 183, 184 and rapier_law.rs:78, 738, 743 in the local checkout. A line-preserving migration should leave fixtures/solver.sha256 unchanged; write T2's restore exports in the 2024 spelling from the start. The dependencies are already edition-2024 crates (rapier3d-f64 0.35.3: edition 2024, rust-version 1.86; nalgebra 0.35.0: edition 2024, rust-version 1.89.0) and editions are per crate, so the solver's own edition changes nothing inside them.
- ✓ **Replace flat-buffer index math with 1.86-1.93 std APIs: as_chunks_mut, get_disjoint_mut, as_array** — lib.rs `body_at` / `field` and `resolve_pair(bodies, i, j)` (two bodies mutated through index arithmetic), rapier_law.rs `body_at` / `collider_at` copy loops and `quat_from_body(&b)` are the index-arithmetic sites; `mix_u64`'s wrapping_mul / wrapping_add must stay wrapping. Any such rewrite changes the digest (code and panic locations move) but should leave the golden hash unchanged; prove that with the three-engine golden run.
- ✓ **Stop sorting floats with partial_cmp().unwrap_or(Equal): 1.81+ sorts panic on a non-total order** — rapier_law.rs `rebuild_snapshot` sorts contact pairs by `(collider1.into_raw_parts(), collider2.into_raw_parts())` - integer tuples, a total order, safe. Future sorts by f64 (T6 reachability sweep, T5 replay corpus ordering) should use total_cmp or integer keys, after NaN rejection.
- ✓ **Treat wasm32-unknown-unknown's six default features as byte changes, and -relaxed-simd as no ban** — solver/.cargo/config.toml and solver/build.mjs both pass -C target-feature=-relaxed-simd; on 1.98.1 that flag changes nothing in the default set (checked), so it guards against a future default, while FLAGS.md's 'this build disables' does not cover a dependency function that opts in with #[target_feature] - only inspecting the module (T3's opcode lint, or the target_features section) catches that. A toolchain bump that changes the default set, as 1.82 and 1.87 did, changes the digest in fixtures/solver.sha256; the golden hash should not move for that reason.
