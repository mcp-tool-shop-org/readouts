### Derive library error enums with thiserror 2; use anyhow or `Box<dyn Error + Send + Sync>` only in binaries
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust thiserror 2.0.21, anyhow 1.0.104 (the oracle's pins)

**thiserror generates the `Display`, `Error::source` and `From` impls you would write by hand and stays out of your public API; anyhow gives application code one opaque error type with `.context()` layers and a cause-chain printer.**

- **How:** Library: `#[derive(Debug, thiserror::Error)]` with one `#[error("...{n}...")]` per variant (fields interpolate as `{n}`, `{0}`, `{n:?}`); `#[from]` on a variant whose only field is the cause generates `From` and implies `#[source]`; a field named `source` is the source automatically; `#[error(transparent)]` forwards `Display` and `source` to an inner error. Application or tool: return `anyhow::Result<T>`, add `.context("what was being attempted")`, check with `ensure!`, print `{:#}` for `outer: cause` on one line. Without either dependency, `Box<dyn Error + Send + Sync + 'static>` takes any `E: Error + Send + Sync` through `?` and a `&str` or `String` through `.into()`.
- **Gotchas:** A `#[from]` variant may hold no field besides the source (and possibly a backtrace). `anyhow::Error::new` requires `Send + Sync + 'static`; the error is one word wide. `{:?}` on an anyhow error prints a `Caused by:` block and includes a backtrace when one was captured, so never compare it byte for byte in a test. A plain `Box<dyn Error>` is not `Send`: returning it from `thread::spawn` is E0277 ("`dyn std::error::Error` cannot be sent between threads safely"). A library that returns `anyhow::Error` leaves its callers only `downcast_ref` to recover a type; that is where the thiserror/anyhow line falls.
- **In si-rpg-engine:** Neither crate belongs in `solver/`: its loading and stepping exports report outcomes as `u32` 1/0 and the crate links only `rapier3d-f64`, so any new dependency there is a change to review against the pinned digest in `fixtures/solver.sha256`. thiserror fits a future native crate around the law (a host binding, a scene loader); anyhow fits Rust-side tools.

### Give a library one error enum per failure mode and let `?` convert wrapped causes through `From`
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any; `Error::source` 1.30+; `core::error::Error` 1.81+

**`?` on `Err(e)` returns `Err(From::from(e))` from the enclosing function, so an error enum plus one `From` impl per wrapped cause turns each fallible call into a single `?`; since 1.81 the `Error` trait is also in `core::error`, so the same impl serves `#![no_std]` code.**

- **How:** Write `enum LoadError { Parse(ParseIntError), TooManyBodies { n: u32, max: u32 } }`: one variant per condition a caller can act on, carrying the data it needs. Implement `Display` (concise, lowercase, no trailing punctuation), `Error` with `source()` returning the wrapped cause, and `impl From<ParseIntError> for LoadError`; then `s.parse::<u32>()?` converts on its own. A reporter walks the chain: `let mut cur = e.source(); while let Some(c) = cur { ...; cur = c.source(); }`. Where an `Option` meets a `Result` function, name the refusal as you convert: `handles[i].ok_or(Refusal::Carried { body: i })?` (the combinators themselves are the types-patterns lane's). In `#![no_std]` write `impl core::error::Error for T`; the compiler accepts that impl wherever `dyn std::error::Error` is asked for (check 1).
- **Gotchas:** A missing `From` impl is E0277 ("`?` couldn't convert the error to `LoadError`"). `?` never converts between `Option` and `Result`, so a bare `None` carries no reason until `ok_or` names one. Put the wrapped error in `source()` or in the `Display` text, not both, or a chain report prints it twice. Do not use `()` as an error type: it implements neither `Error` nor `Display`, its `Debug` says nothing, and downstream crates cannot write a meaningful `From<()>`. `Error::description` (deprecated 1.42) and `Error::cause` (deprecated 1.33) are dead: implement `Display` and `source()`.
- **In si-rpg-engine:** The solver has no error type yet: every refusal in rapier_law.rs (`signature`, `build_world`, `canon_quat`, `write_body`, `integrate`, `rebuild_snapshot`, `ensure`) is an `Option` or a `bool` that collapses into an export's `0`. A fieldless `Refusal` enum returned through `?` is the internal type the export recipe in this lane builds on; being `core`-only, it costs nothing on `wasm32-unknown-unknown`.

### Guard invariants the shipped build keeps with `assert!`; `debug_assert!` vanishes without debug-assertions
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any

**`assert!` is checked in every build and cannot be disabled; `debug_assert!` runs only when `cfg(debug_assertions)` is on, which by default means opt-level 0, and Cargo's release profile turns it off.**

- **How:** `assert!(cond, "... should ...")` for a precondition whose violation would corrupt state; `debug_assert!` only for expensive consistency checks you accept losing in release; `-C debug-assertions=on` (or `debug-assertions = true` in a profile) brings them back in an optimized build. Code behind `#[cfg(debug_assertions)]` or `cfg!(debug_assertions)` must only observe, never change state.
- **Gotchas:** The std docs allow replacing `assert!` with `debug_assert!` only after profiling and only in safe code: unsafe code may rely on `assert!` to uphold invariants. `debug-assertions` and `overflow-checks` are separate switches; overflow checks merely default to follow debug-assertions. Format arguments of an `assert!` message are evaluated only when the assertion fails.
- **In si-rpg-engine:** The solver's release profile does not set `debug-assertions`, so the pinned wasm takes Cargo's release default (off): any `debug_assert!` added to lib.rs or rapier_law.rs exists in native `cargo test` and not in the shipped module. An invariant the golden hash depends on (a unit quaternion, a non-NaN pose) must be an `assert!` or, at the export, a refusal, and state written under `cfg!(debug_assertions)` would make native runs and the wasm disagree.

### Keep panics out of `extern "C"` exports: refuse through an internal `Result` chain mapped to a `u32` status
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust 1.81+ (abort on an unwind out of `extern "C"`); `"C-unwind"` since 1.71

**Since 1.81 a panic that unwinds out of an `extern "C"` function aborts the process, and `catch_unwind` in the caller cannot stop it; so an export never panics: the code behind it returns `Result<(), Refusal>` through `?`, and one `match` at the boundary produces the status code.**

- **How:** `fn step_inner(..) -> Result<(), Refusal>` with `if n > MAX { return Err(Refusal::TooManyBodies) }` and `canon_quat(..).ok_or(Refusal::BadQuaternion)?`; the export is `#[no_mangle] pub extern "C" fn solver_step(..) -> u32 { match step_inner(..) { Ok(()) => 1, Err(_) => 0 } }` (spelled `#[unsafe(no_mangle)]` in edition 2024). Native tests call `step_inner` and assert which `Refusal` came back. If a native host build must survive a bug, build it with `panic = "unwind"` and wrap each export body in `catch_unwind`; `extern "C-unwind"` is for letting a panic cross on purpose (depth: unsafe-ffi).
- **Gotchas:** With `panic = "unwind"`, whether destructors up to the ABI boundary run before the abort is unspecified; nothing beyond the boundary runs (check 1: the caller's guard never drops). On this Windows host the status is 0xC0000409 and stderr reads "panic in a function that cannot unwind" (measured). A bare 0 carries no reason: keep the `Refusal` inside Rust, and if a host ever needs it, a separate export returning the last refusal code (a suggestion) keeps every existing 1/0 contract intact.
- **In si-rpg-engine:** The dispatched cleanup item is already fixed: `rebuild_snapshot` did `continue` on a failed `canon_quat` at `c64f67a`, and `6a33297` changed it to `return false` and made `ensure` check the result; `e5fbcb9` and current `origin/main` keep that. The one `continue` left in `rebuild_snapshot` skips carried bodies (`handles[i]` is `None`), which leave the solver by design. What remains is the shape: `ensure -> signature / build_world / rebuild_snapshot` and `solver_step -> integrate -> write_body` pass `bool`s and `Option`s that a future caller can drop without a warning. A `Result<(), Refusal>` chain with `?` keeps every export's 1/0 ABI unchanged and makes 'refuse, never skip' something the compiler checks.

### Make refusals impossible to drop silently: `Result` is `#[must_use]`, `Option<()>` and `bool` are not
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any

**Discarding a `Result` in an expression statement fires `unused_must_use`, but a refusal returned as `Option<()>`, `bool` or a bare integer compiles with no warning unless the function itself is `#[must_use]`.**

- **How:** Return internal refusals as `Result<(), Refusal>` with an inhabited `Refusal` enum, or put `#[must_use = "a false return is a refusal and must reach the export"]` on each function that reports status through `bool` or `u32`. Promote the lint to an error in CI with `-D unused_must_use`. Discard on purpose with `let _ = f();`, the idiom the Reference names.
- **Gotchas:** The function-based check looks only at an expression statement whose expression is the call: wrapping the call, as in `Some(f())` or `(f(),)`, suppresses it (Reference). `Result<(), E>` with an uninhabited `E` such as `Infallible` is exempt (Reference; check 2). `#[must_use]` on a function in a trait impl does nothing; put it on the trait's declaration.
- **In si-rpg-engine:** Today every caller of `rebuild_snapshot`, `integrate`, `write_body` and `ensure` in rapier_law.rs checks the returned `bool` (`rebuild_snapshot`'s callers since `6a33297`), but nothing makes the next caller check: `rebuild_snapshot(loaded, &mut solver.snapshot);` would compile silently and leave a half-built snapshot (the function clears `out` before it can refuse). `#[must_use]` on those four, or a `Result<(), Refusal>` return, turns that into a warning.

### Know what `panic = "abort"` changes: the hook still runs, then no unwinding, no `Drop`, nothing to catch
