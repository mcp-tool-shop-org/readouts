### Assert equal lengths before zip, handle chunks_exact remainders, and collect into the target you mean
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust chunks_exact 1.31+; as_chunks 1.88+; array_windows 1.94+

**`zip` ends when either input ends, without error; `windows(k)` yields len-k+1 overlapping slices; `chunks_exact(k)` omits the last len % k elements into `remainder()`; `collect` builds any `FromIterator` target: `Result<Vec<_>, E>` stops at the first Err, and a `BTreeMap` sorts by key and keeps one value per key.**

- **How:** `debug_assert_eq!(pos.len(), vel.len()); for (p, v) in pos.iter().zip(&vel) {}`; `for (i, b) in bodies.iter().enumerate()`; `a.iter().chain(&b)` concatenates in order. Fixed strides: `buf.chunks_exact(STRIDE)` and check `.remainder().is_empty()`, or `let (rows, tail) = buf.as_chunks::<17>();` (1.88+, rows are `&[[f64; 17]]`); neighbour pairs: `windows(2)` or `array_windows::<2>()` (1.94+). Parse or refuse: `let xs: Result<Vec<f64>, _> = toks.iter().map(|t| t.parse::<f64>()).collect();`.
- **Gotchas:** Zipping 4 positions with 3 velocities yields 3 pairs and no error. Over 7 items `chunks(3)` gives lengths [3, 3, 1] while `chunks_exact(3)` gives two chunks and hides [7] in `remainder()`. `windows(0)` and `chunks_exact(0)` panic. Collecting into a HashMap or HashSet brings back arbitrary order; into a BTreeMap, duplicate keys keep one value ('all but one of the corresponding values will be dropped'). `collect::<Result<_, _>>()` stops pulling at the first Err, so side effects in the closure stop there too (measured: '1' and 'x' seen, '3' never parsed).
- **In si-rpg-engine:** solver/src/lib.rs lays bodies out as `[f64; MAX_BODIES * BODY_STRIDE]` with BODY_STRIDE = 17 (colliders: COLLIDER_STRIDE = 10), and `body_at` in rapier_law.rs copies a row with an index loop. Over a `&[f64]` view the same rows are `as_chunks::<17>()` with an empty remainder, which puts the stride in the type; how to obtain that view of a `static mut` soundly belongs to the unsafe-ffi lane.

### Choose iter, iter_mut or into_iter by ownership, and consume every adapter chain you build
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust array into_iter by value: edition 2021+ (IntoIterator for arrays exists in every edition since 1.53)

**`for x in &v` iterates `&T` (iter), `for x in &mut v` iterates `&mut T` (iter_mut), `for x in v` consumes v and yields `T` (into_iter); adapters such as `map` are lazy and run nothing until consumed; from edition 2021, `array.into_iter()` yields values, while 2015/2018 resolve it to `(&array).into_iter()`.**

- **How:** Read-only pass: `for b in &bodies {}`; in-place update: `for b in &mut bodies { b.v *= k; }`; transfer ownership: `for b in bodies {}` or `bodies.into_iter().map(..).collect()`. Run side effects in a `for` loop or `.for_each(..)`, never a bare `.map(..)`. Arrays in a 2021+ crate: `for x in [a, b, c]` and `[a, b, c].into_iter()` both give values; call `.iter()` when you want references.
- **Gotchas:** `v.iter().map(|x| println!("{x}"));` compiles with `unused_must_use` ('iterators are lazy and do nothing unless consumed') and `map_unit_fn` warnings and prints nothing. After `for s in v`, `v.len()` is E0382 (v was moved by the loop's implicit `.into_iter()`). In an edition-2018 crate `[1, 2, 3].into_iter().collect::<Vec<i32>>()` is E0277 because the items are `&i32`; code that still compiles there gets the `array_into_iter` lint. Only method-call syntax differs by edition; `for e in [1, 2, 3]` iterates by value in every edition.
- **In si-rpg-engine:** solver/Cargo.toml sets `edition = "2021"`, so in the law crate `array.into_iter()` already yields values; the snapshot and step loops walk bodies by index (`for i in 0..loaded.n_bodies`, `while i < n`) rather than through adapters.

### Delete from a hashed Vec with remove/retain/drain, not swap_remove; pre-size it with with_capacity/reserve
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any

**A Vec's order is its index order: remove, retain and drain keep it, swap_remove moves the last element into the hole, and capacity is only a lower bound whose growth the docs leave unspecified.**

- **How:** Pre-size with `Vec::with_capacity(n)` (capacity >= n; the method 'is allowed to allocate for more elements than capacity') or `v.reserve(k)` (capacity >= len + k afterwards). Reuse a per-step buffer with `v.clear()`, which 'has no effect on the allocated capacity'. Remove while keeping order: `v.remove(i)` (shifts the tail, O(n)), `v.retain(|x| keep(x))` (visits each element exactly once in the original order and preserves the order of the retained elements), `v.drain(a..b)` (yields the removed run in order; dropping the Drain unconsumed still removes it). Use `v.swap_remove(i)` (O(1)) only where the order never reaches an output, or sort again before hashing. Never serialise or hash `capacity()`.
- **Gotchas:** `swap_remove(1)` on ['a','b','c','d'] leaves ['a','d','c'] while `remove(1)` leaves ['a','c','d']: same elements, different sequence, different hash. Order-changing removal can also happen inside a dependency: Rapier 0.35.3's graph deletes edges with `edges.swap_remove`, so an iteration order your code never touched still moves. The docs say Vec 'does not guarantee any particular growth strategy when reallocating when full, nor when reserve is called', so `capacity()` after the same pushes is not a portable value. A Drain holds `&mut` on the Vec until it is dropped; leaking it with `mem::forget` may lose elements.
- **In si-rpg-engine:** Rapier 0.35.3 removes contact-graph edges with `self.edges.swap_remove(e.index())` (src/data/graph.rs `remove_edge_adjust_indices`), and `NarrowPhase::contact_pairs()` walks that edges vec in index order (`interactions()` -> `raw_edges().iter()`), so pair order changes whenever a contact ends. That is why `rebuild_snapshot` in solver/src/rapier_law.rs collects the pairs into a Vec and sorts them before hashing; it also reuses the snapshot buffer with `out.clear()`, which keeps its capacity.

### Give every hashed sort a unique total key; if keys can tie, use stable sort_by, not sort_unstable_by
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust 1.81+ (driftsort / ipnsort; sorts may panic on a non-total comparator)

**`sort`, `sort_by` and `sort_by_key` preserve the initial order of equal elements; `sort_unstable*` 'may reorder equal elements', and since the 1.81 switch to ipnsort its docs no longer carry the pdqsort-era promise of 'a fixed seed to always provide deterministic behavior'. With a unique key, both produce identical output.**

- **How:** Make the comparator a total order with no Equal between distinct elements: `v.sort_unstable_by(|a, b| a.key.cmp(&b.key).then(a.id.cmp(&b.id)))`. With such a key the stable and unstable sorts give the same output, so neither an algorithm change nor a toolchain bump can move it. If ties are possible and the key cannot be extended, use stable `sort_by` / `sort_by_key`: equal elements keep their input order, which must itself be canonical. Guard the invariant in tests: `assert!(v.windows(2).all(|w| cmp(&w[0], &w[1]).is_lt()))`.
- **Gotchas:** Measured on 1.98.1: `sort_unstable_by_key` kept equal keys in input order for 20 elements and reordered them at 21 and 100, so a small unit test hides the difference. Since 1.81 both sorts 'may panic' when the comparator is not a total order, and 'even if the function exits normally, the resulting order of elements in the slice is unspecified'; a cyclic comparator panicked stable `sort_by` on a 50-element input (measured). The 1.82 release notes say the rewritten binary_search 'may select a different value among the equal ones than the old implementation': results that depend on how std treats ties do move between releases.
- **In si-rpg-engine:** `rebuild_snapshot` (solver/src/rapier_law.rs, the same at e5fbcb9 and main 4782a8a) sorts `Vec<&ContactPair>` with stable `sort_by` on `(collider1.into_raw_parts(), collider2.into_raw_parts())`. That key cannot tie under Rapier 0.35.3: pair_management.rs adds a contact edge only when the undirected `find_edge(gid1, gid2)` finds none, so each collider pair appears once, and stable or unstable would hash the same bytes. If a later snapshot sorts by a key that can tie (manifold points, a float depth), `sort_unstable_by` would let a move of the 1.98.1 pin reorder tied elements and shift the golden, while `sort_by` would fall back to Rapier's own edge order, which swap_remove rewrites. Extend the key until it is unique instead.

### Let only Vec, VecDeque or BTreeMap/BTreeSet order reach an output; HashMap/HashSet order is random per map
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any

**std defines iteration order for sequences (index 0 upward), VecDeque (front to back) and B-trees (key order); HashMap/HashSet iterate in 'arbitrary order' under a randomly seeded hasher that differs per map and per run, and BinaryHeap::iter/into_vec are arbitrary too.**

- **How:** When order can reach bytes, a hash, a log line or a golden, iterate a `Vec`/slice/array (index order), a `VecDeque` (front to back) or a `BTreeMap`/`BTreeSet` (key order; keys must be `Ord`). Keep `HashMap`/`HashSet` to lookups, or collect and sort before emitting: `let mut ks: Vec<_> = m.keys().copied().collect(); ks.sort_unstable();` (map keys are unique, so an unstable sort is safe). Empty a `BinaryHeap` with `pop()` or `into_sorted_vec()` (ascending), never `iter()`/`into_vec()`. Map equality `a == b` ignores order and is safe; `a.iter().eq(b.iter())` compares orders and is not.
- **Gotchas:** Two HashMaps filled by the same inserts in one process iterate differently (measured on 1.98.1), and a second run of the same binary prints yet another order, so a test that compares a run with itself passes. The default hasher is 'currently SipHash 1-3, though this is subject to change at any point in the future': neither std's HashMap order nor its hash values are a persistence contract (fixed-seed hashers, IndexMap and FxHash are covered in float-determinism). `{:?}` of a HashMap follows the same order: the two identical maps printed different Debug text (measured), so never put one in a golden. A BinaryHeap collected from [1, 5, 2, 4, 3] iterates as [5, 4, 2, 1, 3] on 1.98.1: heap array order, not sorted. `BTreeMap<f64, _>` does not compile (E0277, `f64: Ord` is not satisfied).
- **In si-rpg-engine:** solver/src (e5fbcb9 and main 4782a8a) holds no HashMap, HashSet or BTreeMap: bodies and colliders live in fixed `static mut` arrays walked in index order, plus `Vec<Option<RigidBodyHandle>>`. Rapier's `contact_pairs()` is Vec-backed but not canonical (see the swap_remove recipe), which is why the snapshot sorts it. Any map added for mesh collision or host bindings should stay off the snapshot path or be a BTreeMap.

### Sort f64 with sort_by(f64::total_cmp), find first matches with partition_point, and dedup floats by bits

Before 1.82 the float identity was +0.0, so an empty sum hashed through `to_bits()` changes sign across that release. Parallel reductions (rayon) regroup additions (concurrency-async lane).
