### Encode snapshots canonically: to_le_bytes in a fixed field order, sorted pairs, no padding, a version tag
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any; bytemuck 1.25.2 for the Pod derive

**A snapshot is a byte string the law defines — explicit little-endian numbers in a declared order, collections sorted by a total key, and a header with a magic, a law version and counts — never a struct's memory image, whose field order and padding belong to the compiler.**

- **How:** Write every field with `to_le_bytes()` into a `Vec<u8>`: the header `b"SIRS"`, `LAW_VERSION.to_le_bytes()` (u32) and the counts, then per body pose and velocity in one order, then pairs after `sort_by_key(|p| (p.a, p.b))`. The decoder refuses a foreign magic, another law version, and any length that is not the layout (`16 + 48 * bodies + 24 * pairs` in the check). If a record is cast to bytes, make it `#[repr(C)]` and derive `bytemuck::Pod`, which refuses padding at compile time; spell padding as a zeroed field (`_pad: u32`) so the layout is explicit (16 bytes, `0700000000000000000000000000e03f` in the check).
- **Gotchas:** `#[repr(C)] struct { flag: u8, impulse: f64, kind: u8 }` is 24 bytes, 14 of them padding (offsets 0, 8, 16), and the same fields under the default representation are 16 bytes, because the default representation guarantees only what soundness needs and may reorder fields. Deriving Pod on `{ pair: u32, impulse: f64 }` fails with `error[E0080]: evaluation panicked: derive(Pod) was applied to a type with padding`. `to_ne_bytes` is native order, and the std docs say portable code should use `to_be_bytes` or `to_le_bytes`; wasm memory is little-endian, so the two agree there and part ways on a big-endian host. Without a version word a layout change shows only as a length change, and a same-length change of meaning passes. Canonicalise -0.0 before writing (the float-determinism lane owns that detail).
- **In si-rpg-engine:** rapier_law.rs rebuild_snapshot already follows most of this: `push_f64` writes `canon(x).to_le_bytes()` per field in a fixed per-body order (pose, velocity, quaternion, spin, sleep counter in quanta, sleeping flag), then the pair count, then pairs sorted by `(collider1.into_raw_parts(), collider2.into_raw_parts())` with seven warm-start f64s per manifold point; counts and ids go in as f64, exact below 2^53. It has no magic and no version word, which is why T3 records length plus digest to notice a layout change. T2's solver_restore must refuse a foreign snapshot; a version word in the header is the direct way, and adding one moves the product golden once.

### Keep the law out of an ECS: archetype tables swap-remove rows and query iteration order is not guaranteed
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust bevy_ecs 0.19.1 (0.20.0-rc.1 exists), hecs 0.11.1; neither is in the oracle set, so the check models the mechanism

**bevy_ecs 0.19.1 and hecs 0.11.1 keep entities in archetype tables that swap-remove rows, bevy documents query iteration order as not guaranteed and runs non-conflicting systems in parallel, and Entity bits are not stable across releases; for a 64-record law an ECS buys composition it does not need and costs an explicit sort, a pinned executor and ambiguity checks to win determinism back.**

- **How:** Keep the law as flat arrays in record order and let an ECS, if any, live on the host's presentation side, receiving committed frames. If law-relevant code does run in bevy_ecs: iterate with `QueryIter::sort` by a stable id component (stable, built on `slice::sort`, not cached across system runs) or `iter_many` over a sorted id list (items come back in the list's order); install `SingleThreadedExecutor::new()` with `Schedule::set_executor`, or order every system; raise `ScheduleBuildSettings::ambiguity_detection` from its default `LogLevel::Ignore`; never persist `Entity` bits. hecs is 'a library, not a framework' with no System abstraction, so ordering stays in your code, but its archetypes still swap-remove.
- **Gotchas:** Measured on a model of the mechanism (hecs's `Archetype::remove` and bevy's `Table::swap_remove_unchecked` move the last row into the hole; hecs's `World::insert` appends the entity to its new archetype): iteration [1,2,3,4,5] becomes [1,5,3,4] after despawning 2 and [4,5,3,1] after 1 moves to another archetype; sorting by id gives [1,3,4,5]. `par_iter`: 'Iteration order and thread assignment is not guaranteed'. bevy's Entity docs: the internal bit representation 'is liable to change from release to release', and `to_bits`/`from_bits` identify entities only within one running instance. Not measured: whether bevy's allocator hands out the same ids for the same spawn and despawn sequence is not documented, so do not rely on it.
- **In si-rpg-engine:** The law is solver/src: stride-17 `BODIES`, stride-10 `COLLIDERS` and one Rapier `PhysicsWorld` whose handles follow insertion order (recipe on stable ids). An ECS in the law would add a second storage whose order must be sorted back into record order before every Rapier insert and before the snapshot. The Godot and Unreal hosts after Phase 2 bring their own scene trees; keep them on the presentation side of the boundary. Judgment, not measurement: no ECS in the law; revisit only if the record outgrows fixed strides.

### Key records by stable ids, keep insertion and removal history in the record, and sort by a total id key
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any; rapier3d-f64 0.35.3, slotmap 1.1.1, indexmap 2.14.2

**Generational handles encode history — Rapier's generation is one counter per set, raised on every removal, and slotmap reuses slots under new versions — so persisted ids are the world file's own, handles are reproduced only by replaying the same inserts and removals, and every order-sensitive step iterates in sorted full-key order, never container order.**

- **How:** Key the record by world-file ids; treat `ColliderHandle` and `RigidBodyHandle`, slotmap keys and `bevy_ecs::Entity` as process-local. Insert into Rapier in file order and record removals, because both decide `into_raw_parts()`. Before any order-sensitive step (a reduction, a snapshot, event dispatch) sort by a key that cannot tie: `pairs.sort_by_key(|p| (p.collider1.into_raw_parts(), p.collider2.into_raw_parts()))`; `ColliderHandle` has no `Ord` at 0.35.3, so calling `.sort()` on handle tuples is E0277. Iterate law-side maps as `BTreeMap` (key order) or as `IndexMap` with explicit `shift_remove` and `sort_keys`; never iterate a `HashMap` in the law.
- **Gotchas:** Rapier 0.35.3: three colliders get (0,0), (1,0), (2,0) in insertion order, so reordering the file reassigns them; after one removal every new handle carries generation 1, even in a fresh slot (a(0,0) b(1,0) c(0,1) d(2,1) e(1,2) f(3,2)), because the arena's `remove` does `self.generation += 1` and each insert takes `generation: self.generation`. slotmap: after a remove and an insert, iteration runs a, d, c (slot order, not insertion order); a map rebuilt from its live values has different keys, and `KeyData::as_ffi` promises nothing about its value beyond round-tripping through `from_ffi`. IndexMap's `remove` is deprecated because it is `swap_remove` (30,40,20); `shift_remove` keeps order (30,20,40). Two HashMaps holding the same 64 keys in one process iterate in different orders. The same four impulses summed in three orders give 1.0, 0.0 and 2.0. A stable sort on a key that can tie keeps the incoming order of the tied items, so container order leaks through: sorted by body only, two input orders stay different; sorted by the full pair they agree.
- **In si-rpg-engine:** rapier_law.rs build_world inserts the static colliders, then the heightfield, then the bodies, in record order; rebuild_snapshot sorts pairs with `sort_by` on `into_raw_parts()` and pushes both colliders' index and generation as f64, so insertion and removal history sit inside the hashed bytes. Today nothing is removed without a reload (a carried body changes the signature and ensure() rebuilds the world), so generations stay 0. S1 pins 6 and 9 keep the stable sort and add a removal-and-reinsertion case to T3's insertion-order test (T3 pin 5); T2's restore must reproduce the removal count as well as the live set.

### Parse host-written body slots into a typed record at the boundary, with named refusals for the mode slot
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any

**Every f64 the host writes into the law's buffers is untrusted: decode each record once into a typed value — finite floats, positive half-extents, a unit quaternion, and a mode that is exactly 0, 1, 2 or 3 — and refuse anything else with a reason naming the body, the slot and the raw bits, so every law reads the same decoded value.**

- **How:** `impl TryFrom<&[f64; 17]> for Body { type Error = Refusal; ... }` (TryFrom is for conversions 'that may fail in a controlled way'). Test every slot with `is_finite()`, which refuses NaN and both infinities; half-extents with `> 0.0`; the quaternion with `(norm - 1.0).abs() <= 1e-9` (T2's tolerance), or canonicalise it by one stated rule that load and restore share. Decode slot 16 in one function: canonicalise zero, then match `to_bits()` against 0x0000000000000000 (dynamic), 0x3ff0000000000000 (kinematic), 0x4000000000000000 (lifted) and 0x4008000000000000 (carried); anything else is `Refusal::UnknownMode { body, bits }`. That is the canonical refusal for the field: the body index, slot 16, the bit pattern (NaN prints 7ff8000000000000), and the step returning 0. Laws then `match` the `Mode` enum, so a law that forgets a mode fails to build with E0004.
- **Gotchas:** The two readers of slot 16 disagree today: 3.0 is driven to the box step (`!= 0.0`) and carried to signature(); 0.5, 4.0, -1.0, NaN and infinity are driven to the box step and dynamic to the product law; neither refuses. A NaN-only guard lets infinity through, and `!(x > 0.0)` catches NaN and non-positive values but passes +inf. Float literal patterns also work as a decoder (they compile clean on 1.98.1, -0.0 matches the `0.0` arm and NaN matches no arm, so `_ => refuse` catches it); matching `to_bits()` makes the four accepted bit patterns explicit. Silent normalisation means the file says one rotation and the law simulates another. The JavaScript world loader refuses non-unit quaternions today, but a Godot or Unreal binding will not run that loader, so the Rust boundary must carry every refusal itself.

### Persist hashes of explicit little-endian bytes, never #[derive(Hash)] streams or DefaultHasher output
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any; xxhash-rust 0.8.18, blake3 1.8.7

**What `Hash` feeds a hasher is not portable (usize length prefixes, native endianness) and `DefaultHasher`'s algorithm is unspecified across releases, so any hash that is stored, compared across hosts or pinned in a golden is a named function (FNV-1a, xxh3, BLAKE3) over bytes the law encoded itself.**

- **How:** Choose by job. FNV-1a (RFC 9923; 32-bit prime 0x01000193, basis 0x811C9DC5; 64-bit prime 0x100000001B3, basis 0xCBF29CE484222325) is a few lines with no dependency. xxh3 (`xxhash_rust::xxh3::xxh3_64` or `xxh3_128`, feature `xxh3`) is the fast choice; its output was declared stable in xxHash v0.8.0 (2020) and is identical on little- and big-endian systems, and the streaming `Xxh3::new()` / `update` / `digest()` gives the one-shot value (checked over five chunkings). BLAKE3 (`blake3::hash`, 32-byte output, crate 1.8.7) when a digest must resist deliberate forgery, such as a replay bundle someone else hands you. Hash `encode(&state)` (previous recipe): the same FNV-1a 64 over the same 35 bytes returned 845153761026826623 on x86_64 and on wasm32. Keep `Hash`, `DefaultHasher` and `RandomState` for in-process maps.
- **Gotchas:** The std `Hash` docs: data fed by `Hash` 'should not be considered portable across platforms' and 'tests shouldn't probe hard-coded hash values'; `DefaultHasher`: 'The internal algorithm is not specified, and so it and its hashes should not be relied upon over releases'; HashMap's SipHash 1-3 is 'subject to change at any point in the future'. Measured: `#[derive(Hash)]` on `{ id: u32, name: String, cells: Vec<u8> }` feeds 18 bytes on x86_64 and 14 on wasm32, because the Vec's length prefix is a usize (a str ends with a 0xff byte instead). Neither FNV nor xxHash resists an adversary (RFC 9923: NOT RECOMMENDED where collision or preimage attacks must be infeasible; the xxHash README: not a cryptographic hash). A word-wise mixer `h = h * P + x` with FNV's constants is not FNV-1a, which XORs one octet and then multiplies, and it collides algebraically: (x1 + 1, x2 - P) gives the same value as (x1, x2).

### Stop feeding u32-only streams to both FNV-1a lanes: such a digest repeats one 32-bit half
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any (the checks are a Rust port of the JavaScript hasher)

**packages/frame/hash.js mixes every u32 into both lanes from the same basis, so a digest built only from u32 input — the T1 trace's snapshot digest and the snapshot digests T3 adds to the behaviour file — has identical halves and carries 32 bits; frame hashes keep the lanes apart because each double's low and high words go to different lanes.**

- **How:** Confirmed in hash.js: `u32(w)` runs `h0 = mix(h0, v); h1 = mix(h1, v)`, both lanes start at 0x811c9dc5 (RFC 9923's 32-bit offset basis), `float(x)` sends the low little-endian word to lane 0 and the high word to lane 1, and `digest()` is `hex(h0) + hex(h1)`; harness/trace-line.mjs `snapshotField` feeds `u32(snap.length)` and then `u32(snap[i])` for every byte. Fix options, cheapest first. (A) At the u32-only digest sites only, split the byte stream across the lanes the way a double is split (the low four bytes of each 8-byte word to lane 0, the high four to lane 1): the frame hash, the product golden fd2f6c03fb982d77 and the arithmetic golden 0d38671370d12d1e stay, and the trace's `snap` digests and the behaviour file's snapshot digests move once. (B) Change `u32()` so the lanes see different images of each word (lane 1 takes it bit-reversed, or one lane its 8-byte widening): every frame hash mixes u32 and text input (seed, tick, ids, zone and link indices, snapshot bytes), so the product golden and every fixture's frame hashes move once; the float-only arithmetic golden does not. (C) A real 64-bit function, FNV-1a 64 or xxh3 over the bytes: one 64-bit state, but JavaScript needs BigInt or 16-bit-limb multiplication in all three shells (or the law computes and exports the digest), and every digest it replaces moves.
- **Gotchas:** Birthday arithmetic: 32 bits give an even chance of some collision among about 77,000 distinct snapshots, 64 bits among about 5 billion; in the check two of 125,346 arbitrary one-word snapshots share f7da4862f7da4862, and each of the three fixes separates them. Option A still leaves each lane guarding only the half of every word it sees, so a change confined to low words is protected by 32 bits; option C has no such split. The frame hash's own snapshot section (tick.js `mixSnapshot`) also feeds bytes as u32 to both lanes, and its halves differ only because floats were mixed earlier. Identical halves make a cheap tripwire: a test that fails when a digest's first eight hex digits equal its last eight catches a regression of any digest meant to carry 64 bits.
- **In si-rpg-engine:** packages/frame/hash.js `u32()` and `digest()`; harness/trace-line.mjs `snapshotField`, the T1 trace's `snap <len> <digest>` token; and the behaviour-file digests: the T3 branch (PR #44, head b99a636) records `snapshotDigest` load 52bfc19452bfc194 and last 41b1e63f41b1e63f in fixtures/golden-behaviour.json, both with identical halves. S1 pin 13 (docs/dispatch-s1-soundness.md) takes option A and states that the product golden and every frame hash stay while the behaviour-file digests move once with that reason.

### Version the law with golden hashes plus behaviour numbers, so each golden move names what moved
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any; checked with rustc --test on 1.98.1

**A golden hash says only that something changed; behaviour numbers recorded beside it — each body's sleep quantum, final positions, snapshot length and digest — checked by the same test and rewritten by the same command turn a move into a named, reviewable change, as Box2D's CI does with its step count to sleep and a hash of the resting transforms.**

- **How:** Keep two kinds of golden: a contract golden that must never move (the engine's arithmetic golden) and a law golden that moves only with a stated reason. Bump discipline: one command rewrites the golden and the behaviour file together and prints each moved number; the commit and the changelog carry the new golden and the reason; a bump of rapier3d-f64 or the toolchain reruns the outcome tests before any golden may move; the binary digest is a separate pin. A law variant can be modelled under test with `--cfg` (`--cfg law_bump` turns on `#[cfg(law_bump)]`).

### Run the law on integer quanta from a host-owned accumulator; keep render interpolation out of the state
`▸ plausible` · ✓ verified · ✔ compiles as claimed · Rust any (checked on 1.98.1); bevy_time 0.19.1 for the comparison

**A 1/64 s quantum is exact in binary, so the law counts time as an integer tick; the host's accumulator, kept in integer nanoseconds, decides how many quanta a frame runs and the render alpha, and neither the alpha nor any clock value reaches the hashed state.**

- **How:** Give the law `tick: u64` and `const DT: f64 = 1.0 / 64.0`; derive seconds as `tick as f64 * DT`, never by `t += DT`. Keep the accumulator in the host: `acc_ns += frame_ns; while acc_ns >= 15_625_000 { law.step(&inputs_for(tick)); tick += 1; acc_ns -= 15_625_000; }`, then draw with `alpha = acc_ns as f64 / 15_625_000.0`. Presentation receives shared references to committed state and returns a pose, e.g. `fn draw(prev: &State, cur: &State, alpha: f64) -> f64 { prev.y + (cur.y - prev.y) * alpha }`; an assignment through `&State` is E0594, so safe code cannot write a smoothed pose back. Bevy 0.19.1 makes the same choices: `Time<Fixed>` defaults to 64 Hz (15625 µs), keeps its accumulated `overstep()` as a `Duration`, may run the fixed schedule 0, 1 or more times per frame, and offers `overstep_fraction()` for interpolation.
- **Gotchas:** 1/60 is not exact: sixty 1/60 steps accumulate to 1.0000000000000013 and an hour of them to 3600.0000000182276, while `ticks as f64 * dt` gives 3600.0; with 1/64 both give exactly 3600.0. An f64-seconds accumulator fed 1/60, 1/120 or 1/144 s frames ran 63 quanta after one second of frames (64 at 240 Hz), while the integer-nanosecond accumulator ran 64 at every pacing: which frame a quantum lands in then depends on pacing, harmless only when inputs are stamped with their quantum (next recipe). `Duration::from_secs_f64` rounds (1/60 s becomes 16.666667ms), so convert a frame time once and accumulate integers. E0594 guards safe code holding `&State` only: an `extern "C"` export that returns a pointer into a `static mut` buffer gives the host a writable view, so the law re-checks every value it reads on every call.
- **In si-rpg-engine:** packages/tick/tick.js runs the 1/64 s quantum in JavaScript and mixes `hasher.u32(tick)`, so time enters the hash as an integer; solver/src/lib.rs and rapier_law.rs hold `DT = 1.0 / 64.0` as a constant and read no clock. README: 'Presentation has no path back into the hash', and packages/frame/frame.js freezes the committed frame the host receives. The gap is the ABI: `bodies_ptr`, `colliders_ptr` and `heights_ptr` hand JavaScript writable f64 views, so on the Rust side the rule rests on signature()'s per-call checks, not on types. A Godot or Unreal host keeps its own accumulator and drives the law by quantum count, never by frame delta.
