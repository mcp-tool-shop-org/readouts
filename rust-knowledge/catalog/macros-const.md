### Compute tables in const fn with while, match and &mut; expect E0015 on for-loops, trait calls and formatting
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust 1.83+ (&mut in const), 1.82+ (float ops in const fn), 1.57+ (panic in const); no stable const traits on 1.98.1

**On 1.98.1 const code runs loop/while/if/match, takes &mut (1.83), does float arithmetic (1.82) and panics with literal messages (1.57); for-loops, iterator methods, trait operators on your own types, PartialEq on str, heap allocation and formatted panic messages are refused.**

- **How:** Const contexts, always evaluated at compile time: array lengths and repeat counts, const and static initializers, enum discriminants, const generic arguments, `const { }` blocks. Write loops as `let mut i = 0; while i < N { ...; i += 1; }` or `loop { ... break v; }`; pass `&mut [T; N]` into a const fn to fill a table in place and bind the result: `const TABLE: [f64; 4] = { let mut t = [0.0; 4]; fill(&mut t, 0.25); t };`. Panic with `panic!("literal")` or `assert!(cond, "literal")` (one &str through `{}` also works); failure is E0080 'evaluation panicked: ...'. Measured refusals on 1.98.1: `for i in 0..n` -> E0015 'cannot use `for` loop on `std::ops::Range<u32>` in constant functions'; `a.iter().sum()` -> E0015 plus '`iter` is not yet stable as a const fn'; `a + b` through a user `impl Add` -> E0015 'cannot call non-const operator'; `a == b` on &str -> E0658 '`PartialEq` is not yet stable as a const trait'; `Vec::push` -> E0658 plus E0493 (destructor at compile time); `assert!(x == 17, "stride is {}", x)` with a usize -> E0015 'cannot call non-const formatting macro'.
- **Gotchas:** A const fn called outside a const context is not guaranteed to run at compile time; bind it to a const or wrap it in `const { }` to force it. Overflow and out-of-bounds indexing in a const context are compile errors, not wraps or run-time panics. A mutable reference may not become part of a const's final value (1.83 post). Generic code over `T: Add` cannot be const on stable, so write concrete f64/usize const fns.
- **In si-rpg-engine:** lib.rs's `step` and `resolve_pair` already use index while loops, a const-compatible style. The realistic const work in the solver is proofs and tables over the ABI constants (see 'Pin the solver ABI with const _ assertions...'); the step itself reads `static mut` buffers at run time and stays an ordinary fn.

### Embed build inputs with include_bytes!, include_str!, env! and concat!, and know which of them fail the build
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any

**include_bytes!/include_str! embed a file located relative to the current source file, env! bakes in a compile-time variable and fails the build when it is unset (option_env! returns None), concat! joins literals into a &'static str, stringify! returns tokens as text, and compile_error! stops the build with your message.**

- **How:** `include_bytes!("pinned/si_solver.wasm")` -> `&'static [u8; N]`, the path relative to the current file and interpreted per platform (write `/`); a missing file fails with 'couldn't read ...'. `env!("NAME")` -> `&'static str`; unset -> 'environment variable `NAME` not defined at compile time'; `env!("NAME", "msg")` replaces the text; `option_env!("NAME")` -> `Option<&'static str>`. `concat!("si-solver/", 17, "/", 2.5, "/", true, "/", 'x')` -> "si-solver/17/2.5/true/x"; arguments may be macro calls that expand to literals (stringify!, env!, your own). `stringify!(BODY_STRIDE * 8 + HX)` -> "BODY_STRIDE * 8 + HX". They compose with const fn: a const FNV-1a over `include_bytes!(file!())` is computed during compilation and equals a run-time recomputation. `compile_error!` in a macro_rules! fallback arm turns bad input into your message (`law!(havok)` -> 'law! accepts `box` or `rapier`').
- **Gotchas:** env! reads the environment of the rustc process, so a variable present on one CI machine and absent on another changes the bytes or breaks the build; under Cargo, OUT_DIR is set only during compilation. std warns that stringify!'s expansion 'may change in the future': use it for single identifiers in a names table, never as hashed or persisted text. A backslash path in include_bytes! does not compile on Unix. include_bytes! copies the file into the artifact at compile time; a changed file means a rebuild, not a reload.
- **In si-rpg-engine:** build.mjs embeds the pinned wasm into JS as a Uint8Array literal. A native Rust host shell (the Godot or Unreal bindings slice) would embed it with include_bytes!(".../si_solver.wasm") and can refuse to compile against any other module with a const-fn digest check over those bytes; the pin itself stays the SHA-256 in fixtures/solver.sha256, and FNV-1a here only demonstrates compile-time hashing.

### Emit cargo:: lines from build.rs, pair rustc-cfg with rustc-check-cfg, and read the target from CARGO_CFG_*
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust cargo:: 1.77+; rustc-check-cfg respected 1.80+; cargo::error 1.84+

**A build script is a host program Cargo compiles and runs before the crate; since Cargo 1.77 it speaks `cargo::KEY=VALUE`, it must learn the target from CARGO_CFG_* (cfg! there describes the host), write only into OUT_DIR, and declare every cfg it sets.**

- **How:** Directives (Cargo Book): `cargo::rerun-if-changed=PATH` (a directory is scanned whole), `rerun-if-env-changed=VAR`, `rustc-cfg=KEY[="VALUE"]`, `rustc-check-cfg=CHECK_CFG` (respected from 1.80), `rustc-env=VAR=VALUE`, `warning=MSG`, `error=MSG` (1.84+, fails the build), `metadata=KEY=VALUE`, and the rustc-link-* family. `cargo::KEY=VALUE` needs Cargo 1.77 (rust-lang/cargo#12201, milestone 1.77.0); older toolchains need `cargo:KEY=VALUE`, where unsupported keys are taken as metadata. Measured on a scratch crate with `cargo +1.98.1 build --target wasm32-unknown-unknown --offline`: `cargo::rustc-cfgg=x` -> error 'invalid output in build script ... Unknown key: `rustc-cfgg`', while `cargo:rustc-cfgg=x` passed silently; the script printed `cfg!(target_arch = "wasm32") = false` beside `CARGO_CFG_TARGET_ARCH = wasm32`, `CARGO_CFG_TARGET_FAMILY = wasm`, `HOST = x86_64-pc-windows-msvc`; with `rerun-if-changed=build.rs` and `=abi.txt`, editing src/lib.rs recompiled only the lib and editing abi.txt re-ran build-script-build; `cargo build -v` showed the script's lines arriving as `--cfg si_abi_generated --check-cfg 'cfg(si_abi_generated)'` next to Cargo's defaults `--check-cfg 'cfg(docsrs,test)' --check-cfg 'cfg(feature, values())'`. Generated code goes to `OUT_DIR` and in with `include!(concat!(env!("OUT_DIR"), "/abi.rs"));`. Cost, cold on this rig: a trivial script took 0.32 s to compile and 0.05 s to run against 0.13 s for the lib; the solver's graph compiles 8 dependency build scripts (0.34-0.49 s each) and runs them (0.08-0.29 s).
- **Gotchas:** `cargo::rustc-cfg=X` without `cargo::rustc-check-cfg=cfg(X)` makes every `#[cfg(X)]` warn unexpected_cfgs although X is set (measured). cfg!/#[cfg] inside build.rs test the host, so a wasm cross-build silently takes the host branch; the Cargo Book says to use CARGO_CFG_* instead. With no rerun-if line Cargo reruns the script whenever any file in the package changes. OUT_DIR is not cleaned between builds and may hold stale files. 'Scripts should not modify any files outside of that directory', so a build.rs cannot legitimately write a JS module next to the wasm. A build script is arbitrary host code inside the build: reading the clock, undeclared env vars or files outside the package makes the artifact depend on the machine.
- **In si-rpg-engine:** The solver has no build.rs; its generator is node (solver/build.mjs), outside Cargo. A build.rs that generated the ABI table could write only the Rust half into OUT_DIR, so build.mjs would still have to read the same data file itself; that is why the macro table in 'Pin the solver ABI with const _ assertions...' is the smaller change. If one is ever added, it must test CARGO_CFG_TARGET_FAMILY (wasm), never cfg! (the Linux or Windows host), and every clean build gains a compile and a run unit.

### Gate wasm code on target_family = "wasm" and turn a forbidden target feature into compile_error!
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any; unexpected_cfgs on by default in Cargo 1.80+

**#[cfg] removes items before type checking, cfg! only yields a bool, and cfg_attr adds attributes conditionally; on 1.98.1 wasm32-unknown-unknown sets target_family = "wasm", target_arch = "wasm32", target_os = "unknown" and panic = "abort", so `#[cfg(target_feature = "relaxed-simd")] compile_error!(...)` turns a flag slip into a failed build.**

- **How:** `#[cfg(pred)]` on items with `all()`, `any()`, `not()`; `cfg!(pred)` is the literal true or false, so both branches must compile (calling a cfg'd-out fn is E0425); `#[cfg_attr(pred, a, b)]` expands to each listed attribute (the check exports `law_version` through `cfg_attr(target_family = "wasm", unsafe(no_mangle), inline(never))`). Measured `rustc +1.98.1 --print cfg`: wasm32-unknown-unknown -> target_family="wasm", target_arch="wasm32", target_os="unknown", panic="abort", target_feature bulk-memory, multivalue, mutable-globals, nontrapping-fptoint, reference-types, sign-ext; wasm32v1-none -> target_os="none" with only mutable-globals; `-C target-feature=+relaxed-simd` also sets simd128; `-C target-cpu=bleeding-edge` turns on relaxed-simd and simd128. The guard `#[cfg(target_feature = "relaxed-simd")] compile_error!("...");` compiles by default and fails with its message under +relaxed-simd. Name checking: Cargo 1.80+ passes --check-cfg by default and the warn-by-default unexpected_cfgs lint flags unknown names and values (measured: `#[cfg(si_abi_generatd)]` -> 'there is a config with a similar name: `si_abi_generated`'); declare static custom cfgs with `[lints.rust] unexpected_cfgs = { level = "warn", check-cfg = ['cfg(name)'] }` and build-script ones with `cargo::rustc-check-cfg`. Use target_family = "wasm" for any wasm target and target_arch = "wasm32" when the 32-bit pointer width matters.
- **Gotchas:** cfg! does not remove code; the other branch must still resolve and type-check. target_family can hold several values at once (the Reference names unix together with wasm), so compare, never assume a single value. Plain rustc, and this KB's oracle, checks cfg names only when a --check-cfg flag is passed ('Well known names and values are implicitly added as long as at least one --check-cfg argument is present'), so typos surface only in Cargo builds. A guard written as `#[cfg(not(target_family = "wasm"))] compile_error!` would also break host `cargo test` of pure functions: forbid the feature, not the host. The rustc feature name is relaxed-simd, and enabling it implies simd128.
- **In si-rpg-engine:** solver/.cargo/config.toml and solver/build.mjs both pass `-C target-feature=-relaxed-simd` because RUSTFLAGS replaces the config's rustflags (build.mjs says so). Two lines in lib.rs, `#[cfg(target_feature = "relaxed-simd")] compile_error!(...)`, make the source refuse that configuration however the flags arrive, e.g. a `RUSTFLAGS="-C target-cpu=bleeding-edge"` build that forgot the disable. T3's opcode lint stays the check on the bytes. Measured on a scratch copy of solver/ at e5fbcb9: appended to the end of lib.rs, the guard left si_solver.wasm byte-identical, and a RUSTFLAGS='-C target-cpu=bleeding-edge' build then failed with the guard's message.

- **How:** Fragments on 1.98.1 (Reference): block, expr, expr_2021, ident, item, lifetime, literal, meta, pat, pat_param, path, stmt, tt, ty, vis. Repetition is `$( ... ) sep op` with `*`, `+` or `?` (`?` takes no separator); end a list with `$(,)?` to accept a trailing comma. `expr` and `stmt` may be followed only by `=>`, `,` or `;`, so `($e:expr $i:ident)` is rejected where the macro is defined. Locals and labels created inside an expansion are invisible to the caller (E0425, 'not accessible due to macro hygiene'); other names resolve at the call site. A macro enters textual scope after its definition; `#[macro_export]` makes it pub at the crate root (`crate::slot!`, `other_crate::slot!`), so name every item the expansion uses as `$crate::module::item`. Edition 2024: for `example!(const { 1 + 1 })` the same two-arm macro prints 'second rule' in 2021 and 'first rule' in 2024; `m!(_)` goes to the `tt` arm in 2021 and the `expr` arm in 2024; `expr_2021` (stable in every edition since 1.83) restores the 2021 set, and the `edition_2024_expr_fragment_specifier` lint that `cargo fix --edition` applies rewrites `expr` to `expr_2021`. For ABI numbers use `$v:literal`, which no edition changes. Use macro_rules! to declare items (consts, exports, impls) or to name them with `stringify!`; compute values with const fn.
- **Gotchas:** Arms are tried in order and the first match wins, so an `expr` arm placed before a `const`-prefixed arm silently changes which arm fires when the crate moves to 2024. `cargo fix --edition` turns every `expr` into `expr_2021`: behaviour-preserving, but it hides whether the new meaning was wanted. `#[macro_export]` ignores the defining module's path (the macro lives at the crate root); `local_inner_macros` exists for pre-$crate code and is discouraged in new code. Invoking a macro above its definition fails with 'cannot find macro' (rustc notes that one exists later); a non-exported macro inside `mod abi` is invisible outside it unless the module carries `#[macro_use]`. Diagnostics point into expansions, so keep macro bodies to declarations and call functions for logic.
- **In si-rpg-engine:** solver/src/lib.rs and rapier_law.rs (e5fbcb9) contain no macro_rules! today. The first one that earns its place is the ABI table (see 'Pin the solver ABI with const _ assertions...'): one invocation declaring BODY_STRIDE, HX..DRIVEN and COLLIDER_STRIDE plus their stringify!'d names. The solver crate is edition 2021, so write `$v:literal` (or `expr_2021`) there: an `expr` fragment written today would widen on a 2024 migration.

### Pin the solver ABI with const _ assertions and generate the JS strides from one Rust table, not by hand
`▸ plausible` · ✓ verified · ✔ compiles as claimed · Rust 1.57+ (panic in const); offset_of! 1.77+

**`const _: () = { ... }` blocks, offset_of! (1.77) and size_of turn layout and slot invariants into E0080 build failures that add no bytes when appended; a macro_rules! table can emit the consts, the proof and one exported descriptor so JS never retypes 17 or 10.**

- **How:** Free const items are always evaluated, even inside unused functions, so the proof runs on every build. Proof: list every slot of the record, `const SLOTS: [usize; BODY_STRIDE] = [0, 1, 2, 3, 4, 5, QX, QY, QZ, QW, WX, WY, WZ, HX, HY, HZ, DRIVEN];`, then check in while loops that each is below BODY_STRIDE and no two are equal: 17 distinct values below 17 cover the record exactly once. Mirror the layout in a `#[repr(C)]` struct and assert `size_of::<Body>() == BODY_STRIDE * 8` and `offset_of!(Body, driven) == DRIVEN * 8`. A macro `abi_layout! { BODY_STRIDE = 17; HX = 13, HY = 14, HZ = 15, DRIVEN = 16 }` emits the consts, the same proof and `#[unsafe(no_mangle)] extern "C" fn abi_word(i: u32) -> u32` over a static table; the check builds it for wasm32 and abi_word(0) returns 17. Measured bytes. A const _ proof guards the Rust side only; build.mjs's literals can still drift until the glue reads the numbers from the module or from a generated file.
