### Build hashed math from f64 + - * / and sqrt: the same bits on IEEE CPUs, wasm engines and in const eval
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any stable (semantics per RFC 3514); float ops in const fn 1.82+; mul_add const 1.94+; checked on 1.98.1

**The IEEE 754 basic operations (+, -, *, /, sqrt) are correctly rounded (round to nearest, ties to even) in Rust and in WebAssembly, neither flushes subnormals, and rustc's const evaluator computes them in a host-independent soft-float, so a computation built only from them has one bit pattern natively, in every wasm engine and at compile time; only NaN bit patterns may differ.**

- **How:** Keep hashed arithmetic in f64 built from `+ - * /` and `f64::sqrt` (plus bit operations such as `abs`, comparisons and exact int-to-float conversions). Prove agreement the way the checks do: run one chain natively and in wasm and compare `to_bits()`. A 100 000-step chain that also makes a subnormal every step digests to 7853152472807335572 on x86-64 at -O0 and at -O and in wasm32 under node 22's V8; `50.0 * PI / 180.0` is 0x3febecde5da115a9 as a const, at run time natively, and at run time in wasm (4606035483714196905). Derived constants may be `const`/`const fn` (float ops in const fn since 1.82; `mul_add` const since 1.94), but a transcendental in a const is E0015. Leave the floating-point environment alone: Rust assumes the default rounding with denormals-are-zero off, and changing MXCSR's rounding or DAZ bits is immediate UB (`_mm_setcsr` docs); wasm operators round to nearest, ties to even, unless an operator says otherwise (trunc, floor, ...), in non-stop mode, and there is no mode to change.
- **Gotchas:** RFC 3514's own caveat: 32-bit x86 returns floats in x87 registers, altering NaN payloads, and i586 targets use x87 even more pervasively; that is a native 32-bit concern, not wasm32. The guarantee is per operation: a different order ((a+b)+c vs a+(b+c)), an f32 intermediate or a transcendental breaks bit equality. NaN bits made at compile time need not match run time (std docs). On the no_std target wasm32v1-none `f64::sqrt` does not exist on stable (E0599; core's float math is unstable), so a no_std law calls `libm::sqrt`.
- **In si-rpg-engine:** solver/src/lib.rs states the rule in its header ('No other operation than add, sub, mul, div, and sqrt') for `step` and `resolve_pair`; rapier_law.rs's own arithmetic (`canon_quat`, the collider centres and half-extents in `build_world`) stays inside it apart from min/max on positive half-extents, and CLIMB_ANGLE / SLIDE_ANGLE are const-evaluated basic ops. FLAGS.md's 'Nothing in the flags flushes subnormals, so they stay subnormals' holds on both sides: Rust treats a changed DAZ/FTZ state as UB, and wasm defines no flush mode. This is why V8, SpiderMonkey and JavaScriptCore can print one golden.

### Canonicalize -0.0 to +0.0 before to_bits() feeds a hash: equal values, different bits
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any

**`0.0 == -0.0` is true but their bits differ (0x0000000000000000 vs 0x8000000000000000), so a hash over `to_bits()` splits equal states; the sign survives the wasm-to-JS boundary, `total_cmp` orders -0.0 before +0.0, and min/max may return either zero on a tie.**

- **How:** Canonicalize at every point where bits are stored or hashed: `if x == 0.0 { 0.0 } else { x }` (the engine's `canon`) or `x + 0.0` (Rapier's `canonicalize_zero`; -0.0 + 0.0 is +0.0 under round to nearest). Both leave NaN alone, so refuse NaN separately. Shown: raw `mix_f64` of 0.0 and -0.0 differ while the canonical mix is equal; in wasm `canon_zero(-0.0)` returns 0 while an identity export hands -0 to JS.
- **Gotchas:** Canonicalizing only inside the hash still lets -0.0 flow on: 1.0 / -0.0 is -inf, so canonicalize where the value is written too (write_body does). `x + 0.0` looks like dead code to a reviewer or a refactor; name it. `abs()` also clears the sign but changes negative numbers. Sorting by `total_cmp` without canonicalizing separates keys that compare equal.
- **In si-rpg-engine:** rapier_law.rs canonicalizes in `write_body` (every stored field), `canon_quat`, `push_f64` (the snapshot) and the exported `canon_zero`, and Rapier 0.35.3 canonicalizes the warm-start impulses it writes under enhanced-determinism. One path hashes raw bits: `signature()` feeds collider and height values to `mix_f64`, and `same_sig` compares the result, so a quantum whose record writes -0.0 where the previous one wrote +0.0 reloads the world and drops the warm-start cache (build.mjs's `box.qx || 0` canonicalizes only the quaternion's x, y, z). That is a reading of the code, not an observed failure; canon before mix_f64 closes it.

### Expect a*b+c to stay unfused: rustc never contracts, mul_add always rounds once, wasm has no scalar fma
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any (no contraction); mul_add const 1.94+; algebraic_* stable 1.98.0+

**rustc never turns `a * b + c` into a fused multiply-add, not at -O and not with `-C target-feature=+fma`; `f64::mul_add` always rounds once, and on wasm32 it is a software fma compiled into the module (no import); wasm 3.0 has no scalar fma instruction, so hardware-chosen fusion can only enter through relaxed SIMD's relaxed_madd; the stable opt-in to contraction since 1.98.0 is the `algebraic_*` family.**

- **How:** Write `a * b + c` when the law means two roundings (what a JS kernel computes). Write `a.mul_add(b, c)` only when you want IEEE fusedMultiplyAdd on every target: the std docs guarantee 'the rounded infinite-precision result', and it differs from the unfused form (inputs 1+eps, 1-eps, -1 give -4.930380657631324e-32 fused and 0 unfused on x86-64 at -O0, at -O with +fma, and in wasm32). Keep `algebraic_add/sub/mul/div/rem` out of the law (the rust-currency lane covers them; a source grep for `algebraic_` refuses them). Keep relaxed SIMD disabled (`-C target-feature=-relaxed-simd`) and let T3's opcode lint prove that no relaxed instruction reached the binary.
- **Gotchas:** 'Rust may contract a*b+c like a C compiler' is wrong: RFC 3514 precludes it because rounding would change. The reverse mistake is treating `mul_add` as a speed hint that equals `a*b+c`: it is a different result, and without FMA hardware it is a library call. SIMD crates choose per target: wide 1.7.1's `f64x2::mul_add` fuses on x86 with the `fma` feature and on aarch64 NEON and rounds twice elsewhere; relaxed_madd may be fused or unfused, fixed per environment.
- **In si-rpg-engine:** FLAGS.md's 'Fused multiply-add is not in that set. It arrives only with relaxed SIMD, which this build disables' is right about hardware fusion, but an explicit `mul_add` in solver/src or in a dependency still yields a fused result (a deterministic software fma), so the sentence is safest as 'no implicit fusion; mul_add only where written'. solver/src at e5fbcb9 has no mul_add; the rapier3d-f64 0.35.3 and parry3d-f64 0.30.2 sources have none either (grep this session). T3's relaxed-SIMD opcode lint is the gate for the only hardware-dependent fusion path.

### Gate toolchain and Cargo.lock bumps on goldens plus a libm canary; keep fixed-point for integer-exact parts
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust rustc 1.98.1, libm 0.2.16, fixed 1.31.0

**Results move on a bump through three mechanisms, each measured here: a libm version changes an algorithm (rustc 1.98.1's in-tree hypot returns 0x4018842a6ab3fa86 where libm 0.2.16 returns ...85 for the same input), a dependency reorders a sum (floating-point addition is not associative), and codegen changes tie choices such as min/max of zeros. Fixed-point arithmetic removes the float-specific classes (reassociation, NaN, signed zero, platform libm) but not the need for a gate.**

- **How:** Keep both pins (rust-toolchain.toml and Cargo.lock) and move them only through a gate: the golden hash, the behaviour numbers and the T4 course, plus a Rust canary test that asserts the bits of the few libm outputs the law depends on, so a lockfile bump fails by name before a golden moves. Shown: `(0.1+0.2)+0.3` is 0x3fe3333333333334 and `0.1+(0.2+0.3)` is ...33; the harmonic sum to 1000 differs forwards and backwards; the same values as Q32.32 integers (what `fixed`'s I32F32 stores) sum identically both ways. Use `fixed` (1.31.0) for new integer-exact subsystems, not for the physics law: Rapier and parry are f64 code.
- **Gotchas:** A digest-only gate says that something moved, not what; the canary and the behaviour numbers name it. A bump stays silent until a scene reaches the changed path, so the golden scenes must exercise what the law uses (the BVH optimizer's log2 matters only when its rounding decision flips). Fixed-point is not free: range is limited, overflow is an error class of its own (the crate offers Wrapping, Saturating and Strict wrappers), and the law would have to leave Rapier.
- **In si-rpg-engine:** Mirrors T4 pin 6, which makes any bump of the toolchain or of rapier3d-f64 rerun the course before a golden may move; extend the same rule to libm, simba and glam(x) in Cargo.lock, add the canary as a `cargo test` in solver/, and list toolchain-supplied libm symbols from the built wasm (see the rust-toolchain.toml recipe) so the review sees which pin a change came through.

### Treat rust-toolchain.toml as part of the law: the solver links the toolchain's own log2, acos, cos and sin
`▸ plausible` · ✓ verified · ✔ compiles as claimed · Rust rustc 1.98.1; parry3d-f64 0.30.2; glamx 0.3.1; libm 0.2.16

**Inherent calls such as `x.log2()` or `x.acos()` on an f64 resolve to std's method (inherent methods are searched before trait methods, and a `#![no_std]` crate that links std sees them), so libm_force cannot reroute them; in parry 0.30.2's bvh_optimize.rs and glamx 0.3.1's eigen3.rs the ComplexField import is compiled only without std. - **How:** Treat a toolchain bump like a libm bump: rerun the goldens and behaviour numbers before accepting it. - **Gotchas:** Grepping a dependency for `libm::` or trusting 'enhanced-determinism = libm everywhere' misses inherent calls; only the built binary tells you which math is linked. The same calls compiled natively (host bindings) use the platform C library, so a native law would diverge where the wasm law does not. Equality with libm today is a measurement, not a contract.
