### Benchmark before tuning: criterion or divan with harness = false, black_box on every input and output
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust black_box 1.66+ (const 1.86+); criterion 0.8.2; divan 0.1.21 (Rust 1.80+)

**Stable Rust has no built-in bench harness (#[bench] is nightly-only), so time work with criterion 0.8 or divan 0.1 under [[bench]] harness = false and route inputs and results through std::hint::black_box so the optimizer cannot fold the measured work away.**

- **How:** Cargo.toml: `[[bench]] name = "quantum"` + `harness = false`, dev-dependency `criterion = "0.8"` (`criterion_group!` / `criterion_main!`, `c.bench_function("solver_step", |b| b.iter(|| step(black_box(&scene))))`) or `divan = "0.1"` (`#[divan::bench]` + `divan::main()`; divan 0.1.21 needs Rust 1.80+, and its `AllocProfiler` measures GlobalAlloc usage). Import `std::hint::black_box` (stable 1.66, const since 1.86): criterion 0.8.2 deprecates `criterion::black_box` with 'use `std::hint::black_box()` instead'. Wrap inputs so they are not treated as known constants and wrap outputs so a pure call is not deleted, as the two examples in the std docs do. `cargo bench` uses the `bench` profile, which inherits `release`. Time a whole unit (load a fixed scene, then N quanta inside the timed region), warm up first, and compare medians of interleaved runs. Checks can prove behaviour, never a speedup.
- **Gotchas:** black_box is best-effort: the std docs say programs cannot rely on it for correctness beyond behaving as the identity function and it gives no constant-time guarantee, so never use it to enforce behaviour. `#![feature(test)]` + `#[bench]` is rejected on stable with E0554. The bench profile follows [profile.release], so a size-tuned release profile slows benches too. Desktop timing is noisy: in the V8 runs below, three 25-rep medians of one unchanged artifact were 17.10, 17.75 and 24.82 ms, so one run proves nothing; interleave variants and repeat. A debug build is meaningless for tuning (opt-level 0 made the product scene 30x slower in V8).
- **In si-rpg-engine:** The solver has no bench today and its crate-type is cdylib only. In a scratch copy with crate-type ["cdylib", "rlib"], an example linked the law, called `step` and `bodies_ptr` directly, and reached the rapier_law exports through an `extern "C"` block because `mod rapier_law` is private. Baseline on this rig (pinned profile, V8 in node 22.22.3): 17.6 ms per 400 quanta of `solver_step` for a 13-body scene, 203 us per 400 quanta of the box law `step`.

### Get SIMD on stable from auto-vectorization, std::arch and #[target_feature]; std::simd is still nightly-only
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust safe #[target_feature] fns 1.86+; wasm32 simd128 intrinsics stable; std::simd nightly-only

**Once a SIMD feature is enabled, LLVM vectorizes elementwise loops and integer reductions but keeps float reductions in order; std::arch intrinsics are safe #[target_feature] functions that need `unsafe` unless the caller itself enables the feature (on wasm they are always safe to call); std::simd (portable_simd) needs nightly.**

- **How:** Measured on wasm32 (`--emit=asm`, opt-level 3): without a flag all three loops are scalar; with `-C target-feature=+simd128`, `y[i] = y[i] + a * x[i]` becomes f64x2.mul / f64x2.add, a wrapping i64 sum becomes i64x2.add, and an f64 sum stays nine sequential f64.add (unrolled, never reassociated). Enable per function with `#[target_feature(enable = "simd128")]` or per crate with `-C target-feature=+simd128`; the flag does not rebuild the precompiled std, and wasm has no runtime detection, so a module either has SIMD and needs an engine with SIMD or has none. x86 native: runtime dispatch with `is_x86_feature_detected!("avx2")` and a `#[target_feature(enable = "avx2")]` fn called in `unsafe` (safe functions may carry the attribute since 1.86). Measured on 1.98.1: `_mm_add_pd` (SSE2, in the host's default features) from a plain fn is E0133; from a `#[target_feature(enable = "sse2")]` fn it compiles without unsafe. `#![feature(portable_simd)]` is E0554 on stable (tracking issue rust-lang/rust#86656).
- **Gotchas:** Relaxed-SIMD intrinsics such as f64x2_relaxed_madd have implementation-specific results (core::arch::wasm32 docs); the pinned build disables relaxed-simd and another lane owns the opcode lint. Rewriting a float reduction into lanes changes its result; LLVM will not do it for you, so a law must not do it silently. rustc calls -C target-feature unsafe (undefined behaviour on a CPU without the feature). A target feature enabled only by the global target default did not count as 'the caller enables' on 1.98.1 (E0133 for SSE2): annotate the caller.
- **In si-rpg-engine:** The solver builds with no SIMD feature and -relaxed-simd (FLAGS.md). A +simd128 build of the scratch copy gave identical results on the scene, 1,478,802 bytes (-3.0%), a target_features section of 157 instead of 148 bytes, and 0.95x V8 time (inside the +-10% noise). The small change is consistent with glam 0.33.10 (the version glamx 0.3.1 uses) keeping its simd128 paths in f32 and bool types (0 target_feature cfgs under src/f64). SIMD is not worth a new digest today.

### Keep target-cpu=native, PGO and BOLT out of the pinned artifact: they tie codegen to a machine or a profile
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust rustc 1.98.1; wide 1.7.1; cargo-pgo current

**target-cpu=native targets 'the processor of the host machine' and turns on its features (38 instead of 5 on this rig), which flips any cfg(target_feature) path such as wide 1.7.1's fused mul_add; for wasm32, rustc 1.98.1 ignores it with warnings. PGO bytes depend on a training run and cannot even be instrumented for wasm32-unknown-unknown (E0463 profiler_builtins); BOLT rewrites only x86-64 and AArch64 ELF.**

- **How:** Measured: `rustc +1.98.1 --print cfg -C target-cpu=native` on this host (rustc names it arrowlake-s) lists 38 target_feature entries against 5 by default (cmpxchg16b, fxsr, sse, sse2, sse3), adding avx, avx2, fma, bmi1/2 and more. For wasm32, `-C target-cpu=native` printed "'arrowlake-s' is not a recognized processor for this target (ignoring processor)" plus one ignored-feature warning per x86 feature, and the code section was byte-identical to the default build (the file differed only in the module name, which follows the output filename); `--print target-cpus --target wasm32-unknown-unknown` lists bleeding-edge, generic (default), lime1 and mvp. The checks show the mechanism: a cfg(target_feature = "fma") branch prints the fused 2^-54 with +fma and 0 without, while plain a * b + c prints 0 both ways (no contraction). wide 1.7.1's f64x2::mul_add documents the same split (vfmadd single rounding with FMA, vfmaq_f64 on ARM64 NEON, (self * m) + a two roundings otherwise). PGO: rustc's four steps are -Cprofile-generate, run, llvm-profdata merge, -Cprofile-use (cargo-pgo wraps them and BOLT); `-Cprofile-generate` with --target wasm32-unknown-unknown fails with error[E0463]: can't find crate for `profiler_builtins`. BOLT 'operates on X86-64 and AArch64 ELF binaries'. For any native build of the law, pin the target CPU explicitly (never native) and record it next to the digest.
- **Gotchas:** A native binary may use instructions other CPUs lack: std::arch says to run a feature-enabled binary only on systems with the feature, and rustc calls -C target-feature unsafe. PGO output is 'optimized with respect to the profiled workloads' (cargo-pgo), so a different training run gives different bytes and a different workload can even run slower; profiles go stale as code changes. That PGO or BOLT cannot change IEEE results is an inference from the float semantics, not measured here, because wasm could not be instrumented. Do not count on wasm32 ignoring native forever: it is a warning today, and an unpinned flag in RUSTFLAGS is still an unpinned input.
- **In si-rpg-engine:** The wasm artifact is untouched by the builder's CPU today (native is ignored for wasm32 on 1.98.1) and cannot be PGO-instrumented. The real exposure is the planned native host bindings (Godot, then Unreal), where native or +fma flips cfg(target_feature) paths. In the pinned graph those sit in wide (reached through simba 0.10.2) and in glam's f32 types; rapier3d-f64 0.35.3, parry3d-f64 0.30.2, glamx 0.3.1, nalgebra 0.35.0 and simba 0.10.2 have 0 such cfg lines. aarch64-unknown-linux-gnu enables neon by default, so an ARM64 native build selects wide's fused path wherever it is reached. A native law must pin its CPU baseline and match the wasm golden.

### Lay out hot data by access: struct-of-arrays when loops read few fields, rows sized against cache lines
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any

**Struct-of-arrays lets a loop load only the fields it reads; array-of-structs keeps one element's fields together; either way the sizes come from size_of / align_of and #[repr(align(N))], and cache-line sizes are per-architecture guesses (crossbeam assumes 128 bytes on x86_64 and aarch64, 64 on most others).**

- **How:** Know the numbers before choosing: `[T; N]` has size `size_of::<T>() * N` and T's alignment, and a size is always a multiple of its alignment; repr(Rust) guarantees only that fields are aligned, so use repr(C) when a layout is an ABI. Raise alignment with `#[repr(align(64))]` (a power of two up to 2^29; not combinable with packed). SoA in Rust is one Vec per field (or a derive such as soa_derive 0.14.0, which generates a Vec per field) and loops that zip the fields they need; soa_derive states the main advantage is loading only some fields when iterating. Keep hot types small: the perf book notes types larger than 128 bytes are copied with memcpy rather than inline code, and smaller types reduce memory traffic and cache pressure. Cache-line padding (crossbeam-utils CachePadded) exists to stop false sharing between threads.
- **Gotchas:** SoA gives up indexing into one element as a struct (soa_derive's generated vector cannot be indexed into a reference) and turns a one-element copy into scattered loads. repr(Rust) may reorder fields, so never compute offsets by hand without repr(C). There is no std constant for the cache-line size; crossbeam calls its per-architecture values reasonable guesses. On 1.98.1 a non-power-of-two alignment is E0589 and packed + align is E0587. Changing a layout that crosses an ABI is an interface change, not an optimization.
- **In si-rpg-engine:** The solver ABI is array-of-structs: BODIES is [f64; 64 x 17] = 8,704 bytes, 136 bytes per body (2.125 64-byte lines, so rows straddle lines), and build.mjs hard-codes the stride 17 and every offset. rapier_law.rs `body_at` returns [f64; 17] = 136 bytes by value, just over the perf book's 128-byte memcpy size. The V8 profile of the scene put 65% of wasm samples in parry and Rapier and 4.0% in the law's own code, so there is no measured case for changing the ABI layout.

### Reuse per-quantum buffers: clear() keeps capacity, with_capacity sizes once, SmallVec/ArrayVec for small lists

- **Gotchas:** RFC 3514 keeps one latitude in IEEE operations: NaN bit patterns are non-deterministic and may differ between compile-time and run-time evaluation, so an optimization change can move a NaN's bits; refuse or canonicalise NaN before anything is hashed. std documents sin, cos, exp, powf and friends as having unspecified precision that can differ even between invocations in one execution, so inlining or folding them differently is allowed to change results. overflow-checks = false is already the release default; wrapping_* methods ignore the knob, plain `+` does not. One scene is evidence, not proof: overflow-checks and debug-assertions did not trap here, which says nothing about other scenes. Any edit to the profile, including one that changes no codegen, is a new artifact that needs a new pin.
