### Choose extern "C" (a panic aborts, 1.81+) or extern "C-unwind" (a panic unwinds) for every boundary fn
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust "C-unwind" 1.71+; abort on a panic escaping extern "C" 1.81+

**Since 1.81 a panic that reaches an extern "C" function aborts the process instead of unwinding into the caller; extern "C-unwind" (added in 1.71) lets it unwind; under panic=abort nothing unwinds anywhere; a foreign exception entering Rust through a "C" frame is UB.**

- **How:** Default every export to extern "C" and never use a panic as the error channel: return a status such as u32 1/0, and, in a panic=unwind build whose host must survive, run the body under catch_unwind inside the export. Use "C-unwind" only where unwinding across the boundary is intended (a Rust callback allowed to panic through C++ frames, or a C++ exception passing through Rust), and declare imported functions that can throw as "C-unwind" too: calling a "C-unwind" function through a "C" declaration or fn pointer is UB. Under -C panic=abort (the solver's profile, and the default of wasm32-unknown-unknown on 1.98.1) a panic aborts whichever ABI is written and catch_unwind never catches.
- **Gotchas:** Code from before 1.81 that let panics unwind out of extern "C" relied on UB; it now aborts with 'panic in a function that cannot unwind'. The Reference's table: panic=unwind with a non-unwinding ABI aborts on a Rust panic but is UB for a foreign unwind; panic=abort aborts every panic without unwinding. On this Windows host an abort exits 0xC0000409 (3221226505, measured); other hosts report other codes. catch_unwind is no safety net in a panic=abort build.
- **In si-rpg-engine:** Every solver export is extern "C", the release profile sets panic = "abort", and wasm32-unknown-unknown defaults to panic=abort (measured below), so a panic inside an export (for example the .unwrap() on the plan lookup in rapier_law.rs) aborts inside the module and never unwinds into JS; "C-unwind" would add nothing. Refusals already travel as u32 0 (the errors-panics lane owns that policy; wasm-raw-abi owns what the JS caller sees on an abort). A future native Godot or Unreal build compiled with panic=unwind must keep "C" or wrap each export body in catch_unwind and return 0.

### Cross the C ABI only with repr(C) types, scalars and raw pointers; pass strings as &CStr, c"" or CString
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust c"" literals 1.77+ and edition 2021+; repr(C) any

**Give C only types with a C-compatible layout (#[repr(C)] or #[repr(transparent)] structs, primitive numbers, raw pointers, Option of a non-null pointer or fn); improper_ctypes_definitions warns when an extern "C" fn takes Vec, &[T], &str or a default-repr struct; c"..." literals (1.77, edition 2021+) are &'static CStr with the NUL added, and CString owns one.**

- **How:** Pass arrays as (ptr, len) pairs and strings as *const c_char, from CStr::as_ptr when borrowed or CString::into_raw when ownership goes to C (it must come back through CString::from_raw, never C's free). CString::new returns NulError on an interior NUL; a c"" literal cannot contain one. Option<extern "C" fn(..)> and Option<&T> are the nullable-pointer forms. Generate a C/C++ header from a Rust library with cbindgen, and Rust declarations for a C/C++ library with bindgen; cbindgen's changelog records parsing of unsafe attributes from 0.28.0 (PR #1020), so pin at least that for an edition-2024 crate.
- **Gotchas:** improper_ctypes_definitions only warns: the crate still builds and the layout is still unspecified. A default-repr struct passed by value is flagged even when every field is FFI-safe. c"" does not parse in edition 2018 ('c-string literals require Rust 2021 or later'). `CString::new(..).unwrap().as_ptr()` dangles when the statement ends (the dangling_pointers_from_temporaries lint warns; bind the CString first). A CString handed out with into_raw must come back through CString::from_raw, and a string C allocated is only borrowed as &CStr, never freed as a CString. Inference, not verified: a cbindgen older than 0.28 may skip #[unsafe(no_mangle)] items; the changelog entry is the only evidence.
- **In si-rpg-engine:** The solver's exports pass only u32, f64, *mut f64 and *const u8, all FFI-safe, which is why the crate is lint-clean; no strings cross. The body, collider and height buffers are f64 arrays addressed by index constants (BODY_STRIDE 17, COLLIDER_STRIDE 10), not repr(C) structs. If a C-header host binding (Unreal, host-embedding lane) wants a struct view, add #[repr(C)] structs whose size matches the stride and assert it at compile time (macros-const lane).

### Make raw pointers with &raw const / &raw mut, move bytes with std::ptr, and change addresses with map_addr
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust &raw 1.82+; strict-provenance APIs 1.84+; debug precondition checks 1.78+

**&raw const / &raw mut (1.82) point at a place without the intermediate reference that makes `&packed.field` or a reference to uninitialized memory UB; std::ptr's read, write and copy_nonoverlapping carry stated preconditions that debug builds partly assert (1.78); the strict-provenance APIs (1.84) change an address without an integer round trip.**

- **How:** Write `&raw const place` / `&raw mut place` wherever the place may be unaligned (repr(packed) fields), uninitialized (a MaybeUninit field) or must not be claimed by a reference; addr_of! / addr_of_mut! are the older macro spelling of the same pointer. Read an unaligned place with read_unaligned. ptr::copy_nonoverlapping(src, dst, count) is memcpy with the arguments swapped and count in elements: both pointers valid and aligned (even for count 0) and the two ranges disjoint, otherwise use ptr::copy. ptr::read makes a bitwise copy, so a non-Copy T now has two owners (double-drop trap); ptr::write overwrites without dropping the old value. With debug-assertions on (dev and test profiles) a violated precondition aborts with 'unsafe precondition(s) violated'; with them off (the release default) these checks are skipped. For address arithmetic use p.addr(), p.with_addr(a) and p.map_addr(|a| a | TAG), which keep the pointer's provenance, instead of `p as usize` and back; ptr::without_provenance(n) makes a pointer that can serve as a tag or sentinel but cannot access memory (zero-sized accesses aside). On a raw slice pointer call p.len(), not (*p).len().
- **Gotchas:** `&packed.x as *const f64` is E0793: the reference is the UB even when a pointer is all you wanted. `*p` on a misaligned raw pointer is still UB; only read_unaligned / write_unaligned tolerate it (the E0793 help says so). The debug precondition checks are optional and cannot be relied on for safety (the panic text says so; the 1.78 notes say how much is checked is not stable), and they are off in release. std calls exposed provenance (expose_provenance, with_exposed_provenance, integer-to-pointer casts) poorly specified and incompatible with Miri: use it only when an integer address is unavoidable. `(*p).len()` on a *const [T] is denied by the dangerous_implicit_autorefs lint because it silently creates a reference.
- **In si-rpg-engine:** The solver's release profile keeps debug assertions off, so these precondition checks never run in the wasm; a native dev-profile test of the law gets them. T2's `solver_restore` will parse snapshot bytes that `push_f64` wrote with to_le_bytes: read each value back with f64::from_le_bytes on an 8-byte slice (safe, no alignment question), not by casting a pointer into the Vec<u8> to *const f64, which is misaligned unless the offset happens to be a multiple of 8 from an 8-aligned base.

### Probe UB with const evaluation, which rejects invalid values and bad accesses with E0080; runtime is unchecked
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any; diagnostic wording measured on 1.98.1

**The Reference lists the UB classes (data races, dangling or misaligned access, aliasing violations, mutating immutable bytes, wrong call ABI or unwinding through a non-unwind frame, invalid values) and std adds library UB such as reaching unreachable_unchecked; rustc's const evaluator rejects the invalid-value, uninitialized, null, misaligned, dangling and unreachable cases it executes with E0080, while the same operations in runtime code compile silently.**

- **How:** Invalid values to know by heart: a bool other than 0/1; an enum tag the type does not declare; a char that is a surrogate (0xD800..=0xDFFF) or above char::MAX; any integer, float or raw pointer read from uninitialized memory; a null, dangling or misaligned reference or Box; wide-pointer metadata that does not match the tail. Producing such a value is UB even if nothing uses it (assigning, passing and returning all count as producing). To settle a doubt about one operation, evaluate it in a const item: rustc 1.98.1 names the violation ('expected a valid enum tag', 'memory is uninitialized', 'entering unreachable code', 'alignment 2 is required', 'this pointer is dangling'). Data races and aliasing violations are not in reach of this trick. Runtime code needs Miri (see the Miri recipe); at compile time only pattern lints remain, such as the warn-by-default invalid_value (obvious mem::zeroed / MaybeUninit::uninit().assume_init() misuse) and deny-by-default ones like deref_nullptr and invalid_reference_casting, and each sees only the shapes it matches. Prefer unreachable!() to unreachable_unchecked unless a benchmark shows a gain.
- **Gotchas:** The Reference says its list is not exhaustive and that there is no formal model of unsafe Rust yet; the const evaluator's own note says its check 'might be overzealous'. A clean const-eval run proves nothing about runtime code: `transmute::<u8, bool>(2)` inside a fn compiles with no diagnostic at all. 'Integers accept every bit pattern, so an uninitialized u8 is fine' is wrong: MaybeUninit's docs call it UB. Reaching unreachable_unchecked lets the optimizer miscompile unrelated code. 'Dangling' means the bytes are not all inside one live allocation, which includes a stack local after its function returned.
- **In si-rpg-engine:** Every ABI slot of the solver is an f64, and floats are only required to be initialized, so whatever bits JS writes into the Float64Array views over BODIES / COLLIDERS / HEIGHTS (NaN included) are valid values: the NaN refusals in `step` and `write_body` are law rules, not UB guards. Keep flags such as DRIVEN as f64 compared with `!= 0.0`, as lib.rs does; a future u8 / bool / enum field decoded from shared memory must go through a match on the integer, never a transmute or a pointer cast to bool or an enum.

### Read unsafe as a short list of unlocked operations, never as a switch that turns the borrow checker off
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any; the Reference's list includes the edition-2024 extern-block and unsafe-attribute entries

**An unsafe block unlocks a fixed set of operations and nothing else: every other check keeps running inside it, and the code must still never produce a value that breaks its type's validity invariant.**

- **How:** The Book names five unlocked operations: dereference a raw pointer, call an unsafe fn, read or write a static mut, implement an unsafe trait, read a union field. The Reference's list adds calling a #[target_feature] fn from code without that feature, declaring an extern block (edition 2024) and applying an unsafe attribute. Outside unsafe, dereferencing, calling an unsafe fn, touching a static mut and reading a union field are each E0133; implementing an unsafe trait without `unsafe impl` is E0200; the extern-block and attribute cases have their own errors (see the unsafe-attribute recipe); assigning to a union field needs no unsafe. Inside the block the borrow checker still reports E0499 and the rest. Keep two invariants apart: the validity invariant must hold whenever a typed value is produced (bool is 0 or 1, a reference is non-null, aligned and points to a valid value, integers and floats are initialized), and breaking it is immediate UB; a safety invariant is a library promise (str is UTF-8, a Vec's len <= capacity) that unsafe code may break inside its own boundary but must restore before safe code can observe it. Put only the unlocked operation inside the block, not the safe logic around it.
- **Gotchas:** 'It is inside unsafe, so the checker is off' is wrong: E0499 still fires inside the block, and a block with nothing unsafe in it earns unused_unsafe. The const evaluator enforces validity (a bool made from 2 is E0080) but accepts a non-UTF-8 &str constant, because UTF-8 is a library invariant: std says building such a str is not immediate UB, but any str function may then cause UB. A literal with invalid bytes passed to from_utf8_unchecked is caught separately by the deny-by-default invalid_from_utf8_unchecked lint; bytes computed by a const fn are not. The UCG glossary that defines validity vs safety invariant is not normative; the Reference's invalid-values list is the binding text.
- **In si-rpg-engine:** solver/src/lib.rs `step` wraps its whole ~120-line body in one unsafe block although only the `&mut BODIES` / `&COLLIDERS` borrows need it. ### Replace every reference to a static mut with &raw mut before edition 2024 turns static_mut_refs into deny
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust &raw 1.82+; static_mut_refs warns in edition 2021 and is deny-by-default in edition 2024 (1.85+)

**Taking & or &mut of a static mut, including hidden autorefs such as B.as_mut_ptr(), B.len() or S.field.as_ptr(), warns in edition 2021 and is denied in 2024; cargo fix --edition does not rewrite it; the sound form is a raw pointer from &raw mut (no unsafe needed since 1.82), with at most one short-lived reference made from it per call.**

- **How:** The exact rewrite for a single-threaded, non-reentrant module: (1) pointer exports return `(&raw mut BODIES).cast::<f64>()` with no unsafe block; (2) an export that needs a slice takes `let bodies: &mut [f64; N] = unsafe { &mut *(&raw mut BODIES) };` and `let colliders: &[f64; M] = unsafe { &*(&raw const COLLIDERS) };`, each under a // SAFETY: line naming the invariant (one thread; no export calls another while the borrow lives; JS touches the buffers only between calls); (3) a field of a struct static is reached as `unsafe { (*(&raw const SOLVER)).snapshot.as_ptr() }`; (4) element access such as `BODIES[i]` creates no reference and is not linted. Keep every reference made from a static short-lived: pointers are the default unit, references are made on demand.
- **Gotchas:** The lint is syntactic, not a soundness proof: `&mut *(&raw mut B)` and `(*(&raw const S)).v.as_ptr()` pass it silently and are exactly as unsound if two such references overlap (the Edition Guide: you still need to uphold the aliasing constraints). Merely creating an overlapping reference is instantaneous UB even if it is never used. #![allow(static_mut_refs)] also silences the 2024 deny: unlike the unsafe attribute and extern-block changes it is a lint, not a hard error. A plain `static` of UnsafeCell is E0277 (UnsafeCell is not Sync); the wrapper's `unsafe impl Sync` promises no two threads touch it, a promise a native host must keep by serialising every call on one thread. ### Write #[unsafe(no_mangle)], #[unsafe(export_name)], #[unsafe(link_section)] and unsafe extern blocks now
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust 1.82+ in all editions; required from edition 2024

**Edition 2024 makes the bare no_mangle / export_name / link_section attributes and unmarked extern blocks hard errors; the unsafe(...) attribute form and `unsafe extern` blocks with per-item `safe fn` / `unsafe fn` are accepted by every edition since 1.82, so the rewrite can land before the edition bump.**

- **How:** Exports: `#[unsafe(no_mangle)] pub extern "C" fn step(n: u32) -> u32` and `#[unsafe(export_name = "law_version")]`; sections: `#[unsafe(link_section = "...")]`. Imports: `unsafe extern "C" { pub safe fn sqrt(x: f64) -> f64; pub unsafe fn strlen(p: *const c_char) -> usize; }`: an item with no qualifier defaults to unsafe (callers need an unsafe block, E0133), a `safe` item is callable from safe code, and the author of the block vouches for every signature. safe / unsafe qualifiers are only allowed inside an `unsafe extern` block. Migration: cargo fix --edition applies both; to see the sites early under 2021, enable #![warn(unsafe_attr_outside_unsafe, missing_unsafe_on_extern)].
- **Gotchas:** Both are hard errors in 2024 (rustc: 'accepted in the current edition (Rust 2021) but is a hard error in Rust 2024'), not lints you can allow, unlike static_mut_refs. The errors carry no E-code: 'unsafe attribute used without unsafe', 'extern blocks must be unsafe'. `safe fn` moves the proof onto whoever wrote the block: a wrong signature marked safe is UB reachable from safe code. The Edition Guide's `#[export_name = "malloc"]` example shows why the attribute is unsafe at all: a symbol clash that crashes with no unsafe block in sight. cargo fix cannot check the signatures it wraps.
- **In si-rpg-engine:** All ten exports use a bare #[no_mangle]: lib.rs `bodies_ptr`, `colliders_ptr`, `step`; rapier_law.rs `heights_ptr`, `canon_zero`, `solver_load`, `solver_step`, `snapshot_ptr`, `snapshot_len`, `solver_clear_warmstart`. The crate's edition 2021 accepts that; each becomes a hard error at the edition bump. #[unsafe(no_mangle)] compiles clean under 2021 on 1.98.1 and keeps the export names, so switch now. The solver declares no extern blocks (the module imports nothing), so unsafe extern first matters for host bindings; a law-version custom section through #[unsafe(link_section)] is wasm-raw-abi's topic.

### Never write through a pointer cast from &T: the solver's warm-start clear does, and rustc's lint misses it
`▸ plausible` · ✓ verified · ✔ compiles as claimed · Rust rapier3d-f64 0.35.3; the rule holds in every Rust version

**solver_clear_warmstart turns each &ContactPair from NarrowPhase::contact_pairs() into *mut and reborrows it as &mut to zero warm-start impulses; a pointer derived from a shared reference never carries write permission, whoever holds the owner, rustc documents the &T-to-&mut T cast as UB, and its lint catches only the one-expression forms, not this Vec hop.**

- **How:** Why it is UB even though the caller holds `&mut Loaded`: permission travels with the pointer, not with the owner. std's ptr docs say a shared reference only ever has provenance that permits reads (outside UnsafeCell); `contact_pairs(&self)` hands out such references, and a raw pointer cast from one keeps that read-only permission (in Tree Borrows a raw pointer simply inherits its parent's tag). Stacked Borrows (Miri's default) has no reservation phase: a new &mut is immediately Unique, and its paper counts creating it as a write access of the source pointer, which a pointer with only read permission cannot perform, so `&mut *ptr` is itself the violation. Tree Borrows gives a shared reference the Frozen permission and a new &mut the Reserved one; the first write through that &mut to bytes the &T covered is a local write to a Frozen tag, which is UB. What the lint does: invalid_reference_casting (deny by default) rejects `&mut *(from_ref(p) as *mut T)` and `*(from_ref(p) as *mut T) = v` written in one place; it lets through a field write `(*(from_ref(p) as *mut T)).f = v` and the same cast split across a Vec of pointers, which is the solver's shape. The fix is a &mut path that starts at the owner, never a cast: `for pair in narrow.contact_pairs_mut() { zero_manifolds(&mut pair.manifolds); }` needs no unsafe at all. rapier3d-f64 0.35.3 exposes no such accessor, so the path must come from a pinned [patch.crates-io] fork that adds `&mut self` access (the crate's own contact_pair_at_index reads self.contact_graph.graph.edges[i].weight), from another rapier API that hands out &mut (not assessed in this lane), or the cache is not mutated at all.
- **Gotchas:** 'One thread owns the world, so it is fine' answers data races, not aliasing. The Reference still calls its aliasing rules an outline ('not determined yet'); the operative texts are rustc's lint documentation (the cast is UB, and the diagnostic adds 'even if the reference is unused') and std's provenance rule. ContactPair's fields (two ColliderHandles, manifolds and solver_clusters as Vec<ContactManifold>) contain no interior mutability, so no UnsafeCell exemption applies. A clean compile is no evidence: the lint matches expression shapes. Analysis, not run (Miri is not installed here): the solver writes only into the Vec buffers behind each pair, never into the pair's own bytes, so Tree Borrows may not flag this exact shape while Stacked Borrows flags the reborrow; a pass under -Zmiri-tree-borrows would not make it sound. UB means the golden hash surviving today is no guarantee across a toolchain or dependency bump.
- **In si-rpg-engine:** solver/src/rapier_law.rs `solver_clear_warmstart`: `core::ptr::from_ref(pair) as *mut ContactPair` for each pair of `loaded.world.narrow_phase.contact_pairs()`, pushed into a Vec<*mut ContactPair>, then `&mut *ptr` and `zero_manifolds` on `manifolds` and `solver_clusters`. T2's `solver_restore` needs the same kind of write (docs/rust-kb-requests.md, request 1). At 0.35.3 docs.rs lists only &self accessors, `contact_pairs_mut` is E0599 and the `contact_graph` field is E0616, so both jobs need a &mut route from outside today's public API; which warm-start fields must be written is the restore-internals lane's question.
