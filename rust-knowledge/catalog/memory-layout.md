### Budget pointer widths: Box<T> is one word, Box<[T]> and &dyn Trait carry metadata, ZSTs take no space
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any

**Box<T> for sized T is guaranteed to be one pointer, ABI-compatible with C's T*; pointers to dynamically sized types ([T], str, dyn Trait) also carry a length or a vtable pointer and are two words today; zero-sized types occupy no memory, and a Vec of a ZST never allocates and reports capacity usize::MAX.**

- **How:** Keep fixed-size data inline, on the stack or in a static; the Book: stack data must have a known, fixed size, while data whose size is unknown at compile time or can change goes on the heap. Box::new moves a value to the heap. vec.into_boxed_slice() discards excess capacity and yields a Box<[T]>: a fixed-length heap buffer with no capacity field, so it cannot grow and its allocation stays put for the box's life. Vec<T> is a (pointer, capacity, length) triplet (field order unspecified) that never stores elements inline on the stack. Use unit structs and PhantomData as markers and Map<K, ()> as a set: stores of a ZST compile to nothing.
- **Gotchas:** The Reference hedges on DST pointer width: all pointers to DSTs are 'currently' twice the size of usize, 'though you should not rely on this'; assert it in a const only for the target you ship. Unsafe code must special-case ZSTs: pointer offsets are no-ops and allocators require a non-zero size (Rustonomicon), and a Box of a ZST holds a dangling but aligned pointer.
- **In si-rpg-engine:** The ABI buffers (BODIES and COLLIDERS in lib.rs, HEIGHTS in rapier_law.rs) are statics, neither stack nor heap: all references and raw pointers to a static refer to the same allocation, so their addresses never change. The heap holds the Rapier world, SOLVER.snapshot and the per-quantum scratch Vecs in integrate(). If an ABI buffer ever needs a length chosen at load time, a Box<[f64]> made once with into_boxed_slice keeps the fixed address that a growing Vec lacks.

### Count on Option's niche only for std-listed types; give boundary enums #[repr(u8)] and explicit values
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any

**Option<T> has exactly the size, alignment and call ABI of T when T is &U, &mut U, Box<U>, a fn pointer, a NonZero integer, NonNull<U>, or a #[repr(transparent)] wrapper of one of these; types in which every bit pattern is valid (u32, f64) have no niche, so Option<u32> is 8 bytes and Option<f64> is 16.**

- **How:** Use NonZeroU32 (NonZero<u32>) for ids that are never 0, and Option<&T> / Option<Box<T>> instead of nullable raw pointers: all free under the guarantee. Give a fieldless enum that crosses a boundary #[repr(u8)] and explicit discriminants; the Reference makes it the size of u8 with discriminants 0..=255, and a value of 300 is rejected by the deny-by-default overflowing_literals lint. Decode incoming numbers with match or a TryFrom impl that returns Err for anything else.
- **Gotchas:** Niche filling outside the std list is the compiler's choice, not a promise: slotmap's key is a repr(Rust) struct { idx: u32, version: NonZeroU32 } and Option<DefaultKey> measures 8 bytes on 1.98.1, but std guarantees that only for the listed types. An explicit repr on an enum WITH fields turns niche filling off: enum { Nothing, Some(&u16) } is 8 bytes plain and 16 bytes with #[repr(u8)] (Rustonomicon; measured). Option<MaybeUninit<bool>> is 2 bytes because MaybeUninit has no invalid values.
- **In si-rpg-engine:** rapier_law.rs keeps `handles: Vec<Option<RigidBodyHandle>>`; RigidBodyHandle is #[repr(transparent)] over rapier's Index { index: u32, generation: u32 }, which has no invalid bit pattern, so each slot costs 12 bytes (measured), harmless at 64 bodies. The body mode travels as the f64 in slot DRIVEN (16) and is tested with == 1.0 / 2.0 / 3.0; if it becomes a Rust enum, #[repr(u8)] plus a TryFrom<f64> keeps a stray 7.0 from JS an error instead of an invalid value.

### Keep entities in a generational arena keyed by (index, generation); insertion order hands out the ids
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust slotmap 1.1.1; rapier3d-f64 0.35.3

**A generational arena (slotmap, Rapier's RigidBodySet and ColliderSet) stores values in a Vec and returns a Copy key of slot index plus version, so a removed key stays invalid even after its slot is reused; which index a value gets is decided by insertion order and the free list, and in Rapier the generation is one counter for the whole arena.**

- **How:** Give each kind of entity its own key type (slotmap's new_key_type!; a key used on the wrong map is safe but unspecified), store keys rather than references, and resolve with get(), which returns None for a stale key. Where state is hashed or restored, insert in a fixed order and sort by an explicit tuple such as Rapier's into_raw_parts() -> (index, generation). Use typed-arena when values of one type all live until the arena drops (allocation is typically a Vec push, and values may form cycles), and a bump allocator such as bumpalo for phase-oriented scratch freed all at once (its Drop impls are not run).
- **Gotchas:** slotmap keys implement Ord, but its docs say key order is unspecified and as_ffi() promises nothing about the value, so never order hashed output by slotmap key. In rapier3d-f64 0.35.3 every removal bumps one arena-wide generation and pushes the freed index onto a LIFO free list: after one removal the reused slot returns as (2, 1) and even a never-used slot starts at generation 1, so ids depend on removal history, not only on what exists. slotmap versions can wrap after 2^31 reuses of one slot.
- **In si-rpg-engine:** rapier_law.rs build_world inserts the fixed colliders first, then the heightfield, then each non-carried body, so a record index i is not its RigidBodyHandle index; hence `handles: Vec<Option<RigidBodyHandle>>`. rebuild_snapshot sorts contact pairs by `(collider1.into_raw_parts(), collider2.into_raw_parts())` and writes each index and generation into the hashed bytes, so the hash depends on insertion order (the subject of T3's insertion-order test) and on generations. Today every world is built fresh and nothing is removed, so every generation is 0; once any path removes a body or collider, the generations of everything inserted later shift, and T2's rebuild from bytes would reproduce the snapshot only by replaying the same removals.

### Mutate through & only via UnsafeCell-based types; a &T-to-&mut T cast is UB even where the lint is silent
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust OnceCell/OnceLock 1.70+; LazyCell/LazyLock 1.80+

**UnsafeCell<T> is the only allowed way to mutate data behind a shared reference, and Cell, RefCell, OnceCell, LazyCell and the thread-safe cells and atomics are built on it; mutating through a &T any other way, including a &T -> *mut T -> &mut T cast, is undefined behaviour.**

- **How:** Pick by thread and write pattern: Cell<T> (values moved or copied in and out, no borrow tracking); RefCell<T> (borrows checked at run time: a second borrow_mut panics with 'RefCell already borrowed', try_borrow_mut returns Err instead); OnceCell<T> and LazyCell<T, F> (written once). For statics and threads use the Sync counterparts: Mutex / RwLock, OnceLock<T> (1.70) and LazyLock<T, F> (1.80; initialises on first access and is poisoned if the initialiser panics). A static must be Sync, so RefCell, LazyCell and bare UnsafeCell statics fail with E0277. When a library hands you only &T and you must write, get a &mut path from the owner or rebuild the data; never cast.
- **Gotchas:** The deny-by-default invalid_reference_casting lint rejects `&mut *(ptr::from_ref(x) as *mut T)` written as one expression ('casting `&T` to `&mut T` is undefined behavior, even if the reference is unused'), but it matches a pattern: the same cast with the pointer parked in a Vec<*mut T> and dereferenced later compiles with no diagnostic at all. UnsafeCell lifts only the immutability of shared references: there is no legal way to obtain aliasing &mut, even with UnsafeCell, and it does nothing against data races. RefCell turns a borrow bug into a run-time panic, not a compile error.
- **In si-rpg-engine:** rapier_law.rs solver_clear_warmstart() collects `core::ptr::from_ref(pair) as *mut ContactPair` for each &ContactPair that `narrow_phase.contact_pairs()` yields, then writes the manifold points through `&mut *ptr`. rapier3d-f64 0.35.3 offers no &mut path: every NarrowPhase accessor (contact_pairs, contact_pair, contact_graph) takes &self and returns shared references, and ContactPair's manifolds and solver_clusters are plain Vec<ContactManifold>, not cells. rustc denies this cast when it is written inline and accepts it once the pointer goes through a Vec (the first two checks), so the export compiles cleanly but sits outside what the std docs and the lint text permit. T2's solver_restore must write warm-start impulses into the same points: build it, and the clear, on a sound path (rebuild the world from the bytes, or a &mut accessor in a pinned rapier patch) rather than on this cast. What Miri's aliasing models say about it is the unsafe-ffi lane's question.

### Point Rc/Arc edges one way (strong down, Weak back) or a strong cycle leaks and its destructors never run
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any

**Rc and Arc drop their value when the last strong handle goes, so a cycle of strong handles never reaches zero: no destructor runs and nothing warns, because leaks are memory-safe in Rust. Weak (Rc::downgrade / Arc::downgrade) does not own, and upgrade() returns None once the value is gone.**

- **How:** Shape shared ownership as a tree: parent to child as Rc/Arc, child to parent as Weak, upgrade() at the point of use. Rc's count is non-atomic and Rc is not Send (moving one into thread::spawn is E0277); Arc's count is atomic and Arc<T> is Send + Sync as long as T is, because Arc makes shared ownership thread-safe but adds no thread safety to the data, so mutation behind it needs Mutex, RwLock or atomics. Write Rc::clone(&x) / Arc::clone(&x) to show a count bump rather than a deep copy. For simulation state prefer a single owner (a Vec or an arena) plus Copy indices, and keep Rc/Arc for immutable shared leaves such as collision shapes.
- **Gotchas:** A leaked cycle is silent: in the check, strong_count stays 1 and no drop line prints after both handles are dropped. ### Predict destructors: fields drop in declaration order, locals in reverse, statics and forgotten values never

- **How:** Get the drop order you need by ordering fields: ManuallyDrop's docs recommend reordering declarations over ManuallyDrop, which needs unsafe code to drop. Dropping a MaybeUninit does nothing: a panic midway through a fill leaks, it never double-drops. Calling ManuallyDrop::drop twice is UB. Rc cycles and process::exit also skip destructors, so no soundness argument may rest on Drop running.
