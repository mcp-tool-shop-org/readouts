### Choose wasm32v1-none only for an all-no_std crate graph: MVP features, own panic handler and allocator
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust 1.98.1 (target installed via rustup, tier 2)

**wasm32v1-none ships core and alloc built for WebAssembly 1.0 (MVP plus mutable-globals) on stable; the crate must be #![no_std] with a #[panic_handler] and needs a #[global_allocator] to use alloc - and the pinned solver graph cannot build for it.**

- **How:** Measured on 1.98.1: rustc --print cfg --target wasm32v1-none lists only target_feature="mutable-globals" and panic="abort"; a std crate fails with E0463 ('the wasm32v1-none target may not support the standard library'); a #![no_std] cdylib without a handler fails ('#[panic_handler] function required, but not found'); extern crate alloc without an allocator fails ('no global memory allocator found but one is required'). A #![no_std] add() with #[panic_handler] fn on_panic(_: &core::panic::PanicInfo) -> ! { core::arch::wasm32::unreachable() } built to 216 bytes (213 at -C opt-level=3), imports nothing, and its target_features section holds only +mutable-globals (wasm32-unknown-unknown: 8 entries). Pick it when the compiler itself must guarantee that no post-1.0 instruction and no std stub enters; the equivalent on wasm32-unknown-unknown is -Ctarget-cpu=mvp plus nightly -Zbuild-std.
- **Gotchas:** It is not a drop-in: every dependency must build without std. Measured: rapier3d-f64 0.35.3 is #![no_std] with std and alloc features, but its enhanced-determinism feature enables parry3d-f64's, which turns on an indexmap dependency declared without default-features = false; indexmap's default std then fails with E0463. A dependency can still enable features per function with #[target_feature]. Which allocator to install is binary-and-limits'.
- **In si-rpg-engine:** The solver (solver/Cargo.toml: rapier3d-f64 0.35.3 with enhanced-determinism) cannot target wasm32v1-none today: a scratch cargo build --target wasm32v1-none with default-features = false and features dim3, f64, alloc, enhanced-determinism stopped at indexmap 2.14.2 with E0463. So T3's refusal of relaxed-SIMD and memory.grow must come from the binary lint (solver/lint.mjs), not a target switch; revisit only if parry's indexmap dependency drops its default features.

### Export the law with #[unsafe(no_mangle)] extern "C" fns and read each signature as JS sees it
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust 1.96+ for the link-error behaviour; unsafe(no_mangle) 1.82+, required in edition 2024

**In a wasm cdylib the no_mangle / export_name attribute (not pub, not extern "C") decides what is exported, an undeclared extern is a link error since Rust 1.96, and every argument and result crosses JS as an i32, i64 (BigInt), f32 or f64.**

- **How:** Write #[unsafe(no_mangle)] pub extern "C" fn step(n: u32) -> u32; rename with #[unsafe(export_name = "law_step")]. The unsafe(...) form is accepted in every edition since 1.82 and required in 2024. Measured on 1.98.1 with node's WebAssembly.Module.exports: a cdylib exports memory plus exactly the no_mangle/export_name functions - a non-pub #[unsafe(no_mangle)] extern "C" fn is exported, a pub extern "C" fn without it is not, and __data_end / __heap_base are not exported (pass -C link-arg=--export=__heap_base to get them as globals). Host functions need #[link(wasm_import_module = "host")] unsafe extern "C" { fn host_log(x: f64); }, which becomes the import host.host_log; without the attribute rust-lld fails with 'undefined symbol: host_log'. JS side (JS API ToJSValue / ToWebAssemblyValue, measured in node): a u32 result comes back signed (u32::MAX is -1; use x >>> 0); u64 is a signed BigInt (u64::MAX is -1n; use BigInt.asUintN(64, x)) and passing a plain number to a u64 parameter throws TypeError; an i32/u32 parameter goes through ToInt32, so 2.9 arrives as 2 and NaN as 0 with no error; bool returns 1/0; an f32 parameter rounds (0.1 -> 0.10000000149011612); f64 passes exactly, including -0. Keep export signatures to u32/i32/f64 and pointers.
- **Gotchas:** pub exports nothing from a cdylib, while a stray #[no_mangle] on a helper does. A count computed in JS from NaN or a division silently arrives as 0 or truncated - validate with Number.isInteger before the call. Tuples and structs by value in an extern "C" signature draw improper_ctypes_definitions. Pre-2026 advice that an undeclared extern becomes an env import is out of date since 1.96; -C link-arg=--allow-undefined restores that behaviour on purpose only.
- **In si-rpg-engine:** solver/src/lib.rs and solver/src/rapier_law.rs export ten functions with bare #[no_mangle] under edition 2021; the local build's export list is memory, bodies_ptr, canon_zero, colliders_ptr, heights_ptr, snapshot_len, snapshot_ptr, solver_clear_warmstart, solver_load, solver_step, step, with no imports (node). An edition-2024 bump must rewrite each as #[unsafe(no_mangle)]. T2's solver_restore(world_id, n_bodies, n_colliders, rows, cols, cell, shape, len) takes seven u32 arguments that JS coerces with ToInt32, so the restoreSolver binding in solver/build.mjs should reject non-integers before calling; a NaN len would arrive as 0.

### Hand JS pointers to 8-aligned static f64 buffers made with &raw mut, and index Float64Array only by ptr / 8
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust 1.98.1 (measured); static_mut_refs is warn before edition 2024, deny in 2024

**A static [f64; N] is 8-aligned on wasm32 so ptr / 8 is an exact index; a byte buffer is 1-aligned unless raised with repr(align(8)); and a misaligned whole-buffer index is silently ignored by JS.**

- **How:** Form the pointer without a reference: (&raw mut BODIES).cast::<f64>() (safe code on 1.98.1), and pin the assumption with const _: () = assert!(core::mem::align_of::<f64>() == 8); because the Reference makes f64 alignment platform-specific. For a byte buffer the host may view as f64 use #[repr(C, align(8))] struct Bytes([u8; N]);. Measured in node: new Float64Array(buffer, ptr + 4, 1) throws RangeError 'start offset of Float64Array should be a multiple of 8', but view[(ptr + 4) / 8] = 99 on a whole-buffer view stores nothing and reads back undefined, with no error. Decode byte records with chunks_exact(8) and f64::from_le_bytes, which needs no alignment and fixes the byte order: wasm memory is little-endian, typed arrays use the platform's order (DataView takes an explicit flag). Export a capacity with every input buffer and refuse len > CAP in Rust: JS can write any byte of linear memory, so an overlong copy lands in the neighbouring static without a fault.
- **Gotchas:** BODIES.as_mut_ptr() on a static mut takes a reference: static_mut_refs warns in 2021 and denies in 2024. Vec::new().as_ptr() is dangling - 1 for Vec<u8>, 8 for Vec<f64> (measured) - and taking it from a temporary warns dangling_pointers_from_temporaries. A pointer into a Vec is valid only until it reallocates, so re-read ptr and len after every call. Never slice::from_raw_parts(p as *const f64, n) over a byte buffer: a misaligned f64 read is UB.
- **In si-rpg-engine:** solver/src/lib.rs:28 BODIES.as_mut_ptr(), lib.rs:33 COLLIDERS.as_mut_ptr(), rapier_law.rs:78 HEIGHTS.as_mut_ptr() and rapier_law.rs:738/743 SOLVER.snapshot.as_ptr()/.len() are the static_mut_refs shape (warnings under the crate's edition 2021, confirmed on a replica; errors under 2024). The local build's pointers are 8-aligned (1101432, 1110136) and build.mjs's bodies_ptr() / 8 depends on that. snapshot_ptr() returns 1 before any load, with snapshot_len() 0, which snapshotBytes() handles. T2's restore_ptr() should point at a fixed static with an exported capacity (or reserve before returning), and solver_restore should decode with from_le_bytes to match push_f64's to_le_bytes.

### Inspect the pinned .wasm with node, wasmparser or wasm-tools; never wasm-opt it unless that step is pinned too
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust 1.98.1; cargo strip default 1.77+; wasmparser 0.259.0; binaryen version_133

**The digest pins exactly what cargo emitted; wasm-opt, wasm-pack's default wasm-opt pass and strip settings all rewrite bytes, and wasm-opt's -tnh and -ffm change behaviour, so any post-processing must be pinned in the build and re-pinned in the digest.**

- **How:** Zero-install inspection in node: WebAssembly.Module.exports(m), .imports(m), .customSections(m, 'producers'). In Rust: wasmparser 0.259 - Parser::new(0).parse_all(bytes) yielding Payload::ExportSection / MemorySection / CustomSection, and Validator::new().validate_all(bytes) (the check below). CLI, per its README (not installed on this rig): wasm-tools validate | print | objdump | strip | metadata show, via cargo install --locked wasm-tools; twiggy, the code-size profiler, was archived read-only on 2026-03-14. Measured bytes for one add() cdylib from plain rustc (no -O): 1,629,285 with -C strip=none (almost all .debug_* sections from the precompiled std), 366 with strip=debuginfo (custom sections name, producers, target_features left), 74 with strip=symbols (no custom sections; exports kept). Cargo release applies strip = "debuginfo" when debug is off (since 1.77), which is why si_solver.wasm carries a 182,205-byte name section and a producers section recording 'rustc 1.98.1 (48a229cea 2026-09-01)' but no DWARF. binaryen version_133's wasm-opt: -g is what keeps the name section, -tnh optimises assuming no trap is reached, -ffm ignores NaN, rounding and negative-zero corner cases; wasm-pack runs wasm-opt by default for release.
- **Gotchas:** The producers section embeds the rustc version string, so a toolchain bump moves the digest even when codegen is identical. wasm-opt output depends on the binaryen release as well as its flags, so running it 'just to shrink' makes the digest unreproducible unless both are pinned; -tnh can delete the trap paths that guard a status-code design. The oracle and plain rustc keep std's debuginfo; compare sizes and bytes only between like builds.
- **In si-rpg-engine:** fixtures/solver.sha256 pins cargo's output from solver/build.mjs (release, implicit strip = "debuginfo", name section kept). Do not add wasm-opt or wasm-pack to build.mjs; if size ever matters, strip = "symbols" in solver/Cargo.toml [profile.release] is a pinned in-toolchain step that moves the digest once. T3's solver/lint.mjs can cross-check its hand parser against wasmparser's Validator or node's WebAssembly.validate on the same bytes.
