### Apply the whole orphan rule: a local type before any uncovered type parameter, and no overlapping impls
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any (rules of RFC 2451; checked on 1.98.1)

**For `impl<P1..=Pn> Trait<T1..=Tn> for T0` with a foreign trait, one of T0..=Tn must be local and no uncovered type parameter may appear before the first local one (RFC 2451); `&`, `&mut`, `Box` and `Pin` are fundamental, so `&Local` and `Box<Local>` count as local; overlapping impls are E0119, including overlap that only a future upstream impl could create.**

- **How:** Read the error code: E0117 = foreign trait on only foreign types (`impl Display for Vec<f64>`, `impl From<[f64; 17]> for rapier3d_f64::prelude::Vector`) — wrap in a local newtype or record type; E0210 = uncovered type parameter before the first local type (`impl<T> From<Snapshot> for T`); E0119 = overlap. Shapes that pass: `impl<T> From<Snapshot> for Vec<T>` (T covered by Vec, Snapshot local), `impl Display for Box<Snapshot>` and `impl From<&BodyRecord> for Vector` (fundamental wrappers of a local type). A blanket impl `impl<T: Display> Describe for T` claims every type that can ever satisfy the bound: add specific impls only for local types that do not meet it.
- **Gotchas:** The one-sentence rule ('the trait or the type must be local') is incomplete: `impl<T> From<Snapshot> for T` names a local type and still fails with E0210. Coherence reasons about the future: next to `impl<T: Display> Describe for T`, `impl Describe for Vec<u8>` is E0119 today even though `Vec<u8>` is not Display ('upstream crates may add a new impl of trait `std::fmt::Display`...'), while the same pair for a local non-Display type compiles. Rapier's `Vector` is glam's `DVec3` at 0.35.3 (rustc names it in the E0117 note), so it is foreign to the solver crate.
- **In si-rpg-engine:** Conversions between the solver's stride-17 body records (solver/src/lib.rs) and Rapier values must go through a local type: `impl From<[f64; 17]> for Vector` is E0117, `impl From<&BodyRecord> for Vector` with a local `BodyRecord` compiles and converts (the BodyRecord check prints `0 1.5 0`).

### Choose associated types for one-impl-per-type outputs; enforce associated consts and GATs at compile time
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any; GATs 1.65+ (checked on 1.98.1)

**An associated type fixes one output per implementing type (a second impl is E0119) while a generic parameter allows many impls; an associated const is evaluated only when an instantiated path references it; generic associated types (stable since 1.65) let an associated type borrow from self.**

- **How:** Use `trait Law { type Input; const STRIDE: usize; ... }` when each implementor has exactly one natural choice (the Book's `Iterator::Item` argument). Use a generic parameter (`trait Integrate<T>`) when one type must serve several (f32 and f64), and disambiguate with `<Euler as Integrate<f64>>::integrate(&e, ..)`. Defaults shorten impls: `const ID: i32 = 1;` in the trait, `trait Add<Rhs = Self>`. Put an invariant on an associated const as `const STRIDE_OK: () = assert!(Self::STRIDE > 0, "...");` and reference it (`let () = Self::STRIDE_OK;`) inside the method that relies on it: an impl that violates it fails the build with E0080 ('evaluation panicked: ...') as soon as that method is instantiated. For a lending iterator write a GAT: `type Item<'a> where Self: 'a; fn next<'a>(&'a mut self) -> Option<Self::Item<'a>>;` so each item may be `&'a mut [f64]` into the iterator's own buffer, which `Iterator` cannot express.
- **Gotchas:** The `where Self: 'a` on a GAT is mandatory whenever a method signature proves it (`&'a mut self` returning `Self::Item<'a>`); leaving it off is a hard error, 'missing required bound on `Item`', with no error code. An associated-const assert only fires on a path the build instantiates: the same `STRIDE = 0` impl compiles in a binary that never calls `stride()` on it, and in a library whose only caller is private dead code; it fails once `main`, a test or a `pub fn` reaches it. A generic associated const cannot size an array on stable (`[f64; L::STRIDE]` is 'generic parameters may not be used in const operations'). Associated consts and GATs each make the trait dyn-incompatible. The GAT stabilization post lists known limits: an implied 'static requirement from higher-ranked bounds such as `for<'a> I::Item<'a>: Debug`, and borrow-checker false errors with lending iterators.
- **In si-rpg-engine:** If the solver grows a Law trait, `const STRIDE: usize` plus an assert-const is how BODY_STRIDE = 17 and COLLIDER_STRIDE = 10 (solver/src/lib.rs) become per-law compile-time facts. A concrete path still sizes the static buffers (`[f64; 64 * <BoxLaw as Law>::STRIDE]` is 1088 elements), but code generic over `L: Law` cannot declare `[f64; L::STRIDE]` on stable, so the buffers stay concrete arrays.

### Choose variance on purpose: &'a T, Box and Vec are covariant; &mut T and Cell invariant; fn(T) contravariant
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any

**Rust subtyping is over lifetimes (`&'static str` is a subtype of `&'a str`); covariant constructors pass it through (`&'a T`, `*const T`, `[T]`, `fn() -> T`, `PhantomData<T>`, Box, Vec), `fn(T)` flips it, and `&'a mut T` (in T), `*mut T`, `UnsafeCell<T>`/`Cell<T>` and `dyn Trait<T>` (in T) forbid it; a struct takes the combination of its fields, and a parameter used both ways becomes invariant.**

- **How:** Expect invariance wherever a type can write a T: `fn assign<T>(input: &mut T, val: T)` called with `&mut hello` (a `&'static str`) forces `T = &'static str`, so passing `&world` is E0597. Rely on covariance to shorten lifetimes (`Box<&'static str>` to `Box<&'a str>`, `Vec<&'static str>` to `Vec<&'a str>`). A sink `fn(&'a str)` may stand where `fn(&'static str)` is expected, never the reverse (E0521). In your own generic types choose with PhantomData: `PhantomData<fn(&'id ()) -> &'id ()>` makes `'id` invariant, a brand the compiler will not shrink. rustc's notes name the culprit: 'the struct `Cell<T>` is invariant over the parameter `T`'.
- **Gotchas:** Invariance errors surface far from the cause, as 'does not live long enough' (E0597) or 'lifetime may not live long enough' (no code), because an annotation such as `&'static str` pinned the lifetime. Putting a `Cell`, `RefCell` or `&mut` of a borrowed type inside a long-lived struct makes that struct invariant, which then refuses ordinary shortening. `dyn Trait<T> + 'a` is covariant in 'a but invariant in T.

### Control what impl Trait captures: RPITIT/async fn in traits (1.75), use<..> (1.82; traits 1.87), 2024 rules
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust 1.75+ RPITIT/async fn in traits; 1.82+ use<..>; 1.87+ use<..> in traits; edition 2024 (1.85+) capture rules

**A free function's `-> impl Trait` captures every in-scope lifetime in edition 2024 but only lifetimes named in its bounds in 2021; `use<..>` (1.82) states the captured set in any edition and, since 1.87, inside trait definitions; `-> impl Trait` and `async fn` in traits (1.75) capture every in-scope lifetime in every edition unless a `use<..>` bound narrows it, and make the trait dyn-incompatible.**

- **How:** Edition 2021, returning a borrow through `impl Trait`: add `+ use<'_>` (rustc's fix for E0700). Edition 2024, result does not borrow the argument: add `+ use<>`, or callers get E0502 when they mutate the argument while holding the result. `use<..>` must list every in-scope type and const parameter; in a trait method it must list `Self` (`-> impl Iterator<Item = u32> + use<Self>`), while the impl writes `use<>` because `Self` there is an alias (E0799). Before moving a crate to 2024 run `cargo fix --edition` (the `impl_trait_overcaptures` lint inserts `use<..>`); preview with `-W impl_trait_overcaptures`. For `async fn` in a public trait, heed `async_fn_in_trait`: write `fn load(&self, id: u32) -> impl Future<Output = bool> + Send` if callers need Send.
- **Gotchas:** One signature, two meanings: `fn indices(v: &Vec<f64>) -> impl Iterator<Item = usize>` lets the caller push to `v` in 2021 and is E0502 in 2024 (rustc adds 'Rust 2024 has adjusted the `impl Trait` lifetime capture rules'). The `+ 'a` outlives trick and the `Captures<..>` trait still compile but are obsolete. A trait with RPITIT or async fn cannot be `dyn` (E0038, 'references an `impl Trait` type in its return type'). `use<..>` cannot appear on items with argument-position `impl Trait`. Writing `use<>` in a trait method is an error ('must mention the `Self` type of the trait in `use<...>`').
- **In si-rpg-engine:** solver/Cargo.toml pins `edition = "2021"`: any `-> impl Iterator` helper added to solver/src (for example over body records for T2's restore) follows the 2021 capture rules, and moving the crate to 2024 changes borrow behaviour at call sites; run the edition migration and let the pinned golden hash and fixtures/solver.sha256 digest checks decide whether the bump is clean.

### Encode solver states as zero-sized type parameters, seal traits privately, and import extension traits

### Keep a trait dyn compatible or fence methods with `where Self: Sized`; a &dyn is two words: data + vtable
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any; the 'dyn compatible' wording is what 1.98.1 prints

**A trait can be a `dyn` base only if its supertraits are dyn compatible, `Sized` is not a supertrait, it has no associated consts and no GATs, and each method is dispatchable (no type parameters, `Self` only in the receiver `&self`/`&mut self`/`Box<Self>`/`Rc<Self>`/`Arc<Self>`/`Pin<P>`, no `async fn`, no `-> impl Trait`) or is excluded by `where Self: Sized`; otherwise E0038, which on 1.98.1 reads 'the trait `X` is not dyn compatible' (formerly 'object safety').**

- **How:** Audit a trait against the Reference list before writing `&dyn Trait` or `Box<dyn Trait>`. Move generic helpers behind `where Self: Sized`: they stay callable on concrete types and leave the vtable. Pointers to DSTs are twice a thin pointer: `&dyn T`, `Box<dyn T>` and `&[f64]` are `2 * size_of::<usize>()`, i.e. 16 bytes on x86_64 and 8 on wasm32, holding the data pointer plus a vtable pointer (trait objects) or a length (slices, str). The vtable holds one function pointer per method of the trait and its supertraits. Write `T: ?Sized` on a type parameter to accept `str`, `[f64]` or `dyn Trait` behind a reference (trait `Self` is already `?Sized`). `Box<dyn T>` means `Box<dyn T + 'static>`; a trait object that borrows needs `Box<dyn T + '_>`.
- **Gotchas:** Calling a `where Self: Sized` method on a trait object fails with 'the `visit` method cannot be invoked on a trait object' (no error code). Adding a generic method, an associated const, a GAT, an `async fn` or an RPIT method to a trait that is used as `dyn` breaks every `dyn` user. Older docs and crates say 'object safe'; the diagnostic changed from 'cannot be made into an object' in rust-lang/rust#133372 (merged 2025-01-22, milestone 1.86.0), following the lang-team rename proposal. Returning `Box<dyn Probe>` built from a borrowing type fails with 'lifetime may not live long enough' because of the implicit 'static. Fat-pointer sizes are per target: never hard-code 16 in code that also builds for wasm32.
- **In si-rpg-engine:** rapier3d-f64 0.35.3 puts dynamic dispatch on the solver's path: `PhysicsWorld::step()` is `self.step_with_events(&(), &())` with parameters `hooks: &dyn PhysicsHooks, events: &dyn EventHandler`, and `warm_broadphase` in solver/src/rapier_law.rs passes `&(), &()` to `CollisionPipeline::step`, with `()` as the no-op implementor. The solver's own `step` and `resolve_pair` (solver/src/lib.rs) use no trait objects; on wasm32 each fat pointer is two 32-bit words.

### Let auto traits follow the fields, steer them with PhantomData, and know a Drop impl drives drop check
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any

**Send, Sync, Unpin, UnwindSafe and RefUnwindSafe are auto traits: a struct gets one when all its fields have it, and stable code cannot write negative impls; `PhantomData<*const ()>` removes Send and Sync, `PhantomData<fn() -> T>` keeps a typed handle Send + Sync whatever T is, and since RFC 1238 a `PhantomData<T>` field is superfluous for drop check when the type has an explicit Drop impl: the Drop impl itself makes drop check strict, while the phantom still sets variance and auto traits.**

- **How:** Assert auto traits in code: `fn assert_send<T: Send>() {}` then `assert_send::<MyType>();` (E0277 names the field that breaks it). Choose the phantom from the Nomicon table: `PhantomData<T>` (owns T, covariant, inherits Send/Sync), `PhantomData<fn() -> T>` (covariant, always Send + Sync: typed ids and handles), `PhantomData<*const ()>` (!Send + !Sync), `PhantomData<fn(T) -> T>` (invariant). `size_of::<PhantomData<T>>() == 0` is guaranteed, so `Handle<Body> { index: u32, _for: PhantomData<fn() -> Body> }` is 4 bytes and a `Handle<Collider>` passed where `Handle<Body>` is wanted is E0308. ### Put the box and product laws behind a Law trait only when Rust code drives both; keep every export monomorphic

**Since Rust 1.86 a pointer to `dyn Sub` coerces to a pointer to `dyn Super` for any supertrait, so with `trait Law: Any` a `&dyn Law` becomes `&dyn Any` and `downcast_ref::<ProductLaw>()` works with no `as_any` boilerplate; `Any` requires `'static`, and `Box<dyn Any>::downcast` recovers ownership.**

- **How:** Declare `trait Law: Any { .. }`, hold `Vec<Box<dyn Law>>`, then `let any: &dyn Any = &**law; any.downcast_ref::<ProductLaw>()`, or owning: `let any: Box<dyn Any> = law; any.downcast::<ProductLaw>()`. The coercion also works for other supertraits (`&dyn Law` to `&dyn Report`) and may drop auto traits (`dyn T + Send` to `dyn U`). Supertrait items are usable in default methods (`trait Report: Display { fn banner(&self) -> String { format!("[{}]", self.to_string()) } }`), and every implementor must implement the supertrait too (E0277 otherwise). Downcast API: `is`, `downcast_ref`, `downcast_mut` on `dyn Any`, `dyn Any + Send`, `dyn Any + Send + Sync`; `downcast` on `Box<dyn Any>`.
- **Gotchas:** `boxed.type_id()` on a `Box<dyn Any>` is the TypeId of the Box, not of the value (the check prints `false`): use `(&*boxed).type_id()` or `boxed.is::<i32>()`. `Any` cannot hold non-'static borrows: coercing `&&str` of a local String to `&dyn Any` is E0597 ('coercion requires that `name` is borrowed for `'static`'). Pre-1.86 code carries `fn as_any(&self) -> &dyn Any` methods that upcasting makes unnecessary. The unchecked downcasts (`downcast_unchecked*`) are nightly-only.

### Write for<'a> bounds when a generic must accept a borrow that the function creates itself
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any

**A lifetime parameter on a function is chosen by the caller and outlives the call, so it cannot name a borrow of a local; a higher-ranked bound (`F: for<'a> Fn(&'a f64) -> f64`, or the elided `Fn(&f64) -> f64`, or `where for<'a> &'a C: IntoIterator<Item = &'a f64>`) must hold for every lifetime, including that local one.**

- **How:** When a generic calls a closure on data the function owns or borrows internally, write the bound elided (`F: Fn(&f64) -> f64`) or explicit (`F: for<'a> Fn(&'a f64) -> f64`); the Reference expands elided Fn-trait lifetimes to `for<'a>`. To iterate any collection by reference: `fn sum_all<C>(c: C) -> f64 where for<'a> &'a C: IntoIterator<Item = &'a f64>` serves `Vec<f64>`, `[f64; N]` and `VecDeque<f64>` with one body. `for<'a>` may prefix the whole bound (`for<'a> F: Fn(&'a i32)`) or just the trait; only the scope of the name differs.
- **Gotchas:** The tempting fix of adding `<'a>` to the function (`fn sum_all<'a, C: 'a>(c: C) where &'a C: IntoIterator<..>`) fails with E0597 ('`c` does not live long enough'), because `'a` must outlive the whole call. Elided lifetimes in `Fn(&T) -> &U` bounds and in `fn(&T)` pointer types are already higher-ranked; `for<'a>` must be written out for non-Fn traits such as `&'a C: IntoIterator`.
