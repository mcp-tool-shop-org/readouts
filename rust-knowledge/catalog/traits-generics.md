### Define traits with required and default methods; state generic bounds inline or in a where clause
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any (checked on 1.98.1)

**A trait's body-less methods are required and its methods with bodies are defaults an implementor may override; generic code can call only what its bounds name.**

- **How:** Write `trait Solid { fn half_extents(&self) -> [f64; 3]; fn volume(&self) -> f64 { let [x, y, z] = self.half_extents(); 8.0 * x * y * z } }`. Every `impl Solid for T` must supply each required item (a missing one is E0046) and may override `volume`. Bound generic code inline (`fn total<T: Solid>(..)`) or, once the list grows, with `where T: Solid + Debug`; the Reference defines the two spellings as the same bound. Inside the body only methods of the named bounds resolve: `.volume()` on an unbounded `T` is E0599 ('items from traits can only be used if the type parameter is bounded by the trait'), and a caller whose type lacks the impl gets E0277 ('the trait bound `f64: Solid` is not satisfied').
- **Gotchas:** An overriding method cannot call the default it replaces (the Book says so), so put shared logic in a separately named helper that both call. Overriding a default does not excuse a missing required item (the E0046 check below overrides `volume` and still fails). Adding a body-less method to a published trait breaks every existing impl with E0046; adding one with a default body does not trigger E0046.
- **In si-rpg-engine:** solver/src (lib.rs, rapier_law.rs) declares no trait, impl block or derive today (read at origin/main 4782a8a; solver/ is unchanged since 2c2631f): the law is free functions over static f64 buffers. A trait earns a place only where two implementations must be interchangeable; whether the box law and the product law share one is traits-advanced's hook.

### Derive Debug, Clone, Copy, PartialEq and Default on plain data; implement Display by hand
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any; enum #[derive(Default)] with #[default] 1.62+

**A derive is legal only when every field implements the trait, and each carries a contract: Copy is an implicit bitwise copy that requires Clone, derived Default uses each field's default, derived Debug output is not stable across Rust versions, and Display cannot be derived.**

- **How:** `#[derive(Debug, Clone, Copy, PartialEq, Default)] struct Vec3 { x: f64, y: f64, z: f64 }` gives `{:?}` output, implicit copies, field-wise ==, and `Vec3 { x: 1.0, ..Default::default() }`. For an enum put `#[default]` on a unit variant (1.62+). Write Display yourself: `impl fmt::Display for Vec3 { fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result { write!(f, "({}, {}, {})", self.x, self.y, self.z) } }`, which also provides `to_string()`. A hand-written Clone on a Copy type must be equivalent to `*self`.
- **Gotchas:** `#[derive(Clone, Copy)]` on a struct with a Vec field is E0204. There is no Display derive ('cannot find derive macro `Display` in this scope'), and `#[default]` on a variant with fields is rejected ('may only be used on unit enum variants'). Derived Debug formats may change with future Rust versions: never hash, golden-test or parse `{:?}` output. Copy is part of the public API, and a type that implements Drop can never be Copy. On a generic struct a derive adds `T: Trait` bounds to the generated impl.
- **In si-rpg-engine:** Snapshot bytes in solver/src/rapier_law.rs are written value by value with `push_f64` (`canon(x).to_le_bytes()`), never through Debug formatting. Keep it that way: derived Debug output may change across Rust versions, which would move a golden on a toolchain bump (the toolchain is pinned to 1.98.1 by solver/rust-toolchain.toml).

### Derive only PartialEq and PartialOrd on structs with f64 fields; derived Eq, Hash and Ord fail with E0277
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any

**f64 implements PartialEq and PartialOrd but not Eq, Ord or Hash, so derives stop at the partial traits, and the derived == inherits float semantics: NaN is unequal to itself and 0.0 equals -0.0.**

- **How:** For a struct with an f64 field, `#[derive(Debug, Clone, Copy, PartialEq, PartialOrd)]` is as far as derive goes. `derive(Eq)`, `derive(Hash)` and `derive(Ord)` each fail with E0277 ('the trait bound `f64: Eq` / `f64: Hash` / `f64: Ord` is not satisfied'). With the derived impls a value holding NaN is not equal to itself, `partial_cmp` returns None, and values at +0.0 and -0.0 compare equal though their bits differ. When you need an Eq/Hash/Ord key, wrap the float and build all the impls from its bits (next recipe).
- **Gotchas:** The common wrong fix is `impl Eq for Pose {}`: it compiles (Eq has no methods, so the compiler cannot check reflexivity) and is a logic error once a NaN arrives. A HashSet then holds two 'NaN' entries and cannot find either. std calls this a logic error: behaviour unspecified, not UB, and unsafe code must not rely on these impls. Derived PartialOrd compares fields in declaration order, so reordering fields changes the ordering. assert_eq! on a struct holding NaN fails even when compared with itself.
- **In si-rpg-engine:** For T2 (`solver_restore`: restore, rerun, require an identical trace), compare restored state with `to_bits()`, not with a derived `==`: derived PartialEq calls 0.0 and -0.0 equal and NaN unequal to itself, while the hashed snapshot compares bits. The law also uses float == on purpose: `canon` in rapier_law.rs (`if x == 0.0 { 0.0 } else { x }`) folds -0.0 into +0.0 because -0.0 == 0.0, and in `signature` each value passes `bad` (`x.is_nan()`) before it is mixed into `geom`.

### Implement From for lossless conversions and TryFrom for checked ones; never Into; accept AsRef or Borrow
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust TryFrom 1.34+ (in the 2021 prelude)

**From is for infallible, lossless conversions and gives Into for free through a blanket impl, so a hand-written Into for the same pair collides (E0119); TryFrom carries an Error type for conversions that can fail; AsRef is a cheap view, and Borrow additionally promises identical Eq, Ord and Hash.**

- **How:** `impl From<f64> for Meters` lets call sites write `Meters::from(x)` or `x.into()`, and parameters take `impl Into<Meters>`. For checked construction write `impl TryFrom<f64> for UnitInterval { type Error = f64; fn try_from(v: f64) -> Result<Self, f64> { if (0.0..=1.0).contains(&v) { Ok(Self(v)) } else { Err(v) } } }`; the range test also rejects NaN. `u8::try_from(300u32)` is `Err` where `300u32 as u8` silently gives 44. `HashMap<String, V>::get("key")` works because String: Borrow<str> hashes and compares like str. Accept `impl AsRef<str>` or `impl AsRef<[f64]>` when a function only needs to read.
- **Gotchas:** From must not fail or lose information; a fallible or lossy From (e.g. f64 to an integer id) breaks its contract, use TryFrom. Do not implement Borrow for a wrapper whose Eq or Hash differ from the inner type's (std's CaseInsensitiveString example); AsRef is the safe choice there. When bounding a generic parameter, prefer `T: TryInto<U>` over `U: TryFrom<T>` (std's advice), and implement only From/TryFrom yourself: the API guidelines say never implement Into or TryInto.
- **In si-rpg-engine:** rapier_law.rs `signature` turns raw ABI values into refusals by returning None (NaN via `bad`, non-positive half-extents, counts over MAX_BODIES or MAX_COLLIDERS). A `TryFrom<f64>` newtype such as a positive half-extent is the trait-shaped version of that check, done once at the boundary; the #[repr(u8)] mode enum with TryFrom<u32> is types-patterns' hook.

### Implement Iterator for your own type with type Item and next(); the adapters and for loops come free
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any

**Iterator has one required method, `next(&mut self) -> Option<Self::Item>`; map, filter, zip, sum, collect and for-loop support all come from its provided methods and std's blanket IntoIterator impl.**

- **How:** Keep the cursor state in a struct and implement next: return `Some(item)` and advance, or `None` when done. Example: `impl<'a> Iterator for Rows<'a> { type Item = &'a [f64]; fn next(&mut self) -> Option<&'a [f64]> { .. } }` over a flat stride-17 buffer then works in `for r in rows`, `.map(|r| r[0]).collect::<Vec<_>>()` and `.filter(..).count()`. Override `size_hint` when the length is known (the default is (0, None)); call `.fuse()` or implement FusedIterator if callers rely on None staying None.
- **Gotchas:** Omitting `next` or `type Item` is E0046. After next returns None a plain Iterator may resume (the fuse check shows Some, None, Some); `.fuse()` pins None. size_hint is advisory, and unsafe code must not trust it to skip bounds checks. Iterators are lazy: `v.iter().map(f);` with no consumer does nothing and rustc warns (`unused_must_use`: 'iterators are lazy and do nothing unless consumed'). Before writing one, check std: fixed-stride rows are what `slice::chunks_exact` (1.31+) already yields, as the run check confirms (collections lane).
- **In si-rpg-engine:** rapier_law.rs walks bodies by index (`for i in 0..n_bodies as usize { let b = body_at(i); .. }`), where `body_at` copies one 17-slot row out of `static mut BODIES` into a `[f64; BODY_STRIDE]`. An iterator replacing those loops should keep yielding copies (Item = [f64; BODY_STRIDE]) so it holds no reference into the static; static mut rules are the unsafe-ffi lane's.

### Key f64 values by their bits: Eq and Hash from to_bits, Ord from total_cmp, never partial_cmp().unwrap()
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust total_cmp 1.62+; to_bits 1.20+

**`f64::total_cmp` (1.62) orders every bit pattern by IEEE 754 totalOrder and `to_bits` (1.20) exposes the exact pattern; total_cmp compares a sign-adjusted copy of the bits as i64, so it reports Equal exactly when the bits match, and Eq/Hash from to_bits plus Ord from total_cmp form one consistent key.**

- **How:** `#[derive(Clone, Copy, Debug)] struct Bits(f64);` with `impl PartialEq for Bits { fn eq(&self, o: &Self) -> bool { self.0.to_bits() == o.0.to_bits() } }`, `impl Eq for Bits {}`, `impl Hash for Bits { fn hash<H: Hasher>(&self, h: &mut H) { self.0.to_bits().hash(h) } }`, `impl Ord for Bits { fn cmp(&self, o: &Self) -> Ordering { self.0.total_cmp(&o.0) } }`, `impl PartialOrd for Bits { fn partial_cmp(&self, o: &Self) -> Option<Ordering> { Some(self.cmp(o)) } }`. Sort plain slices with `v.sort_by(f64::total_cmp)`, giving [-NaN, -inf, -0.0, 0.0, 1.5, inf, NaN]. If numerically equal values must collide, canonicalise before keying (map -0.0 to 0.0, refuse NaN). A struct whose float fields are stored as `to_bits()` u64 can simply derive PartialEq, Eq and Hash.
- **Gotchas:** `sort_by(|a, b| a.partial_cmp(b).unwrap())` panics as soon as it meets a NaN (exit 101). total_cmp disagrees with ==: -0.0 sorts before +0.0, and NaNs of different sign or payload are different keys (a negative NaN sorts first, and Debug prints both as `NaN`). Mixing policies breaks the Hash/Eq rule (k1 == k2 implies hash(k1) == hash(k2)): a derived PartialEq (0.0 == -0.0) paired with a to_bits Hash hashes equal keys differently. `ordered_float::OrderedFloat` 5.5.0 picks the opposite policy (±0 equal; NaN equal to itself and greater than everything). Choose one policy per key type and build all four impls from it. std says data fed to a Hasher by Hash is not portable across platforms or stable across compiler versions, so a persisted or golden hash should hash explicit bytes (`to_le_bytes`, `to_bits`) with a hasher that documents stability (sim-architecture lane), never a derived Hash through std's hashers.
- **In si-rpg-engine:** `mix_f64(h, x)` in solver/src/rapier_law.rs is `mix_u64(h, x.to_bits())` (multiply by 0x100000001b3, add; seed 0xcbf29ce484222325), so 0.0 and -0.0 feed different words. `push_f64` writes `canon(x).to_le_bytes()` into the snapshot, but `signature` mixes raw collider and height values into `geom`, and `same_sig` compares `geom`: a collider coordinate of -0.0 therefore signs a different world (reload) than 0.0. That is a reading of the code, not a measured failure, and worth one test. `Signature` already keys its float by bits (`cell: u64` = `cell.to_bits()`), so every field is an integer and `#[derive(PartialEq, Eq, Hash)]` would be legal and would replace the hand-written `same_sig`, which silently ignores a field someone forgets to add. The snapshot pair sort keys on pairs of `(u32, u32)` tuples from `into_raw_parts()`; ColliderHandle itself derives Eq and Hash but not Ord in rapier3d-f64 0.35.3, so it cannot be sorted directly, and integer tuples need no float comparator.

### Prefer monomorphized generics; use Box<dyn Trait> for mixed-type collections or to cut code size

**Generic code is compiled once per concrete type (static dispatch, inlinable, no run-time dispatch cost, paid for in compile time and binary size); a dyn Trait call goes through a vtable (one copy of the code, a run-time lookup, no inlining) and is what lets one container hold different types.**

**`impl Trait` in argument position is an anonymous generic parameter; in return position the function picks one concrete type the caller cannot name, and every return path must produce that same type.**

- **How:** `fn sum_two(a: &impl Solid, b: &impl Solid)` takes two independently chosen types (with `<T: Solid>(a: &T, b: &T)` both must be the same, E0308 otherwise). `fn ticks(n: u32) -> impl Iterator<Item = f64> { (0..n).map(|i| i as f64 / 64.0) }` returns an unnameable closure adapter with no box and no dynamic dispatch. When branches produce different types, return `Box<dyn Solid>` (a heap allocation plus vtable calls) or an enum.
- **Gotchas:** Returning `Slab` from one branch and `Cube` from the other under `-> impl Solid` is E0308 ('`if` and `else` have incompatible types'). Callers cannot turbofish an impl-Trait parameter: `show::<Cube>(..)` is E0107 with the note '`impl Trait` cannot be explicitly specified as a generic argument'; use a named `<T: Solid>` when callers must choose. For the same reason, switching a public parameter between `impl Trait` and `<T: Trait>` changes the number of generic arguments and can break callers (the Reference says so). impl Trait is allowed only in function argument and return types: `let c: impl Solid = ..` is E0562. In edition 2024 return-position impl Trait captures all in-scope lifetimes by default (`use<..>` narrows it); depth belongs to traits-advanced.
