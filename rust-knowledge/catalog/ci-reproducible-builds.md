### Cache solver deps with Swatinem/rust-cache@v2 and build with --locked; build.mjs's flags never reach the key
`✅ solid` · ✓ verified · · no code check · Rust Cargo 1.98.1; Swatinem/rust-cache v2 (release v2.9.2)

**rust-cache@v2 keys on the runner OS and CPU, the `rustc -vV` release, host and commit, any job env var whose name starts with CARGO, RUST, CC, CFLAGS, CXX or CMAKE, and the solver's Cargo.lock, Cargo.toml, rust-toolchain.toml and .cargo/config.toml. It never sees flags a script sets for its own child process, and it skips the save on a full key match. Cargo's fingerprints keep a restored cache correct, but only `--locked` stops a stale Cargo.lock being rewritten silently.**

- **How:** Measured in the engine's CI run 36121826863 (main f84c98b):
- The key was `v0-rust-engines-Linux-x64-6ff13d87-a62750e7`.
- Env considered: CARGO_HOME, CARGO_INCREMENTAL, CARGO_TERM_COLOR.
- Lockfiles considered: solver/.cargo/config.toml, Cargo.lock, Cargo.toml, rust-toolchain.toml.
- The restore reported `full match: true`, `node solver/build.mjs --check` printed the pinned ede99ea1… about 1.4 s later, and the post-job step printed `Cache up-to-date.` with no save.

Add `--locked` to build.mjs's cargo arguments (today: `build --release --target wasm32-unknown-unknown`) and to every cargo step. Measured on cargo 1.98.1 after bumping si-solver's version without regenerating the lock: `--locked` failed with `cannot update the lock file ... because --locked was passed to prevent this`, while plain `cargo build` or `cargo tree` rewrote the root `version` line of Cargo.lock without a message. An offline `cargo generate-lockfile` re-resolved smallvec 1.16.1 to 1.16.2 from the local cache. `--frozen` is `--locked` plus `--offline`; run `cargo fetch --locked` first if the build must be offline. When build.mjs's flags change, add `key: ${{ hashFiles('solver/build.mjs') }}` to the rust-cache step.
- **Gotchas:** A flag change made only inside build.mjs leaves the key unchanged. Each run then restores deps built with the old flags, Cargo rebuilds them (its fingerprints include rustflags), and the full-match rule never saves the new ones. The build stays correct but slow. A job-level RUSTFLAGS or CARGO_ENCODED_RUSTFLAGS does enter the key through the RUST/CARGO prefixes, and it also replaces the solver's config rustflags. rust-cache never caches workspace crates, drops artifacts older than a week and sets CARGO_INCREMENTAL=0. The Cargo CI guide's latest-dependencies job (`cargo update`, then build) is the opposite of a pinned artifact: run it only as a separate, non-gating scheduled check.
- **In si-rpg-engine:** ci.yml runs `Swatinem/rust-cache@v2` with `workspaces: solver`, and solver/build.mjs calls `spawnSync(cargo, ['build', '--release', '--target', 'wasm32-unknown-unknown'])` without `--locked`. In run 36121826863 the cached build still reproduced fixtures/solver.sha256. The weekly uncached rebuild (scheduled-jobs recipe) is what proves the cache hides nothing.

- **Verifier (solid):** CI log matches exactly: key v0-rust-engines-Linux-x64-6ff13d87-a62750e7, full match true, env/lockfiles considered, digest ede99ea1... 1.37s later, post-step 'Cache up-to-date.' with no save.
- **Compiler:** no code check (a claim code cannot show)

### Gate the solver in ci.yml with fmt --check, clippy -D warnings for wasm32 and host cargo test --lib
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust 1.98.1; &raw const/&raw mut need 1.82+

**Rust gates need no new push-triggered workflow file. rustfmt --check, clippy with -D warnings for the wasm32 target and host unit tests of pure functions all fit in ci.yml, and `cargo test --lib` works on a cdylib-only crate. But today's solver fails -D warnings on seven static_mut_refs warnings, and integration tests or doctests would need "rlib", which moves the digest.**

- **How:** One `rust` job in ci.yml, `working-directory: solver` (the paths filter already includes solver/**):
1. `rustup toolchain install --no-self-update` (with clippy and rustfmt listed in the toolchain file).
2. `cargo fmt --all -- --check` (the rustfmt README's CI form, which exits non-zero when formatting differs).
3. `cargo clippy --locked --target wasm32-unknown-unknown -- -D warnings`. This keeps .cargo/config.toml's pin in play, which job-level RUSTFLAGS would not.
4. `cargo test --locked --lib` on the host.

The test harness always unwinds: Cargo ignores `panic` for tests, and rustc refuses `--test -C panic=abort` with `building tests with panic=abort is not supported without -Zpanic_abort_tests`. Use Clippy from the same toolchain as the build. Set `style_edition` in a rustfmt.toml so cargo fmt and rustfmt agree. ### Give the ARM lane the x64-built solver and check sha256 of its embedded bytes against fixtures/solver.sha256
`✅ solid` · ✓ verified · · no code check · Rust rustc 1.98.1 artifact; GitHub arm64 runners GA 2025-08-07

**Free arm64 Linux runners (ubuntu-24.04-arm, ubuntu-22.04-arm) have been generally available for public repositories since 2025-08-07. An aarch64 rebuild is expected to give different bytes, so the ARM lane runs the module the x64 job built and proves it is the pinned binary by hashing the embedded wasm, not by trusting the artifact's name.**

- **How:** x64 job: after `node solver/build.mjs --check`, record the byte length and SHA-256 of si_solver.wasm and upload solver/dist/solver.mjs with actions/upload-artifact. The current major is v7; its `artifact-digest` output is the SHA-256 of the artifact, and artifacts are immutable since v4. ARM job: `runs-on: ubuntu-24.04-arm`, `needs:` the x64 job, a `timeout-minutes`, and the same concurrency group. It downloads with actions/download-artifact (v8 verifies the server hash, `digest-mismatch: error` by default). Then, before any trace, it hashes the module's exported `bytes` (the Uint8Array build.mjs emits) with node:crypto SHA-256, compares the result to fixtures/solver.sha256, and prints the length. For public repositories the docs list 4 CPU / 16 GB / 14 GB runners under ubuntu-24.04-arm, ubuntu-22.04-arm and ubuntu-26.04-arm. Length plus digest also gives a first diagnosis, as T3 plans for snapshots. Measured: removing the remap changed the length (1,526,380 vs 1,524,412), the host-unit profile changed it by 56 bytes, and a separator swap cannot change it (one byte for one). An informational aarch64 rebuild may print its own digest to gather evidence, but must never write or gate the pin.
- **Gotchas:** download-artifact's check covers the artifact archive, not the wasm inside it, so without the byte hash the lane proves only that some x64 job uploaded something. The arm64 partner image's inventory lists Node.js 20.20.0 and Rust 1.93.0 with rustup 1.28.2, so install Node 22 as T3 plans. rust-cache keys include the CPU architecture, so an ARM Rust job never reuses the x64 cache. The evidence that aarch64 bytes differ is a mechanism in Cargo's source plus user reports on rust-lang/cargo#8140; it was not measured on this rig.
- **In si-rpg-engine:** docs/dispatch-t3-platforms.md pin 1 says the ARM job 'does not rebuild the solver: it downloads the x64 job's solver/dist/solver.mjs artifact'. Keep that, and add the sha256(bytes) == fixtures/solver.sha256 assertion. Keep the ARM job inside .github/workflows/ci.yml: the studio caps push-triggered workflow files at two, and ci.yml plus pages.yml already fill both slots. ci.yml still references actions/upload-artifact@v4.

### Guard the solver's dependency graph with cargo tree and cargo deny: no parallel, no rayon, crates.io only
`✅ solid` · ✓ verified · · no code check · Rust rapier3d-f64 0.35.3, parry3d-f64 0.30.2, Cargo 1.98.1 (resolver 2, edition 2021)

**Cargo builds each dependency with the union of the features requested anywhere in the graph. One new dependency could turn on rapier3d-f64's `parallel` (rayon) without anyone touching solver/Cargo.toml. A cargo tree assertion on the wasm32 graph plus cargo-deny's bans (including per-crate feature bans), sources, licenses and advisories checks turns that and other supply-chain drift into a CI failure.**

- **How:** Measured on cargo 1.98.1 in a scratch copy: `cargo tree --locked --target wasm32-unknown-unknown -e normal --prefix none --format '{p} [{f}]'` printed:
- `rapier3d-f64 v0.35.3 [alloc,block-solver,default,dim3,enhanced-determinism,f64,std]`
- `parry3d-f64 v0.30.2 [alloc,dim3,ena,enhanced-determinism,f64,hashbrown,indexmap,required-features,slab,std]`
- `simba v0.10.2 [libm,libm_force,std,wide]`
- `wide v1.7.1 [std]`

Grepping those brackets for `parallel|simd-stable|simd-nightly` found nothing, and `cargo tree -i rayon` said "package ID specification `rayon` did not match any packages". Assert both absences and the presence of `enhanced-determinism` and `libm_force`. For the declarative form, write solver/deny.toml:
- `[graph] targets = ["wasm32-unknown-unknown"]`
- `[bans] deny = [{ crate = "rayon", reason = "..." }]`
- `[[bans.features]] crate = "rapier3d-f64"`, `deny = ["parallel"]`, and the same for parry3d-f64
- `[sources] unknown-registry = "deny"`, `unknown-git = "deny"`
- `[licenses] allow = [...]`, built from the lock's actual licenses

Then run `cargo deny check`. Its four checks are licenses, bans, advisories and sources. For audits, add cargo-vet: `cargo vet init`, then `cargo vet --locked` in CI, with exemptions ratcheted down. Read every Cargo.lock diff line by line in review.
- **Gotchas:** `cargo tree` defaults to the host platform, so pass --target wasm32-unknown-unknown. Resolver 2 keeps build-dependencies and proc-macros from sharing features with normal deps, hence `-e normal`. cargo-deny's `unknown-registry` and `unknown-git` default to warn, not deny. `multiple-versions = "deny"` would fail today: solver/Cargo.lock holds glam 0.30.10, 0.31.1, 0.32.1 and 0.33.10, plus two hashbrown and two syn, so start at warn. rapier3d-f64 0.35.3 has no simd-stable or simd-nightly feature to ban; its `parallel` adds rayon and turns on parry3d-f64/parallel.
- **In si-rpg-engine:** solver/Cargo.toml declares `rapier3d-f64 = { version = "0.35.3", features = ["enhanced-determinism"] }`. solver/FLAGS.md says 'parallel is off' and 'This version has no simd-stable or simd-nightly feature', and the measured tree line and docs.rs both confirm it. Encode it in the `rust` job so FLAGS.md stops being the only record. ci.yml runs `npm audit --audit-level=high` for JS but nothing yet for the 61-package solver/Cargo.lock.

- **Verifier (solid):** Independently reran `cargo tree --target wasm32-unknown-unknown -e normal --format '{p} [{f}]'` against rapier3d-f64=0.35.3: all 4 claimed lines (rapier3d-f64/parry3d-f64/simba/wide) matched byte-for-byte, incl. the rayon-absent error text.

### Pass build.mjs's flags via CARGO_ENCODED_RUSTFLAGS and refuse relaxed-simd in code: the bytes hide the pin
`▸ plausible` · ✓ verified · ✔ compiles as claimed · Rust 1.98.1 (wasm32-unknown-unknown defaults as measured); any Cargo with CARGO_ENCODED_RUSTFLAGS

**Cargo uses only the first rustflags source it finds: CARGO_ENCODED_RUSTFLAGS, then RUSTFLAGS, then target rustflags, then build rustflags. RUSTFLAGS is split on whitespace. An inherited CARGO_ENCODED_RUSTFLAGS, even an empty one, drops every flag build.mjs sets. And on 1.98.1, losing `-C target-feature=-relaxed-simd` changes no byte, so only a compile-time guard notices a lost pin.**

- **How:** In build.mjs, set `CARGO_ENCODED_RUSTFLAGS: flags.join('\x1f')` in the child env and delete any inherited RUSTFLAGS or CARGO_ENCODED_RUSTFLAGS. Measured on 1.98.1:
- With a checkout path containing a space, the space-joined RUSTFLAGS failed before compiling: `--remap-path-prefix must contain '=' between FROM and TO`.
- The same flags joined with 0x1f in CARGO_ENCODED_RUSTFLAGS built the identical b21c7f15….
- An empty `CARGO_ENCODED_RUSTFLAGS=` beside build.mjs's RUSTFLAGS produced the unremapped c8782b06…, and si_solver's rustc line carried neither the pin nor any remap.
- RUSTFLAGS without the pin produced b21c7f15… again, byte for byte. The module's target_features section lists only `+bulk-memory +bulk-memory-opt +call-indirect-overlong +multivalue +mutable-globals +nontrapping-fptoint +reference-types +sign-ext`.

Add to solver/src/lib.rs the crate-level guard the wasm-raw-abi lane also recommends: `#[cfg(target_feature = "relaxed-simd")] compile_error!("...");`. rustc evaluates the cfg from whichever flags actually reached it, so the guard fires whichever source won.
- **Gotchas:** With --target, these flags reach only target units, never build scripts or proc-macros. The Clippy book's `env: RUSTFLAGS: "-Dwarnings"` pattern replaces .cargo/config.toml's pin for that job and changes rust-cache's key. The wasm32-unknown-unknown default feature set changes over time (nontrapping-fptoint and bulk-memory became defaults in 1.87.0), so 'off by default today' is not a pin. The guard sees crate-level flags only: measured, cfg!(target_feature = "relaxed-simd") stays false even inside a function marked #[target_feature(enable = "relaxed-simd")], and the guard compiles. Such a function is the binary-and-limits lane's case; T3's opcode lint covers it. So the guard checks the flags and the lint checks the bytes, and both stay.
- **In si-rpg-engine:** solver/build.mjs spreads `...process.env` and sets `RUSTFLAGS: rustflags` built with `.join(' ')`, repeating solver/.cargo/config.toml's `[target.wasm32-unknown-unknown] rustflags = ["-C", "target-feature=-relaxed-simd"]`. Switch that to CARGO_ENCODED_RUSTFLAGS and add the compile_error! guard to solver/src/lib.rs. Then T3's solver/lint.mjs checks the opcodes, and the guard checks the flags.
