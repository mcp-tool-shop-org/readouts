### Expect 1.86-1.98 lint escalations to break old unsafe and macro code on a toolchain bump
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust per lint as listed (1.86-1.98); measured on 1.98.1

**Lints tightened in the period, in every edition: dangerous_implicit_autorefs (added 1.88, deny 1.89), missing_fragment_specifier (hard error 1.89), semicolon_in_expressions_from_macros (deny 1.91), never_type_fallback_flowing_into_unsafe and dependency_on_unit_never_type_fallback (deny 1.92), deref_nullptr (deny 1.93), invalid_runtime_symbol_definitions (new, deny 1.98); new warn-by-default lints include missing_abi (1.86), mismatched_lifetime_syntaxes (1.89), dangling_pointers_from_locals (1.91) and linker_messages (1.97, outside the `warnings` group).**

- **How:** Treat each toolchain bump as a lint audit: build with the new pin and read every new warning and error. Write `&mut *ptr` / `&*ptr` explicitly before indexing or calling methods through a raw pointer; annotate `f::<()>()?` where code relied on `()` never-type fallback; always spell `extern "C"`; no trailing `;` in a macro used as an expression; never define `memcmp` / `memset` / `strlen`-named symbols with another signature (no_std wasm crates sometimes do); never return a pointer to a local.
- **Gotchas:** The never-type lints fire only when the affected crate itself is built (1.92 announcement), so a dependency with the pattern keeps building while a copied snippet fails. linker_messages is not affected by the warnings lint group (1.97 announcement). The wasm_c_abi future-compatibility warning became a hard error in 1.86.
- **In si-rpg-engine:** On 1.98.1 the solver builds with its 7 static_mut_refs warnings and no other lint (measured), and rapier_law.rs's `unsafe { &mut *core::ptr::addr_of_mut!(SOLVER) }` is already the explicit form these lints accept. Build the next bump with CARGO_BUILD_WARNINGS=deny (see the Cargo recipe) so a newly escalated lint stops CI instead of scrolling past.

### Expect edition 2024 to drop if-let scrutinee and tail-expression temporaries earlier
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust edition 2024 (1.85+); let chains 1.88 (2024 only); if-let guards 1.95 (every edition)

**Edition 2024 drops the temporaries of an `if let` scrutinee before the `else` branch runs and drops a block's tail-expression temporaries before its local variables; both reorder `Drop` side effects (checked), and the first is why let chains (stable 1.88) are 2024-only.**

- **How:** Rules: in `if let P = e { .. } else { .. }` the temporaries of `e` now drop before `else` (2021: after the whole expression); in a tail expression they now drop before the block's locals (2021: after), so `c.borrow().len()` as the tail of the block that owns `c` compiles (E0597 in 2021). Migration: `if_let_rescope` is auto-fixed by rewriting to `match`, which keeps the 2021 order, so review each rewrite; `tail_expr_drop_order` only warns. After the switch write `if let Some(x) = a && let Ok(y) = f(x) { .. }` instead of nested if-lets. `if let` guards in match arms (`Some(s) if let Some(x) = parse(s) =>`, 1.95) are not tied to the edition: they compile in 2021 as well (checked).
- **Gotchas:** The automatic `match` rewrite preserves the old, later drop, so the deadlock the edition fixes (a RwLock read guard kept alive into an `else` that takes the write lock) survives the migration unless the rewrite is undone on purpose. In 2021 a let chain is the error 'let chains are only allowed in Rust 2024 or later' (checked). Tail-expression temporaries are also sometimes no longer extended to the enclosing scope, so a borrow that compiled through extension in 2021 can fail in 2024. 1.91 applied the 2024 if-let rule to temporaries made by pin!, format_args!, write! and writeln! in 2024 scrutinees.
- **In si-rpg-engine:** cargo fix --edition on the solver copy reported no if_let_rescope or tail_expr_drop_order site (measured): `ensure()` in rapier_law.rs uses `if let Some(loaded) = solver.loaded.as_ref()` with no else, and the other matches are let-else. The rules start to matter in the planned host bindings (Godot, then Unreal), where a wrapper may hold a lock guard or RefCell borrow over the solver's static state across an if-let.

### Expect wasm32 undefined symbols to fail the link since 1.96 and the standard C ABI since 1.89
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust 1.84 (wasm32-wasi removed, wasm32v1-none Tier 2), 1.89 (standard C ABI), 1.96 (no --allow-undefined); measured on 1.98.1

**Since 1.96 rustc no longer passes --allow-undefined to wasm-ld, so an extern function with no definition is a link error ('undefined symbol') instead of a silent `env` import; since 1.89 `extern "C"` on wasm32-unknown-unknown follows the standard tool-conventions C ABI, which changed how aggregates are passed and left scalars alone; 1.84 removed the wasm32-wasi target name (now wasm32-wasip1) and added wasm32v1-none at Tier 2.**

- **How:** Declare each intended host import explicitly with `#[link(wasm_import_module = "env")]` (or another module name) on its `unsafe extern "C"` block; `-C link-arg=--allow-undefined` restores the old behaviour for a whole build. Keep exports scalar and pointer only (u32, f64, *const u8), which both ABIs lower the same way; a #[repr(C)] struct passed by value is passed indirectly under the 1.89+ ABI where the legacy ABI split it into separate parameters. Name WASI targets wasm32-wasip1 or wasm32-wasip2.
- **Gotchas:** Before 1.96 a misspelt or missing extern fn produced a module importing `env.<name>`, which a loader that instantiates with no import object discovered only at instantiation. 1.86 made the wasm_c_abi future-compatibility warning a hard error (it concerned wasm-bindgen older than 0.2.89). 1.91.0 broke #[link(wasm_import_module)] across crates (same-named imports from different modules could resolve to the wrong function); 1.91.1 fixed it.
- **In si-rpg-engine:** The solver declares no extern block and imports nothing (build.mjs instantiates with `new WebAssembly.Instance(module)` and no import object), so on 1.96+ an accidental undefined symbol fails `cargo build` instead of the JS instantiation. Its ten exports take u32/f64 and return u32/f64/pointers, the class the C ABI post says is unaffected. Keep T3's no-imports check as a second gate, and give T2's restore exports the same scalar/pointer signatures.

  - *Check 3: -C link-arg=--allow-undefined restores the pre-1.96 behaviour* · `compiles` · edition 2024 · wasm32-unknown-unknown · cdylib · exports fall · **✔ oracle pass**

### Keep 1.98's f64::algebraic_* methods out of the law: the std docs allow different results per run
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust algebraic_* 1.98; const-fn float arithmetic 1.82; NAN quiet guarantee 1.88

**1.98 stabilized `algebraic_add`, `_sub`, `_mul`, `_div` and `_rem` on f32 and f64, which let the compiler combine and reorder operations, swap division for reciprocal multiplication and ignore the sign of zero; the core docs say the same inputs may produce different results even within one program run. They compile on stable with no feature gate and no warning (checked).**

- **How:** Keep the law to + - * / and sqrt, as lib.rs's header comment says, and keep algebraic_* (and mul_add) out of solver/src by review plus a CI grep for `algebraic_`. Constants may be computed by const fn since 1.82: `const SLIDE_ANGLE: f64 = radians(50.0)` has the same bits as the runtime call for this non-NaN expression (checked). Never hash a NaN's bits: f64::NAN is guaranteed quiet since 1.88, but its payload and sign may change across Rust versions and targets, and a NaN produced at compile time need not match the one produced at run time - reject or canonicalize first.
- **Gotchas:** A model trained before 1.98 calls these nightly-only; on 1.98.1 they are plain stable methods and nothing in rustc warns about them. The 1.82 announcement warns that `(0.0 / 0.0).is_sign_positive()` can differ between compile time and run time and across hardware, optimization level and surrounding code, and advises fully portable code to avoid to_bits and to test `f.signum() == 1.0` rather than `f.is_sign_positive()` (the advice concerns NaN results). No `algebraic_` appears in the pinned rapier3d-f64 0.35.3, parry3d-f64 0.30.2, nalgebra 0.35.0, simba 0.10.2, glam 0.33.10 or libm 0.2.16 sources (grep of the local cargo registry), so a dependency bump is where they could enter.

### Treat wasm32-unknown-unknown's six default features as byte changes, and -relaxed-simd as no ban
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust 1.70 (sign-ext, mutable-globals), 1.82 (multivalue, reference-types), 1.84 (wasm32v1-none Tier 2), 1.87 (bulk-memory, nontrapping-fptoint); measured on 1.98.1

**On 1.98.1 wasm32-unknown-unknown enables sign-ext and mutable-globals (in codegen since 1.70), multivalue and reference-types (default since 1.82, LLVM 19) and bulk-memory and nontrapping-fptoint (since 1.87, LLVM 20); simd128 and relaxed-simd are off. None of the six is float arithmetic: `f64 as i32` saturates the same with nontrapping-fptoint and bulk-memory switched off (checked), while every change to the default set changes module bytes. `-C target-feature=-relaxed-simd` leaves the default set as it is and does not stop a function that enables relaxed-simd itself.**

- **How:** Read the set with `rustc +1.98.1 --print cfg --target wasm32-unknown-unknown` or `cfg!(target_feature = "...")`, and read what a built module used from its `target_features` custom section (the solver copy lists +bulk-memory, +bulk-memory-opt, +call-indirect-overlong, +multivalue, +mutable-globals, +nontrapping-fptoint, +reference-types, +sign-ext). For an MVP-only module on stable use wasm32v1-none (Tier 2 since 1.84; no std, only core and alloc; only mutable-globals); turning features off on wasm32-unknown-unknown does not rebuild the precompiled std, and a full MVP build needs nightly -Zbuild-std. Keep the -relaxed-simd pin in .cargo/config.toml and build.mjs, and add a cheap gate that the module's target_features section lists neither +relaxed-simd nor +simd128, beside T3's opcode lint.
- **Gotchas:** reference-types (1.82) changed call_indirect's table immediate to an over-long 5-byte LEB (the +call-indirect-overlong entry), which decoders without reference-types support reject. Enabling multivalue did not change the extern "C" ABI. The relaxed-SIMD intrinsics (e.g. core::arch::wasm32::f64x2_relaxed_madd) are stable since 1.82: a `#[target_feature(enable = "simd128,relaxed-simd")]` function compiles under `-C target-feature=-relaxed-simd` (checked) and, in the scratch probe, emitted f64x2.relaxed_madd, recorded +relaxed-simd in target_features, and returned the fused result under node 22 on this x86 host (-8.67e-19 where a separate multiply and add give 0). On wasm such a function is callable without an unsafe block. Switching bulk-memory and nontrapping-fptoint off changed the probe's size (1591014 -> 1591189 bytes) but not its results.
- **In si-rpg-engine:** solver/.cargo/config.toml and solver/build.mjs both pass -C target-feature=-relaxed-simd; on 1.98.1 that flag changes nothing in the default set (checked), so it guards against a future default, while FLAGS.md's 'this build disables' does not cover a dependency function that opts in with #[target_feature] - only inspecting the module (T3's opcode lint, or the target_features section) catches that. A toolchain bump that changes the default set, as 1.82 and 1.87 did, changes the digest in fixtures/solver.sha256; the golden hash should not move for that reason.
