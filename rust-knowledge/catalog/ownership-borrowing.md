### Keep one &mut xor any number of & live at once, and end each borrow at its last use (E0499, E0502, E0506)
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust NLL on every edition since 1.63; problem case #3 still rejected on 1.98.1

**A value may have one live mutable reference or any number of live shared ones; since Rust 1.63 NLL is the borrow checker on every edition and a borrow lasts only until its last use, so most conflicts are fixed by reordering rather than by blocks, clones or RefCell.**

- **How:** Read the code as the access that conflicts: E0499 = two live `&mut` (`let a = &mut v; let b = &mut v; a.push(..)`); E0502 = a `&` and a `&mut` overlap (`let first = &v[0]; v.push(x); use(first)`, or `v.push` inside `for x in &v`); E0506 = assigning to a place that is still borrowed; E0503 = reading or writing a place while it is mutably borrowed. Fix: move the last use of the first borrow above the conflicting access; copy the value out (`let first = v[0];` for Copy data) instead of keeping a reference; for iterate-and-mutate, collect the change first and apply it after the loop (`let extra: Vec<_> = v.iter()..collect(); v.extend(extra);`). NLL still rejects returning a borrow on one path while mutating the same data on another (NLL problem case #3, `if let Some(s) = vec.last() { return s; } vec.push(..)` is E0502 on 1.98.1): test without holding the borrow (`if vec.is_empty() { vec.push(..) } vec.last().unwrap()`), or use `map.entry(k).or_default()` for maps.
- **Gotchas:** The four codes are one rule seen through different accesses (second borrow E0499/E0502, assignment E0506, plain use E0503), and all four are fixed by ending the first borrow earlier. The E0506 page still shows a scoped `{ let r = &x; .. }` block as a fix; under NLL a block is unnecessary when the reference is simply not used after the conflict. Polonius Alpha, shown accepting the HashMap `get_mut_or_default` example (RFC 2094's problem case #3 shape), was switched on for nightly only in August 2026 with stabilization aimed before the end of 2026: snippets that compile on nightly can still fail on the pinned 1.98.1.
- **In si-rpg-engine:** `step` and `resolve_pair` in solver/src/lib.rs never keep a reference across a write - each read is copied into a local first - so NLL has nothing to reject; keep that order in Phase-2 code. rapier_law.rs `integrate` already uses the collect-then-apply fix: it builds `plans` in one loop and calls `set_next_kinematic_translation` in a second.

### Keep the owner alive past its last borrow: fix E0597, E0716 and E0515 by binding it or returning owned data
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any; the tail-expression rule differs: edition 2021 E0597, edition 2024 accepted

**A reference must not outlive what it points to: a named local dropped at the end of its block gives E0597, a temporary dropped at the end of its statement gives E0716, and returning a reference to a local gives E0515; the fix is to bind the owner in the outer scope or to return owned data.**

- **How:** E0597: declare the owner before and outside the scope that uses the reference (`let data = ..;` above the struct or block that borrows it). E0716: bind the temporary to a `let` first (`let s = String::from(..); let r = s.as_str();`), or write `let r = &String::from(..);` - a borrow in the `let` initializer extends the temporary to the end of the block, as do tuple-struct/enum constructor arguments (`let x = Some(&temp());`) and the tail of a block, `if` or `match` in the initializer. Function-call arguments and method receivers are not extended: `let s = String::from("a").as_str();` and `let x = identity(&temp());` are E0716 once `s`/`x` is used. E0515: return the owned value (`Vec<f64>`, `String`, `v.into_iter()`) instead of `&local`. Edition matters: in edition 2021 a temporary in a block's tail expression is dropped after the block's locals, so `let c = RefCell::new(..); c.borrow().len()` as the tail is E0597; edition 2024 drops tail temporaries first and accepts it; in 2021 bind the result to a local and return that.
- **Gotchas:** The E0716 page's own failing example, `let p = bar(&foo());`, is the function-argument case: it looks like the extended `let x = &foo();` but is not. The Reference lists tuple-struct and enum-variant constructor arguments as extending, so `let x = Some(&temp());` compiles on 1.98.1 although it looks like a call. A compiler suggestion to add `'static` is almost never the fix (Book).
- **In si-rpg-engine:** solver/ is edition 2021 (solver/Cargo.toml), so a helper whose tail expression creates a guard that borrows a local (the `RefCell::borrow()` shape) hits the 2021 E0597 rule even though the same code compiles in an edition-2024 crate; bind the value to a local before returning.

### Move a value out from behind &mut with mem::take, mem::replace or mem::swap instead of fighting E0507
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust mem::take 1.40+; mem::replace and mem::swap 1.0+ (const 1.83 / 1.85); Option::take 1.0+, Option::replace 1.31+

**A non-Copy value cannot be moved out of a place behind `&mut` or out of an index (E0507), because the place would be left empty; `std::mem::take`, `std::mem::replace`, `std::mem::swap` and `Option::take`/`replace` move it out while leaving a valid value behind.**

- **How:** `mem::take(&mut self.buf)` returns the old value and leaves `T::default()` (needs `T: Default`). `mem::replace(&mut self.phase, Phase::Done)` returns the old value and installs the one you pass - the state-machine idiom for enums without a Default. `mem::swap(&mut a, &mut b)` exchanges two places. For `Option` fields use `opt.take()` (leaves `None`) and `opt.replace(v)` (leaves `Some(v)`, returns the old option). Moving out by index is the same error (`let s = v[0];` on a `Vec<String>` is E0507): write `mem::take(&mut v[0])` or borrow `&v[0]`.
- **Gotchas:** rustc's E0507 help offers only 'consider borrowing here' and 'consider cloning the value'; neither hands you ownership without a copy, which is what take/replace do. `mem::take` builds a `Default` value, so use `replace` with an explicit sentinel when Default allocates or has no meaning. `mem::replace` drops neither value: the old one's destructor runs wherever the returned value is dropped.
- **In si-rpg-engine:** The solver's `*field(bodies, i, slot)` reads in solver/src/lib.rs work only because the payload is f64 (Copy); the same accessor over a non-Copy payload is E0507. In rapier_law.rs, `Solver { loaded: Option<Loaded>, snapshot: Vec<u8> }` is the state that `ensure` replaces today with `solver.loaded = Some(loaded)`; if T2 `solver_restore` needs the old world or buffer back, `solver.loaded.replace(new)` or `mem::take(&mut solver.snapshot)` returns it by move, with no clone.

### Name lifetimes only where the three elision rules fail: two reference inputs, none, or a struct field (E0106)
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any; `mismatched_lifetime_syntaxes` 1.89+ (supersedes elided_named_lifetimes)

**Elision gives each elided input its own lifetime, assigns a sole input lifetime to every elided output, and with `&self`/`&mut self` assigns self's lifetime; a returned reference with two candidate inputs and no self, with no reference input, or any reference stored in a struct or enum needs a named lifetime (E0106).**

- **How:** Leave single-input accessors elided: `fn field(bodies: &mut [f64], i: usize, slot: usize) -> &mut f64` means `fn field<'a>(bodies: &'a mut [f64], ..) -> &'a mut f64`. Name one lifetime when the result may come from several inputs: `fn longest<'a>(x: &'a str, y: &'a str) -> &'a str` (without it E0106 'missing lifetime specifier'). With no reference input (`fn get_str() -> &str`, E0106) return an owned value. In methods the `&self` rule wins silently: `fn pick(&self, fallback: &str) -> &str` that returns `fallback` fails with 'lifetime may not live long enough', which has no error code; name `'a` on both. A struct holding a reference needs a parameter, `struct View<'a> { xs: &'a [f64] }` (a bare `&[f64]` field is E0106); inside `impl<'a> Cursor<'a>` take `&mut self` and return `&'a T`, not `&'a mut self`. Since 1.89 the warn-by-default `mismatched_lifetime_syntaxes` lint flags a lifetime hidden in a return path (`fn iter(&self) -> std::slice::Iter<f64>`); write `Iter<'_, f64>`.
- **Gotchas:** Do not answer E0106 or a lifetime error by adding `'static`: the Book says such suggestions usually mean a dangling reference or mismatched lifetimes. `&'a mut self` on a struct with parameter `'a` keeps the struct mutably borrowed for its whole life, so the second call is E0499; a 2022 ICSE study of 100 Stack Overflow questions shows this exact trap and counts 30 of 118 violations as inter-procedural lifetime mistakes. The 'lifetime may not live long enough' error has no E-code, so the error index cannot explain it.
- **In si-rpg-engine:** `field` in solver/src/lib.rs is the rule-2 case: one reference input (`&mut [f64]`) and two `usize`s, so the returned `&mut f64` borrows `bodies` and nothing else. The crate is edition 2021 on 1.98.1, so `mismatched_lifetime_syntaxes` fires on any new helper that returns an `Iter<f64>`-style type beside a reference input.

### Pass a held &mut to generic parameters as &mut *r: concrete &mut parameters reborrow, generic T moves (E0382)
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any; the generic-parameter move is still open upstream on 1.98.1 (rust-lang/rust#108532)

**A held `r: &mut T` passed where the parameter's type is known to be `&mut T` is implicitly reborrowed (`&mut *r`) and stays usable; passed to a generic `T` or `impl Trait` parameter, the reference itself is moved and the next use is E0382.**

- **How:** Concrete parameters just work: `fn bump(x: &mut f64)`, then `bump(r); bump(r);`. For generic parameters write the reborrow yourself - `consume(&mut *r)`, which is what rustc's help suggests ('consider creating a fresh reborrow of `r` here') - or name the type, `consume::<&mut f64>(r)`. The same split applies to `let`: `let r2 = r;` moves `r`, while `let r2: &mut f64 = r;` (a `let` with an explicit type is a coercion site) reborrows and freezes `r` until `r2`'s last use; re-borrowing `r` inside that window (`bump(r)` while `r2` is still used) is E0499. A mutable reborrow in function arguments is also one of rustc's two-phase borrow sites, so `Vec::push(r, r.len())` compiles.
- **Gotchas:** The generic case is a known compiler gap, not a rule you misread: rust-lang/rust#162690 (September 2026) was closed as a duplicate of #108532 ('From::from call doesn't do reborrowing', open since 2023), so `Handle::from(r)` (any `From::from` call) and `fn f(x: impl Sized)` still move a `&mut`. `&mut T` is not Copy (copying it would alias), which is why a moved `&mut` reports E0382 like a moved String. The Reference documents reborrowing thinly - its reborrowing issue (rust-lang/reference#788) is still open - so trust the compiler over prose on edge cases.
- **In si-rpg-engine:** `step` in solver/src/lib.rs binds `let bodies = &mut BODIES;` (type `&mut [f64; 1088]`) once and passes it to `field` and `resolve_pair` on every iteration; each call reborrows and unsizes it to `&mut [f64]` because those parameters are concrete. A Phase-2 helper written generically (e.g. `fn apply<B: AsMut<[f64]>>(b: B)`) would move `bodies` on the first call and fail with E0382 on the second - pass `&mut *bodies`.

### Treat every by-value use as a move: derive Copy only for plain data, clone on purpose (E0382, E0505, E0204)
`✅ solid` · ✓ verified · ✔ compiles as claimed · Rust any

**Assigning, passing or returning a non-Copy value moves it and kills the source (E0382 on reuse, E0505 if a borrow of it is still live); Copy types are bit-copied implicitly; Clone is an explicit and possibly expensive call.**

- **How:** Read `let b = a;`, `f(a)` and `return a` as moves unless the type is Copy (integers, bool, char, f64, and tuples/arrays whose elements are Copy). A use after a move is E0382 ('borrow of moved value' / 'use of moved value'; inside a loop the label reads 'value moved here, in previous iteration of loop'). Fix E0382 by borrowing (`f(&a)`), by `a.clone()` only when a second owner is really wanted, or by `#[derive(Clone, Copy)]` on small plain-data types; Copy requires Clone and every field Copy, else E0204. Fix E0505 (a move while a reference to the value is still used later) by finishing with the reference first - NLL ends a borrow at its last use - or by passing `&a` instead of `a`.
- **Gotchas:** Copy is always an implicit bitwise copy, so a Copy array or struct of arrays (a whole [f64; 17] row) is duplicated silently on every by-value use. Implementing Copy is part of a type's public API: std says to leave it off if the type may stop being Copy. A type that implements Drop can never be Copy, and `&mut T` is never Copy (copying it would alias). rustc's E0382 help offers `.clone()` 'if the performance cost is acceptable'; check whether a borrow or a reorder is the real fix before paying for a deep copy.
- **In si-rpg-engine:** solver/src/lib.rs reads every slot as `let ax = *field(bodies, i, 0);`: f64 is Copy, so the value is copied out and the `&mut f64` from `field` dies in that statement. rapier_law.rs copies whole rows the same way (`body_at(i) -> [f64; BODY_STRIDE]`), and `integrate` copies `loaded.controller` out of `&mut Loaded` because `KinematicCharacterController` derives Copy in rapier3d-f64 0.35.3; a non-Copy field on that line would be E0507.

### Know where two-phase borrows apply: v.push(v.len()) compiles, Vec::push(&mut v, v.len()) is E0502

### Split one flat buffer into disjoint &mut with split_at_mut, as_chunks_mut and get_disjoint_mut (1.86+)
`▸ plausible` · ✓ verified · ✔ compiles as claimed · Rust split_at_mut 1.0+; split_at_mut_checked 1.80+; get_disjoint_mut 1.86+; as_chunks_mut 1.88+ - all available on the pinned 1.98.1

**The borrow checker treats every index of a slice or array as the same place, so `&mut v[i]` and `&mut v[j]` together are E0499 even when i != j; `split_at_mut`, `split_first_mut`, `as_chunks_mut`, `chunks_exact_mut` and `get_disjoint_mut` hand out non-overlapping `&mut` safely.**

- **How:** `let (lo, hi) = v.split_at_mut(mid);` gives `&mut v[..mid]` and `&mut v[mid..]` (panics if `mid > len`; `split_at_mut_checked`, 1.80+, returns `None` instead). `v.get_disjoint_mut([i, j])` (1.86+) returns `Result<[&mut T; 2], GetDisjointMutError>`: `Err(OverlappingIndices)` when the indices overlap, `Err(IndexOutOfBounds)` past the end; indices are all `usize`, all `Range` or all `RangeInclusive`, checked pairwise (O(n^2)). For fixed-stride records, `as_chunks_mut::<STRIDE>()` (1.88+) turns `&mut [f64]` into `(&mut [[f64; STRIDE]], &mut [f64])`, and `get_disjoint_mut([i, j])` on the rows gives two `&mut [f64; STRIDE]`; `chunks_exact_mut(STRIDE)` iterates rows mutably and `slice.swap(i, j)` swaps two elements with no split. rustc's E0499 help for the index case says 'use `.split_at_mut(position)` to obtain two mutable non-overlapping sub-slices'.
- **Gotchas:** Copying values out first (the resolve_pair shape) is often simpler than splitting and is not a workaround to remove. `get_disjoint_mut` returns `Err` for equal indices, so handle it rather than unwrap when callers can pass i == j. `split_at_mut(j * STRIDE)` needs i < j. `get_disjoint_unchecked_mut` is unsafe: overlapping or out-of-bounds indices are UB even if the references go unused. An array field's elements also borrow as a whole while tuple fields split (`add(&mut p.a[0], &p.a[1])` is E0502, the tuple form compiles); the 2022 ICSE study found this array-vs-tuple difference confused a non-negligible share of participants; split the array with `split_first_mut` or `split_at_mut`.
- **In si-rpg-engine:** solver/src/lib.rs `resolve_pair(bodies, i, j)` copies every slot it needs into a local through `*field(..)` (7 per body up front, positions re-read before each write), so two `&mut` into the flat `BODIES` buffer (64 bodies x stride 17) never coexist and nothing needs splitting; keep that while the kernel mirrors the JS order. If a rewrite wants both rows mutable at once, use `let (rows, _) = bodies.as_chunks_mut::<BODY_STRIDE>();` then `let Ok([a, b]) = rows.get_disjoint_mut([i, j]) else { return };`, or `bodies.split_at_mut(body_at(j))` with i < j (the only order `step` passes); two `field()` results held together are E0499.
