### Autoload discipline — official rule: singletons manage ONLY their own data · `✅ solid` · Godot 4.x (stable; official best-practices page)
**Use autoloads sparingly and ONLY for wide-scope systems that manage their OWN state and do not reach into other objects' data. The official Godot guidance: 'If the autoload is managing its own information and not invading the data of other objects, then it's a great way to create systems that handle broad-scoped tasks.' Systems that modify OTHER systems' data must be regular scripts/scenes, not autoloads. This prevents the god-singleton anti-pattern (a single point of failure, project-wide debugging, mis-allocated resources).**
- **How:** Keep a SMALL, named set of autoloads, each with a single self-contained responsibility: `Events` (signal bus, no state), `GameState` (run/save data: party roster, gold, story flags — owns this data, nothing else writes it directly), `SceneManager` (owns the current-scene swap + transitions), `AudioDirector` / settings, `DataDB` (read-only registry that preloads and indexes all.tres unit/ability catalogs). A system that needs to MODIFY another's data (e.g. combat resolution mutating unit HP) is NOT an autoload — it's a node in the battle scene that reads from DataDB and writes through owned APIs. Access an autoload by its registered name directly (`GameState.party`, `SceneManager.goto(...)`). NEVER `free()`/`queue_free()` an autoload at runtime — the engine crashes.
- **Gotchas:** (1) The classic trap is a giant `Global.gd` that holds AND mutates everyone's data — explicitly the anti-pattern the docs warn against. Split by responsibility. (2) Autoload initialization order = their order in the Autoload list; if `GameState` reads `DataDB` at `_ready()`, `DataDB` must be listed FIRST. (3) C# autoloads need a manual `static Instance` property set in `_Ready()`; GDScript exposes the node name globally for free. (4) Autoloads persist across `change_scene_*`, which is exactly why they're right for run-state — but that also means stale data survives a 'new game' unless you explicitly reset it.
- **Verify (solid):** The quoted official line ('managing its own information and not invading the data of other objects…') is verbatim from the Godot best-practices 'autoloads versus internal nodes' page. Init-order-by-list and 'never queue_free an autoload' are correct. [no external verdict — not checked]
- **Sources:** [Autoloads versus regular nodes — Godot Engine 4.4 docs](https://docs.godotengine.org/en/4.4/tutorials/best_practices/autoloads_versus_internal_nodes.html) ; [Singletons (Autoload) — Godot Engine (stable) docs](https://docs.godotengine.org/en/stable/tutorials/scripting/singletons_autoload.html)

### Avoid Godot-3-only APIs — the migration deprecation checklist (STALE-API GATE) · `✅ solid` · Godot 4.x (stable) — migration reference from official 'Upgrading from Godot 3 to Godot 4'
**A reject-list of Godot-3 APIs/nodes that the LLM crew will hallucinate from stale training data, with their Godot-4 replacements. Any generated GDScript or scene using these is STALE and must be rewritten — flag on sight. Godot 4 renamed nodes for 2D/3D suffix consistency, replaced coroutines, demoted Tween from a node, and renamed scene instancing.**
- **How:** Reject → replace mapping (current 4.x): `KinematicBody2D`/`KinematicBody3D` → `CharacterBody2D`/`CharacterBody3D` (and `move_and_slide()` now takes NO args — it reads the built-in `velocity` property; you no longer pass velocity in). `Spatial` → `Node3D`; `translation`/`global_translation` → `position`/`global_position` (3D, matching 2D). `yield(obj, "signal")` coroutines → `await obj.signal` / `await some_coroutine()`. `Tween` as a NODE → create on-demand objects via `create_tween()` (one-off `Tween` objects, not a child node). `PackedScene.instance()` → `PackedScene.instantiate()`. `get_tree().change_scene(path)` → `change_scene_to_file(path)` / `change_scene_to_packed(packed)`. `export var x` (old keyword) → `@export var x` (annotation). `onready var` → `@onready var`. `setget` → property `set:`/`get:` blocks. `OS.get_ticks_msec()` still exists but prefer `Time.get_ticks_msec()`. `KinematicCollision2D`/raycast and signal-connect syntax (`obj.connect("sig", self, "_m")`) → first-class `obj.sig.connect(_m)`.
- **Gotchas:** (1) The most insidious is `move_and_slide()` — old code passes a velocity arg and 'works' syntactically in some snippets but is semantically Godot-3; in 4.x set `velocity =...` THEN call `move_and_slide()` with no args. (2) `await` only suspends inside a function; you can't `await` at class scope. (3) `create_tween()` tweens are bound to the node that created them and auto-free — don't keep a long-lived Tween node around like in 3.x. (4) Connecting signals with the old string-based 4-arg `connect("name", target, "method")` still half-exists via Callable in 4.x but is the wrong idiom — use `signal.connect(callable)`. (5) Some tutorials/blogs (and kidscancode 3.x recipes) are still Godot-3 — verify the page's version before trusting a snippet.
- **Verify (solid):** Every mapping verified against the official Godot 3→4 upgrade guide: KinematicBody2D/3D→CharacterBody2D/3D, move_and_slide() now no-args reading the velocity property, Spatial→Node3D, translation→position, yield→await, Tween-node→create_tween(),.instance()→.instantiate(), change_scene→change_scene_to_file/_packed, export/onready→@export/@onready, setget→set/get, string-connect→signal.connect(callable). The move_and_slide() semantic-vs-syntactic warning is the correct subtle catch. [no external verdict — not checked]

### Composition over inheritance — entity = parent node + component child nodes/Resources · `✅ solid` · Godot 4.x (stable)
**Build game entities by COMPOSING reusable components rather than deep inheritance trees. Godot nodes are already a composition system (a node IS a component in a scene). The canonical pattern: an 'entity' is a parent node whose 'components' are child nodes (HealthComponent, MoveComponent, LootComponent) and/or attached data Resources. This scales to the combinatorial variety a tactical RPG needs (a unit that is both 'shootable' and 'meltdown-on-death' and 'lootable') where inheritance can't combine orthogonal traits.**
- **How:** Two complementary Godot-4 composition styles: (a) NODE components — give a Unit child nodes like `HealthComponent` (`class_name HealthComponent extends Node`, holds hp, emits `died`), `StatusComponent`, `LootComponent`; the Unit wires them or they self-register to a group. (b) RESOURCE components — the Unit's behavior set is an `Array[AbilityData]` / `Array[PartData]` of data Resources swapped per unit (data-driven composition, ideal for LLM authoring). Mix both: nodes for runtime behavior + lifecycle, Resources for the authorable stat/ability/part loadout. Do NOT adopt a parallel ECS framework — it means abandoning Godot's node system; the node tree already gives you composition. Keep inheritance shallow (one `Unit` base at most); push variation into components/Resources.
- **Gotchas:** (1) Resist real ECS (e.g. bolting on a third-party ECS): it discards Godot's node niceties and creates a parallel world — community + docs consensus is 'use nodes as components, not ECS'. (2) Over-componentizing (a node per trivial field) adds tree bloat and indirection — group cohesive data into one component/Resource. (3) Components that need to talk should go through the Unit (call down / signal up) or the `Events` bus, not sibling `get_node` tree-walking. (4) A component child node still costs per-instance memory — for purely-data traits prefer a Resource over a node.
- **Verify (solid):** Node-as-component + Resource-as-component composition is the documented 4.x consensus; the 'don't bolt on a 3rd-party ECS' guidance matches godot-proposals#2796 and community/docs position. No version-wrong APIs. [no external verdict — not checked]
- **Sources:** [Code the Entity-Component pattern in Godot — GDQuest](https://www.gdquest.com/tutorial/godot/design-patterns/entity-component-pattern/) ; [Favoring Composition Over Inheritance — Game Development Patterns with Godot 4 (O'Reilly/Packt, Ch.4)](https://www.oreilly.com/library/view/game-development-patterns/9781835880289/B22405_04.xhtml) ; [Use a component-based system instead of inheritance [NOT ECS] — godot-proposals#2796](https://github.com/godotengine/godot-proposals/issues/2796)

### Custom Resources (.tres) as the data-driven authoring layer for Units / Abilities / Parts · `✅ solid` · Godot 4.x (stable; 4.4+ confirmed)
**Model all designer/LLM-authorable game data (unit stats, abilities, lootable parts, loot tables, status effects) as custom Resource scripts (`class_name UnitData extends Resource`) saved as.tres text files. Resources are pure data containers with no scene presence — cheap to load, share, and version-control. Nodes are 'things that exist in the world'; Resources are 'the data things are made of'. This is the single highest-leverage Godot-4 pattern for a 1-director + LLM-crew studio because.tres is a plain-text, diffable, deterministic format the crew can generate and edit without opening the editor.**
- **How:** Define `class_name UnitData extends Resource` with `@export` fields (`@export var max_hp: int`, `@export var move_range: int`, `@export var abilities: Array[AbilityData]`, `@export var parts: Array[PartData]`). Use TYPED arrays (`Array[AbilityData]`) — they filter the inspector's resource picker to the correct type and give static-typing safety. Group fields with `@export_group("Combat")` / `@export_category` for inspector legibility. Compose, don't inherit: a `UnitData` HOLDS an `Array[AbilityData]` and an `Array[PartData]` rather than subclassing per unit. Load at runtime with `load("res://data/units/enemy_chassis.tres")` or `preload(...)` for compile-time-known paths. For reactive data, back an `@export` with a setter that calls `emit_changed()` (Resources do NOT auto-emit `changed` on property writes) and have UI `connect` to the `changed` signal — this kills signal-cascading through intermediate nodes (e.g. a `health` resource shared by the unit and its HP bar). Convert.tres →.res only for release builds (binary: faster load, smaller, but not human-readable).
- **Gotchas:** (1) THE SHARED-INSTANCE TRAP — Resources are shared by reference by default. If 5 enemy scenes all reference `enemy_chassis.tres`, they share ONE HP value; damaging one damages all. Call `resource.duplicate(true)` (deep) when instantiating a runtime unit so each combatant gets its own mutable copy. (2) `resource_local_to_scene = true` is buggy under node DUPLICATION (godot#45350): duplicated scene instances still share the resource instead of getting unique copies — prefer explicit `.duplicate()` in code over relying on local-to-scene for combat-instance uniqueness. (3) Put NO heavy runtime logic in Resources (keep them data + tiny helpers); behavior lives in nodes/systems. (4) NEVER store a Node reference in a Resource you save — it won't serialize and corrupts saves.
- **Verify (solid):** class_name extends Resource, @export typed arrays (Array[AbilityData]), @export_group, duplicate(true) deep-copy, emit_changed(), and the shared-instance trap are all current 4.x. Minor: issue #45350 was filed against 3.2.3 not 4.x, but the local-to-scene+duplication caveat does persist into 4.x (cf #115487/#111807) and the advice (prefer explicit.duplicate()) is correct. [no external verdict — not checked]
- **Sources:** [Custom Resources in Godot Engine 4.x — Simon Dalvai](https://simondalvai.org/blog/godot-custom-resources/) ; [Resource-based architecture for Godot 4 — Mayke Fernandes (Medium)](https://medium.com/@sfmayke/resource-based-architecture-for-godot-4-25bd4b2d9018) ; [resource_local_to_scene copies the reference when you duplicate an instance — godotengine/godot#45350](https://github.com/godotengine/godot/issues/45350) ; [Creating and Using Custom Resources — Data-Driven Design in Godot (UhiyamaLab)](https://uhiyama-lab.com/en/notes/godot/custom-resource-data-driven/)

### Event Bus autoload (signals-only singleton) for decoupled cross-system communication · `✅ solid` · Godot 4.x (stable)
**Create ONE autoload named `Events` (a.k.a. EventBus / SignalBus) that extends Node and declares only `signal` definitions — no state, no logic. Distant systems that can't easily get a node reference (combat resolver → UI log, loot system → inventory, turn manager → camera) emit and listen via this single hub. Implements the Observer pattern globally: emitters fire events without knowing who listens, keeping far-apart nodes decoupled at low cost.**
- **How:** Script `events.gd`: `extends Node` then a block of signals, e.g. `signal unit_damaged(unit, amount)`, `signal part_looted(part_data, from_unit)`, `signal turn_started(unit)`, `signal ability_resolved(result)`. Register it in Project Settings > Globals > Autoload with name `Events`. Anywhere: `Events.part_looted.emit(part, target)` to fire; `Events.part_looted.connect(_on_part_looted)` to subscribe. Name signals as PAST-TENSE events ('this happened'), never as commands. The bus is a post office, not a warehouse: it carries messages, it does not hold game state. Keep the signal list curated and documented in one file so the LLM crew has a single legible contract for all global events.
- **Gotchas:** (1) Do NOT route everything through the bus — for parent↔child or near neighbors, a direct signal or a node group is simpler and more debuggable. Over-use produces 'signal spaghetti' that's hard to trace. (2) The bus must hold NO mutable game state (that belongs in a dedicated GameState system, see the autoload-discipline recipe) — mixing the two recreates the god-object anti-pattern. (3) Connections to a bus persist for the listener's lifetime; free'd listeners auto-disconnect, but a listener that outlives its relevance keeps firing — disconnect explicitly when a node's interest ends.
- **Verify (solid):** First-class signal syntax Events.sig.emit(...) / Events.sig.connect(callable) is correct 4.x (the 3.x string-connect idiom is gone). Autoload registration, past-tense naming, and no-state discipline all match GDQuest/official guidance. [no external verdict — not checked]
- **Sources:** [The Events bus singleton — GDQuest](https://www.gdquest.com/tutorial/godot/design-patterns/event-bus-singleton/) ; [Smarter Godot Signals with the Event Autoload pattern — GDQuest guidelines](https://www.gdquest.com/docs/guidelines/best-practices/godot-gdscript/event-bus/) ; [Godot Signals Architecture: Best Practices & Event Bus — Febucci (2024)](https://blog.febucci.com/2024/12/godot-signals-architecture/)

### Node-based Finite State Machine for the deterministic combat turn loop · `✅ solid` · Godot 4.x (stable; pattern uses 4.x @export typed refs, AnimatedSprite2D, Input.get_axis)
**Implement the combat flow (and per-unit behavior) as a node-based FSM: a `StateMachine` Node holding child `State` nodes, each State owning the code for one phase. The machine is in exactly one state at a time; states request their own transitions. This is the standard Godot-4 pattern for anything that needs per-state enter/exit hooks (play an animation, highlight valid cells, lock input) — far cleaner than a sprawling `match` on an enum once you have setup/teardown per phase.**
- **How:** Base class `class_name State extends Node` with the interface `enter(previous_state: State)`, `exit()`, `process(delta)`, `physics_process(delta)`, and (for combat) `handle_input(event)`. `class_name StateMachine extends Node` exposes `@export var initial_state: State` (drag-assigned in the inspector), and in `_ready()` INJECTS references into each child state (`state.state_machine = self`, `state.host = get_parent()`) — do NOT use `@onready` in State for these (it fights inheritance order in Godot 4). The machine delegates `_process`/`_physics_process`/input to the active state. States transition by calling `state_machine.transition_to(target_state)`, which runs `current.exit()` → swaps → `next.enter(prev)`. For combat, model states as `SelectUnit → SelectAction → SelectTarget → ResolveAction → EnemyTurn → CheckVictory`. Use typed `@export var` State references over NodePath strings for type-safety.
- **Gotchas:** (1) In Godot 4, inject `state_machine`/`host` refs from `StateMachine._ready()` — do NOT `@onready var sm =...` inside State; inheritance + ready-order makes that unreliable. (2) `class_name` State/StateMachine are global names — pick project-unique names (`CombatState`, `CombatStateMachine`) to avoid collisions with other FSMs (unit-behavior vs turn-flow). (3) For only 3-5 trivial states with no enter/exit work, a plain enum + `match` is lighter — don't node-ify reflexively. (4) Guard against re-entrant transitions (a state calling `transition_to` from inside `exit()`).
- **Verify (solid):** Standard current-4.x node-FSM pattern; @export typed State refs, inject state_machine/host from StateMachine._ready() (the @onready-fights-inheritance caveat is a real 4.x gotcha), class_name collision warning valid. godot-open-rpg cited as reference is genuinely Godot 4 (4.6.2). [no external verdict — not checked]
- **Sources:** [Node-Based State Machine in Godot 4: A Complete Implementation — Godot Foundry](https://godotfoundry.com/blog/godot-4-state-machine-tutorial) ; [Make a Finite State Machine in Godot 4 — GDQuest](https://www.gdquest.com/tutorial/godot/design-patterns/finite-state-machine/) ; [godot-open-rpg (turn-based combat reference, targets Godot 4.6.2, MIT) — GDQuest](https://github.com/gdquest-demos/godot-open-rpg)

### Save / Load with custom Resources (ResourceSaver/ResourceLoader) — and the untrusted-resource security rule · `✅ solid` · Godot 4.x (stable)
**For a Godot-native, type-safe save system, persist a `SaveGame extends Resource` (party roster, looted-parts inventory, campaign flags, RNG seed) via `ResourceSaver.save()` and reload via `ResourceLoader.load(..., CACHE_MODE_IGNORE)`. Resources beat JSON for game saves on type-safety, brevity, and performance (they round-trip Vector2/Color/typed arrays natively). Use JSON only for data EXCHANGE or human-editable config — JSON can't represent Godot types without manual dict conversion. CRITICAL SECURITY caveat below.**
- **How:** Define `class_name SaveGame extends Resource` with `@export` fields. Save: `ResourceSaver.save(save_game, "user://slot1.tres")` (write to `user://`, the per-user writable dir; check the returned `Error` == OK). Load: `var sg = ResourceLoader.load("user://slot1.tres", "", ResourceLoader.CACHE_MODE_IGNORE)` — CACHE_MODE_IGNORE forces a fresh read from disk instead of returning the in-memory cached copy (without it, reloading a slot returns stale data). For sensitive/anti-tamper saves use `FileAccess.open_encrypted_with_pass()`. Alternative binary path: `FileAccess.store_var()` / `get_var()` — secure by default (object/code serialization OFF) and needs no conversion code.
- **Gotchas:** (1) SECURITY — Godot scenes/scripts ARE Resources, so `ResourceLoader.load()` on an UNTRUSTED.tres can execute code. For player-shared / cloud / mod saves, do NOT plain-load: use `FileAccess.store_var()` (object serialization disabled), or a vetted add-on like 'Godot Safe Resource Loader' that validates.tres content before loading. For purely local single-player saves the risk is low but still real if a save file could be swapped. (2) Forgetting `CACHE_MODE_IGNORE` on load returns the cached resource → 'my save won't update' bugs. (3) Never store live Node references in `SaveGame` — they don't serialize. (4) `.tres` saves are human-readable = trivially editable by players (fine for SP; not for competitive/anti-cheat — encrypt then).
- **Verify (solid):** ResourceSaver.save / ResourceLoader.load with CACHE_MODE_IGNORE, user:// path, FileAccess.store_var()/get_var() (object serialization off by default), and the critical untrusted-.tres-executes-code security warning are all accurate and current. encrypted FileAccess path correct. [no external verdict — not checked]
- **Sources:** [Saving and Loading Games in Godot 4 (with resources) — GDQuest](https://www.gdquest.com/library/save_game_godot4/) ; [Save and Load: Godot 4 Cheat Sheet (Resource vs JSON vs FileAccess) — GDQuest](https://www.gdquest.com/library/cheatsheet_save_systems/) ; [Implementing Save/Load Systems — JSON, ConfigFile, and Custom Resources compared (UhiyamaLab)](https://uhiyama-lab.com/en/notes/godot/save-load-system/)

### Scene composition: 'call down, signal up' and design scenes with no external dependencies · `✅ solid` · Godot 4.x (stable; official best-practices page)
**Official scene-organization doctrine: design every scene to be as self-contained and dependency-free as possible; when scenes must interact, parents 'call down' (method calls / injected callables / node refs) to children, and children 'signal up' (past-tense event signals) to parents — children never reach UP into parents. The parent-child test: a node should be a child ONLY if it's truly an element of its parent (removing the parent implies removing the child); otherwise make them siblings under a coordinating parent.**
- **How:** Structure each reusable piece (a Unit, an AbilityResolver, a GridCursor, a CombatLogPanel) as its own scene with a clear external interface. To send data DOWN: call a method on the child, assign an exported node reference, or hand the child a `Callable` (safest — child doesn't need to own the method). To send events UP: declare a `signal` on the child (`signal moved(to_cell)`, `signal part_targeted(part)`) and let the parent connect. Use dependency INJECTION: the parent provides what a child needs (`battle.gd` injects the `GridState` into each `Unit`), rather than the child calling `get_node("../../GridState")` and hard-coding tree paths. Prefer `@export var grid: GridState` (inspector-assigned) over fragile `get_node("../..")` traversal.
- **Gotchas:** (1) `get_node("../../Something")` absolute/relative tree-walking is the #1 coupling smell — it silently breaks the moment a scene moves. Inject references instead. (2) Signals are for 'respond to behavior', not to START behavior — don't use a signal where a direct downward method call is clearer. (3) Don't over-nest: if two nodes aren't existentially dependent, they're siblings, not parent/child. (4) `owner` vs `get_parent()` differ: `owner` is the scene root that saved the node, not its tree parent — don't confuse them when instancing.
- **Verify (solid):** Matches the official scene-organization doctrine exactly: dependency-free scenes, call-down via method/Callable/@export ref, signal-up via past-tense signals, get_node("../..") flagged as the coupling smell, owner vs get_parent() distinction correct. ### Scene management: SceneManager autoload using change_scene_to_packed / change_scene_to_file · `✅ solid` · Godot 4.x (stable) — REQUIRED API names changed from Godot 3
**Centralize scene switching (title → overworld → battle → results) in a `SceneManager` autoload that owns the swap and the transition animation, rather than scattering `get_tree().change_scene_*` calls across gameplay code. Autoloads persist across scene changes, so run-state (in GameState) survives while the visible scene is replaced — minimizing memory vs keeping whole scenes alive. Use the Godot-4 API names (the 3.x `change_scene(path)` is gone).**
- **How:** Two current APIs: `get_tree().change_scene_to_file("res://scenes/battle.tscn")` (loads + swaps by path), or `get_tree().change_scene_to_packed(packed_scene)` when you already hold a `PackedScene` (e.g. one `@export var battle_scene: PackedScene` set in the inspector, or a threaded-loaded result — avoids a second disk hit). Wrap both in `SceneManager.goto(target)` that plays an `AnimationPlayer` fade-out, performs the swap (deferred), then fades in — so transitions are uniform and the crew calls one method. For custom control, the docs' deferred pattern: free the old scene, `instantiate()` the new, add it, and set `get_tree().current_scene`. Pass context between scenes via `GameState` (not via the freed scene).
- **Gotchas:** (1) STALE-API FLAG — `change_scene(path)` and `change_scene_to(node)` are Godot-3-era and removed/renamed in 4.x; use `change_scene_to_file(path)` or `change_scene_to_packed(packed)`. (2) Calling `change_scene_*` mid-signal can free the node you're still executing in — do the swap deferred (`call_deferred`) or from a safe point. (3) NEVER `queue_free()` an autoload to 'reset' it — engine crash; expose a `reset()` method instead and call it on new-game. (4) `change_scene_to_file` reloads the.tscn from disk each call; for a frequently-revisited scene, hold a preloaded `PackedScene` and use `change_scene_to_packed` to skip re-reading.
- **Verify (solid):** Official migration guide confirms change_scene() is renamed to change_scene_to_file() in 4.x; change_scene_to_packed(PackedScene) is the correct sibling API. Deferred-swap and 'never queue_free an autoload' guidance correct. Recipe explicitly flags the 3.x name as stale — accurate. [no external verdict — not checked]

### Threaded background loading (ResourceLoader.load_threaded_request) + a read-only DataDB registry · `✅ solid` · Godot 4.x (stable; note: threaded loading has a known WEB-build bug in 4.5 beta — issue #109914)
**Two complementary loading practices: (a) at boot, build a read-only `DataDB` autoload that preloads and INDEXES every unit/ability/part.tres into typed dictionaries so gameplay code looks data up by id, not path; (b) for heavy transitions (entering a battle scene, loading a map), use the threaded loading API to load off the main thread behind a progress bar instead of a synchronous `load()` that freezes a frame. Avoids both magic-string paths scattered through code AND hitch-on-load stutters.**
- **How:** DataDB: in `_ready()`, scan `res://data/units/` (via `DirAccess` or a manifest), `load()` each.tres into `units[id] = res`, exposing `DataDB.get_unit(id)`. Register DataDB FIRST in the autoload order. Threaded load for big scenes: `ResourceLoader.load_threaded_request(path)` to start; each frame call `ResourceLoader.load_threaded_get_status(path, progress)` (pass an empty `Array` — engine fills `progress[0]` with 0.0–1.0 for the loading bar); when status == `THREAD_LOAD_LOADED`, retrieve with `ResourceLoader.load_threaded_get(path)` and instance via `packed_scene.instantiate()`. Use `ResourceLoader.exists(path)` to guard. `use_sub_threads=true` speeds large dependency graphs.
- **Gotchas:** (1) `load_threaded_get_status` needs the SAME path string you requested and an empty Array for the progress out-param — mismatches return INVALID_RESOURCE. (2) Don't `await` a poll loop without yielding a frame, or you re-block the main thread and defeat the purpose. (3) Known bug: threaded background loading may never finish on HTML5/Web exports in 4.5 beta (#109914) — if the project ever targets web, fall back to sync `load()` there. (4) DataDB preloading EVERYTHING at boot lengthens startup; for a very large catalog, lazy-load cold data with the threaded API instead of front-loading all of it.
- **Verify (solid):** load_threaded_request / load_threaded_get_status(path, progress[]) / load_threaded_get / THREAD_LOAD_LOADED / use_sub_threads all verified current 4.x. The cited Web bug #109914 is real and correctly scoped to 4.5 beta (workaround: enable thread_support/SharedArrayBuffer). [no external verdict — not checked]
