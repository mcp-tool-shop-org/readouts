### Abilities, stats, and parts as custom Resources (data-driven .tres the crew authors) · `✅ solid` · Godot 4.x
**Define every ability, stat block, and bolt-on part as a `Resource` subclass with `class_name` + `@export` fields, saved as `.tres` text files. This is the single highest-leverage pattern for a 1-director + LLM-crew studio: the crew generates/edits human-readable `.tres` (and the script can even write/load them programmatically) WITHOUT touching engine code, designers tune by editing exported fields in the Inspector, and shared assets are real external files referenced by id.**
- **How:** `class_name AbilityResource extends Resource` with `@export var id: StringName`, `@export var display_name: String`, `@export var ap_cost: int`, `@export var power: int`, `@export var target_kind: int` (enum: self/ally/enemy/part), `@export var charge_meter: bool`, `@export var status_to_apply: StatusResource`. Make `BattlerStats extends Resource` hold base stats AND derive `final` stats by folding active modifiers (GDQuest's base-vs-final pattern). Create `.tres` via right-click → New Resource → pick the class, or `ResourceSaver.save(res, "res://data/abilities/disable_arm.tres")`; load with `load(...)` / `preload(...)`. CRITICAL 4.x note: call `.duplicate()` on a Resource you mutate per-instance — Resources are shared by reference, so an un-duplicated stat block is shared across every unit. For data that ships with the game, an exported `Array[AbilityResource]` on an autoload registry gives one lookup table.
- **Gotchas:** Forgetting `.duplicate()` is THE classic Resource bug — a shared `BattlerStats.tres` means buffing one unit buffs all of them; duplicate on instantiate. `@export` typed arrays (`Array[AbilityResource]`) need Godot 4.x; older untyped patterns lose Inspector type-safety. Keep `.tres` (text) not `.res` (binary) so the crew and git can diff them. Resource scripts with `class_name` must compile before the editor can create the New Resource entry.
- **Verify (solid):** CORRECTED: duplicate() is a SHALLOW copy by default: 'nested Array, Dictionary, and Resource properties are not duplicated and are shared with the original resource.' So .duplicate() on a BattlerStats does NOT isolate a nested StatusResource or any Array/Dictionary field - use duplicate(true) or duplicate_deep(). The parameter is named 'deep' in current stable (it was 'subresources' through 4.4). The recipe also omits resource_local_to_scene, the engine's built-in per-instance alternative, and the editor entry point is the 'Create Resource GUI'. · Godot 4.7: class_name + extends Resource + @export is the documented pattern, typed export arrays confirmed, and ResourceSaver.save(res, path) is the correct 4.x arg order (3.x was save(path, res)) - recipe passes that test. ### Action-point (AP) economy as plain integer state on the Battler · `✅ solid` · Godot 4.x
**A simple, fully-visible AP budget: each unit has `ap_max` and `ap_current`; abilities declare an `ap_cost`; the SelectAction state only offers abilities whose cost ≤ remaining AP, spends on commit, and ends the unit's turn when AP is exhausted or the player passes. No hidden stamina math — the number is on screen.**
- **How:** On the Battler: `@export var ap_max := 2`, `var ap_current := 2`, plus `func can_afford(a: AbilityResource) -> bool: return a.ap_cost <= ap_current` and `func spend(n: int) -> void: ap_current = max(0, ap_current - n); ap_changed.emit(ap_current, ap_max)`. Reset `ap_current = ap_max` in the queue's per-turn `enter`. Keep AP as an `int` (deterministic, trivially testable); never derive it from `_process` time. Multi-cost moves (a 2-AP heavy strike vs two 1-AP shots) fall straight out of this. The Godot Gameplay Systems addon ships turn-based + action-point nodes if you want a pre-built base, but a hand-rolled int is lighter and easier for the crew to reason about.
- **Gotchas:** Don't conflate AP with the charge meter — they are orthogonal pressures (AP = this turn's actions; charge = loot-tier gate). Keeping them as separate ints prevents the self-contradicting single-meter the combat-design critic flagged. Emit `ap_changed` through the bus rather than letting the HUD poll AP each frame.
- **Verify (solid):** CORRECTED: Godot Gameplay Systems does NOT ship action-point nodes. Turn-based: yes. Action points: no. The addon README also warns that a GDExtension rewrite is in progress and the old API will change. · Godot 4.7: @export, signal .emit() and plain int state are all valid 4.x. The recipe's one external factual claim is half false - verified by cloning and grepping the addon. ### Deterministic damage/effect resolver (subtraction-floor model, no RNG hit-chance) · `✅ solid` · Godot 4.x
**A pure function `resolve(attacker_stats, defender_part, ability) -> DamageResult` with zero randomness: same inputs → same output, every time. Use a defense model that never collapses to a flat 0 and that keeps player-facing numbers legible. Two battle-tested options: subtraction `dmg = max(min_dmg, atk + power - def)` (small, Fire-Emblem-predictable numbers) or the multiplicative floor `dmg = atk * (100.0 / (100.0 + def))` (high defense always still takes something). Pick one and keep it visible.**
- **How:** Put the math in a static/standalone resolver (e.g. `class_name CombatMath`) that takes data, not nodes, and returns a small result struct/Dictionary `{ amount, target_part, disabled: bool, loot_tier }`. Round explicitly (`int(floor(x))`) so results are integers and reproducible. Because there is NO to-hit roll, there is no `randi()`/`randf()` anywhere in resolution — the only 'randomness' you might want (e.g. cosmetic variance) must be excluded from the combat model to keep it a visible number. If you ever DO need reproducible variance elsewhere, seed a dedicated `RandomNumberGenerator` instance with `.seed =...` and keep it out of the damage path. Design guidance: make the player-facing stats (atk, def, the targeted part's armor) dominate the output so the player can predict damage by reading the screen.
- **Gotchas:** Plain `atk - def` subtraction hits the classic 'high def = 0 damage' wall (e.g. 200 atk vs 200 def → 0); guard with a `min_dmg` floor or use the multiplicative form. Keep the resolver free of scene-tree lookups so it runs headless in tests (recipe 9). Do not sprinkle `randf()` 'for feel' into resolution — that breaks the deterministic contract and the pre-commit preview.
- **Verify (solid):** Pure static resolver, int(floor(x)) rounding, and seeding a dedicated RandomNumberGenerator via.seed are all valid Godot 4. No Godot-3-isms; deterministic/headless-testable design is sound. Math claims (subtraction-floor vs atk*(100/(100+def))) are engine-agnostic and correct. [Godot 4.7: randi()/randf() and RandomNumberGenerator.seed exist; docs confirm 'A given seed will give a reproducible sequence.' Determinism follows from documented semantics. The damage formulas are uncited design choice, not engine claims.]
- **Sources:** [RPG Damage Formula (subtraction vs atk*(100/(100+def))) — Fandom RPG wiki](https://rpg.fandom.com/wiki/Damage_Formula) ; [Classic JRPG Damage Formulas — Grasp](https://paths.grasp.study/public-courses/cbd93ffc-1946-433a-bd46-0d9489cdaa7c/modules/2f8c1f0a-3ff4-43a7-aa66-823994f92082/lessons/26153270-8a10-4df9-ae17-66fc5874d835) ; [You smack the rat for damage (visible numbers should dominate output) — jmargaris](https://jmargaris.substack.com/p/you-smack-the-rat-for-damage)

### Enemy AI as a sandboxed BattlerAI returning an Action (utility scoring, deterministic) · `✅ solid` · Godot 4.x
**Each AI-controlled Battler owns a swappable `BattlerAI` object whose single job is: given the battle state, return the chosen Action (ability + target). Use Utility AI — score every (ability, target) candidate with normalized 0–1 considerations (distance, target part HP, kill-secure, collateral) and pick the highest. Keep the AI's scoring deterministic so behavior is testable and the player can learn enemy logic.**
- **How:** GDQuest's sandboxing pattern: `class_name BattlerAI` with `func choose_action(state) -> Action`. For utility scoring, structure considerations as small objects/Resources each returning a 0–1 score, optionally shaped by a `Curve` (`curve.sample(normalized_value)`), then combine per candidate (multiply or average) and take the max via a `get_best_action()` loop. Normalize EVERY consideration to the same 0–1 scale (the one hard rule of utility AI). Return a Command-pattern `Action` object the ResolveAction state executes — same Action type player input produces, so resolution code is shared. Subclass BattlerAI per archetype (Aggressor, Executioner, the courteous Steward) instead of branching one giant `if`. For movement targeting, reuse the AStarGrid2D path/range from recipe 6.
- **Gotchas:** Keep the AI a sandboxed object that returns a decision — do NOT let it directly mutate battler state or drive animations; that belongs to ResolveAction. Don't seed AI choices with `randf()` if you want learnable, deterministic enemies (tie-break by a stable rule like lowest part HP, not a roll). A plain idle/patrol/chase state-machine AI (the common tutorials) is the WRONG shape for tactical turn combat — you need per-turn decision scoring, not real-time behavior states. Avoid one monolithic scoring function; per-archetype subclasses keep each enemy's logic legible and tunable.

GDQuest's Godot 4 material (godot-open-rpg) has no BattlerAI at all: it uses class_name CombatAI extends Node with select_action(source: Battler) -> void. · Godot 4.7: Curve.sample() is the correct 4.x name (Godot 3's interpolate() is gone from the class ref) and AStarGrid2D exists. ### Headless unit tests for the deterministic combat core (GUT or gdUnit4) · `✅ solid` · Godot 4.x
**Because resolution is deterministic and lives in pure functions/Resources, the entire combat math is unit-testable without rendering. Use GUT (Godot Unit Test, 9.x = Godot 4.x) or gdUnit4 to assert exact damage numbers, part-disable thresholds, loot-tier drops, AP spend, and AI decisions — and run them headless in CI on a fixed input set.**
- **How:** Write `extends GutTest` scripts with `test_*` methods asserting concrete outputs: `assert_eq(CombatMath.resolve(atk, part, ability).amount, 14)`, `assert_true(result.disabled)`, `assert_eq(part.loot_tier, 2)`. Test the AI by asserting `BattlerAI.choose_action(fixed_state)` returns the expected Action for a known board (proves the cold-equation enemy always picks the kill-secure). Run headless via the CLI: `godot --headless -s addons/gut/gut_cmdln.gd -gdir=res://test -gexit`. gdUnit4 adds mocking/spies and flaky-test detection if you need scene-level tests; for the pure resolver, plain GUT asserts are enough. Keep every test input fixed (no randomness) — trivial precisely because the model has no hit-roll.
- **Gotchas:** GUT versions matter: use GUT 9.x for Godot 4.x (older GUT is Godot 3). Keep the resolver free of scene-tree/node dependencies (recipes 1 & 4) or tests need a full SceneTree and stop being pure unit tests. Don't test through the UI — test the combat core directly; the signal bus (recipe 8) means the core runs with no UI attached, which is exactly what makes headless CI fast.

### Initiative / turn-order queue with an interleaved (re-sortable) order · `✅ solid` · Godot 4.x
**A TurnQueue/ActiveTurnQueue node that collects all Battler children, orders them by an initiative key (speed, or speed derived from installed parts), and yields the next actor each round. For an interleaved Wasteland-3-style order (units act woven together, not all-allies-then-all-enemies), keep a per-round sorted list and re-derive it whenever speed-affecting state changes.**
- **How:** Build an `Array[Battler]`, sort with a custom comparator: `battlers.sort_custom(func(a, b): return a.stats.speed > b.stats.speed)`. Pop the front for the active actor; advance with index wrap `idx = (idx + 1) % battlers.size()` OR rebuild the list at round start so newly-applied speed buffs reorder next round. Expose `signal round_started`, `signal actor_changed(b)`, `signal round_ended`. Two valid flow styles: (a) callback/`play_turn()` chaining (papierkorp's pattern: `queue.play_turn()` → `actor.play_turn()` → on done, `check_turn_end()` advances), or (b) `await`-driven (`await actor.turn_finished`) which reads top-to-bottom — prefer (b) for legibility (recipe 8). Keep `is_player_controlled` on the Battler so the queue knows whether to await UI input or call the AI (recipe 7).
- **Gotchas:** `sort_custom` in 4.x takes a Callable returning bool (true = a before b); Godot-3 `sort_custom(obj, "method")` (object + method-name string) is stale — do not use it. Don't store the active actor only by array index if units can die mid-round (queue_free shifts indices); hold a direct reference and null-check it. If you `await actor.turn_finished`, guarantee that signal always fires (even on skip/stun) or the queue deadlocks (recipe 8 gotcha).
- **Verify (solid):** sort_custom(func(a,b): return a.stats.speed > b.stats.speed) is exactly correct Godot 4 Callable syntax, and the gotcha correctly flags Godot-3 sort_custom(obj,"method") as stale. Queue-free index-shift warning is real. [Godot 4.7: sort_custom(func: Callable) - 'should return true if the first element should be moved before the second one' - exact match, and the Godot 3 sort_custom(obj, method-name) form is gone (checked vs 3.6 docs).]

### Node-based combat state machine (CombatState child nodes + a tiny CombatStateMachine) · `✅ solid` · Godot 4.x
**Model the battle loop as an explicit finite state machine where each phase is its own Node with a script: StartRound, SelectActor, SelectAction, SelectTarget, ResolveAction, EndTurn, CheckVictory. One CombatStateMachine node holds `current_state`, owns enter/exit/transition, and is visible in the remote scene tree at runtime so you can watch which phase you're in. This is the Godot-idiomatic FSM (node-per-state), the most inspectable and the easiest for an LLM crew to author one small file per state.**
- **How:** Define `class_name CombatState extends Node` with virtual methods `enter(msg:={})`, `exit()`, `update(delta)`, `handle_input(e)` and a signal `transitioned(state_name: StringName, msg: Dictionary)`. The owner `CombatStateMachine extends Node` keeps `@export var initial_state: NodePath`, a `current_state: CombatState`, builds a `{StringName: CombatState}` map from its children in `_ready()`, and on `transitioned` calls `current_state.exit()` then `next.enter(msg)`. Use `StringName` (the `&"resolve"` literal) for state keys — cheaper comparisons than String in 4.x. Drive `update`/`handle_input` by forwarding `_process` / `_unhandled_input` from the machine to the active state only. Keep ALL combat rules out of `_physics_process`; a turn game advances on events (input, `await` of an animation), not per-frame ticks.
- **Gotchas:** Do NOT port a Godot-3 FSM that used `yield(...)` to sequence states — that is stale; use `await` (recipe 8). Avoid the trap of running combat logic in `_process(delta)` every frame; a turn game is event-driven, and frame-tick logic reintroduces nondeterminism. Keep the FSM as pure orchestration — the damage math belongs in plain resolver functions you can unit-test headless (recipe 9), not buried in a state node that needs the scene tree.
- **Verify (solid):** Node-per-state FSM with class_name + transitioned signal is idiomatic Godot 4; StringName &"resolve" literal and await-not-yield guidance all verified current 4.x. Pure-orchestration framing is correct. [Godot 4.7: the &-quote StringName literal is documented verbatim and 'Comparing them is extremely fast compared to regular Strings' confirms the cheaper-comparison claim. Typed signal params and @export NodePath are valid 4.x.]

### Per-part / called-shot targeting hooks (parts as a sub-grid of HP+armor on each Battler) · `✅ solid` · Godot 4.x
**Give each Battler an ordered set of targetable PartResources (e.g. head/torso/left-arm/right-arm/legs/core), each with its own hp, armor, `disabled` flag, `loot_tier`, and the stat-deltas it contributes. Targeting selects a unit AND a part; the resolver (recipe 4) applies damage to that part's armor/hp; reaching 0 disables it (drops its stat contribution and, when the loot gate is met, drops it as loot).**
- **How:** `class_name PartResource extends Resource` with `@export var slot: StringName`, `@export var hp: int`, `@export var armor: int`, `@export var disabled: bool`, `@export var loot_tier: int`, `@export var stat_mods: Dictionary`. On the Battler keep `@export var parts: Array[PartResource]` and `func target_part(slot) -> PartResource`. In SelectTarget, the player picks a unit then a part from a small radial/list; feed `defender_part` into `CombatMath.resolve`. On disable, recompute `BattlerStats.final` by folding only non-disabled parts' `stat_mods`. Looting = `attacker_owner.add_part(dropped_part.duplicate())`. Targeting validity (range, line-of-fire) reuses the AStarGrid2D grid distance from recipe — gate selectable parts by whether the unit is in weapon range. Keep all of this as data + pure functions so the pre-commit preview can show 'this shot disables the arm.'
- **Gotchas:** Duplicate the PartResource when moving it between battlers (same shared-reference trap as recipe 5) or the enemy and your unit will share one mutating part. Don't bake part geometry into the visual sprite — keep parts as data so the painterly 2.5D art (which is NOT real-time 3D) stays decoupled from the hit model; the sprite shows the result, the data IS the result. Recompute `final` stats only from enabled parts, or disabled limbs keep buffing the unit.

### Sequence turns with `await` on signals/coroutines (NOT yield) + a signal-bus for UI decoupling · `▸ plausible` · Godot 4.x
**Two complementary 4.x patterns. (1) Sequencing: use the `await` keyword to write turn flow as linear top-to-bottom code — await player input, await an animation, await resolution — instead of nested callbacks. (2) Decoupling: route combat-to-UI communication through an autoload signal bus ('Events'/'CombatEvents') so the HUD, initiative strip, and damage popups react to events without any hard reference into the combat system.**
- **How:** Sequencing: `await battler.action_chosen` (player), `await anim_player.animation_finished` (Godot 4.x `animation_finished` fires even on interruption and passes the anim name), `await resolver_done`. The instant a function uses `await` it becomes a coroutine — no special declaration. Decoupling: make an autoload `Events extends Node` holding signals like `signal unit_hp_changed(unit, hp, max)`, `signal ap_changed(unit, cur, max)`, `signal actor_changed(unit)`, `signal part_disabled(unit, slot)`, `signal part_dropped(part)`; combat code does `Events.unit_hp_changed.emit(...)`, UI nodes `Events.unit_hp_changed.connect(_on_hp)`. Namespace event names and unsubscribe on `_exit_tree` for nodes that come and go. Not everything needs a signal — a parent configuring its own child should just call the method; use the bus for distant/decoupled listeners only.
- **Gotchas:** `yield(...)` is GODOT-3-ONLY and removed in 4.x — every `yield` must become `await`; flag any tutorial using `yield` as stale. THE await deadlock: if you `await unit.turn_finished` but the unit is `queue_free()`d (dies mid-turn) before emitting, the signal is disconnected and the coroutine hangs forever — always guarantee the awaited signal fires (emit on skip/stun/death paths) or await with a timeout fallback. Don't overuse the bus into 'signal spaghetti'; reserve it for genuine decoupling. Connect in code (not only via the editor) so combat wiring is greppable and reviewable.
