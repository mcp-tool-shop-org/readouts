### Hugging Face TRL + PEFT · `recommended` · production
TRL v1.0 is the unified post-training stack — SFT, reward modeling, DPO, KTO, GRPO — sitting on PEFT (LoRA/QLoRA via the `peft_config` arg) and HF Transformers/Accelerate. This is the right tool the moment you leave plain SFT for preference optimization or RL, and it's the best NATIVE-WINDOWS option: it's pure Python over PyTorch + bitsandbytes, so with PyTorch's cu130 stable wheels and the new sm_120 bitsandbytes Windows wheels it runs on a 5090 without WSL2. v1.0 folded in an Unsloth fast path and data packing; add Liger-Kernel for another ~60% memory cut. Knobs that matter on 32 GB: `SFTConfig(packing=True)`, gradient checkpointing, `load_in_4bit` via PEFT QLoRA, paged 8-bit AdamW, and `use_liger_kernel=True`. Slower than raw Unsloth but unmatched in method coverage and ecosystem.
- **Dev:** Hugging Face · **Type:** training-framework · **Lang:** Python · **Version:** TRL v1.0 (PEFT current alongside) · **Released:** 2026-04 (TRL v1.0)
- **Platforms:** linux, windows (native), macos · **Accelerators:** cuda, cpu, mps, xpu (via Accelerate) · **Formats:** HF safetensors in; LoRA/QLoRA adapters + merged models out
- **Blackwell/Win-ready:** yes · **Optimizes for:** flexibility · **Multi-GPU:** data-parallel / FSDP2 / DeepSpeed (via Accelerate) · **Fit:** rig 5/5 · studio 5/5
- **License:** Apache-2.0 — commercial: **yes**. Fully Apache-2.0 (both TRL and PEFT). No commercial restrictions; the standard permissive stack for shipping fine-tuned models.
- **Best for:** DPO / GRPO / reward-model RLHF on the 5090 (local, fit 5) ; Native-Windows LoRA/QLoRA without WSL2 (windows, fit 5) ; Flexible SFT with full HF model coverage (local, fit 5) ; Reference/teaching stack with the largest ecosystem (reference, fit 5)
- **Speed/notes:** Baseline HF speed, but with the built-in Unsloth fast path (~2x / -70% mem) and/or Liger-Kernel (`use_liger_kernel=True`) it closes most of the gap; the most flexible RLHF/DPO/GRPO engine.

### OpenRLHF · `recommended` · production
The production-grade, Ray-native RLHF framework and a wave-1-flagged must-have. Re-architects scheduling for 70B+ models on Ray + vLLM + DeepSpeed ZeRO-3, exposing PPO, GRPO, Dr.GRPO, RLOO, REINFORCE++/-baseline, DAPO (dynamic sampling/filtering), plus DPO/IPO/cDPO, rejection sampling, and KTO. v0.10 line adds full async agentic RL, multi-turn VLM RL (images in prompt and environment feedback, e.g. Qwen3.5-VL), TIS (truncated importance sampling), and the Muon optimizer. Compared to veRL it trades veRL's HybridFlow flexibility for a simpler, opinionated Ray role model that many teams find easier to operate. For this rig it is the second RL option behind veRL: run ~7B GRPO/DPO in WSL2 with ZeRO-3 offload, or use it as the reference design when renting multi-GPU cloud.
- **Dev:** OpenRLHF community (originated at OpenLLMAI; contributors incl. ByteDance, NVIDIA, Alibaba) · **Type:** training-framework (RLHF / agentic RL) · **Lang:** Python · **Version:** v0.10.3 · **Released:** 2026-05-03
- **Platforms:** Linux (native); Windows via WSL2 only — Ray + DeepSpeed + vLLM stack is Linux-first. Quick-start Docker: nvcr.io/nvidia/pytorch:25.11-py3. · **Accelerators:** NVIDIA (CUDA 12.8+/Blackwell via cu128 torch + DeepSpeed); the NGC 25.11 base image is already cu13-class so sm_120 works in-container · **Formats:** HuggingFace Transformers checkpoints; DeepSpeed ZeRO-3 sharded states; vLLM for generation; supports Qwen3.5/Llama/Mixtral and VLMs (OpenRLHF-M)
- **Blackwell/Win-ready:** yes · **Optimizes for:** Production RLHF at scale with the simplest distributed mental model — Ray schedules separate actor/critic/reward/reference and vLLM-generation roles across GPUs; DeepSpeed ZeRO-3 + AutoTP + RingAttention handle the sharding. Designed for resource utilization on 70B+. · **Multi-GPU:** Ray-based role placement + DeepSpeed ZeRO-3 (with deepcompile, AutoTP, RingAttention) + vLLM auto tensor/pipeline parallel. 70B+ full fine-tune on multi-node A100/H100; 7B full RLHF demonstrated across multiple 24 GB RTX 4090s — so 7B-class RL on a single 32 GB 5090 is plausible with offload. · **Fit:** rig 3/5 · studio 2/5

### Unsloth · `recommended` · production
Unsloth is the single-GPU fine-tuning king: custom Triton kernels for RoPE/RMSNorm/MLP/cross-entropy plus a memory-efficient gradient-checkpointing scheme cut VRAM ~70% and roughly double throughput vs a stock HF Trainer, with zero accuracy loss. On a 32 GB 5090 it QLoRAs 14B models entirely in VRAM and reaches 30-70B by paging the 4-bit-quantized weights + 8-bit paged-AdamW optimizer state, with the 64 GB system RAM as overflow. It officially supports Blackwell (RTX 5060-5090, B200, RTX PRO 6000); the documented Blackwell install uses `uv pip install -U vllm --torch-backend=cu128` then `uv pip install unsloth unsloth_zoo bitsandbytes`. WINDOWS GOTCHA: the blessed install path assumes WSL2/Linux (its xformers/vLLM build notes give WSL memory tweaks); native Windows works but is fiddlier — run it inside WSL2 Ubuntu for the frictionless path. Key knobs: `load_in_4bit=True`, `use_gradient_checkpointing='unsloth'`, `max_seq_length`, LoRA rank/alpha.
- **Dev:** Unsloth AI (Daniel & Michael Han) · **Type:** training-framework · **Lang:** Python (Triton kernels) · **Version:** 2026.x (rolling; pip 'unsloth' + 'unsloth_zoo') · **Released:** 2026 (continuous releases; Blackwell support shipped 2025-2026)
- **Platforms:** linux, windows (native rough; WSL2 smooth) · **Accelerators:** cuda (NVIDIA incl. Blackwell), some AMD/Intel experimental · **Formats:** safetensors / HF transformers in; LoRA adapters + merged 16-bit + GGUF export out
- **Blackwell/Win-ready:** yes · **Optimizes for:** memory · **Multi-GPU:** data-parallel (multi-GPU added; single-GPU is the sweet spot) · **Fit:** rig 5/5 · studio 5/5
- **License:** Apache-2.0 (core); AGPL-3.0 (Unsloth Studio UI component) — commercial: **yes**. Core fine-tuning library is Apache-2.0 — free for commercial/studio use including selling trained LoRAs/models. Only the optional Unsloth Studio web UI is AGPL-3.0; avoid embedding Studio in a closed product, but the CLI/library training path you'd actually use is Apache-2.0.
- **Best for:** Single-GPU LLM LoRA/QLoRA on the 5090 (local, fit 5) ; Squeezing 30-70B QLoRA onto 32 GB VRAM + 64 GB RAM (local, fit 5) ; Fast iteration on style/persona LoRAs for local LLM crew (local, fit 5) ; GGUF export to feed llama.cpp/Ollama after training (local, fit 4)
- **Speed/notes:** ~2x faster training and up to ~70% less VRAM vs vanilla HF SFT/DPO via hand-written Triton kernels + smart gradient checkpointing; the fastest single-GPU LoRA/QLoRA path.

### ms-swift (ModelScope Swift) · `recommended` · production
The broadest actively-maintained post-training framework in the open ecosystem and the single best NEW fit for this rig. One `swift sft|rlhf|pt|export` CLI (plus a Web-UI and Python API) covers SFT, continued pretraining, the entire preference-optimization zoo (DPO/KTO/CPO/SimPO/ORPO/RM) and the entire GRPO RL family (GRPO/DAPO/GSPO/SAPO/CISPO/RLOO/Reinforce++/GKD/PPO) over 600+ LLMs and 300+ multimodal models. Crucially for a 32 GB single-GPU rig it ships first-class rollout acceleration through the very inference engines already in this KB — `--use_vllm true --vllm_mode colocate` runs the vLLM policy-sampler in the same process as the trainer, so RL fits on one 5090 for small policies. Tuning backends span LoRA/QLoRA/DoRA up through DeepSpeed ZeRO-3, FSDP2 and a full Megatron-SWIFT parallel path (TP/PP/EP/CP, FP8). Releases are weekly (v4.2.3, 2026-05-31). Blackwell is supported the same way everything else is — via a PyTorch cu128 base — so pin the nightly first; native Windows is fine for the LoRA+GRPO loop, while the FP8 Megatron-SWIFT path is Linux/WSL2.

### veRL (HybridFlow) · `recommended` · production
The de-facto standard open-source RL post-training framework in 2026 and the wave-1-flagged #1 must-have. Implements PPO, GRPO, GSPO, DAPO, Dr.GRPO, RLOO, REINFORCE++/-baseline, ReMax, and PRIME via a clean HybridFlow programming model that decouples the RL control flow from the heavy compute. Training backends: FSDP, FSDP2, and Megatron-LM. Rollout/inference: vLLM, SGLang, or HF Transformers. Supports LoRA-RL (e.g. GRPO+LoRA on a single H100 in the upstream examples, directly adaptable to one 5090), multi-turn/agentic RL (uni-agent built on top, May 2026), and omni/diffusion RL (VeRL-Omni preview). Hardware reach spans NVIDIA, ROCm, and Ascend. For this rig it is the escalation engine for real GRPO/RLHF — runnable locally on a small policy in WSL2, ideal when scaling out to cloud.
- **Dev:** ByteDance Seed / Volcano Engine — verl-project (community-governed since Jan 2026) · **Type:** training-framework (RL post-training) · **Lang:** Python · **Version:** v0.8.0 · **Released:** 2026-06-01
- **Platforms:** Linux (native); Windows via WSL2 only — Ray + vLLM/SGLang + FSDP stack is Linux-first, no Windows-native path · **Accelerators:** NVIDIA (CUDA 12.8+ / Blackwell sm_120 via cu128 torch), AMD ROCm (MI300X/MI325X/MI355X explicitly supported), Ascend NPU · **Formats:** HuggingFace Transformers checkpoints (Qwen, Llama, Gemma, DeepSeek, Mixtral, VLMs); FSDP/FSDP2 + Megatron-LM sharded states; vLLM/SGLang for rollout generation
- **Blackwell/Win-ready:** yes · **Optimizes for:** Large-scale RL post-training throughput — the HybridFlow single-controller/multi-worker design colocates or disaggregates the actor-training engine (FSDP/Megatron) and the rollout-generation engine (vLLM/SGLang) to keep GPUs saturated across the generate->score->update loop. · **Multi-GPU:** Core competency: FSDP/FSDP2 + Megatron-LM 5D parallelism (TP/PP/DP/CP/EP) for the policy/critic; vLLM/SGLang tensor-parallel rollout; Ray for cluster orchestration. Scales to 100B+ on multi-node. Single-GPU works for <=7B with colocated rollout. · **Fit:** rig 3/5 · studio 3/5
- **License:** Apache-2.0 — commercial: **yes**. Apache-2.0 — unrestricted commercial use, modification, and redistribution. No field-of-use or model-output restrictions imposed by the framework itself (downstream base-model licenses still apply).
- **Best for:** GRPO / PPO / DAPO post-training of a reasoning policy (math, code, agentic) when you need the dominant, well-supported RL stack (rl-post-training, fit 5) ; Multi-node 70B+ RL with Megatron 5D parallelism (rented cloud, not this rig) (datacenter-rl, fit 5) ; Single-GPU GRPO+LoRA on a 1.5B-7B policy in WSL2 with colocated vLLM rollout (learn-local, scale-to-cloud) (local-grpo-small, fit 3)

It is built for 8x+ GPUs; on one card it is the correct tool to learn locally then scale to rented cloud.
