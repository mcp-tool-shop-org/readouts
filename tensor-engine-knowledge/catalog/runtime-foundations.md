### CUDA Toolkit + cuDNN + cuBLAS (the substrate) · `recommended` · production
The non-optional substrate every NVIDIA path in this lane sits on: the CUDA Toolkit (nvcc, runtime, driver API) plus the math libraries cuBLAS/cuBLASLt (GEMM), cuDNN 9.x (conv/attention primitives), and the comms library NCCL. CUDA 12.8 was the FIRST toolkit to support Blackwell across the whole tool/library/compiler suite and introduced Compute-in-Graphics (CiG) on Windows x64 for Blackwell GeForce; the line has since moved to CUDA 13.x (which PyTorch 2.12 adopts as default, dropping the older 12.8 wheels). For this rig you mostly don't hand-install it — PyTorch and llama.cpp Windows wheels bundle the CUDA runtime they need — but you DO need a current NVIDIA Windows driver (570+ class for the CUDA 12.8 Blackwell baseline, newer for CUDA 13) and you must keep the toolkit/cuDNN/framework generations aligned, since the classic Blackwell failure mode ('no kernel image is available' / 'sm_120 not defined') is a mismatch between a framework built for sm_90 and an sm_120 card. Native Windows is fully supported; WSL2 is only needed for the Linux-first frameworks (JAX, TRT-LLM) that sit above it.
- **Dev:** NVIDIA · **Type:** kernel-lib · **Lang:** C/C++/PTX with nvcc compiler; CUDA C++ · **Version:** CUDA 13.x toolkit (CUDA 12.8 was the first Blackwell-capable toolkit); cuDNN 9.x · **Released:** 2025 (CUDA 12.8 Blackwell launch); CUDA 13.x current in 2026
- **Platforms:** windows, linux · **Accelerators:** cuda (NVIDIA GPUs only) · **Formats:** n/a (the GPU programming substrate; kernels + math libs)
- **Blackwell/Win-ready:** yes · **Optimizes for:** throughput · **Multi-GPU:** none directly (NCCL handles collective comms above it) · **Fit:** rig 5/5 · studio 5/5
- **License:** Proprietary (NVIDIA CUDA Toolkit EULA); cuDNN/cuBLAS proprietary — commercial: **conditional**. ### PyTorch (eager + torch.compile / TorchInductor) · `recommended` · production
The foundational eager+compile tensor framework that the entire local-studio stack stands on: ComfyUI/Diffusers (SDXL/Flux), PEFT/LoRA training, and most local LLM tooling are PyTorch underneath. torch.compile lowers eager graphs through TorchInductor to Triton GPU kernels (and a C++/OpenMP CPU backend) for 1.3-2x without code changes; key knobs are mode='reduce-overhead' (CUDA Graphs) or 'max-autotune' (GEMM autotuning via CUTLASS/CK), plus torch.compiler.set_stance. Blackwell/sm_120 has been STABLE on Windows since 2.7.0 (Apr 2026) — but the load-bearing gotcha is that 2.12.0 REMOVED the cu128 build: CUDA 13.0 (cu130) is now the stable default with cu126 as the old-driver fallback, so any guide telling you to install the cu128 index URL is stale and will fail. Windows works natively (no WSL2 needed); FlashAttention coverage on Windows historically lagged Linux, so prefer cuDNN/mem-efficient SDPA backends if a Triton FA kernel won't build.
- **Dev:** PyTorch Foundation (Linux Foundation; originally Meta AI) · **Type:** runtime · **Lang:** Python / C++ (ATen, libtorch); compiler stack in Python + Triton + C++ · **Version:** 2.12.0 · **Released:** 2026-05-13

### ggml / llama.cpp · `recommended` · production
The C/C++ tensor library (ggml) + LLM runtime (llama.cpp) that is the single best local-LLM-delegation engine for this rig. It ships rolling Windows prebuilt binaries with CUDA bundles (current b9484 carries CUDA 12.4 and CUDA 13.3 DLL packs) — unzip and run, no toolchain or WSL2 required, and Blackwell works via the CUDA backend. The decisive feature for a 32 GB-VRAM + 64 GB-RAM box is partial offload: -ngl/--n-gpu-layers puts as many layers on the 5090 as fit, the rest spill to system RAM, and for MoE models --n-cpu-moe / --override-tensor keeps expert tensors on CPU so a model far larger than 32 GB still runs. Other key knobs: --flash-attn, --cache-type-k/-v q8_0 (KV-cache quant to stretch context), --ctx-size, and --tensor-split for multi-GPU. Use it for the 'ollama-intern' style bulk-analysis delegation and any local-first chat/agent that must not burn cloud tokens; it powers Ollama and LM Studio underneath.

### NVIDIA TensorRT for RTX · `recommended` · stable
The consumer-RTX-targeted TensorRT — a compact (<200 MB) drop-in inference compiler for NVIDIA RTX GPUs from Turing (7.5) through Blackwell (compute capability 10.0), and the *right* TensorRT for this rig (datacenter TensorRT and TRT-LLM are heavier and TRT-LLM on GeForce is WSL2-only). It installs as a native Windows pip wheel (pip install tensorrt-rtx; append -cu12 or -cu13 to pick the CUDA variant, default CUDA 13.x), takes an ONNX model and JIT-builds an optimized engine at load time so you avoid the brittle ahead-of-time per-GPU plan files of classic TensorRT. Reach for it when a model is frozen (a production diffusion UNet/VAE, an upscaler, a vision model) and you want the last 1.5-3x of latency and FP8/FP4 Blackwell tensor-core throughput that eager PyTorch leaves on the table. Gotchas: NVIDIA-only and proprietary; it optimizes a static graph, so it's for inference of fixed shapes/models, not flexible training; recent releases note Blackwell-specific Compute-in-Graphics (CiG) fixes.
- **Dev:** NVIDIA · **Type:** compiler · **Lang:** C++ runtime with Python and C++ APIs · **Version:** 1.x (TensorRT-RTX, released 2026-03-17) · **Released:** 2026-03-17
- **Platforms:** windows, linux · **Accelerators:** cuda (NVIDIA RTX only: Turing 7.5 → Blackwell 10.0) · **Formats:** ONNX in; builds an optimized engine plan (JIT-compiled at load, not a portable AOT plan file)
- **Blackwell/Win-ready:** yes · **Optimizes for:** latency · **Multi-GPU:** none (single-GPU inference engine) · **Fit:** rig 5/5 · studio 4/5
- **License:** Proprietary (NVIDIA Software License / SDK EULA) — commercial: **conditional**. No copyleft, but not OSI-open; runs only on NVIDIA RTX GPUs.
- **Best for:** Lowest-latency inference of a frozen ONNX model on the 5090 (nvidia, fit 5) ; FP8/FP4 / INT8 quantized inference using Blackwell tensor cores (nvidia, fit 5) ; Windows-native accelerated inference without WSL2 (windows, fit 5) ; Speeding up a production diffusion/vision pipeline component (local, fit 4)

### ONNX Runtime (+ DirectML / WinML, CUDA EP) · `runner-up` · production
Microsoft's cross-platform ONNX inference (and limited training) runtime — the portable glue layer and standard exchange format of the lane. On this Windows+5090 rig you have two good lanes: the CUDA Execution Provider (or chain the TensorRT EP) for full NVIDIA performance, or DirectML/WinML for a vendor-neutral DX12 path that needs no CUDA install and also reaches the Intel Core Ultra iGPU/NPU. 1.26.0 (May 2026) raised the CUDA floor to 12.0 (CUDA 11.x dropped) and publishes separate cuda12/cuda13 GPU packages, and it has been built successfully for Blackwell. Important Windows-strategy note: DirectML is now in 'sustained engineering' — still supported but new feature work has shifted to WinML, which exposes the same ORT APIs while auto-selecting the best execution provider per hardware (downloadable EPs on Windows 11 24H2+). Reach for ORT when you need one model artifact to run across NVIDIA/Intel/CPU, when embedding inference in a C#/.NET tool, or as the bridge into TensorRT-RTX. It is not the tool for large local LLMs — use llama.cpp for those.

### JAX + XLA · `situational` · production
Google's functional, NumPy-style array framework compiled by XLA (whole-program fusion, layout/autotuning, jit/vmap/grad/pjit) — superb for research and large-scale training, and the default stack on TPU. Blackwell is supported (NVIDIA's JAX containers run on Ampere/Hopper/Blackwell; CUDA-12.8-based JAX 25.01 added Blackwell), so the hardware is not the problem — the PLATFORM is. JAX has no native Windows GPU support: pip GPU installs on Windows fail silently and the documented path is WSL2 (with WSL3's near-native GPU passthrough, announced at Build 2026, poised to improve this). For a Windows-native local game studio doing inference, diffusion, and LoRA training, JAX is the wrong default — PyTorch covers the same ground natively. Record it as reference/standby: if a specific research model ships JAX-only, run it under WSL2 with the NVIDIA jax CUDA wheels; otherwise skip it on this rig.
- **Dev:** Google (JAX); OpenXLA (XLA compiler) · **Type:** compiler · **Lang:** Python (NumPy-like API) → XLA HLO → PTX/LLVM · **Version:** JAX 0.9.x (NVIDIA JAX container 26.03 based on JAX 0.9.0.1 + CUDA 13.2) · **Released:** 2026-03 (container 26.03)
- **Platforms:** linux (native GPU); windows (CPU-only natively, GPU via WSL2); tpu; macos (cpu/experimental Metal) · **Accelerators:** cuda (Linux/WSL2), tpu, cpu; experimental rocm/metal · **Formats:** orbax/flax checkpoints; StableHLO export; not a GGUF/ONNX-first tool
- **Blackwell/Win-ready:** yes · **Optimizes for:** throughput · **Multi-GPU:** data-parallel + tensor/pipeline via pjit/shard_map (SPMD partitioning in XLA) · **Fit:** rig 2/5 · studio 2/5
- **License:** Apache-2.0 — commercial: **yes**. Apache-2.0 — permissive, commercial-friendly. No license barrier; the barrier for this rig is platform (Windows GPU) not license.
- **Best for:** Research models distributed as JAX/Flax (run under WSL2) (reference, fit 3) ; Large-scale training throughput where XLA fusion shines (training, fit 3) ; TPU workloads (not applicable to this rig) (reference, fit 2)

### tinygrad · `situational` · experimental
tinygrad is a pure-Python ML framework/compiler from George Hotz's tiny corp that has matured into a genuinely portable runtime. Its core abstraction is the UOp ('Unified Operation') IR — a single ~90-op IR that represents the tensor graph, the scheduled kernel graph, AND the linearized instructions, the only IR in the whole compiler. It lazily builds a graph and uses search to schedule kernels, then codegens to many backends: CUDA/PTX and the new open NVK/NAK path (via a Mesa NIR backend added in 0.12, Jan 2026), AMD HIP plus tiny corp's own 'AM' userspace driver (RDNA3/3.5/4, MI300X), Apple Metal, Qualcomm, WebGPU, OpenCL, CPU/LLVM, and x86 assembly. MIT-licensed; 0.13.0 shipped 2026-05-22. For THIS rig it is situational: the CUDA backend reaches sm_120, and it's the cleanest codebase in this lane to *learn* compiler internals or prototype a custom backend — but for production training/inference on the 5090, PyTorch+cuDNN and llama.cpp/vLLM are faster and better-supported. Keep it as the 'understand the compiler / weird-backend' tool.
- **Dev:** the tiny corp (George Hotz / geohot) · **Type:** runtime + compiler (minimalist ML framework, UOp IR) · **Lang:** Pure Python (no C++ kernels in core; lazy UOp graph → backend codegen) · **Version:** 0.13.0 · **Released:** 2026-05-22 (0.13.0; 0.12.0 was 2026-01-12 with Mesa NIR backend)

Recorded here purely as CROSS-PLATFORM REFERENCE because this rig has no Mac — rig_fit is 0 by design.
