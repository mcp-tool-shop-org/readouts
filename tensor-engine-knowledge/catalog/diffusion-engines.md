### ComfyUI · `recommended` · production
ComfyUI is the de-facto node-based runtime/engine for local diffusion and the correct base layer for this entire lane — every other accelerator here plugs into it. On Windows the official portable now ships its OWN pinned PyTorch on CUDA 13.0 + Python 3.13 that runs on Blackwell sm_120 out of the box, which is exactly why you must NOT hand-install a torch nightly: let the portable pin torch. Key knobs: launch with --use-sage-attention (after installing a Blackwell SageAttention wheel) for ~30% sampling speedup, never pip install xformers on this env (it silently breaks Blackwell installs), and use comfy-kitchen / NVFP4 model paths (need CUDA 13+) to run FP4-quantized FLUX/Qwen-Image. Gotcha: custom-node sprawl is the #1 source of broken Blackwell installs — keep the env clean and prefer Comfy Manager-vetted nodes.
- **Dev:** Comfy-Org (comfyanonymous + Comfy-Org team) · **Type:** inference-server · **Lang:** Python · **Version:** v0.7.x line (major stable cut ~every 2 weeks; v0.7.0 added Windows ROCm in early Jan 2026) · **Released:** 2026 (rolling; ~bi-weekly stable tags)

### Comfy-WaveSpeed (First Block Cache / TeaCache) · `recommended` · stable
Comfy-WaveSpeed is the spiritual successor to the now-retired stable-fast (same author) and the practical home of dynamic caching in ComfyUI. Its 'Apply First Block Cache' node uses the first transformer block's residual as a change indicator: when consecutive residuals barely differ, it reuses the prior output and skips the remaining blocks, giving ~1.5-2x on iterative DiT models (FLUX, HunyuanVideo, Wan) at near-zero VRAM cost — it stacks cleanly on top of SageAttention and Nunchaku. Knobs: a residual_diff_threshold trades speed vs fidelity (higher = faster, more artifacts). This is the cheapest extra speed in the lane for a single 5090. Gotcha: it's WIP and some node combinations (e.g., certain Kijai HunyuanVideo nodes) are incompatible; caching can soften fine detail at aggressive thresholds, so tune per workflow. The multi-GPU context-parallel path (ParaAttention port) is not relevant on one card.
- **Dev:** chengzeyi (WaveSpeed.ai) · **Type:** runtime · **Lang:** Python · **Version:** WIP / rolling (no formal semver; active 2025-2026) · **Released:** 2026 (continuous)
- **Platforms:** windows, linux, macos · **Accelerators:** cuda, rocm, metal (inherits ComfyUI backend) · **Formats:** n/a (operates on the diffusion model graph; FLUX/SD3/HunyuanVideo/Wan-class DiTs)
- **Blackwell/Win-ready:** yes · **Optimizes for:** throughput · **Multi-GPU:** none on a single rig (multi-GPU context-parallel port is WIP) · **Fit:** rig 4/5 · studio 5/5

### ComfyUI-GGUF (city96) · `recommended` · stable
ComfyUI-GGUF is the VRAM-fit workhorse for this rig: it brings llama.cpp-style GGUF variable-bitrate quantization to native ComfyUI diffusion models, so heavy models that won't fit at 32 GB (large FLUX, Qwen-Image, and especially Wan video) run at Q8 down to Q4 with graceful degradation, and weights spill from VRAM into your 64 GB system RAM via partial offload. Use the 'Unet Loader (GGUF)' (place .gguf in models/unet) and the GGUF CLIPLoader nodes to also quantize the T5 text encoder, which alone reclaims several GB. This is the right tool precisely where Nunchaku doesn't reach — video models and families nobody has SVDQuant-packed. Gotcha: Wan 2.x contains 5D tensors that exceed GGUF dims and must be split out via fix_5d_tensors.py during conversion; and GGUF is a fit/offload play, not a throughput play (it can be slower than fp8 when fully VRAM-resident).

### Hugging Face Diffusers · `runner-up` · production
Diffusers is the reference Python library/runtime for diffusion — the canonical way to script pipelines, train/run LoRAs, and do anything ComfyUI's graph makes awkward. For this rig its value is programmatic control plus first-class memory tooling: enable_group_offload() (with use_stream=True) to spill modules to the 64 GB system RAM, FP8 layerwise casting to roughly halve weight memory, and torchao MXFP8/NVFP4 quantization that, combined with torch.compile, lands ~1.26x (MXFP8) to ~1.68x (NVFP4) on FLUX/Qwen-Image on Blackwell. It runs on Blackwell wherever your PyTorch does. On Windows the gotcha is the same torch/sm_120 pinning as everything else, plus torch.compile on Windows is less battle-tested than on Linux (Triton-Windows required). For a ComfyUI-centric studio it's the secondary, scripting-and-training tool — not your primary inference path.

### Nunchaku (SVDQuant 4-bit kernels) · `recommended` · stable
Nunchaku is the single biggest speed+VRAM lever for a 32 GB Blackwell card. It runs SVDQuant 4-bit diffusion (absorbs activation outliers into a low-rank branch, so 4-bit quality stays near 16-bit) and on the RTX 5090 uses native NVFP4 tensor-core kernels for ~3x throughput and ~3.6x VRAM reduction on FLUX.1-dev — that freed headroom is what lets you stack LoRAs, ControlNets, and higher batch sizes on one card. Supports FLUX.1 (dev/schnell/Krea/Kontext/tools), Qwen-Image + Qwen-Image-Edit, SANA, Z-Image-Turbo, with native ComfyUI nodes and seamless LoRA as of v1.2.x (compatible with ComfyUI 0.7). On Blackwell prefer the NVFP4 checkpoints over INT4 for quality; NVFP4 paths want CUDA 12.8+/13. Gotcha: it's a quant-runtime, not a general engine — you load Nunchaku-format models, so coverage is limited to the families they've quantized (no SDXL UNet, no Wan video yet).

### SageAttention · `recommended` · stable

The CUDA-kernel path has had instability on some 50-series; the Triton fallback always works but may be slower. NEVER pip install xformers alongside it on a Blackwell env.
