### Instructor · `recommended` · production
The application-layer standard for typed LLM outputs (MIT, v1.15.1, ~3M downloads/month), built on Pydantic and provider-agnostic across OpenAI/Anthropic/Google/Mistral/Cohere/Groq/DeepSeek and local Ollama (15+ providers, with TS/Go/Ruby ports). Crucially it is NOT a token-level constrained decoder: it sends the request, validates the returned JSON against a Pydantic model client-side, and on failure automatically re-asks the model with the validation error attached (Tenacity-backed max_retries). That makes it complementary, not competitive, with XGrammar/GBNF — it is the layer that catches the things grammars cannot express (field-level enums, numeric ranges, cross-field invariants, referential checks against your game's registries) and returns a ready-to-use typed Python object. On this rig it is the right wrapper for the LLM-crew's Python tooling: point it at local Ollama with `mode=JSON` (or pair it with Ollama's own `format` schema so attempt-1 is already constrained and retries are rare), and it slots cleanly into the second tier of an EXTERNAL_VERIFIER stack. Zero GPU involvement; pure client-side.

### XGrammar (XGrammar-2) · `recommended` · production
The de-facto default structured-output backend across the serving ecosystem (vLLM, SGLang, TensorRT-LLM, MLC-LLM all ship it as default). It compiles a JSON-schema/regex/EBNF grammar into an adaptive token-mask cache driven by an Earley parser; the per-step mask is computed CPU-side (<40us/token) so it is accelerator- and model-agnostic and inherits Blackwell support directly from the host engine. XGrammar-2 (May 2026) is the generation to use: it adds Structural Tag (a composable JSON DSL that uniformly expresses OpenAI harmony, tool calls, and reasoning channels), TagDispatch for dynamic dispatch, and a Cross-Grammar Cache that reuses substructure compilation across grammars — the reason it claims ~80x faster grammar compile vs v1 and >6x faster tool-calling compile vs prior SOTA. For an LLM-crew doing high-volume tool-calls with many distinct short grammars, that compile amortization is the single biggest win in the lane. Ships native Windows x86-64 wheels (CPython 3.9-3.14), Apache-2.0.

### llama.cpp GBNF grammars + JSON-schema · `recommended` · production
The constrained-decoding capability built directly into the llama.cpp runtime you already use for local GGUF inference — no extra package, fully Windows-native, the local-first default for this rig. GBNF (GGML BNF) is a low-level grammar format that hard-constrains the sampler to valid productions; llama.cpp also ships json_schema_to_grammar, which auto-converts a JSON-schema into GBNF and is wired into llama-server's OpenAI-compatible `response_format`, so you get guided JSON from a plain HTTP call. Two caveats matter: the schema->GBNF converter supports only a SUBSET of JSON-schema (no full $ref / if-then-else, by design — those features are deemed too hallucination-prone), and the schema is NOT injected into the prompt, so you must also describe the shape in the system prompt or the model fills valid-but-wrong values. For raw non-JSON DSLs (custom game-data formats, enum menus, restricted dialogue) hand-authored GBNF is the most direct tool in the lane. GPU side follows the wave-1/2 rules (cu128 build, CUDA graphs, never eager); the grammar layer is orthogonal to those.
- **Dev:** ggml-org (Georgi Gerganov and contributors) · **Type:** runtime (built-in constrained decoding) · **Lang:** C/C++ · **Version:** Tracks llama.cpp master (continuous rolling releases, b6xxx-era tags) · **Released:** Continuous; GBNF + json_schema_to_grammar mature and stable as of 2026-06
- **Platforms:** Windows (native), Linux, macOS — anywhere llama.cpp builds · **Accelerators:** CUDA (sm_120/Blackwell via cu128 build), Vulkan, CPU, Metal; grammar enforcement itself is CPU-side and accelerator-agnostic · **Formats:** GGUF (the native llama.cpp quant format) — the most Windows-friendly local format
- **Blackwell/Win-ready:** yes · **Optimizes for:** Zero-dependency, fully-local, Windows-native grammar constraint and JSON-schema enforcement directly inside llama-server's OpenAI-compatible response_format. The local-first default. · **Multi-GPU:** llama.cpp supports multi-GPU split (--split-mode) but single RTX 5090 is the target; grammar layer is single-process CPU · **Fit:** rig 5/5 · studio 4/5
- **License:** MIT — commercial: **yes**. MIT — fully permissive, no restrictions. The grammar engine is built into the binary you already run for local inference; no separate dependency.
- **Best for:** Fully-local, no-Python-deps structured JSON from GGUF models on Windows (llama-server response_format) (local-json, fit 5) ; Hand-authored GBNF grammars for non-JSON DSLs (custom game-data formats, restricted dialogue, emoji-only, enum menus) (custom-grammar, fit 5) ; Offline / air-gapped artifact generation with zero cloud dependency (offline, fit 5) ; Tool-calling on local models (subset JSON-schema; less ergonomic than XGrammar Structural Tag) (tool-calling, fit 3)

### Outlines (+ outlines-core) · `runner-up` · production
The original FSM-based structured-generation library, now maintained by dottxt and notable for a unified Python API (generate.json / generate.regex / generate.cfg) that runs the SAME code across transformers, llama.cpp, vLLM, Ollama, and (v1.2.10+) MLX via LM Studio — plus OpenAI/Gemini APIs. Its compilation step builds a finite-state-machine index mapping the vocabulary to state transitions for a given regex (derived from a JSON-schema); since v0.1, that core was rewritten in Rust as the separate outlines-core package (Apache-2.0, v0.2.14), co-developed with Hugging Face, cutting index-build time ~2x and adding only microseconds of per-token latency. On this rig its best role is a backend-portable Python library wrapping local llama.cpp/transformers when you want to swap engines without rewriting call sites. As an SGLang grammar backend it covers JSON-schema + regex but NOT EBNF (XGrammar and llguidance do), and XGrammar generally wins tool-calling-fan-out throughput — hence runner-up rather than the default here.

### llguidance · `situational` · production
A Rust Earley-parser constrained-decoding engine (MIT, v1.0.0) that is the grammar engine underneath the Microsoft guidance library and was publicly credited by OpenAI as foundational to their Structured Outputs feature (May 2025) — so it is battle-tested at scale. It enforces full context-free grammars (EBNF), JSON-schema, and regex with ~50us/token CPU time on a 128k tokenizer and negligible startup, and its standout characteristic is fast time-to-first-token even on complex or dynamic grammars (vs XGrammar's edge on reused-grammar per-token latency). It is broadly integrated — vLLM v0.8.2+ (the `guidance` guided-decoding backend), SGLang v0.4.4+ (`--grammar-backend llguidance`), guidance v0.2.0+, llama.cpp, mistral.rs, onnxruntime-genai. On this rig it is situational: reach for it inside vLLM/SGLang when a JSON-schema edge case breaks XGrammar, when you need full EBNF, or for multi-tenant/one-off-grammar workloads where XGrammar's cache gives no benefit. Windows is buildable from source (Rust 1.87+) but wheels are less turnkey than XGrammar's; in practice its platform equals the host engine's.

### Microsoft guidance · `situational` · mature
A Python programming-DSL for controlled generation (MIT, v0.3.2, community-governed under guidance-ai) that lets you interleave fixed text, generated slots, and constrained choices in one program — select() over a fixed option set, gen(regex=...), and full CFG — with token-healing to avoid tokenizer-boundary artifacts. Under the hood it runs on the llguidance Rust engine (~50us/token), and 2026 builds added speculative execution / speculative-decoding integration for ~2x speedups on real-time use. It supports Transformers, llama.cpp, and OpenAI backends and installs cleanly on Windows (pure-Python front end). Its distinguishing strength is expressiveness: when generation is genuinely multi-step (templated dialogue, decision trees, menu-then-fill flows) the program-as-template paradigm is far cleaner than emitting a monolithic schema. The trade-off is weight — for a single guided_json call or a plain tool-call, XGrammar inside the serving engine is simpler and faster, which is why it is situational on this rig rather than a default. Reach for it when the control flow IS the structure.
- **Dev:** guidance-ai (originated Microsoft Research) · **Type:** library / programming-DSL for controlled generation · **Lang:** Python (llguidance Rust engine underneath) · **Version:** 0.3.2 · **Released:** 2026-03-18
- **Platforms:** Windows, Linux, macOS (pure-Python front end; llguidance Rust backend) · **Accelerators:** Backend-dependent; constraint compute is CPU-side via llguidance · **Formats:** Transformers, llama.cpp, OpenAI, and other backends

### LM Format Enforcer · `situational` · stable
A pure-Python token-filtering logits processor (MIT, v0.11.3) that enforces JSON-schema / JSON / regex by masking, at each timestep, the tokens that would break the target format. Its signature design choice is that it deliberately leaves whitespace and indentation under the model's control — only format-critical tokens are filtered — which the author argues reduces the quality degradation that aggressive constraint can cause. It has broad framework reach: HuggingFace transformers, llama-cpp-python, vLLM, ExLlamaV2, plus LangChain and LlamaIndex integrations, with batching, beam-search, and streaming support. Installs on Windows (pure Python). ### Jsonformer · `legacy` · legacy
An early (2023) constrained-JSON library whose clever core idea was to NOT make the model generate the fixed structural tokens at all — it hard-fills the braces, keys, commas and quotes itself and only delegates the content-value tokens to the HuggingFace model, which made it both faster and tamper-proof for a known schema. The technique was influential but is now fully subsumed: XGrammar, Outlines, and llguidance are all faster, support the full JSON-schema/regex/CFG surface (Jsonformer covers only a subset), and integrate with serving engines, whereas Jsonformer is HuggingFace-transformers-only. The repository is effectively unmaintained (last commit 2023-05-30; despite third-party trackers calling it 'active', the main branch has been static for ~3 years). On this rig in 2026 it has no production role — included for completeness and historical reference; blackwell-readiness is unknown/moot since you would not deploy it.
