### Emitted transactions (autonomous on-ledger actions) · `concept` · ● live ✓
Emitted transactions are brand-new transactions a hook creates and emits() into the next ledger, letting hooks make ledger changes (e.g. send a payment, mint a URIToken) beyond merely accepting/rejecting the originating transaction. The hook must present a fully serialized, canonically-formed transaction (no rewriting by xahaud), with signature replaced by an EmitDetails block (nonce, parent txn id, generation, burden). A cbak() callback fires when the emitted transaction is accepted (or on failure). This is what enables autonomous, reactive on-ledger logic.

### Guard / weak-guard (_g) and bounded execution · `pattern` · ● live ✓
Because Hooks are deliberately not Turing-complete, every loop must be guarded: a _g(guard_id, maxiter) call placed as the first branch after the loop instruction declares the maximum iterations the developer promises. If exceeded at runtime the hook auto-rolls back with GUARD_VIOLATION. The ledger uses these guards to compute the worst-case instruction count BEFORE execution, which is the basis for the deterministic execution fee. This is the mechanism that makes hook execution time and cost predictable and DoS-resistant.
- **Chain:** xahau · **Amendment:** Hooks · **Enabled:** 2023-10-31 · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** ["_g(id, maxiter) macro", "GUARD_VIOLATION rollback", "worst-case instruction count = fee basis", "no arbitrary/unbounded loops allowed", "static analysis at SetHook time rejects unguarded loops"]
- **Gotchas:** ["A SetHook with an unguarded loop is rejected outright — you cannot deploy it.", "maxiter is a hard promise; underestimating it causes runtime GUARD_VIOLATION and a fully rolled-back hook (the transaction the hook guarded can be blocked).", "Heavy looping inflates worst-case instruction count and therefore the fee, even if the average run is cheap — fees are charged on the worst case, not the actual path."]

### Hook API (C primitives / function categories) · `library` · ● live ✓
The Hook API is the set of host functions a hook calls to read the originating transaction, manage state, do math, and emit transactions. Categories include control (accept/rollback), guard (_g and guard), state (state, state_set, state_foreign, state_foreign_set), originating-transaction inspection (otxn_*), slot manipulation, XFL float math (the ledger's 64-bit decimal format), emit/etxn for new transactions, and util/hook context (hook_account, hook_param). It is a low-level C ABI; higher-level SDKs (C macros, Rust, JS) wrap it.

### Hook State (namespaced key-value storage) · `concept` · ● live ✓
Hook State is a per-account key-value store that persists data between hook executions. Keys are always 32 bytes (256-bit) and values are variable length up to a validator-voted maximum (256 bytes at time of writing). A 32-byte namespace scopes state so multiple hooks on one account don't clobber each other, and the same key under different namespaces refers to different objects. State consumes owner reserve on a scale (scale 1 = 1 reserve per up-to-256-byte entry; scale 4 = 4 reserve per up-to-1024 bytes).

### Hooks (WASM smart-contract layer) · `concept` · ● live ✓
Hooks are small, efficient WebAssembly modules attached to a Xahau account that execute BEFORE and/or AFTER transactions affect that account, letting the account accept, reject, or augment activity with custom logic. They are intentionally NOT Turing-complete — arbitrary unbounded loops are forbidden — which keeps worst-case execution predictable and priceable. Hooks are the native smart-contract primitive of Xahau and have been live on Xahau mainnet since the 2023-10-31 launch. They do NOT exist on XRPL mainnet; that chain has no native programmability layer.

### SetHook transaction · `transaction` · ● live ✓

### Xahau vs XRPL mainnet (when to choose Xahau) · `concept` · ● live ✓
Xahau is a distinct Layer-1 network forked from XRPL Core (xrpld), not a Layer-2 of XRPL. ### Emitted transactions — emit() / etxn_reserve / burden & generation · `pattern` · ● live ✓
Hooks can autonomously originate NEW transactions via emit(), entered into consensus for the next ledger. A hook must first call etxn_reserve(n) to declare how many it will emit, then build the transaction (the PREPARE macro fills boilerplate) including an EmitDetails block instead of a signature; emitted txns have Sequence 0 and target the next ledger. Anti-fork-bomb controls: each emitted txn carries a generation (sfEmitGeneration, the chain depth, capped at 10) and a burden multiplier that raises cost exponentially for cascading emissions; FirstLedgerSequence must be the next ledger and LastLedgerSequence is capped ~5 ledgers ahead.

### Hook chaining (up to 10 hooks per account) · `pattern` · ● live ✓
An account can install a chain of up to 10 hooks at positions 0–9, executed in order; the chain succeeds only if every installed hook reaches accept(). Blank positions are skipped and treated as successful, so chains can be sparse. At runtime a hook can introspect and steer the chain: hook_pos() (own position), hook_skip() (disable/re-enable downstream hooks), hook_param_set() (pass parameters to later hooks), and hook_again() to request a second WEAK execution after the transaction applies. This enforces the 'each hook does one thing well' composition model.
- **Chain:** xahau · **Amendment:** Hooks · **Enabled:** 2023-10-30 · **Maturity:** production · **Use:** recommended
- **Key fields / API:** ["10 positions (0–9)", "all must accept() to succeed", "blank positions skipped", "hook_pos()", "hook_skip()", "hook_param_set()", "hook_again()"]
- **Gotchas:** Any single hook calling rollback() (or erroring) fails the WHOLE chain and the transaction — composition is AND, not OR. Both the sending and receiving account chains must succeed for a transaction between them to proceed. hook_again() schedules an extra weak pass that CANNOT rollback, so post-application logic there cannot undo the transaction.

### Hook State (key-value store, namespaces, foreign reads) · `concept` · ● live ✓
Each account has a persistent key-value store accessed via state (read), state_set (write), and the cross-account state_foreign / state_foreign_set. Keys are always 32 bytes (a 256-bit integer) and values are variable length up to a validator-voted maximum — currently 256 bytes on mainnet (state_foreign_set was historically capped at 128 bytes on testnet). Namespaces (a 32-byte code) partition state so two hooks on the same account never collide; any hook may READ any other hook's state but only the owning hook may WRITE its own.

Foreign state is read-only across accounts — there is no cross-account write primitive.

### HookOn bitmap (active-low transaction-type trigger mask) · `concept` · ● live ✓
HookOn is a 256-bit field where each bit corresponds to a transaction-type code and decides whether the hook fires on that type. It uses active-LOW (inverted) semantics: a cleared bit means 'fire on this type'. Practically this means a hook configured to run on everything has most bits set the way you would not naively expect, and you flip specific bits to opt OUT of types. The sibling HookCanEmit field (added later) uses the same active-low scheme to whitelist which transaction types the hook is permitted to emit; if absent the hook may emit anything including SetHook.
- **Chain:** xahau · **Amendment:** Hooks · **Enabled:** 2023-10-30 · **Maturity:** production · **Use:** recommended
- **Key fields / API:** ["HookOn (256-bit / Hash256)", "active-low bit per transaction type code", "HookCanEmit (same active-low scheme)"]
- **Gotchas:** The inversion trips up nearly every newcomer — you do NOT set the bit for the type you want; you clear it. Toolkits expose helpers (e.g. invertHookOn / hooksdk constants) precisely to avoid hand-computing the mask. Getting HookOn wrong silently means the hook never runs on the transactions you cared about (no error — it just isn't triggered), so always verify against an explorer execution record.

### Hooks execution model (Layer-1 WASM transaction interceptor) · `concept` · ● live ✓
Hooks are small WebAssembly modules installed on a Xahau account that execute as part of consensus whenever a transaction touches that account. Because they run BEFORE the originating transaction is applied (for strong stakeholders), a hook can rollback and completely block a transaction — this Layer-1 'decide if a transaction is allowed in the first place' semantics is the core differentiator from EVM/L2 smart contracts that only react after the fact. The hook entry points are hook(uint32_t reserved) and the callback cbak(uint32_t); a hook terminates with accept() (allow), rollback() (reject + revert), or errors out.
- **Chain:** xahau · **Amendment:** Hooks · **Enabled:** 2023-10-30 · **Maturity:** production · **Use:** recommended
- **Key fields / API:** ["hook()", "cbak()", "accept()", "rollback()", "WebAssembly bytecode", "reserved param (0=strong, 1=weak, 2=weak-after-strong)"]
- **Gotchas:** A hook is NOT general-purpose compute: it cannot make network calls, cannot loop without a guard, and has a statically-bounded worst-case execution. Reverting via rollback() reverts the whole originating transaction for strong stakeholders only; weak-executed hooks run after application and cannot block. Errors (not just rollback) also fail the hook — there is no silent failure.

### Loop guards — _g() / GUARD macro (bounded-execution requirement) · `pattern` · ● live ✓
Hooks are deliberately non-Turing-complete: every loop must declare an iteration ceiling so the ledger can compute worst-case execution cost before running. The guard is _g(uint32_t id, uint32_t maxiter), wrapped by #define GUARD(maxiter) _g(__LINE__, (maxiter)+1) (the +1 covers the extra hit before the loop condition check). The first branch instruction after a loop MUST be a guard call, guards must use numeric literals (no runtime values), and nested-loop guards multiply (outer 3 × inner 5 → inner GUARD(15)). Exceeding the promise rolls the hook back with GUARD_VIOLATION.
- **Chain:** xahau · **Amendment:** Hooks · **Enabled:** 2023-10-30 · **Maturity:** production · **Use:** recommended
- **Key fields / API:** ["_g(id, maxiter)", "GUARD(maxiter) = _g(__LINE__, maxiter+1)", "__LINE__ as guard id", "numeric-literal maxiter only", "nested loops multiply", "GUARD_VIOLATION rollback"]
- **Gotchas:** An unguarded loop is rejected at compile/validation time by hook-cleaner — it will not even install. maxiter is a literal promise, NOT a runtime bound: you cannot guard with a variable, so data-driven iteration counts must be capped to a constant worst case (which inflates the fee). Forgetting that nested guards multiply is the classic source of silent under-budgeting and a runtime GUARD_VIOLATION.

- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed | net-check: mainnet-live | currency=current | Loop guards with _g()/GUARD macro for bounded execution are enforced on Xahau mainnet.
- **Sources:** [Loops and Guarding (XRPL Hooks)](https://xrpl-hooks.readme.io/docs/loops-and-guarding) — Signature is int32_t _g(uint32_t id, uint32_t maxiter); GUARD(maxiter) is defined as _g(__LINE__, (maxiter)+1); a _g call must be the first branch after a loop, maxiter must be a numeric literal, nested loops multiply, and violation triggers GUARD_VIOLATION rollback. ; [Hooks overview — guards bound execution (Xahau Docs)](https://xahau.network/docs/hooks/) — Xahau Hooks use guards so maximum execution time is well-bounded and known ahead of time, which is what makes the deterministic fee model possible.

### Transactional stakeholders — strong vs weak execution · `concept` · ● live ✓
A Transactional Stakeholder (TSH) is any account affected by a transaction, and the model gives each the right to run hooks. STRONG TSHes (e.g. a Payment destination, a CheckCreate destination) have hooks executed BEFORE the transaction applies and can rollback() to block it; the originating transaction pays their fees. WEAK TSHes (e.g. rippled-through accounts, crossed-offer counterparties, a TrustSet issuer) execute AFTER application and cannot block — they must opt in via the asfTshCollect flag and pay through the collect-call mechanism. The reserved param tells the hook which context it is in (0 strong, 1 weak, 2 weak-after-strong).

- **Gotchas:** Whether your account is a STRONG or WEAK stakeholder for a given transaction type is fixed by protocol, not by you — and only strong stakeholders can actually block. If you need to enforce a rule and your account is merely a weak TSH for that transaction type, you cannot reject it; design around the strong-TSH positions. Weak execution requires the asfTshCollect flag set in advance or the weak hooks simply will not run.

### Hook fees & execution metering · `concept` · ● live ✓
Hook execution is metered at roughly 1 drop of XAH per WebAssembly instruction in the WORST-CASE execution path (including any cbak callback), so a small but loop-heavy hook can attract high runtime fees. Strong hooks must be paid for by the originator of the transaction; an account can carry up to 4 strong hooks on the sending side and 4 on the receiving side. Combined with guard-derived worst-case counts, this makes fees deterministic and computable before submission — but it means cost is driven by the ceiling, not the average path.

### Hook fees & resource limits (deterministic up-front pricing) · `concept` · ● live ✓

### Hook accept/rollback as a pre-transaction economy gate · `concept` · ● live ✓
The foundational primitive every game-economy Hook is built on: a Hook installed on an account runs before and/or after each transaction and returns either accept() (let it through) or rollback() (block it, reverting all effects). Because the Hook executes inside consensus on Layer 1, it can VETO a move before any value changes hands — block a disallowed transfer, reject an underpriced trade, refuse a payment that would break an invariant. This is categorically different from an EVM/L2 contract, which can only react after the originating transaction has already settled. A Hook can sit on the source account, the destination account, or both, and each can independently rollback. This is the lever that makes on-chain economy rules ENFORCEABLE rather than merely observable.
- **Chain:** xahau · **Amendment:** Hooks · **Maturity:** production · **Use:** live
- **Key fields / API:** Hook entry function hook(uint32_t reserved) returns via accept(msg,len,code) or rollback(msg,len,code); HookOn bitmask selects which transaction types trigger the Hook; rollback() reverts ALL ledger effects of the triggering transaction including emitted txns; the originating account still pays the Hook execution fee even on rollback (anti-spam); a Hook on the destination account can block INBOUND transfers (e.g. refuse soulbound items), a Hook on the source blocks OUTBOUND.
- **Gotchas:** rollback() is the ONLY way to block — there is no 'silently drop'; a blocked transaction still consumes the sender's fee, so design error messages/codes to be meaningful. A Hook only fires on transaction types enabled in HookOn; forgetting to set the right bit means the rule silently never runs. Hooks on an account apply to ALL counterparties uniformly — per-counterparty logic must be implemented in code + state, not by the trigger mechanism. The pre/after distinction matters: 'weak' (after) executions cannot rollback the originating txn.

### Hook-emitted reward distribution (autonomous payouts) · `pattern` · ● live ✓

### Hooks vs EVM sidechain vs native objects — choosing the game-logic layer · `concept` · ● live ✓
Three places to put game logic, and the choice is load-bearing. ### On-chain invariant / anti-cheat checks at the ledger layer · `pattern` · ● live ✓
Because a Hook runs inside consensus and can rollback(), it can enforce economy invariants that a client or off-chain server could be tricked into violating — the on-ledger anti-cheat layer. Patterns: refuse a sell if the seller doesn't actually own the item (verify via state or ledger objects), reject a craft that would mint more than a supply cap (check a counter in Hook State), block a transfer that would push a balance negative or above a per-account holding limit, refuse a move that doesn't match a committed game-state hash. The check is deterministic and runs identically on every validator, so there is no trusted server to compromise. This does NOT validate off-chain gameplay (the Hook can't see your render loop) — it validates the ON-CHAIN consequences, which is exactly where value-affecting cheats land.

- **Gotchas:** A Hook only sees what is ON the ledger or in its state — it cannot validate physics, hidden information, or anything the client computed off-chain; treat it as a value-integrity gate, not a full game referee. State writes are limited to your OWN account; cross-account invariants need either state_foreign reads or HookGrants. 256-byte value cap means large game states must be hashed/sharded, not stored whole. Every invariant loop must be GUARD()-ed with a compile-time max — you cannot iterate an unbounded player list inside one execution. ### On-chain randomness via deterministic nonce (and why true RNG is impossible) · `concept` · ● live ✓
There is NO true randomness available to a Hook, by design: every validator must compute the identical result for consensus, so a real RNG would fork the network. What exists is a DETERMINISTIC pseudo-random nonce — etxn_nonce() — seeded by the last-closed ledger hash plus the Hook's account, advanced each call up to a max-call limit. It exists primarily to give emitted transactions distinct hashes, but it's the same value people reach for when they want 'randomness' for loot rolls or matchmaking. The critical caveat for game designers: the seed (last ledger hash) is PUBLIC and can be observed before a transaction is included, and validators have some influence over ledger contents — so anything financially meaningful (rare-drop gacha, jackpots) is manipulable/predictable and must NOT rely on this for fairness. For high-stakes randomness, use a commit-reveal scheme or an external verifiable randomness oracle, not the on-chain nonce alone.
- **Chain:** xahau · **Amendment:** Hooks · **Maturity:** production · **Use:** live
- **Key fields / API:** etxn_nonce() returns a deterministic 32-byte nonce; PRNG seed = last-closed-ledger hash + Hook account; advanced per call, capped at a max number of calls per execution; ledger_last_hash exposed as deterministic seed material; for fairness use commit-reveal (commit a hashed secret one ledger, reveal next) or an off-chain VRF/oracle providing externally verifiable entropy.
- **Gotchas:** DO NOT use the deterministic nonce for anything an adversary profits from predicting — the seed is observable and partially influenceable; treat it as 'unique-ish', not 'fair'. The nonce has a per-execution call cap; you cannot generate unlimited draws. Commit-reveal adds latency (at least one ledger between commit and reveal) and a griefing surface (a player can refuse to reveal an unfavorable outcome — design forfeiture). True VRF/oracle randomness means an external dependency and trust assumptions, which partly defeats the point of L1 enforcement. Many naive 'on-chain RNG' designs from other chains are insecure for the same reason and should not be copied.

### Shared allowlist / blocklist registries via foreign state + HookGrants · `pattern` · ● live ✓
A Hook can READ another account's Hook State (state_foreign), so one account can publish a list and MANY accounts' Hooks can enforce it without each maintaining a copy — the documented Firewall Hook does this, pulling an updated blocklist from a Hook on a separate registry account to reject scam/suspicious transactions automatically. Inverted, it's an allowlist: only let transfers proceed to/from accounts present in a curated registry (whitelisted players, KYC-passed wallets, partner marketplaces). HookGrants is the complement: a registry Hook can authorize specific OTHER accounts to WRITE into its state, enabling a moderated, multi-writer registry (e.g. several studio admin accounts can add/remove entries) while normal players cannot.
- **Chain:** xahau · **Amendment:** Hooks · **Maturity:** production · **Use:** live
- **Key fields / API:** state_foreign(key, namespace, foreign_account) reads the registry account's state read-only; HookGrants array authorizes named accounts to write into THIS Hook's state (set via SetHook Update); namespace isolates the registry's storage; 32-byte keys map naturally to account-id-derived keys for O(1) membership tests; rollback() when an actor is absent from an allowlist or present on a blocklist; the registry is one account, enforcing Hooks live on many accounts.
- **Gotchas:** Foreign state is READ-ONLY — enforcers can check the list but only the owner (or HookGrant-authorized accounts) can change it; key compromise of the registry account is a single point of failure for every enforcer that trusts it. There is no native 'iterate all entries' — model membership as direct key lookups, not scans, because loops are GUARD-bounded. A 256-byte value holds limited data per entry; large lists are many keys, and namespace reset clears at most 512 entries per transaction. Allowlist enforcement only covers ON-CHAIN actions; it can't stop off-chain account sharing.

### Time / rate limiting actions by ledger sequence · `pattern` · ● live ✓
Hooks have no wall-clock (it is non-deterministic), so 'time' for any cooldown, cadence, or rate limit is the ledger sequence number / last-closed-ledger info, which is part of consensus and identical on every validator. The pattern: store the ledger index of the last allowed action in Hook State, and on the next trigger compare the current ledger sequence — reject (rollback) if not enough ledgers have elapsed, otherwise accept and overwrite the stored index. This implements cooldowns (one action per ~N ledgers), token-bucket throttles, daily-claim caps, and auction/round timers entirely on-ledger. It is the timing backbone shared by the vesting and faucet patterns.
- **Chain:** xahau · **Amendment:** Hooks · **Maturity:** production · **Use:** live
- **Key fields / API:** Current ledger sequence read from ledger/transaction context (ledger_last_time / ledger_seq family); last-action ledger index stored per actor in Hook State (key derived from actor account id); delta = current_seq - stored_seq compared against an interval parameter; token-bucket = stored (tokens, last-refill-ledger) tuple refilled proportional to elapsed ledgers; rollback() with a descriptive code when rate exceeded.
- **Gotchas:** Ledger close interval is roughly a few seconds but NOT exactly constant — never assume a fixed seconds-per-ledger; express limits in ledgers and document the approximate wall-time. Per-actor counters mean one state entry per active actor — for a huge player base this grows state; consider expiring stale entries. You cannot use the network clock or any external time oracle. Reading the wrong context field (closing vs last-closed ledger) introduces off-by-one timing bugs that are subtle to catch. Because it's deterministic, every validator agrees — but so does every griefer, who can predict exactly when a window opens.

### What Hooks CANNOT do — the deliberate non-Turing-complete envelope · `concept` · ● live ✓
Hooks are intentionally constrained, and knowing the walls prevents designing a game system that can't ship. Hard limits as of mid-2026: NOT Turing-complete (no unbounded computation); every loop/branch must be GUARD()-ed with a compile-time-known max iteration count (no while-true); ~64 KiB linear memory; no wall-clock, no real RNG, no network/IO, no calls except the Hook API; state values capped at 256 bytes, keys 32 bytes; at most 4 Hooks chain per account; emitted-transaction chains capped at 10 generations; fees are pre-computed from the worst-case duration. The flip side is what you GAIN: predictable bounded fees (no gas blowups or out-of-gas reverts mid-state), guaranteed termination (no halting-problem DoS), deterministic replay, and tiny attack surface. Anything needing big in-contract state, arbitrary loops, complex math libraries, or composable DeFi-style call graphs is OUT of scope — that's the EVM sidechain's job.
- **Chain:** xahau · **Amendment:** Hooks · **Maturity:** production · **Use:** live
- **Key fields / API:** GUARD(maxiter) required before every back-edge; ~64 KiB WASM linear memory; non-Turing-complete by design; HookState value ≤256 bytes, key =32 bytes; ≤4 Hooks per account (positions 0-3); etxn_generation ≤10; fee proportional to MAX computed execution duration, paid by caller even on rollback; only the Hook API is callable (no syscalls, no floats — use XFL); no contract-to-contract synchronous calls (composition is via emitted txns + foreign-state reads, asynchronously).
- **Gotchas:** The single biggest trap is assuming EVM mental models port over: there are no synchronous cross-contract calls, no big mappings, no arbitrary loops, no msg.sender-style reentrancy (composition is async via emit). 256-byte state forces hashing/sharding for anything large. GUARD makes some algorithms (sorting an arbitrary list, unbounded search) simply unimplementable in one execution. Porting a Solidity game contract 1:1 will fail — redesign around accept/rollback + state + emit. JSHooks may relax the authoring ergonomics but NOT the consensus-level limits (still bounded, deterministic).
- **Build-focus tracks:** [game-economies](track-game-economies.md), [identity-compliance](track-identity-compliance.md), [payments](track-payments.md)
- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed | net-check: live on Xahau mainnet (design constraints active) | currency=current | Hooks are deliberately non-Turing-complete with bounded execution constraints on Xahau mainnet.
- **Sources:** [Hooks: Introduction — not Turing-complete (Xahau Docs)](https://github.com/Xahau/Xahau-Docs/blob/main/concepts/introduction/README.md) — Hooks are deliberately NOT Turing-complete; the authors argue Turing-completeness is inappropriate for smart contracts. ; [Hooked #2: Hooks & Security (Wietse Wind, DEV)](https://dev.to/wietse/hooked-2-hooks-security-smart-contracts-on-the-xrp-ledger-83e) — Hooks are limited to ~64 KiB pre-allocated memory, cannot access external processes, can only invoke the Hook API, and the fee equals the maximum computed execution duration; guards bound every loop.

### JSHooks — JavaScript Hooks authoring (alpha, mid-2026) · `concept` · ○ devnet ✓
JSHooks lets Hooks be written in plain JavaScript (and TypeScript, compiled to JS) instead of C/Rust-to-WASM, by running a modified QuickJS engine compiled to WASM as the execution runtime. For a small studio this is a big velocity unlock — gameplay/economy logic in a familiar language, faster iteration, lower the bar for the crew. As of mid-2026 it is ALPHA: there is a dedicated JSHooks testnet with a live explorer, the jshooks-alpha toolkit ('expect dragons'), and the QuickJS runtime build, but it is NOT enabled on Xahau mainnet. The same consensus-level constraints still apply (deterministic, bounded, no real RNG/time) — JSHooks changes the authoring language, not the execution envelope. For anything holding real value today, ship compiled WASM (C, or Rust via hooks-rs); treat JSHooks as a watch-this-space prototyping path.
- **Chain:** xahau · **Amendment:** JSHooks (proposed amendment) · **Maturity:** experimental · **Use:** testnet
- **Key fields / API:** Modified QuickJS runtime compiled to WASM (qjsc.wasm) executes the JS; toolkit compiles .js/.mjs/.cjs/.ts to SetHook-ready hook code (TS → JS first); dedicated JSHooks testnet + XRPLWin JSHooks explorer + JSHook Builder (XWCode); same Hook API surface (accept/rollback/state/emit) exposed to JS; consensus constraints unchanged (deterministic, GUARD-equivalent bounding, no clock/RNG).
- **Gotchas:** NOT mainnet — do not architect a shipping game's value layer on JSHooks until the amendment activates on Xahau mainnet; it can change. 'Expect dragons' is the maintainers' own framing — alpha bugs, breaking changes, incomplete API parity. The QuickJS runtime adds overhead vs hand-written WASM; fee/performance characteristics may differ from compiled hooks. JS's dynamic nature does not exempt you from determinism — non-deterministic JS (Date.now, Math.random) is unavailable/forbidden. Production today = WASM (C / Rust hooks-rs); use JSHooks for prototyping and to track the roadmap.
