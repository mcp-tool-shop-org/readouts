### Arweave permanent storage (service) · `service` · · n/a ✓
Arweave is the pay-once, store-forever alternative to IPFS for XRPL NFT assets. Unlike IPFS, permanence is built into the protocol: you make a single upfront payment (in AR), and an endowment model funds ongoing replication on the 'blockweave' indefinitely -- no recurring pinning. Each upload gets a permanent, immutable transaction ID; the asset is referenced by an ar://<txid> or an Arweave gateway HTTPS URL, which (like IPFS CIDs) is effectively content-addressed and tamper-evident. As of 2026, storage runs roughly USD 0.002-0.005 per MB, so a few-MB image + tiny JSON is on the order of cents for permanent hosting. The classic tradeoff vs IPFS: Arweave has a higher per-byte upfront cost but ZERO ongoing operational burden and the strongest permanence guarantee, making it the better fit for a game's flagship/canonical immutable assets you must guarantee outlive any company. The common production answer is hybrid: Arweave (or pinned IPFS) for cold permanent originals, a fast CDN/gateway cache for hot delivery.
- **Chain:** off-ledger · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** {"permanence": "protocol-level -- pay once, stored indefinitely via endowment model", "addressing": "permanent immutable transaction ID; ar://<txid> or gateway HTTPS URL", "payment": "single upfront fee in AR (no recurring pinning)", "cost_2026": "~USD 0.002-0.005 / MB (a few-MB asset = cents, permanent)", "tamper_evidence": "txid is derived from content -- effectively content-addressed", "tooling": "ArDrive / Turbo / Bundlr-style uploaders; gateways for HTTP delivery", "best_use": "canonical immutable game originals; cold half of a hybrid setup"}
- **Gotchas:** Permanence is also rigidity: you CANNOT delete or edit an Arweave upload -- a leaked or wrong asset is permanent, so vet before uploading. Higher upfront per-byte cost than starting an IPFS pin, so for huge/churning asset libraries the economics favor IPFS until you're storing for years/decades. ar:// is not natively resolved by most wallets/marketplaces -- you typically put the gateway HTTPS URL on-chain, which reintroduces a gateway dependency for display (the data itself stays permanent). Paying in AR adds a token-acquisition step vs a fiat IPFS subscription. Gateway latency still warrants a CDN cache for grid-heavy game UIs. Permanence guards the BYTES, not the link semantics -- a dNFT can still be modified to point away from a permanent asset.

### At-scale minting throughput — Tickets & sequence pipelining · `pattern` · ● live
Without atomic batches (the Batch/XLS-56d amendment is NOT enabled on mainnet as of mid-2026), high-volume minting relies on Tickets to submit many NFTokenMint transactions in parallel instead of strictly one-after-another by Sequence. A single account can pre-allocate up to 200 tickets at once, letting a minting service fire ~200 mints concurrently without sequence-ordering stalls. Reported NFT offer/accept workloads sustained ~751 ops/sec on the ledger, so throughput is rarely the bottleneck; reserve and orchestration are.
- **Chain:** xrpl-mainnet · **XLS:** XLS-20 · **Amendment:** TicketBatch · **Enabled:** 2022-03-08 · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** TicketCreate { TicketCount: up to 250 outstanding, with up to 200 created per group } pre-allocates ticket sequence numbers; each NFTokenMint then sets TicketSequence instead of Sequence so order-independence holds. Limits: 200 transactions in one parallel group; ~751/sec sustained NFT offer+accept throughput observed in RippleX testing. Tickets cost a 0.2 XRP reserve each until consumed. Standard fee per tx applies; budget XRP for fees across thousands of mints.
- **Gotchas:** Tickets give parallelism but NOT atomicity — a 10k mint job can partially fail; you need idempotent retry keyed on TicketSequence and reconciliation against MintedNFTokens, not all-or-nothing. The Batch amendment that WOULD give atomic multi-mint was blocked: a signer-validation vulnerability was found 2026-02-19 and rippled 3.1.1 (2026-02-23) marked Batch + fixBatchInnerSigs unsupported — do not design around atomic batches on mainnet yet. Each outstanding ticket holds 0.2 XRP reserve, so 200 tickets temporarily locks 40 XRP on top of NFT reserve. Watch per-ledger load limits and fee escalation under burst submission.

### Authorized minter (asfAuthorizedNFTokenMinter) · `transaction` · ● live ✓
An account can delegate minting to another account so a hot 'minting service' wallet can issue NFTs on behalf of a cold issuer/brand account. The issuer sets asfAuthorizedNFTokenMinter via AccountSet with the NFTokenMinter field; the delegate then mints with NFTokenMint carrying the Issuer field set to the cold account. Royalties/transfer fees still attribute to the Issuer, and the minted NFToken's issuer is the cold account — not the hot signer. This is the standard production pattern for a studio: keep the brand/issuer key cold while a server-side hot key does the high-volume minting.
- **Chain:** xrpl-mainnet · **XLS:** XLS-20 · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** Setup: AccountSet { Account: issuer, SetFlag: asfAuthorizedNFTokenMinter (10), NFTokenMinter: <delegate> }. Mint: NFTokenMint { Account: delegate, Issuer: <issuer>, NFTokenTaxon, ... } signed by the delegate. Remove: AccountSet { ClearFlag: 10 } and omit NFTokenMinter. Only ONE authorized minter at a time per issuer. The authorized minter (and issuer) can also burn tokens that have tfBurnable set.
- **Gotchas:** Exactly one authorized minter per issuer — you cannot fan out to multiple hot keys via this mechanism; rotate or use Tickets/sequence pipelining on the single delegate. The delegate temporarily 'owns' nothing of the issuer's, but it does hold any NFTs it mints to itself until transferred (and bears that reserve). Forgetting to set the Issuer field on NFTokenMint mints the NFT under the delegate's own account instead of the brand — a silent provenance error. Clearing the flag without omitting NFTokenMinter is a malformed transaction. Transfer-fee/royalty payouts go to Issuer, so the cold account must be set up to receive them.

### Authorized Minter Delegation · `pattern` · ● live ✓
An issuer can authorize a separate account to mint NFTs on its behalf by setting the NFTokenMinter field with the asfAuthorizedNFTokenMinter flag via AccountSet. The minter signs NFTokenMint with the Issuer field set to the authorizing account; royalties (TransferFee) still flow to the issuer. This separates a cold issuer identity from a hot signing key and lets a studio or platform mint for a brand.
- **Chain:** xrpl-mainnet · **XLS:** XLS-20 · **Amendment:** NonFungibleTokensV1_1 · **Enabled:** 2022-10-31 · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** AccountSet with NFTokenMinter = <minter address> and asfAuthorizedNFTokenMinter flag set (clear the flag to revoke). The minter then submits NFTokenMint with Issuer = <issuer address>. Only one authorized minter per issuer at a time. Authorized minter can also burn/modify tfBurnable/tfMutable NFTs of that issuer.
- **Gotchas:** Only ONE authorized minter per issuer at a time; setting a new one replaces the old. Royalties always go to the Issuer, not the minter, so a platform can mint and even hold the NFT while the brand collects royalties. Revoking the minter does not affect already-minted NFTs. Keep the issuer key cold; treat the minter key as operational/hot.

### Batch Minting & NFTokenMintOffer · `pattern` · ● live
Two patterns for scaling supply. Batch minting submits many NFTokenMint transactions efficiently using pre-created Tickets (XRPL tutorials cap UI batches around 200 per run) so a studio can drop a whole collection. The NFTokenMintOffer amendment (enabled on Mainnet) goes further by letting a single NFTokenMint transaction also place a sell offer (via Amount/Destination/Expiration), halving the transaction count for list-on-mint drops.
- **Chain:** xrpl-mainnet · **XLS:** XLS-20 · **Amendment:** NFTokenMintOffer · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** Batch mint: pre-create Tickets, then fire N NFTokenMint transactions (each consuming a ticket) in parallel without sequence contention; tutorials demonstrate up to ~200/run. NFTokenMintOffer: NFTokenMint with Amount (+ optional Destination, Expiration) creates the NFT and its sell offer atomically. Note: this is distinct from the unrelated Batch amendment, which was removed in rippled v3.1.1.
- **Gotchas:** Do NOT confuse NFTokenMintOffer (mint+offer in one tx, live) with the general Batch amendment (multi-tx atomic bundles) which had a bug and was removed in v3.1.1 - do not rely on Batch yet. Ticket-based batch minting needs enough tickets pre-created and enough reserve. fixNFTokenRemint changed sequence derivation (FirstNFTSequence + MintedNFTokens), so plan IDs accordingly.

### Dynamic NFTs (tfMutable + NFTokenModify, XLS-46) · `concept` · ● live ✓
Dynamic NFTs (dNFTs) are the on-chain mechanism for changing an NFToken's metadata after mint, added by the DynamicNFT amendment (XLS-46), enabled on XRPL mainnet 2025-06-11 (rippled 2.4.x line). An NFT is made mutable by setting the tfMutable flag (0x0010) AT MINT TIME -- it cannot be added later and cannot be removed. Once mutable, the issuer or their authorized minter can send an NFTokenModify transaction to rewrite the URI field. Crucially, ONLY the URI can change -- never the issuer, taxon, transfer fee, flags, or NFTokenID. For a game this is the hook for evolving/leveling items, seasonal re-skins, fixing a dead asset link, or progressing state: mutate the URI to point at a new metadata JSON reflecting the new state. The pattern pairs naturally with content-addressed storage (each state = a new CID), giving an auditable on-chain trail of URI changes (every NFTokenModify is a ledger transaction).
- **Chain:** xrpl-mainnet · **XLS:** XLS-46 · **Amendment:** DynamicNFT · **Enabled:** 2025-06-11 · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** {"amendment": "DynamicNFT (XLS-46), mainnet 2025-06-11", "enable_flag": "tfMutable (0x00000010), set ONLY in NFTokenMint", "mutate_tx": "NFTokenModify (updates URI field)", "who_can_modify": "issuer or authorized minter", "what_changes": "URI field ONLY -- no other NFT property", "irreversibility": "mutability cannot be added or removed after mint", "audit_trail": "each URI change is a discrete on-chain NFTokenModify transaction"}
- **Gotchas:** tfMutable MUST be decided at mint -- you cannot make an existing immutable NFT mutable later, and you cannot lock a mutable one. Only the URI changes; you CANNOT alter transfer fee, taxon, flags, or stats on-chain, so 'leveling up' really means swapping the off-chain metadata the URI points at. Mutability is a trust signal: holders/marketplaces know the issuer can rewrite the asset at any time, which can REDUCE perceived value/collectibility -- use it deliberately. Marketplace/wallet caches may serve STALE metadata after a NFTokenModify until they re-resolve, so a mutation isn't instantly visible everywhere. If you mutate the URI to a non-content-addressed location, you lose tamper-evidence; prefer a fresh CID per state.

### Eager (scripted) vs lazy (mint-on-demand) minting · `pattern` · ● live ✓
Two minting strategies with opposite trade-offs. Eager/scripted minting pre-mints the whole collection on-ledger so provenance and serials exist before sale, but you carry the full ~N/12 XRP reserve for unsold inventory. Lazy/mint-on-demand keeps the sale off-ledger (signed offers/allowlist) and mints only at purchase time, so there is zero reserve for unsold supply and no wasted mints on items that never sell — at the cost of no pre-sale on-chain history. For a game with a large or uncertain-demand catalog, lazy minting is usually the capital-efficient default; eager minting fits curated, guaranteed-sellout drops where pre-mint provenance matters.
- **Chain:** xrpl-mainnet · **XLS:** XLS-20 · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** Eager: loop NFTokenMint over the catalog, fund issuer for full reserve, optionally create per-NFT sell offers (extra 0.2 XRP each). Lazy: hold an off-ledger record of intended NFTs (URI + taxon + transferfee + flags), and at purchase execute mint-then-transfer (mint, create Destination-locked sell offer, buyer accepts) — often via an authorized minter service. Decision inputs: collection size, expected sell-through, working capital, need for pre-sale provenance, gas/fee volume tolerance.
- **Gotchas:** Lazy minting means metadata/flags are decided at sale time, so a bug locks every later mint into the wrong transferfee or missing tfTransferable — pin the mint template per item up front. Eager minting wastes reserve and the small mint fee on unsold tail items; for a 10k drop with 30% sell-through you've locked reserve on 7k dead NFTs. With lazy minting you cannot show buyers an on-chain rarity/serial before purchase. Either way, mint serials come from FirstNFTSequence+MintedNFTokens (see remint amendment) so 'reserved slot' numbering must be planned, not assumed sequential-from-1.

### fixNFTokenRemint — NFTokenID derivation & issuer-deletion lock · `concept` · ● live ✓
fixNFTokenRemint changed how NFTokenIDs are generated so a deleted-and-recreated issuer account cannot mint a token that collides with a previously-issued NFTokenID. ### IPFS storage + pinning (service) · `service` · · n/a ✓
IPFS is the most common off-chain home for XRPL NFT media and metadata. Files are content-addressed by a CID (a hash of the bytes), so an ipfs:// URI is tamper-evident -- change the file and the CID changes, so an immutable NFToken URI can't silently point at altered art. The catch: IPFS does NOT guarantee permanence. Data persists only while at least one node PINS it; unpinned data is eventually garbage-collected and the link goes dead. So real use requires a pinning service. The landscape shifted: NFT.Storage Classic decommissioned new uploads on 2024-06-30 (existing data still served, with degrading latency), and the recommended hot-IPFS paths are now Pinata, Lighthouse, and Storacha; Filecoin/Lighthouse cover long-term durable backing. For a game studio IPFS is the pragmatic default for the bulk of immutable assets (sprites, portraits, item icons), giving content-addressing + low/variable cost, as long as you commit to keeping pins alive (or pay a service to).
- **Chain:** off-ledger · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** {"addressing": "CID (CIDv1 recommended) -- hash of content, tamper-evident", "uri_form": "ipfs://<cid> (plus an https gateway URL for viewers that won't resolve ipfs://)", "permanence": "NOT guaranteed -- persists only while pinned; unpinned -> GC'd", "pinning_services_2026": "Pinata, Lighthouse, Storacha (NFT.Storage Classic decommissioned uploads 2024-06-30)", "cost_model": "recurring (pinning subscription / per-GB) -- e.g. Pinata paid tiers", "durable_backing": "Filecoin / Lighthouse for long-term storage deals", "gateway": "needed for fast HTTP fetch; marketplaces cache via gateways"}
- **Gotchas:** Pinning is an ongoing obligation, not one-and-done -- stop paying / lose the pin and an immutable NFT's art vanishes with no on-chain fix. NFT.Storage Classic no longer accepts uploads (since 2024-06-30); old tutorials pointing there are dead -- use Pinata/Lighthouse/Storacha. A bare ipfs:// URI may not render in wallets that lack a resolver; ship a gateway URL or expect blank images. Public gateways are rate-limited and slow for grid scrolling, which is exactly why marketplaces cache -- your own app should pin AND use a dedicated/gateway endpoint. ### Mint-time flags & TransferFee (royalty) decisions · `transaction` · ● live ✓
Every NFTokenMint locks in a set of permanent flags and an optional secondary-sale royalty (TransferFee) that can NEVER be changed after mint. The choices: tfTransferable (can the asset move between players at all — without it, only issuer<->holder transfers, which makes a non-tradeable bound item), tfBurnable (can the issuer burn it later, e.g. to retire/redeem an asset), tfOnlyXRP (restrict sale currency to XRP), and TransferFee (0.000%-50.000% royalty on secondary sales, requires tfTransferable). These flags ARE the asset's economic policy; choosing them wrong is unrecoverable except by burn+remint.
- **Chain:** xrpl-mainnet · **XLS:** XLS-20 · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** Flags: tfBurnable=1, tfOnlyXRP=2, tfTrustLine=4 (DEPRECATED), tfTransferable=8 (required for any 3rd-party trade and for any non-zero TransferFee), tfMutable=16 (mutable URI; requires DynamicNFT). TransferFee: UInt16, valid 0..50000 = 0.000%..50.000% in 0.001% steps; only valid when tfTransferable is set; paid to the Issuer on each secondary sale. Other fields: NFTokenTaxon (req), Issuer (when authorized minting), URI (<=256 bytes, hex), and optional Amount/Expiration/Destination for an auto-created sell offer at mint.
- **Gotchas:** TransferFee and all flags are immutable post-mint — no NFTokenModify for these (NFTokenModify only touches URI of mutable NFTs). Setting TransferFee without tfTransferable is malformed and rejected. tfTrustLine is deprecated by fixRemoveNFTokenAutoTrustLine — do not set it. Forgetting tfTransferable produces a soulbound-style token that players can never trade on a marketplace (sometimes desired for bound gear, usually a mistake for collectibles). A 50% cap means you cannot encode a >50% sink via royalty. Royalties accrue to Issuer, so with authorized minting confirm the cold issuer is the fee recipient.

### NFToken URI field (XLS-20) · `concept` · ● live ✓
The URI field is the ONLY metadata-bearing field a native XRPL NFToken carries on-chain. It is an optional, variable-length blob capped at 256 bytes, stored hex-encoded (use convertStringToHex / similar). The protocol does NOT validate or dereference it: it can hold an ipfs:// CID, an https:// URL, an ar:// / Arweave gateway URL, a magnet link, or an inline RFC-2397 data: URI. It must not be an empty string if present. By default the URI is immutable for the life of the token -- it can only change if the NFToken was minted with the tfMutable flag (see DynamicNFT). Because 256 bytes is too small for real metadata, the URI is virtually always a pointer to an off-chain JSON document, not the metadata itself. This single field is the entire bridge between the on-chain token and everything a player/marketplace sees.
- **Chain:** xrpl-mainnet · **XLS:** XLS-20 · **Amendment:** NonFungibleTokensV1_1 · **Enabled:** 2022-10-31 · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** {"max_length": "256 bytes (hex-encoded on-chain)", "encoding": "hex string (e.g. xrpl.js convertStringToHex)", "validity_check": "none -- protocol stores bytes verbatim, never fetches", "supported_schemes": "ipfs://, https://, ar:// / Arweave gateway, magnet:, RFC-2397 data: URI", "mutability": "immutable by default; mutable only if minted with tfMutable (0x0010)", "set_where": "NFTokenMint transaction URI field", "empty": "field may be omitted, but must not be an empty string when present"}
- **Gotchas:** 256 BYTES, not characters -- a long https URL plus query string can blow the budget; content-addressed ipfs:// CIDs are compact and the safer default. The URI is hex-encoded on the wire; forgetting to encode (or double-encoding) is a classic mint bug. The ledger never checks the link works, so a dead gateway = a permanently broken-looking NFT with no on-chain remedy unless tfMutable was set. The URI is immutable after mint UNLESS tfMutable was enabled AT mint -- you cannot retrofit mutability. Do NOT stuff raw metadata into the URI via data: in production: it bloats every ledger entry and you lose the 256-byte budget instantly.

### NFTokenBurn — supply & sink mechanics · `transaction` · ● live ✓
NFTokenBurn permanently removes an NFT from the ledger. - **Chain:** xrpl-mainnet · **XLS:** XLS-20 · **Maturity:** stable · **Use:** recommended

### NFTokenTaxon collection-identity strategy · `pattern` · ● live ✓
XRPL has no native 'collection' ledger object. Collection identity is the pair (Issuer account, NFTokenTaxon) — every NFT minted by the same issuer with the same taxon is, by convention, one collection. The taxon is an arbitrary UInt32 the minter chooses, so taxon strategy (one collection = one taxon, vs sub-series/rarity tiers = distinct taxons, vs per-asset-type taxons for a game) is a deliberate design decision made at mint time and effectively permanent. Indexers, marketplaces, and your own game backend group by (issuer, taxon), so getting the scheme right up front is core to a game's asset taxonomy.
- **Chain:** xrpl-mainnet · **XLS:** XLS-20 · **Amendment:** NonFungibleTokensV1_1 · **Enabled:** 2022-10-31 · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** NFTokenTaxon (UInt32, required on NFTokenMint, range 0..4294967295; values >= 2147483648/0x80000000 are reserved by the protocol's scrambling — pick from the lower half to be safe). Collection = (Issuer, taxon). Taxon is scrambled inside the NFTokenID but the logical/unscrambled value is what you query on. There is no rename, no merge, no on-chain collection name/size/floor — those live off-ledger (metadata + marketplace). Sequence/serial within a collection comes from the NFTokenID's sequence component, set automatically per mint.
- **Gotchas:** No way to change an NFT's taxon after mint — a mistaken taxon means a permanently mis-grouped asset, only fixable by burn+remint. Two different issuers can use the same taxon number with zero collision because identity includes the issuer account, but a single issuer reusing a taxon across what you intended as two collections silently merges them in every indexer. Don't encode rarity or stats in the taxon expecting tooling to parse it — taxon is opaque to the protocol; use the URI/metadata for that. Reserved taxon range (>=0x80000000) behaves oddly with scrambling; stay below it.

### On-chain URI vs off-chain metadata hosting (pattern) · `pattern` · · n/a ✓
The core architectural split for every XRPL game asset: the ledger stores almost nothing (a hex URI <=256 bytes inside the NFToken), and ALL descriptive metadata + media lives off-chain at the resolved location. This is a deliberate cost/scalability tradeoff -- XRPL deliberately avoids fat on-chain blobs. The pattern that survives long-term: (1) host immutable media (sprites, portraits, 3D models) on content-addressed storage so the bytes can't silently change; (2) write a metadata JSON (OpenSea-compatible, optionally + game extension) that references those media URIs; (3) content-address the JSON too and put THAT URI on-chain; (4) reserve tfMutable+NFTokenModify only for assets whose state must evolve. The rare alternative -- a fully on-chain inline data: URI -- only fits trivially small SVG/text because of the 256-byte ceiling, so it is impractical for real game art. The off-chain choice is where permanence/mutability/cost tradeoffs (IPFS vs Arweave vs centralized) actually get made; the on-chain URI is just the pointer.
- **Chain:** xrpl-mainnet · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** {"on_chain": "URI only, <=256 bytes hex, no validation, immutable unless tfMutable", "off_chain": "metadata JSON + media (image/animation/3D) at the resolved URI", "content_addressing": "ipfs:// CIDv1 or ar:// txid so bytes are tamper-evident", "json_then_media": "URI -> JSON; JSON.image -> media URI (two hops)", "fully_on_chain_option": "inline data: URI -- only viable for tiny SVG/text payloads", "permanence_decision": "made off-chain (Arweave permanent vs IPFS pinned vs centralized)"}
- **Gotchas:** An on-chain URI does NOT make your asset on-chain or permanent -- the token can outlive the host, leaving a valid NFT pointing at nothing (the #1 long-term NFT failure mode). HTTP(S) URLs are mutable and centralized: the issuer (or a hijacker) can swap what an immutable NFT 'shows' without any on-chain change -- content-addressing closes that hole. Two-hop resolution (URI->JSON->image) means BOTH hops must stay alive; pinning the JSON but not the image still breaks the asset. The 256-byte budget rules out fat on-chain metadata, so 'put it all on-chain' is not an option for game art. Plan media permanence at mint time -- there is no cheap retrofit for an immutable NFT whose host died.

- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed | net-check: n/a | currency=current | XRPL NFTs use on-chain URI pointers to off-chain metadata storage as standard architecture pattern.
- **Sources:** [NFToken -- XRPL.org protocol data type](https://xrpl.org/docs/references/protocol/data-types/nftoken) — The NFToken carries only a 256-byte URI on-chain; metadata is stored off-chain and the URI is not validated by the protocol, supporting IPFS/HTTP/data URIs. ; [NFT Marketplace Overview -- XRPL.org](https://xrpl.org/docs/use-cases/tokenization/nft-mkt-overview) — Most XRPL NFTs store their media and attributes off-chain on IPFS or Arweave to avoid centralization, while the ledger holds only the pointer.

### OpenSea-compatible NFT metadata schema · `standard` · · n/a ✓
The de-facto JSON metadata schema that most NFT marketplaces and wallets -- including the XRPL ecosystem's Bithomp, Sologenic, onXRP/XPMarket, and xrpl.org-aligned tooling -- understand for free. ### Owner reserve & cost-per-NFT math (NFTokenPage packing) · `concept` · ● live ✓

### Off-Chain Metadata vs On-Chain Mutability (XLS-24d) · `concept` · ◐ pending
The two distinct axes of 'changeability' a studio must reason about separately. ### Metadata Centralization Risk & Durable Hosting · `concept` · ● live ✓
An XRPL NFT stores only a 256-byte URI on-chain; the actual art and trait JSON live wherever that URI points. ### NFT vs MPT vs IOU — Per-Item Asset-Type Decision · `concept` · ● live ✓
The foundational economy decision: choose the right ledger primitive per item type. Unique, individually-identified, individually-tradeable assets (a named legendary sword, a land plot, a hero character, a 1-of-1 cosmetic) are NFTs. Interchangeable, stackable, quantity-tracked items (currency, potions, ammo, crafting mats, XP/reputation points, season passes by tier) should be Multi-Purpose Tokens (MPTs) — the v2 fungible standard with attachable metadata. ### NFTokenModify Transaction · `transaction` · ● live ✓
The transaction that actually performs the mutation: it updates (or deletes) the URI field of a mutable NFToken. This is the on-chain action a game backend submits when an item levels up or changes state -- the issuer (or authorized minter) rewrites the URI to point at the new metadata document. It is the single mechanism for true on-chain mutability of game items on XRPL.

### Reserve-Cost Blowup Anti-Pattern (NFTokenPage Economics) · `concept` · ● live ✓

### tfMutable Mint Flag · `concept` · ● live ✓
The mint-time decision that makes (or forever forecloses) an NFT's mutability. tfMutable (0x00000010) is set in the Flags field of NFTokenMint; it persists on the ledger object as lsfMutable (0x0010). This is a one-shot, irreversible design choice: an NFT minted without tfMutable can NEVER become mutable, and one minted with it is permanently eligible for NFTokenModify. For a game studio this is the most important line of code in the minting pipeline.
- **Chain:** xrpl-mainnet · **XLS:** XLS-46d · **Amendment:** DynamicNFT · **Enabled:** 2025-06-11 · **Maturity:** production · **Use:** live
- **Key fields / API:** tfMutable transaction flag = 0x00000010 (decimal 16), set in NFTokenMint.Flags; corresponds to ledger flag lsfMutable = 0x0010 on the NFToken object. Sits alongside tfBurnable (0x00000001), tfOnlyXRP (0x00000002), tfTransferable (0x00000008).
- **Gotchas:** Decision is permanent and cannot be retrofitted -- you cannot add mutability to an already-minted NFT, full stop. The transaction-flag value (0x00000010) and the ledger-flag value (0x0010) differ in width; don't confuse them when reading vs writing. Combine flags with bitwise OR (e.g. tfTransferable | tfMutable = 0x18) -- a common mint for tradeable evolving gear. ### URI-Only Mutability Boundary · `concept` · ● live ✓
The precise answer to 'what exactly is mutable?' -- ONLY the URI field. Everything else on an NFToken is frozen at mint forever: Flags, Issuer, NFTokenTaxon, TransferFee, and the NFTokenID itself. There are no native on-chain stat/attribute fields to mutate. This boundary is the single most important design constraint for evolving game items on XRPL: all evolving state must live behind the URI (in off-chain metadata), never in NFToken fields.
- **Chain:** xrpl-mainnet · **XLS:** XLS-46d · **Amendment:** DynamicNFT · **Enabled:** 2025-06-11 · **Maturity:** production · **Use:** live
- **Key fields / API:** Mutable: URI (256-byte Hex Blob, via NFTokenModify). Immutable forever: Flags, Issuer, NFTokenTaxon (collection/series id), TransferFee (royalty 0-50000 = 0-50%), Sequence, and the composite NFTokenID (Flags|TransferFee|Issuer|Taxon|Sequence).
- **Gotchas:** You cannot change royalty (TransferFee) or move an item between collections (Taxon) post-mint -- bake these into mint correctly. The NFTokenID is content-addressed from immutable fields, so it never changes even when URI does -- good for stable references, but means the ID alone tells a marketplace nothing about current state (it must re-fetch the URI). Because only a pointer changes, 'mutability' is really 'repointing' -- the integrity of evolution depends entirely on how trustworthy the off-chain target is.

### XLS-24d NFT metadata schema · `standard` · ◐ pending ✓
XLS-24d ('Metadata Structure for XLS-20d NFTs', XRPLF/XRPL-Standards Discussion #69) is the XRPL-native community standard for the off-chain JSON document an NFToken URI points to. It is a DRAFT with NO on-chain enforcement -- nothing in the protocol validates it; it is a shared convention so marketplaces and galleries can render NFTs consistently. Notably it defines a top-level `type` field and explicitly lists `game_item` alongside `art`, `ticket`, and `general_purpose` as first-class NFT types -- directly relevant to a game studio. The shape is type/name/description/creators[]/collection/localization/properties, where `properties` holds the type-specific payload: primary_display (a file object), primary_animation, an `attributes` array of typed traits ({attribute_name, value_type, value} with value_type like string/decimal/int/vector), additional `files`, and expiration handling. It is more structured and type-aware than the OpenSea schema, but adoption across XRPL marketplaces is uneven, so most production NFTs pair or replace it with the OpenSea-style flat schema for maximum display compatibility.
