### Account Sequence & Fee Model · `concept` · ● live ✓
Each account has a strictly incrementing Sequence number; a transaction is valid only when Sequence is exactly the account's next number (unless it uses a Ticket). The Fee is an integer of XRP drops destroyed (not paid to anyone) — a base minimum (~10 drops on a healthy network) scaled up under load and by transaction type (multisign and special transactions cost more). This deflationary, ordered model gives XRPL its at-most-once execution guarantee and spam resistance. Builders must serialize transactions per account or use Tickets/Batch to parallelize.
- **Chain:** all · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** Sequence (uint32, strictly +1 per applied tx); Fee (drops, integer, destroyed); base fee scales with server load (open-ledger cost) and tx type; multisign fee = base x (1 + number of signatures); reference reserves: 1 XRP base account reserve, 0.2 XRP per owned object (owner reserve) as of mid-2026.
- **Gotchas:** Sending two transactions with the same Sequence makes the second a tefPAST_SEQ once the first validates — to send many txs fast you must pre-assign distinct Sequences (and risk a gap stalling everything) or use Tickets. Fee is BURNED, never refunded, even on tec failures. Under network load the autofilled fee can spike sharply; cap it in code to avoid overpaying. A single stuck low Sequence blocks every higher-Sequence transaction from the same account.
- **Build-focus tracks:** [game-economies](track-game-economies.md), [nft-assets](track-nft-assets.md), [payments](track-payments.md)
- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed | net-check: mainnet-live | currency=current | Sequence incrementing and fee destruction model are core XRPL account mechanics that have always been active.
- **Sources:** [Transaction Common Fields (Sequence & Fee)](https://xrpl.org/docs/references/protocol/transactions/common-fields) — States Sequence must be exactly one greater than the account's previous transaction and Fee is an integer amount of XRP in drops destroyed as the cost of distributing the transaction.

### AccountSet Flags · `transaction` · ● live ✓
AccountSet configures persistent account-level options via SetFlag/ClearFlag (one asf flag per transaction) and a handful of legacy tf flags. These flags control security and economic policy: requiring destination tags, requiring trustline authorization, disabling the master key, default rippling, deposit authorization, freeze controls, clawback opt-in, blocking unwanted incoming objects, and authorizing an NFT minter. AccountSet is the primary lever for hardening and shaping an account before it issues tokens or receives funds.
- **Chain:** all · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** SetFlag/ClearFlag take ONE asf value: asfRequireDest(1), asfRequireAuth(2), asfDisallowXRP(3, advisory), asfDisableMaster(4), asfAccountTxnID(5), asfNoFreeze(6, irreversible), asfGlobalFreeze(7), asfDefaultRipple(8), asfDepositAuth(9), asfAuthorizedNFTokenMinter(10), asfDisallowIncomingNFTokenOffer(12), asfDisallowIncomingCheck(13), asfDisallowIncomingPayChan(14), asfDisallowIncomingTrustline(15), asfAllowTrustLineClawback(16), asfAllowTrustLineLocking(17). Also Domain, EmailHash, MessageKey, TransferRate, TickSize, NFTokenMinter, RegularKey fields.
- **Gotchas:** asfNoFreeze and (effectively) clawback decisions are IRREVERSIBLE — asfNoFreeze permanently surrenders freeze ability, and asfAllowTrustLineClawback can only be set on an account with no existing trustlines/balances. asfDisallowXRP is advisory only — it does NOT actually block XRP at the protocol level, only signals client UIs. asfRequireAuth must be set BEFORE issuing tokens. Only one asf flag changes per AccountSet; the legacy tf flags (tfRequireDestTag etc.) are being phased out in favor of asf. Setting asfDisableMaster without a working regular key or signer list locks you out.
- **Build-focus tracks:** [game-economies](track-game-economies.md), [identity-compliance](track-identity-compliance.md), [nft-assets](track-nft-assets.md), [payments](track-payments.md)
- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed | net-check: mainnet-live | currency=current | AccountSet flags and options have been available on XRPL mainnet since the protocol's inception.
- **Sources:** [AccountSet](https://xrpl.org/docs/references/protocol/transactions/types/accountset) — AccountSet enables/disables account options via SetFlag/ClearFlag using asf flags (asfRequireDest, asfRequireAuth, asfDisableMaster, asfNoFreeze, asfDefaultRipple, asfDepositAuth, asfAllowTrustLineClawback, etc.).

### Multisigning (SignerListSet) · `transaction` · ● live ✓
SignerListSet attaches a list of authorized signers (1-32 entries, each with a SignerWeight) plus a SignerQuorum threshold to an account, enabling M-of-N multisignature control. A transaction is then authorized by collecting enough signatures whose combined weight meets the quorum, supplied in the Signers array. This is the production pattern for treasury accounts, DAOs, and shared studio/wallet control. The MultiSignReserve amendment cut the owner-reserve cost of a signer list to a flat amount instead of scaling per signer.
- **Chain:** all · **Amendment:** MultiSign / MultiSignReserve · **Enabled:** 2016-06-27 · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** SignerListSet.SignerQuorum (min combined weight; 0 = delete list); SignerEntries[] of {Account, SignerWeight}; 1-32 signers, no duplicates, sender cannot list itself; SignerListID (currently only 0 supported); delete by SignerQuorum=0 AND omitting SignerEntries; multisign fee = base x (1 + number of signatures included).
- **Gotchas:** To delete a signer list you must set SignerQuorum=0 AND omit SignerEntries — doing only one gives temMALFORMED. The submitting account may not appear in its own SignerList. Quorum cannot exceed the sum of weights or the tx fails. Multisigned transactions cost MORE (fee multiplied per included signature) — budget for it. Pre-MultiSignReserve lists carry a higher legacy owner reserve; recreate them to benefit from the lower flat reserve. Pair with asfDisableMaster to make multisign the sole control path.
- **Build-focus tracks:** [game-economies](track-game-economies.md), [identity-compliance](track-identity-compliance.md), [payments](track-payments.md)
- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed | net-check: mainnet-live | currency=current | Multisign functionality via MultiSign amendment has been live on XRPL mainnet since 2016.
- **Sources:** [SignerListSet](https://xrpl.org/docs/references/protocol/transactions/types/signerlistset) — SignerListSet sets a 1-32 entry signer list with per-signer weights and a SignerQuorum (0 deletes the list), enabling multisignature authorization; requires the MultiSign amendment with reserve improved by MultiSignReserve.

### Parallel payout via Ticket pool · `pattern` · ● live ✓
The mid-2026 reference architecture for paying many players concurrently from a backend: maintain a pool of reserved Tickets on one or more funded payout accounts, assign each pending payout a distinct Ticket, then sign and submit Payments in parallel. Because each Payment is pinned to its own Ticket (not the advancing account Sequence), submissions do not have to be strictly ordered and a failed/dropped send can be retried in its own slot without blocking others. A slot-allocator maps (player, payout-id) -> Ticket, and a refiller issues new TicketCreate batches as Tickets are consumed, keeping the outstanding count under the 250 ceiling per account.
- **Chain:** xrpl-mainnet · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** {"building_blocks": "TicketCreate (reserve up to 250 slots) + Payment with TicketSequence per player", "concurrency_unit": "One Ticket = one independently submittable, independently retryable payout slot", "throughput_scaling": "Shard across K payout accounts to exceed the per-account 250-Ticket / 10-queue limits; aggregate throughput ~ K * ledger-inclusion rate", "idempotency_hook": "Persist (payout-id -> Ticket, tx hash, LastLedgerSequence); a Ticket is consumed at most once, so a retry that reuses the same Ticket cannot double-pay", "vs_batch": "Provides parallel throughput but NOT atomicity; if you need all-or-nothing, wait for BatchV1_1"}
- **Gotchas:** This pattern does NOT give atomic group semantics — partial completion is normal and your accounting must reconcile per-payout, not per-job. Owner reserve (0.2 XRP/Ticket) is real working capital; size the pool to in-flight demand, not the whole job. The 10-txns-per-account queue cap means a single account cannot have hundreds of Payments simultaneously in the open-ledger queue — pace submission to ledger close (~3-5s) and/or shard. Always set LastLedgerSequence on every Payment so abandoned sends expire deterministically and their Tickets can be safely reclaimed/retried. Beware destination requirements (DestinationTag, trustlines/authorized for IOUs, account existence + base reserve for first-time XRP recipients) — a payout to a non-existent account or missing trustline yields tec results that still consume the Ticket.
- **Build-focus tracks:** [game-economies](track-game-economies.md), [payments](track-payments.md)
- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed | net-check: Composed from Mainnet-enabled primitives (TicketCreate + Payment) | currency=current | This pattern is viable using existing Mainnet capabilities, though constrained by 10-transaction queue limit per account.
- **Sources:** [Use Tickets — xrpl.org](https://xrpl.org/use-tickets.html) — Tickets enable out-of-order, parallel transaction submission, each pinned to a distinct reserved Ticket. ; [Transaction Queue — xrpl.org](https://xrpl.org/docs/concepts/transactions/transaction-queue) — A single sending address can have at most 10 transactions queued simultaneously, bounding per-account concurrency and motivating account sharding. ; [Tickets — xrpl.org concepts](https://xrpl.org/docs/concepts/accounts/tickets) — Up to 250 Tickets per account; 0.2 XRP reserve each — sets the pool-size and capital limits for the pattern.

### Reliable Transaction Submission Lifecycle (autofill -> sign -> submit -> verify) · `pattern` · ● live ✓
The canonical four-phase pattern for getting a transaction onto a validated ledger safely. Autofill populates Fee (from current load), Sequence (from account_info), and LastLedgerSequence (last validated + a small buffer). Sign locally (secret never touches the network), producing SigningPubKey + TxnSignature + the tx hash. Submit returns only a PROVISIONAL result. Verify by polling the tx by hash until validated:true, or treat the tx as permanently failed once LastLedgerSequence passes without inclusion. This pattern is the difference between idempotent, recoverable payment systems and double-spend/limbo bugs.
- **Chain:** all · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** Autofill: Fee, Sequence, LastLedgerSequence (set to last validated ledger + ~4). Sign: SigningPubKey, TxnSignature, computed tx hash. Submit: provisional engine_result (NOT final). Verify: tx method by hash, check validated:true; persist hash+Sequence+LastLedgerSequence BEFORE submit for crash recovery.
- **Gotchas:** A success engine_result from submit means 'received', NOT 'applied to a validated ledger' — never confirm a payment on the provisional result. Without LastLedgerSequence a stuck tx can be applied much later (limbo). The Sequence number provides at-most-once semantics: re-signing the same Sequence after the original validated produces a tefPAST_SEQ, not a double-spend — but you MUST persist the hash to know which happened. tesSUCCESS and tec are only final in a validated ledger.
- **Build-focus tracks:** [game-economies](track-game-economies.md), [identity-compliance](track-identity-compliance.md), [nft-assets](track-nft-assets.md), [payments](track-payments.md)
- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed | net-check: mainnet-live | currency=current | The reliable submission pattern with autofill, signing, and validation polling is standard practice on XRPL mainnet.
- **Sources:** [Reliable Transaction Submission](https://xrpl.org/docs/concepts/transactions/reliable-transaction-submission) — Prescribes autofilling Fee/Sequence/LastLedgerSequence, local signing, persisting before submit, and polling for validated:true since submit results are only provisional.

### Reward-distribution architecture: per-tx vs batched · `pattern` · ● live ✓
The mid-2026 answer to 'one Payment per player vs one batched envelope' for a studio is: one Payment per player, parallelized via Tickets, behind an idempotent payout service — because atomic on-ledger Batch (XLS-56) is NOT available on Mainnet and even BatchV1_1 caps inner txns at 8. Structure the service in two layers: (1) an accounting/ledger of intended payouts (player, amount, currency, payout-id, status) that is the source of truth and is currency-agnostic to the submission mechanism; (2) a submission layer that maps each pending payout to a Ticket, fees it to the open-ledger cost, submits, and updates status by validated result. This separation means flipping to BatchV1_1 later (to batch small atomic groups) changes only the submission layer. Cost is dominated by destination/reserve concerns and pacing, not the ~10-drop base fee.
- **Chain:** xrpl-mainnet · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** {"decision_mid_2026": "Per-player Payment + Ticket parallelism is the only production-viable high-throughput option; batched-atomic is unavailable", "layering": "Accounting layer (intent + status, source of truth) decoupled from submission layer (Ticket allocation, fee, submit, result-handling)", "cost_math": "~10 drops base/Payment under no load (10k payouts ~= 0.1 XRP in base fees, trivial); real costs are recipient base reserve for new XRP accounts and 0.2 XRP/Ticket working capital, plus escalated fees if you flood", "atomicity_tradeoff": "Per-tx = no all-or-nothing (reconcile partials); future BatchV1_1 = atomic groups of <=8 only", "scaling": "Shard across K payout accounts to beat the 10-queue / 250-Ticket per-account caps; pace to ledger close (~3-5s) to avoid fee escalation", "audit": "Persist tx hash + LastLedgerSequence per payout for reconciliation and idempotency"}
- **Gotchas:** Do not architect around Batch today — it is blocked, and BatchV1_1 has no release date and only batches <=8. Do not assume base fees are the cost driver; they are negligible — the spend that bites is recipient base reserve (a first-time XRP recipient needs the account-reserve to exist) and Ticket owner-reserve capital. For IOU/token rewards, the recipient must hold a (possibly authorized) trustline or the Payment tecs — pre-flight check trustlines. Build reconciliation for partial completion as a first-class state, not an error path, since per-tx payouts are not atomic. Keep the submission layer swappable so BatchV1_1 (or a future bulk primitive) is a drop-in, not a rewrite.
- **Build-focus tracks:** [game-economies](track-game-economies.md), [payments](track-payments.md)

- **Sources:** [Known Amendments — xrpl.org](https://xrpl.org/resources/known-amendments) — Batch is 'Obsolete' and not enabled on Mainnet, forcing per-transaction payout architecture until BatchV1_1 ships. ; [Tickets — xrpl.org concepts](https://xrpl.org/docs/concepts/accounts/tickets) — Up to 250 Tickets (0.2 XRP reserve each) enable the parallel per-player Payment pattern that replaces batching today. ; [Transaction Cost — xrpl.org](https://xrpl.org/docs/concepts/transactions/transaction-cost) — Base reference cost (~10 drops) is negligible at scale; load-based escalation and reserves dominate real payout cost planning.

### SetRegularKey (Regular Key Pair) · `transaction` · ● live ✓
SetRegularKey assigns (or removes) a secondary key pair that can sign transactions for the account in place of the master key. This is the standard XRPL key-rotation and hot/cold separation primitive: keep the master key offline, sign day-to-day with the regular key, and rotate the regular key if it is compromised without losing the account. Combined with asfDisableMaster it lets you fully retire the master key in favor of a rotatable regular key or a signer list.
- **Chain:** all · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** SetRegularKey.RegularKey (the new authorized address; omit the field to remove the regular key). The regular key can sign anything the master can EXCEPT it cannot, by itself, re-enable a disabled master in all configurations — plan recovery carefully. Works alongside multisign and (when enabled) delegation.
- **Gotchas:** If you set asfDisableMaster and your regular key is later lost or compromised with no signer-list fallback, the account can become permanently uncontrollable — always keep a recovery path (signer list or recoverable master). The regular key is a single key; for M-of-N control use SignerListSet instead. Removing the regular key (omit RegularKey) while the master is disabled is a lockout trap.
- **Build-focus tracks:** [game-economies](track-game-economies.md), [identity-compliance](track-identity-compliance.md), [payments](track-payments.md)
- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed | net-check: mainnet-live | currency=current | Regular key functionality has been part of XRPL mainnet since the protocol's early days.
- **Sources:** [Transaction Common Fields / Cryptographic Keys (SigningPubKey)](https://xrpl.org/docs/references/protocol/transactions/common-fields) — Transactions are authorized by the account's master, regular, or signer-list keys; SigningPubKey identifies which key signed, supporting regular-key rotation set via SetRegularKey.

### Source & Destination Tags · `concept` · ● live ✓
SourceTag and DestinationTag are optional 32-bit integers that route a transaction to a specific subaccount or context within a hosted/shared XRPL address — the backbone of how exchanges and custodial services map one on-chain address to many users. DestinationTag identifies the recipient subaccount; SourceTag identifies the sender's context for refunds/replies. An account can require a destination tag by setting asfRequireDest, which rejects untagged incoming payments.
- **Chain:** all · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** DestinationTag (uint32, routes to recipient subaccount); SourceTag (uint32, sender context); asfRequireDest (AccountSet flag) enforces that incoming payments include a DestinationTag (else tecDST_TAG_NEEDED). Tags are plaintext metadata, not encrypted.
- **Gotchas:** Tags are NOT enforced by default — a payment without a DestinationTag to an exchange address often becomes unrecoverable (lost-to-support) unless the receiver set asfRequireDest. Tags are public plaintext, not private. They are arbitrary integers with no protocol-level meaning beyond the asfRequireDest gate — the mapping lives entirely in the receiver's off-ledger system. Always set asfRequireDest on shared/custodial receiving accounts to fail-closed on missing tags.
- **Build-focus tracks:** [game-economies](track-game-economies.md), [identity-compliance](track-identity-compliance.md), [payments](track-payments.md)
- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed | net-check: mainnet-live | currency=current | Source and destination tags have been available on XRPL mainnet since the protocol's inception.
- **Sources:** [Source and Destination Tags (Common Fields)](https://xrpl.org/docs/references/protocol/transactions/common-fields) — SourceTag and DestinationTag are optional integers that identify a sender/recipient subaccount within a hosted address; asfRequireDest can force incoming payments to include a DestinationTag.

### Tickets (out-of-order sequence reservation) · `transaction` · ● live ✓
A Ticket reserves a sequence number in advance so a later transaction can be submitted out of normal sequence order by setting TicketSequence instead of Sequence. This is THE mechanism that makes concurrent payout submission safe today: with Batch blocked, a payout service pre-reserves a block of Tickets (one TicketCreate makes up to 250), then fires many Payments in parallel — each pinned to its own Ticket — without serializing on the account's single advancing Sequence number. Because each send consumes exactly one Ticket and does not touch the normal sequence, retries and reordering are deterministic and idempotent at the slot level.
- **Chain:** xrpl-mainnet · **XLS:** XLS-8d / XLS-13d · **Amendment:** TicketBatch · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** {"TicketCreate": "One signed transaction reserves up to 250 sequence numbers as Tickets at once", "max_tickets": "An account may hold at most 250 Tickets in the ledger at a time, and cannot create more than 250 at a time", "reserve": "0.2 XRP owner reserve per Ticket (each Ticket is a separate owner-reserve item); reclaimed when the Ticket is consumed", "TicketSequence": "Set on a later transaction to spend a specific reserved Ticket instead of using Sequence; consuming a Ticket removes its Ticket object and does NOT advance the account's normal sequence number", "sequence_derivation": "A TicketCreate sent with Sequence N produces Tickets starting at TicketSequence N+1", "parallelism": "Different in-flight transactions use different Tickets, so they can be prepared/signed/submitted concurrently with no sequence-number contention"}
- **Gotchas:** 250 is a hard ceiling on outstanding Tickets per account — to sustain thousands of concurrent sends you must continuously top up Tickets and/or shard across multiple payout accounts. Each Ticket locks 0.2 XRP of owner reserve until consumed, so over-reserving ties up capital. A Ticket is single-use; consuming it (even by a failed tec result) burns the slot, so your slot-allocator must track which Ticket each retry uses to stay idempotent. Tickets give parallelism, not atomicity — they do NOT make a group of payouts all-or-nothing (that is what Batch/BatchV1_1 would provide). The transaction queue still caps each sending account at 10 queued txns regardless of how many Tickets exist.
- **Build-focus tracks:** [game-economies](track-game-economies.md), [payments](track-payments.md)
- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed | net-check: Enabled on Mainnet via TicketBatch amendment | currency=current | Tickets are live on Mainnet and provide out-of-order transaction capability with 250 ticket limit per account.
- **Sources:** [Tickets — xrpl.org concepts](https://xrpl.org/docs/concepts/accounts/tickets) — Max 250 Tickets per account at a time and per TicketCreate; 0.2 XRP owner reserve each; TicketSequence spends a Ticket without advancing the normal sequence; a TicketCreate with Sequence N yields Tickets from N+1. ; [Use Tickets — xrpl.org](https://xrpl.org/use-tickets.html) — Tickets let transactions be sent out of normal sequence order and in parallel, each pinned to a distinct Ticket. ; [XLS-8d Tickets: Supporting out-of-sequence transactions — XRPLF/XRPL-Standards Discussion #23](https://github.com/XRPLF/XRPL-Standards/discussions/23) — Original Tickets standard defining out-of-sequence transaction support on the XRP Ledger.

### Tickets (TicketCreate / TicketSequence) · `transaction` · ● live ✓
Tickets let an account reserve specific sequence numbers ahead of time so transactions can be sent out of order or in parallel. A TicketCreate reserves N sequence numbers (advancing the account Sequence past them); later you submit a transaction with Sequence 0 and TicketSequence set to a reserved number. This solves multi-party signing collected over time, parallel dispatch from a shared account, and pre-authorizing future actions without knowing the live sequence. Each Ticket is one-use and costs 0.2 XRP owner reserve until consumed.
- **Chain:** all · **XLS:** XLS-2 · **Amendment:** TicketBatch · **Enabled:** 2022-02-09 · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** TicketCreate.TicketCount (how many to reserve); resulting Ticket ledger entries; on use: set Sequence=0 and TicketSequence=<reserved number>; max 250 outstanding Tickets per account; 0.2 XRP owner reserve per outstanding Ticket (released on use); within a ledger, Ticketed txs execute after regular-sequence txs, ordered low->high TicketSequence.
- **Gotchas:** A Ticket is single-use — it is consumed (removed from the ledger) whether the transaction succeeds or fails with tec. Creating Tickets immediately bumps your account Sequence past all of them, so don't mix that up with normal sequencing. The 250-outstanding cap and 0.2 XRP per-ticket reserve limit how many you can pre-stage. Required the TicketBatch amendment (now long enabled on mainnet).
- **Build-focus tracks:** [game-economies](track-game-economies.md), [identity-compliance](track-identity-compliance.md), [payments](track-payments.md)
- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed | net-check: mainnet-live | currency=current | Tickets functionality via TicketBatch amendment has been enabled on XRPL mainnet since 2020.
- **Sources:** [Tickets](https://xrpl.org/docs/concepts/accounts/tickets) — Tickets reserve sequence numbers for later use (max 250, 0.2 XRP reserve each), enabling out-of-order transactions via the TicketSequence field; requires the now-active TicketBatch amendment.

### Transaction Common Fields · `concept` · ● live ✓
Every XRPL transaction shares a common field set regardless of TransactionType: Account (sender address), TransactionType, Fee (drops destroyed), Sequence (must be exactly account's next number), and optional Flags, Memos, SourceTag, LastLedgerSequence, AccountTxnID, NetworkID, Signers, SigningPubKey, TxnSignature, TicketSequence, and Delegate. These fields are the foundation of all account interaction; understanding them correctly is prerequisite to building anything. Many fields (SigningPubKey, TxnSignature) are added during signing; others (Fee, Sequence, LastLedgerSequence) are typically autofilled.
- **Chain:** all · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** Account (sender); TransactionType; Fee (integer drops); Sequence (exactly account's next, or 0 when using TicketSequence); Flags (bitwise, type-specific + global tfFullyCanonicalSig 0x80000000 deprecated under RequireFullyCanonicalSig); Memos (array of {Memo:{MemoData,MemoType,MemoFormat}} hex, ~1KB cap); SourceTag (uint32); LastLedgerSequence (expiry ledger); AccountTxnID (chain to prior tx hash); NetworkID (required on networks id>=1025, replay protection); SigningPubKey/TxnSignature (auto on sign); TicketSequence; Delegate (sender-on-behalf-of, pays fee).
- **Gotchas:** Sequence must be EXACTLY one greater than the account's last applied sequence — gaps stall all later transactions. Memos must be hex-encoded; the ~1KB total cap is easy to exceed. DestinationTag/SourceTag are NOT enforced unless the receiving account sets asfRequireDest — never assume tag routing is mandatory. tfFullyCanonicalSig is now a no-op (deprecated). NetworkID is mandatory on sidechains/custom networks (id>=1025) but must be omitted on mainnet (id 0).

### Idempotent retry on transaction results (tem/tef/ter/tec) · `pattern` · ● live ✓
Reliable mass payouts hinge on routing each transaction result to the correct retry decision, and on a LastLedgerSequence + tx-hash idempotency key so a retry can never double-pay. The five result classes have distinct meanings: tes = success; tec = applied-and-charged-but-failed (a ledger change happened, the fee was burned — do NOT retry, the slot/Sequence is consumed); ter = not-yet-applied, provisionally retried by the server, may succeed in a later ledger; tef = failed and cannot succeed in any future ledger (e.g. tefPAST_SEQ) — do NOT resubmit as-is; tem = malformed, will never succeed — fix the transaction, never blind-retry. The safe pattern: submit with a known LastLedgerSequence, poll for a validated result, and only consider a payout 'unsent' (eligible for a fresh attempt on a new Ticket/Sequence) once the original LastLedgerSequence has definitively passed without inclusion.
- **Chain:** xrpl-mainnet · **Maturity:** stable · **Use:** must-understand
- **Key fields / API:** {"tes": "tesSUCCESS — applied successfully; final once validated", "tec": "Applied to a ledger to charge the cost and possibly other side effects, but the intended action failed; NOT retried (retry would likely repeat); Sequence/Ticket consumed", "ter": "Not yet applied; server may auto-retry; could succeed in a future ledger (e.g. terQUEUED, terPRE_SEQ) — wait, do not resubmit a duplicate", "tef": "Failed, not in a ledger, but could have succeeded in some theoretical ledger; typically can no longer succeed in any future ledger (e.g. tefPAST_SEQ, tefMAX_LEDGER) — treat as terminal for that submission", "tem": "Malformed; cannot succeed under protocol rules; never applied — fix and rebuild, do not retry verbatim", "idempotency_key": "Validated tx hash + the txn's LastLedgerSequence; a payout is only re-eligible after that ledger passes with no inclusion", "finality_rule": "A submitted-but-unconfirmed txn is NOT safe to replace until its LastLedgerSequence is in the past (then it can never be included)"}
- **Gotchas:** Never resubmit on a tec — it already consumed the fee and the sequence slot; treat it as a (failed) outcome and reconcile, do not pay again. Never blind-retry a tem (malformed will fail identically) or a tef (terminal). ### Open-ledger fee escalation & transaction queue · `concept` · ● live ✓
The XRPL sets a soft per-ledger transaction target; once exceeded, the cost to be included in the current ('open') ledger escalates exponentially, and transactions that won't pay it are placed in a queue for a future ledger. For mass payouts this is the throughput governor: a flood of cheap Payments from one account will queue (capped at 10) and require rapidly increasing fees to jump the queue. Read open_ledger_fee and load_factor from server_info / server_state and set each Payment's Fee accordingly — pay the open-ledger cost to land this ledger, or pay the minimum and accept queueing. Sustained high-volume payouts should pace to ledger close and shard across accounts rather than fee-bidding into an exponential.
- **Chain:** xrpl-mainnet · **Amendment:** FeeEscalation · **Maturity:** stable · **Use:** must-understand
- **Key fields / API:** {"base_cost": "~10 drops (0.00001 XRP) reference cost per standard transaction under no load", "escalation": "Required cost rises exponentially each time the open-ledger target is exceeded within a ledger", "queue_cap_per_account": "At most 10 transactions queued per sending address at once", "queue_ordering": "Ranked by fee level (relative to the type's minimum), ties broken by tx hash ascending; same-sender txns ordered by Sequence", "priority_cost": "To push your queued txns into the open ledger you must pay enough to cover the open-ledger cost of this txn plus all your prior queued txns — compounds with queue depth", "signals": "server_info -> validated_ledger.base_fee_xrp, load_factor; server_state -> load_factor, load_base; use these to compute Fee before submit"}
- **Gotchas:** Do not hardcode 10-drop fees for a payout flood — under load they will silently queue and may expire. Queue ordering for a single sender is by Sequence, which is exactly why Ticket-based parallel sends behave better than Sequence-based ones under contention. ### Sequence vs Ticket submission management · `concept` · ● live ✓
Every transaction from an account consumes either the account's monotonically increasing Sequence number OR a reserved Ticket (via TicketSequence). Sequence forces strict ordering — txn N+1 cannot apply before N — which is a hard serialization bottleneck for payouts: one stuck or slow send blocks everything behind it. Tickets break that dependency, letting each payout advance independently. Choosing Sequence for a few ordered admin txns and Tickets for the parallel payout fan-out is the central design decision in a high-throughput sender.
- **Chain:** xrpl-mainnet · **Maturity:** stable · **Use:** must-understand
- **Key fields / API:** {"Sequence": "Per-account counter; each non-Ticket txn must use the next value, enforcing strict in-order application", "TicketSequence": "Spends a pre-reserved Ticket; does not advance Sequence, so multiple Ticket txns are mutually independent", "head-of-line_blocking": "A queued/stuck low-Sequence txn blocks all higher-Sequence txns from the same account until it clears or expires", "concurrency_model": "Tickets convert a strictly-ordered stream into a set of independent slots safe for parallel submission and per-slot retry", "local_tracking": "High-throughput senders track next-Sequence and the free-Ticket set client-side to avoid terPRE_SEQ / tefPAST_SEQ from racing submissions"}
- **Gotchas:** Mixing Sequence-based and Ticket-based sends carelessly causes ordering surprises — a Sequence txn submitted while many Ticket txns are in flight still slots by Sequence. Re-reading Sequence from the network mid-flood is racy; maintain it locally and reconcile against validated ledgers. Don't forget consumed Tickets free their reserve; a long-running service must refill Tickets to keep the parallel pool full.
