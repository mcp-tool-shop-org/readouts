On XRPL it is a first-class issued currency that integrates with the native DEX, AMM, payments, and escrow. Redeemable 1:1 for USD against a segregated cash/cash-equivalent reserve.

### RLUSD XRPL issuer flag configuration · `pattern` · ● live ✓
The exact, observable set of AccountSet flags Ripple uses on the live RLUSD issuing account — a reference blueprint for a production regulated stablecoin on XRPL. It demonstrates the canonical 'compliance via recourse' posture: keep the door open (no RequireAuth) but retain clawback and global-freeze authority, with rippling enabled so the token flows across the DEX.
- **Chain:** xrpl-mainnet · **Enabled:** 2024-12 · **Maturity:** stable · **Use:** recommended

DefaultRipple ON is required for the token to ripple between holders but increases the issuer's exposure surface — pair with a hot/cold (operational/issuing) wallet split.

### Token Clawback · `amendment` · ● live ✓
Lets a token issuer forcibly recover (claw back) issued tokens from a holder's balance — the key compliance lever for sanctioned-address recovery, fraud reversal, and court-ordered seizure. Disabled by default and must be armed before any tokens are issued. Applies to trust-line issued currencies; MPTs have an equivalent CanClawback flag.
- **Chain:** xrpl-mainnet · **XLS:** XLS-39d · **Amendment:** Clawback · **Enabled:** 2024-02 · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** Clawback transaction type; lsfAllowTrustLineClawback flag set via AccountSet (must be set when issuer has no trust lines yet); Amount/holder specified per claw-back; mutually exclusive with lsfNoFreeze considerations.
- **Gotchas:** Cannot be enabled after the issuer has issued tokens or has trust lines — it is a genesis-time decision. It is mutually exclusive with the No Freeze setting in spirit (an issuer wanting full irreversibility would set NoFreeze and forgo clawback). XRP itself has no issuer and can NEVER be clawed back — clawback only applies to issued tokens. Holders can see the flag, so clawback-armed tokens may be perceived as less trustless; institutions treat it as a feature, retail may not.
- **Build-focus tracks:** [identity-compliance](track-identity-compliance.md), [payments](track-payments.md)
- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed | net-check: mainnet-live | currency=current | Clawback amendment (XLS-39d) is enabled on mainnet allowing token recovery for regulatory compliance.
- **Sources:** [Clawing Back Tokens — XRPL.org](https://xrpl.org/docs/concepts/tokens/fungible-tokens/clawing-back-tokens) — Issuers can recover issued tokens from sanctioned or fraudulent accounts; clawback is disabled by default and enabled via the lsfAllowTrustLineClawback flag using AccountSet. ; [XLS-39d: Clawback — XRPLF/XRPL-Standards Discussion #94](https://github.com/XRPLF/XRPL-Standards/discussions/94) — XLS-39d specifies the Clawback transaction allowing an issuer to recover issued tokens for regulatory compliance.

### Token Freeze (individual, global, deep freeze) · `concept` · ● live ✓
Issuer controls to halt movement of issued tokens. Individual freeze locks a single holder's trust line; global freeze halts all transfers and DEX trading of the issuer's tokens; deep freeze (DeepFreeze amendment) additionally blocks the holder from sending OR receiving, closing a gap in the original freeze. The No Freeze flag permanently surrenders this power. RLUSD retains freeze authority (NoFreeze off).
- **Chain:** xrpl-mainnet · **Enabled:** 2014-09-15 · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** TrustSet with tfSetFreeze / tfSetDeepFreeze for individual lines; lsfGlobalFreeze via AccountSet for global; lsfNoFreeze (irreversible opt-out); DeepFreeze amendment enables the stricter variant.
- **Gotchas:** lsfNoFreeze is irreversible — once you renounce freeze you can never freeze again (a trust signal to holders, a loss of control for the issuer). Global freeze stops legitimate users too, so it is a break-glass action. Original individual freeze only stopped the holder from SENDING; DeepFreeze was added so a frozen holder also cannot receive — use deep freeze for true holds. XRP cannot be frozen (no issuer).
- **Build-focus tracks:** [identity-compliance](track-identity-compliance.md), [payments](track-payments.md)
- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed | net-check: mainnet-live | currency=current | Freeze capabilities including individual, global freeze and DeepFreeze amendment are mainnet-enabled.
- **Sources:** [Stablecoin Settings — XRPL.org](https://xrpl.org/docs/concepts/tokens/fungible-tokens/stablecoins/settings) — Issuers can freeze individual trust lines or enact a global freeze to enforce holds or stop suspected fraud. ; [Known Amendments — XRPL.org](https://xrpl.org/resources/known-amendments) — The DeepFreeze amendment is enabled on mainnet, extending freeze so a frozen holder can neither send nor receive the issuer's tokens.

### XRPL stablecoin issuer pattern (trust-line issued currency) · `pattern` · ● live ✓
The proven, battle-tested pattern for issuing a fiat-backed token on XRPL using native trust-line issued currencies. Three steps: choose a currency code, have holders create trust lines to the issuer, then send Payment transactions up to trust limits. Uses a hot/cold wallet split (cold = issuing address, hot = operational/distribution) for security. This is what RLUSD itself uses.
- **Chain:** xrpl-mainnet · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** Currency code (3-char ISO-like OR 40-char hex for longer/custom); TrustSet (holder establishes trust line + limit); Payment (issuer mints by paying out, holders transfer); AccountSet flags (DefaultRipple, RequireAuth, GlobalFreeze, NoFreeze, AllowTrustLineClawback); TransferRate (transfer fee); hot/cold two-account architecture.
- **Gotchas:** Sending issued tokens back to the issuer burns/redeems them (balance nets to zero). DefaultRipple must be ON for tokens to ripple between third parties. Each trust line costs the holder an owner reserve in XRP. Decide clawback at issuer genesis (cannot add later). Do NOT trade from the issuing (cold) address — use a separate hot account for DEX/AMM to maintain security boundaries. Issuers should complete Ripple's Token Issuer Self-Assessment Questionnaire for compliance.

- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed | net-check: mainnet-live | currency=current | Trust-line based stablecoin issuance is a native XRPL capability with RequireAuth and other compliance features.
- **Sources:** [Stablecoin Issuer — XRPL.org use cases](https://xrpl.org/docs/use-cases/tokenization/stablecoin-issuer) — The recommended pattern establishes a currency code, creates trust lines between issuer and holders, and sends payments up to agreed limits, separating trading from the issuing address. ; [Authorized Trust Lines — XRPL.org](https://xrpl.org/docs/concepts/tokens/fungible-tokens/authorized-trust-lines) — Enabling RequireAuth means other accounts can only hold the issuer's tokens after the issuer authorizes their trust lines.

### Credentials · `amendment` · ● live ✓
An on-ledger, privacy-preserving attestation primitive: a trusted issuer attaches a verifiable credential (e.g., 'KYC-passed', 'accredited investor') to an account, recording only PROOF of the credential on-chain while personal data stays off-ledger. It is the foundation of the XRPL permissioning stack and a prerequisite for Permissioned Domains.
- **Chain:** xrpl-mainnet · **XLS:** XLS-70 · **Amendment:** Credentials · **Enabled:** 2026-01 · **Maturity:** new · **Use:** recommended
- **Key fields / API:** CredentialCreate / CredentialAccept / CredentialDelete transactions; Credential ledger object holding issuer, subject, credential type, optional expiration and off-chain URI; consumed by PermissionedDomainSet and DepositAuth preauth.
- **Gotchas:** Credentials carry only a reference/proof — the actual identity data lives off-chain with the credential issuer; you must trust that issuer. Permissioned Domains require Credentials to be enabled; PermissionedDomainSet transactions are invalid without it. A credential is only as good as its issuer's vetting and revocation discipline — design for expiration and revocation.
- **Build-focus tracks:** [identity-compliance](track-identity-compliance.md)
- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed | net-check: mainnet-live | currency=current | Credentials amendment (XLS-70) is enabled on mainnet for off-chain credential verification.
- **Sources:** [Known Amendments — XRPL.org](https://xrpl.org/resources/known-amendments) — The Credentials (XLS-70) amendment is enabled on mainnet; PermissionedDomainSet transactions are invalid if Credentials is not also enabled. ; [Permissioned Domains and DEXs on XRPL: What We Learned — XRPL Commons](https://www.xrpl-commons.org/newsroom/permissioned-domains-and-dexes-on-xrpl-what-we-learned) — Only proof that a credential is valid is recorded on-chain while personal details remain off the ledger, enabling KYC and sanctions checks without exposing PII.

### Multi-Purpose Tokens (MPTs) · `standard` · ● live ✓
A native, compact fungible-token primitive purpose-built for RWA and institutional issuance — the modern alternative to trust-line tokens. MPTs use a simpler unidirectional model (no rippling, no balance netting), embed supply caps, transfer fees, lock/clawback/auth flags and on-chain metadata directly in the ledger, and require no smart contracts. Each issuance gets a unique 192-bit MPTokenIssuanceID instead of relying on currency codes.
- **Chain:** xrpl-mainnet · **XLS:** XLS-33 · **Amendment:** MPTokensV1 · **Enabled:** 2025-10-01 · **Maturity:** new · **Use:** recommended
- **Key fields / API:** MPTokenIssuanceCreate / MPTokenAuthorize / MPTokenIssuanceSet / MPTokenIssuanceDestroy transactions; flags lsfMPTCanTransfer, lsfMPTRequireAuth, lsfMPTCanLock, lsfMPTCanClawback, lsfMPTCanEscrow, lsfMPTCanTrade (DEX not yet implemented); MaximumAmount (supply cap), TransferFee (0-50% in 0.0001% increments), AssetScale; on-chain metadata <=1024 bytes (keys: t=ticker, n=name, ac=asset class rwa/defi/gaming, as=subclass stablecoin/treasury/equity/real_estate, in=issuer name, i=icon).
- **Gotchas:** Issuers cannot hold their own MPTs; returning an MPT to the issuer burns it. lsfMPTCanClawback and the immutable control flags must be chosen at issuance — they cannot be added later (DynamicMPT/XLS-94 to relax some metadata is still in development). MPT DEX trading (CanTrade) is not yet implemented, so MPTs do not yet trade on the native DEX/AMM the way trust-line tokens do — for tradable stablecoins today, trust-line issued currencies remain the path. Metadata is immutable today.
- **Build-focus tracks:** [game-economies](track-game-economies.md), [identity-compliance](track-identity-compliance.md), [nft-assets](track-nft-assets.md), [payments](track-payments.md)
- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed | net-check: mainnet-live | currency=current | MPTokensV1 amendment activated October 1, 2025, enabling native MPT standard with supply caps and compliance flags.
- **Sources:** [XLS-33: Multi-Purpose Tokens (MPTs)](https://xls.xrpl.org/xls/XLS-0033-multi-purpose-tokens.html) — XLS-33 defines Multi-Purpose Tokens as a native fungible-token standard with supply caps, transfer fees, lock/clawback/auth flags and on-chain metadata. ; [Multi-Purpose Tokens — XRPL.org](https://xrpl.org/docs/concepts/tokens/fungible-tokens/multi-purpose-tokens) — MPTs require the MPTokensV1 amendment and use a unidirectional model with flags Can Transfer, Require Auth, Can Lock, Can Clawback, and a unique 192-bit issuance ID rather than currency codes. ; [Multi-Purpose Token (MPT) standard goes live on XRP Ledger mainnet — Cryptopolitan](https://www.cryptopolitan.com/mpt-standard-on-xrp-ledger-mainnet/) — The MPTokensV1 amendment was activated on October 1 2025 after receiving 28 of 38 validator approvals, embedding the MPT standard for RWA issuance natively into the ledger.

### Permissioned Domains · `amendment` · ● live
Credential-gated zones on the public XRPL. A domain operator defines which credentials are accepted; any account holding a valid accepted credential automatically becomes a member. This lets institutions apply KYC/sanctions constraints to activity (e.g., who may participate in a liquidity venue) without forking the chain or moving off the public ledger.
- **Chain:** xrpl-mainnet · **XLS:** XLS-80 · **Amendment:** PermissionedDomains · **Enabled:** 2026-02-04 · **Maturity:** new · **Use:** recommended
- **Key fields / API:** PermissionedDomainSet / PermissionedDomainDelete transactions; PermissionedDomain ledger object listing accepted credential types/issuers; referenced by Permissioned DEX offers and other domain-aware features; requires Credentials amendment.
- **Gotchas:** Requires Credentials to be active — a domain references credential types, so the credential layer must exist first. Membership is dynamic: it follows credential validity, so revoking/expiring a credential changes membership. Activated on mainnet ~Feb 4 2026 after >91% validator support — relatively new, so tooling and ecosystem adoption are still maturing. Domains gate eligibility; they do not themselves move or custody assets.

### Tokenized real-world assets (RWA) on XRPL · `pattern` · ● live ✓
The institutional pattern of representing off-chain assets (treasuries, money-market funds, equity, fixed income, real estate, commercial paper) as on-ledger tokens, combining MPTs or trust-line tokens with the compliance stack (clawback, freeze, credentials, permissioned domains). XRPL RWA grew from ~$24M (2023) to ~$2B+ by early 2026, with Ondo (OUSG treasuries), Archax, Mercado Bitcoin and Guggenheim among issuers.
- **Chain:** xrpl-mainnet · **XLS:** XLS-33 · **Amendment:** MPTokensV1 · **Enabled:** 2025-10-01 · **Maturity:** new · **Use:** recommended

### AMM Clawback · `amendment` · ● live ✓
Extends clawback to tokens that are locked inside Automated Market Maker (AMM) pools, so a clawback-enabled issued token can participate in XRPL's native AMM without creating an un-recoverable gap. Without it, a clawback-armed token could not safely be added to an AMM; with it, regulated tokens get DEX/AMM liquidity while preserving issuer recovery authority.
- **Chain:** xrpl-mainnet · **Amendment:** AMMClawback · **Enabled:** 2025-01-30 · **Maturity:** stable · **Use:** situational
- **Key fields / API:** Activated via the AMMClawback amendment; lets issuer claw back a holder's share of token held in an AMM LP position; depends on Clawback + AMM amendments being active.
- **Gotchas:** Only relevant if your token has clawback enabled AND you want it in AMM pools — otherwise no action needed. Clawing back from an AMM affects the holder's LP position, not other LPs' assets; understand the pool-share mechanics before relying on it for enforcement. This is enabling infrastructure, not something most app builders call directly.

### Authorized Trust Lines (RequireAuth) · `concept` · ● live ✓
An allow-listing mechanism: when an issuer sets the Require Auth flag, no account can hold the issuer's token until the issuer explicitly authorizes that account's trust line. This is the strictest on-ledger holder gating for a trust-line stablecoin — used by issuers who need every holder pre-approved (e.g., permissioned securities). RLUSD deliberately does NOT use it.
- **Chain:** xrpl-mainnet · **Maturity:** stable · **Use:** situational
- **Key fields / API:** lsfRequireAuth flag set via AccountSet (must be set before issuing); TrustSet with tfSetfAuth by the issuer to authorize a specific holder's trust line; combine with DepositAuth for inbound payment gating.
- **Gotchas:** Must be enabled before issuing any tokens. Creates operational overhead — the issuer must authorize every single trust line, which doesn't scale for open retail distribution (hence RLUSD skips it and relies on clawback/freeze instead). For dynamic, credential-based gating that scales, prefer Permissioned Domains + Credentials over per-trust-line RequireAuth. RequireAuth gates HOLDING; DepositAuth gates RECEIVING payments — they are different controls.
- **Build-focus tracks:** [identity-compliance](track-identity-compliance.md)
- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed | net-check: mainnet-live | currency=current | RequireAuth flag is native XRPL functionality enabling authorized-only token holding.
- **Sources:** [Authorized Trust Lines — XRPL.org](https://xrpl.org/docs/concepts/tokens/fungible-tokens/authorized-trust-lines) — With the Require Auth flag enabled, other accounts can only hold the issuer's tokens if the issuer has authorized those accounts' trust lines. ; [Stablecoin Settings — XRPL.org](https://xrpl.org/docs/concepts/tokens/fungible-tokens/stablecoins/settings) — Authorized trust lines, freeze and clawback are documented as configurable compliance settings for a stablecoin issuer.

### Permissioned DEX · `amendment` · ● live
Brings credential-gated trading to XRPL's native decentralized exchange. Offers and order books can be scoped to a Permissioned Domain so only accounts holding the accepted credentials can place or match within that compliant book — giving institutions on-ledger 'compliant liquidity pools' while keeping the open public DEX separate. Completes the XRPL permissioning stack (Credentials + Domains + DEX).

### Issuer freeze & clawback controls for a real-value currency · `standard` · ● live ✓
The XRPL protocol-native toolkit that makes a real-value game currency operable under real-world rules: an issuer can freeze a holder's trust line (and DeepFreeze to also block incoming/outgoing), claw back issued tokens (Clawback amendment), and require authorization to hold the token (authorized trust lines). RLUSD itself runs with clawback + global/deep freeze + deposit auth enabled, specifically so Ripple can comply with court orders and law enforcement. For a studio issuing its own backed currency, these are the levers for fraud reversal, sanctioned-wallet freezing, and refund handling -- the on-chain half of a compliance program. Distinct from generic IOU mechanics: this is the deliberate compliance-control surface.
- **Chain:** xrpl-mainnet · **XLS:** XLS-77d · **Amendment:** DeepFreeze · **Enabled:** 2025-02-10 · **Maturity:** production · **Use:** live

### Regulatory & compliance reality of paying players real value · `concept` · ● live ✓

### Stablecoin-pegged / stablecoin-backed in-game currency · `pattern` · ● live ✓
Issuing your OWN game currency as an XRPL IOU and pegging or fully backing it to RLUSD, rather than handing players raw RLUSD. You control the token (name, transfer fee, freeze, authorized trust lines), while RLUSD is the reserve/redemption asset. Two flavors: (1) soft-peg -- a display/quoting peg where your token is just a points balance redeemable for RLUSD at a fixed rate at the cash-out boundary; (2) hard-backed -- you hold 1 RLUSD in reserve per unit minted and let players redeem on demand. The on-chain swap between your IOU and RLUSD can run on XRPL's native DEX/AMM, but the BACKING (holding the RLUSD reserve, honoring redemption) is your application-layer obligation.
- **Chain:** xrpl-mainnet · **Maturity:** production · **Use:** live
- **Key fields / API:** Your token: a normal XRPL trust-line IOU you issue. Issuer controls available: TransferFee (built-in fee on secondary transfers), lsfGlobalFreeze / DeepFreeze, lsfAllowTrustLineClawback (must be set BEFORE issuance), RequireAuth (authorized trust lines) to whitelist holders, TickSize. Native DEX + AMM (XLS-30) can provide an on-ledger your-token<->RLUSD market. Redemption math: 1 unit = fixed RLUSD; reserve held off-chain or in a treasury wallet.
- **Gotchas:** A token you can freeze/claw back/whitelist is the right call for a controlled game economy, but it is NOT decentralized money -- be honest with players. If you hard-back it, you are now custodying RLUSD against a redeemable liability, which can look like issuing a stablecoin yourself (potential GENIUS-Act/money-transmitter exposure) -- soft-peg points that are only redeemed at a regulated boundary is the safer default. lsfAllowTrustLineClawback can ONLY be enabled when the issuing account has issued nothing yet; retrofitting is impossible, so decide at genesis. An AMM pool exposes your peg to arbitrage and impermanent loss; a managed redemption desk avoids that but is centralized. RequireAuth means every player must be individually authorized -- great for compliance, heavy for onboarding.
