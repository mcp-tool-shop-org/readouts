### Authorized Trust Lines (RequireAuth) · `concept` · ● live ✓
An issuer can set the RequireAuth flag so that no holder can hold its tokens until the issuer explicitly authorizes that holder's trust line — an allow-list / KYC gate at the protocol level. After RequireAuth is set, the issuer authorizes a line by sending a TrustSet from the issuing address naming the holder, value 0, with the tfSetfAuth flag.
- **Chain:** xrpl-mainnet · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** AccountSet asfRequireAuth (must be set before issuing); account flag lsfRequireAuth; TrustSet tfSetfAuth (issuer-only, cannot be cleared); trust-line flags lsfLowAuth/lsfHighAuth.
- **Gotchas:** RequireAuth must be enabled before the account issues any tokens. Authorization is one-way: tfSetfAuth cannot be cleared once granted (revocation is done via freeze/clawback, not de-authorization). Every new holder requires an issuer transaction, which adds operational overhead for large user bases — consider MPT RequireAuth instead for new projects.
- **Build-focus tracks:** [identity-compliance](track-identity-compliance.md), [payments](track-payments.md)
- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed | net-check: mainnet-live | currency=current | RequireAuth trust line authorization is core XRPL functionality.
- **Sources:** [Authorized Trust Lines](https://xrpl.org/docs/concepts/tokens/fungible-tokens/authorized-trust-lines) — With RequireAuth set, an issuer must authorize each holder's trust line via TrustSet with tfSetfAuth before they can hold the token.

### Issued Currencies (IOUs) & Trust Lines · `concept` · ● live ✓
Issued currencies (IOUs) are tokens represented as balances on bidirectional trust lines between an issuer and a holder, stored as RippleState ledger entries. A holder opens or modifies a trust line with a TrustSet transaction declaring a currency code, issuer, and credit limit. This is the original XRPL fungible-token model and underpins stablecoins, fiat representations, and most DEX/AMM liquidity. Each trust line consumes an owner reserve, so issuers and holders must budget XRP reserves.
- **Chain:** xrpl-mainnet · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** TrustSet: LimitAmount {currency, issuer, value}, Flags (tfSetNoRipple, tfSetfAuth, tfSetFreeze). RippleState: Balance, LowLimit, HighLimit, HighNode/LowNode, Flags. Currency codes: 3-char standard or 40-char hex. Owner reserve per trust line.
- **Gotchas:** Each trust line costs an owner reserve in XRP for the account holding it; mass distribution scales reserve cost. Balances net bidirectionally and can ripple between holders of the same issuer unless NoRipple is set. A trust line with limit 0 and zero balance can be deleted to reclaim reserve. Currency 'XRP' is reserved/invalid as an issued code.
- **Build-focus tracks:** [game-economies](track-game-economies.md), [identity-compliance](track-identity-compliance.md), [payments](track-payments.md)
- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed | net-check: mainnet-live | currency=current | Core XRPL functionality since inception, trust lines and RippleState entries are fundamental.
- **Sources:** [Trust Line Tokens](https://xrpl.org/docs/concepts/tokens/fungible-tokens/trust-line-tokens) — Issued currencies on XRPL are held as balances on bidirectional trust lines between an issuer and a holder. ; [RippleState ledger entry](https://xrpl.org/docs/references/protocol/ledger-data/ledger-entry-types/ripplestate) — A RippleState entry stores a trust line's balance and limits between two accounts for one currency.

### Rippling, NoRipple & Default Ripple · `concept` · ● live ✓
Rippling is atomic net settlement of balances among parties who hold the same issuer's currency, letting one holder pay another with the issuer as a passive intermediary. The No Ripple flag (set per trust line via TrustSet tfSetNoRipple) prevents a line from rippling. The account-level Default Ripple setting determines the default NoRipple state for new trust lines: when Default Ripple is disabled (the account default), new lines default to NoRipple enabled.
- **Chain:** xrpl-mainnet · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** TrustSet flags tfSetNoRipple / tfClearNoRipple; trust-line flag lsfNoRipple (lsfLowNoRipple/lsfHighNoRipple); AccountSet asfDefaultRipple flag; account flag lsfDefaultRipple.
- **Gotchas:** Issuers MUST enable Default Ripple so that holders can pay each other through them — without it, the issuer's own lines block rippling and the token does not circulate. Conversely, ordinary users and operational/treasury wallets should keep NoRipple set to avoid unwanted value flowing across their lines. NoRipple only has an effect when set on BOTH sides relevant to a path. This is a top source of 'why won't my token move' bugs.
- **Build-focus tracks:** [game-economies](track-game-economies.md), [payments](track-payments.md)
- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed | net-check: mainnet-live | currency=current | Core trust line behavior controls, fully operational on mainnet.
- **Sources:** [Rippling](https://xrpl.org/docs/concepts/tokens/fungible-tokens/rippling) — Rippling is atomic net settlement between parties trusting the same issuer, controllable via the No Ripple flag. ; [Default Ripple](https://xrpl.org/docs/concepts/tokens/fungible-tokens/rippling) — When Default Ripple is disabled, new trust lines default to NoRipple enabled; issuers must enable Default Ripple to let their token circulate.

### TrustSet Transaction · `transaction` · ● live ✓
TrustSet creates or modifies a trust line linking two accounts for a specific issued currency. Holders use it to declare a credit limit (LimitAmount) toward an issuer; issuers use it to authorize trust lines (with tfSetfAuth) and to set per-line flags such as NoRipple and Freeze. It is the single transaction that drives nearly all IOU lifecycle operations from the relationship side.
- **Chain:** xrpl-mainnet · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** LimitAmount {currency, issuer, value}; Flags: tfSetfAuth, tfSetNoRipple/tfClearNoRipple, tfSetFreeze/tfClearFreeze, tfSetDeepFreeze/tfClearDeepFreeze; QualityIn, QualityOut.
- **Gotchas:** tfSetfAuth can only be set by the issuer and cannot be cleared once set. Setting a trust line authorization (RequireAuth flow) requires submitting TrustSet from the issuing address with the holder as the issuer of LimitAmount and value 0. Deep freeze flags require the standard freeze to already be in place. Quality fields (QualityIn/QualityOut) affect exchange rates and are easy to misconfigure.
- **Build-focus tracks:** [game-economies](track-game-economies.md), [identity-compliance](track-identity-compliance.md), [payments](track-payments.md)
- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed | net-check: mainnet-live | currency=current | Standard transaction type for managing trust lines, live since XRPL launch.
- **Sources:** [TrustSet](https://xrpl.org/docs/references/protocol/transactions/types/trustset) — TrustSet creates or modifies a trust line and can set per-line flags including auth, NoRipple, and freeze.

### IOU vs MPT — Decision Guide · `pattern` · ● live ✓
Choosing between trust-line IOUs and MPTs is the central token decision in mid-2026. Pick MPTs for NEW issuances that want native on-chain metadata, a hard supply cap, bundled per-issuance controls (auth/lock/clawback), and low reserve/relationship overhead for many holders — the recommended default for fresh stablecoin/RWA projects. Pick IOUs when you need deep DEX/AMM liquidity and pathfinding/rippling TODAY, interop with the large existing token ecosystem, or arbitrary decimal precision, since MPT DEX/AMM support is still maturing (MPTokensV2 in development).
- **Chain:** xrpl-mainnet · **XLS:** XLS-33 · **Amendment:** MPTokensV1 · **Enabled:** 2025-10-01 · **Maturity:** new · **Use:** recommended
- **Key fields / API:** Decision axes: liquidity needs (DEX/AMM today -> IOU), holder scale & reserve cost (large -> MPT), need for on-chain metadata/supply cap (-> MPT), need for mutable controls later (-> IOU now, watch DynamicMPT), rippling/pathfinding (-> IOU), precision (arbitrary decimals -> IOU, fixed integer+scale -> MPT).
- **Gotchas:** MPT capability flags are immutable in V1 — mis-scoping at mint is unrecoverable; IOU controls are more retrofittable but with their own pre-issuance gotchas (clawback/RequireAuth must precede issuance). MPTs cannot yet be traded on the native DEX/AMM in V1. Do not assume an IOU and a same-named MPT are interchangeable — they are separate ledger systems. Neither model applies to XRP, which carries no issuer controls at all.
- **Build-focus tracks:** [game-economies](track-game-economies.md), [identity-compliance](track-identity-compliance.md), [nft-assets](track-nft-assets.md), [payments](track-payments.md)
- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed | net-check: mainnet-live | currency=current | Valid comparison between trust-line tokens and MPTs, both available on mainnet.
- **Sources:** [Tokens overview](https://xrpl.org/docs/concepts/tokens) — XRPL offers trust-line tokens and Multi-Purpose Tokens as distinct fungible-token models with different trade-offs. ; [Multi-Purpose Tokens vs trust lines](https://xrpl.org/docs/concepts/tokens/fungible-tokens/multi-purpose-tokens) — MPTs differ from trust-line tokens by being unidirectional, fixed-precision, metadata-carrying, and lower-overhead, but with maturing DEX support.

### MPT Controls (Lock, RequireAuth, Clawback, Transfer Fee, Metadata) · `concept` · ● live ✓
MPTs bundle their issuer controls into per-issuance capability flags and fields rather than separate account-wide settings. lsfMPTCanLock enables locking (freeze) of individual or all balances via MPTokenIssuanceSet; lsfMPTRequireAuth enables allow-listing; lsfMPTCanClawback enables a Clawback against MPT holders; lsfMPTCanTransfer enables peer-to-peer transfer; a per-issuance transfer fee (0–50%) is burned on transfer; and a 1024-byte on-chain JSON metadata field carries ticker/name/icon/asset-class.
- **Chain:** xrpl-mainnet · **XLS:** XLS-33 · **Amendment:** MPTokensV1 · **Enabled:** 2025-10-01 · **Maturity:** new · **Use:** recommended
- **Key fields / API:** Issuance flags: lsfMPTCanLock, lsfMPTRequireAuth, lsfMPTCanClawback, lsfMPTCanTransfer, lsfMPTCanEscrow, lsfMPTCanTrade. MPTokenIssuanceSet (tfMPTLock/tfMPTUnlock). TransferFee field (0–50%, burned). MPTokenMetadata (<=1024 bytes JSON). Clawback transaction works against MPT holders when CanClawback set.
- **Gotchas:** These capabilities are decided at MPTokenIssuanceCreate and (in V1) cannot be enabled afterward — a token minted without lsfMPTCanClawback can never be clawed back, without lsfMPTCanLock can never be frozen. Locking applies per-holder or globally via MPTokenIssuanceSet. lsfMPTCanTrade is reserved but DEX trading not implemented in V1. DynamicMPT (in development) will allow some properties to be mutable. MPT transfer fee (0–50%) differs in cap and mechanism from IOU TransferRate (0–100%).
- **Build-focus tracks:** [game-economies](track-game-economies.md), [identity-compliance](track-identity-compliance.md), [payments](track-payments.md)
- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed | net-check: mainnet-live | currency=current | MPT capability flags and controls implemented per XLS-33 specification.
- **Sources:** [Multi-Purpose Tokens (controls)](https://xrpl.org/docs/concepts/tokens/fungible-tokens/multi-purpose-tokens) — MPT issuer controls are per-issuance flags (CanLock, RequireAuth, CanClawback, CanTransfer) plus a 0–50% burned transfer fee and 1024-byte JSON metadata. ; [XLS-0033 capability flags](https://xls.xrpl.org/xls/XLS-0033-multi-purpose-tokens.html) — XLS-33 defines the MPT capability flag set determining lock, auth, clawback, transfer, escrow, and trade behavior.

### MPTokenAuthorize (Hold / Authorize an MPT) · `transaction` · ● live ✓
MPTokenAuthorize is the transaction a prospective holder sends to opt in to receiving a given MPT (creating an MPToken object on their account), analogous to opening a trust line but far lighter. When the issuance has lsfMPTRequireAuth set, the issuer also uses MPTokenAuthorize to authorize (allow-list) a specific holder. It can also be used by a holder to remove their MPToken when balance is zero.
- **Chain:** xrpl-mainnet · **XLS:** XLS-33 · **Amendment:** MPTokensV1 · **Enabled:** 2025-10-01 · **Maturity:** new · **Use:** recommended
- **Key fields / API:** MPTokenAuthorize: MPTokenIssuanceID; Holder (set by issuer when authorizing under RequireAuth); Flags (tfMPTUnauthorize to opt out / remove). Creates/deletes an MPToken ledger object.
- **Gotchas:** Under RequireAuth, BOTH steps are needed: the holder opts in AND the issuer authorizes — order and roles confuse newcomers. A holder cannot remove their MPToken while it still holds a nonzero balance. The much-lower reserve/relationship footprint vs trust lines is the main reason MPTs scale better for large holder counts.

### MPTokenIssuanceCreate (Issue an MPT) · `transaction` · ● live ✓
MPTokenIssuanceCreate is the transaction an issuer submits to mint a new Multi-Purpose Token, producing an MPTokenIssuance ledger entry and a unique MPT Issuance ID. It sets the token's permanent configuration: capability flags, supply cap (MaximumAmount), transfer fee, asset scale, and on-chain metadata. Companion transactions are MPTokenIssuanceDestroy (delete an empty issuance) and MPTokenIssuanceSet (toggle lock/unlock and limited mutable settings).
- **Chain:** xrpl-mainnet · **XLS:** XLS-33 · **Amendment:** MPTokensV1 · **Enabled:** 2025-10-01 · **Maturity:** new · **Use:** recommended
- **Key fields / API:** MPTokenIssuanceCreate: Flags (tfMPTCanLock, tfMPTRequireAuth, tfMPTCanEscrow, tfMPTCanTrade, tfMPTCanTransfer, tfMPTCanClawback), MaximumAmount, TransferFee, AssetScale, MPTokenMetadata (hex-encoded JSON). Related: MPTokenIssuanceSet, MPTokenIssuanceDestroy.
- **Gotchas:** Most flags are immutable post-creation in V1 — a missing tfMPTCanTransfer or tfMPTCanClawback cannot be added later. MPTokenMetadata is a single hex blob capped at 1024 bytes; oversized or malformed JSON fails. MPTokenIssuanceDestroy only works when no tokens are outstanding. Plan the full control surface before minting.

### Multi-Purpose Tokens (MPTs) · `standard` · ● live ✓
Multi-Purpose Tokens (XLS-33) are a native XRPL fungible-token type optimized for stablecoins and real-world assets, enabled on mainnet by the MPTokensV1 amendment around 2025-10-01. Unlike trust-line IOUs, an MPT is a single MPTokenIssuance ledger object identified by a 192-bit MPT Issuance ID, is unidirectional (clean holder/issuer separation, no balance netting, no rippling), uses fixed-precision integers, carries on-chain JSON metadata, and exposes per-issuance capability flags. It dramatically reduces the relationship/reserve overhead of mass token distribution.
- **Chain:** xrpl-mainnet · **XLS:** XLS-33 · **Amendment:** MPTokensV1 · **Enabled:** 2025-10-01 · **Maturity:** new · **Use:** recommended
- **Key fields / API:** MPTIssuanceID (192-bit); on-chain metadata (up to 1024 bytes JSON: ticker, name, icon URI, asset class/subclass, issuer name, URIs); MaximumAmount (supply cap); TransferFee (0–50%, 0.0001% increments, burned); AssetScale; issuance flags lsfMPTCanTransfer, lsfMPTRequireAuth, lsfMPTCanLock, lsfMPTCanClawback, lsfMPTCanEscrow, lsfMPTCanTrade.
- **Gotchas:** Capability flags are mostly FIXED at issuance and cannot be added later in V1 — decide CanTransfer/CanClawback/CanLock/RequireAuth up front (DynamicMPT, in development, will relax some of this). Without lsfMPTCanTransfer the token is non-transferable (holder<->issuer only). lsfMPTCanTrade exists but DEX/AMM trading of MPTs is not yet implemented in V1 (MPTokensV2 in development). MaximumAmount is a hard cap. MPTs and IOUs are separate systems — an MPT is not interchangeable with a same-named IOU.

- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed | net-check: mainnet-live | currency=current | MPTokensV1 amendment (XLS-33) activated on mainnet around 2025-10-01 as reported.
- **Sources:** [Multi-Purpose Tokens](https://xrpl.org/docs/concepts/tokens/fungible-tokens/multi-purpose-tokens) — MPTs are unidirectional fixed-precision tokens with a 192-bit issuance ID, on-chain JSON metadata, and per-issuance capability flags, enabled by MPTokensV1. ; [XLS-0033: Multi-Purpose Tokens](https://xls.xrpl.org/xls/XLS-0033-multi-purpose-tokens.html) — XLS-33 defines the MPT standard for efficient native fungible tokens distinct from trust-line IOUs. ; [MPT standard goes live on XRP Ledger mainnet](https://www.cryptopolitan.com/mpt-standard-on-xrp-ledger-mainnet/) — The MPTokensV1 amendment activated on mainnet around 2025-10-01 after reaching the required validator approvals.

### Clawback as an economy-recall lever (IOU + MPT) · `transaction` · ● live ✓
Clawback lets the issuer forcibly recover issued tokens from a holder's balance — the single most important anti-exploit lever for a live game economy (recall duplicated gold from an exploited mint bug, drain a confirmed botter/RMT account, reverse a fraudulent transfer). For IOUs, the issuer enables it with the lsfAllowTrustLineClawback AccountSet flag BEFORE issuing, then sends a Clawback transaction. For MPTs, the issuer must set tfMPTCanClawback at issuance and then claw back from a holder's MPToken. Clawback never applies to native XRP.
- **Chain:** xrpl-mainnet · **XLS:** XLS-39 · **Amendment:** Clawback · **Enabled:** 2024-02-08 · **Maturity:** production · **Use:** recommended
- **Key fields / API:** IOU: AccountSet asfAllowTrustlineClawback (must be set before any tokens issued; one-way, cannot be disabled) then Clawback tx; MPT: tfMPTCanClawback(0x40) at MPTokenIssuanceCreate then Clawback tx referencing the holder + MPTokenIssuanceID; cannot claw back XRP
- **Gotchas:** Must be opted in BEFORE issuance for both models — you cannot enable clawback on an IOU after any token is issued, and MPT flags are immutable, so a currency minted without the clawback flag is permanently un-recallable. This is a powerful, irreversible (for the holder) action: pair it with a named compensator/audit trail and clear ToS, since players experience a clawback as confiscation. Clawing back does not by itself stop the holder from re-acquiring the currency — combine with Freeze/Lock to fully sanction.
- **Build-focus tracks:** [game-economies](track-game-economies.md), [identity-compliance](track-identity-compliance.md)
- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed | net-check: mainnet-live | currency=current | Clawback amendment (XLS-39) enabled Feb 2024 for both IOU and MPT.
- **Sources:** [Clawback (concepts)](https://xrpl.org/docs/concepts/tokens/fungible-tokens/clawing-back-tokens) — Clawback lets issuers recover issued tokens; the issuer must enable the AllowTrustLineClawback account flag before issuing, and it cannot be used with XRP. ; [XRP Ledger Clawback Amendment Goes Live on Mainnet](https://coingape.com/xrp-ledger-xrpl-clawback-amendment-goes-live-on-mainnet/) — The Clawback amendment was enabled on XRPL mainnet on February 8, 2024 and complements the existing Freeze feature; it cannot be used with XRP.

### Freeze tiers as sanction levers (Individual / Global / Deep Freeze) · `concept` · ● live
For IOU game currencies the issuer has a graduated sanction ladder. Individual Freeze (tfSetFreeze on a trust line) stops a specific holder from sending the currency to anyone but the issuer and unfunds their offers, while they can still RECEIVE — good for a temporary penalty. Deep Freeze (XLS-77, enabled 2025-05-05) extends Individual Freeze so the holder also cannot RECEIVE the currency — a full quarantine of an abusive account. Global Freeze (lsfGlobalFreeze) halts the entire currency at once — the doomsday circuit-breaker for a compromised issuer or planned shutdown.
- **Chain:** xrpl-mainnet · **XLS:** XLS-77 · **Amendment:** DeepFreeze · **Enabled:** 2025-05-05 · **Maturity:** production · **Use:** recommended
- **Key fields / API:** Individual: TrustSet tfSetFreeze / tfClearFreeze; Deep Freeze: TrustSet tfSetDeepFreeze / tfClearDeepFreeze (requires DeepFreeze amendment); Global: AccountSet asfGlobalFreeze (lsfGlobalFreeze); permanence: AccountSet asfNoFreeze (lsfNoFreeze) PERMANENTLY disables individual freeze and global-freeze-clear (master-key only)
- **Gotchas:** Setting lsfNoFreeze is irreversible and disables your individual-freeze AND your ability to ever clear a global freeze — only choose it as a public trust commitment, never by accident. ### IOU trust-line token as uncapped soft currency · `standard` · ● live ✓
Trust-line issued currencies (IOUs) have NO supply-cap field: the issuer mints by paying out and can mint without limit, which is exactly what a SOFT earned currency wants (gold, XP-shop coin, daily-reward currency that you sink as fast as you mint). IOU config (Freeze, RequireAuth, TransferRate, NoFreeze) is mutable over the life of the issuer account, so soft-currency policy can evolve. IOUs also have the most mature DEX/AMM, wallet, and explorer support today, so a soft currency that needs to be tradeable or pooled works immediately, unlike MPT DEX which is not yet on mainnet.
- **Chain:** xrpl-mainnet · **Maturity:** production · **Use:** recommended
- **Key fields / API:** Issuer mints via Payment from the issuing account; no MaximumAmount (supply governed by off-ledger issuer policy); TransferRate (transfer fee, 1000000000=0%); AccountSet flags lsfDefaultRipple, lsfRequireAuth, lsfGlobalFreeze, lsfNoFreeze; currency code (3-char or 160-bit hex) is the identity (non-unique across issuers)
- **Gotchas:** No protocol scarcity guarantee — uncapped supply is a feature for soft currency but a liability if you intended scarcity; use MPT for hard currency instead. Currency-code identity is NOT unique (collisions across issuers), so always pair currency+issuer. Bidirectional rippling can create surprise balance paths; set lsfDefaultRipple deliberately and freeze/NoFreeze with intent. Each holder's trust line costs the HOLDER 0.2 XRP reserve.
- **Build-focus tracks:** [game-economies](track-game-economies.md)
- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed | net-check: mainnet-live | currency=current | Trust-line tokens have existed since XRPL inception with no supply cap.
- **Sources:** [Trust Line Tokens](https://xrpl.org/docs/concepts/tokens/fungible-tokens/trust-line-tokens) — Trust-line tokens are bidirectional with rippling and identified by currency code + issuer; they have no protocol supply cap. ; [Multi-Purpose Tokens (concepts) - MPT vs trust line](https://xrpl.org/docs/concepts/tokens/fungible-tokens/multi-purpose-tokens) — The bidirectional, rippling model of trust-line tokens is intentionally omitted from MPT; each MPT issuance is separate with no rippling.

### MPT as fixed-supply hard currency (MaximumAmount cap) · `pattern` · ● live ✓
An MPToken issuance carries a protocol-enforced MaximumAmount (1 to 2^63-1 integer units), making it the natural primitive for a HARD in-game currency where total supply is a designed, auditable constant (premium gems, a deflationary trophy currency, a scarce governance token). The cap lives in the MPTokenIssuance ledger entry and the ledger refuses any mint that would push circulating supply past it. Because MPT uses fixed-precision integers with AssetScale for the decimal point, there is no rippling and no surprise inflation path. If holders burn tokens back to the issuer, the issuer may re-mint up to the cap, so the cap bounds MAX circulating, not lifetime mints.
- **Chain:** xrpl-mainnet · **XLS:** XLS-33 · **Amendment:** MPTokensV1 · **Enabled:** 2025-10-01 · **Maturity:** production · **Use:** recommended
- **Key fields / API:** MPTokenIssuanceCreate.MaximumAmount (UInt64, 1..9223372036854775807); AssetScale (UInt8 0..255, decimal places, default 0); MPTokenIssuance ledger entry holds OutstandingAmount vs MaximumAmount; supply cap immutable post-create
- **Gotchas:** MaximumAmount is set once and cannot be raised later (no minted-supply migration without a new issuance) — pick the cap with headroom. There is NO cap field on trust-line IOUs, so if you need hard scarcity you MUST use MPT, not an IOU with an off-ledger promise. AssetScale only moves the decimal point for display/precision; it does not add to the cap. MPT DEX trading is not yet on mainnet (XLS-82 in development), so a capped premium MPT cannot be market-traded natively in mid-2026.

- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed | net-check: mainnet-live | currency=current | MPTokensV1 amendment is live with MaximumAmount cap as described.
- **Sources:** [Multi-Purpose Tokens (concepts)](https://xrpl.org/docs/concepts/tokens/fungible-tokens/multi-purpose-tokens) — MaximumAmount ranges 0 to 2^63-1; if holders burn tokens back to the issuer, the issuer can re-issue up to the cap. ; [MPTokenIssuanceCreate](https://xrpl.org/docs/references/protocol/transactions/types/mptokenissuancecreate) — MaximumAmount is a UInt64 (1..9223372036854775807); AssetScale is a UInt8 setting decimal places; fields set at creation are immutable.

### MPTokenIssuanceCreate — issuer config for a game currency · `transaction` · ● live ✓
MPTokenIssuanceCreate is the single transaction that defines a game currency's entire on-chain policy in one shot: supply cap, decimals, transfer fee, capability flags, and metadata. Because every field is IMMUTABLE after creation (until/unless XLS-94 mutable-fields ships), this transaction is the most consequential design decision in the whole token economy — get the flags right or re-issue a new currency. It costs the issuer 0.2 XRP owner reserve per issuance, and one account can create many distinct issuances (e.g., gems + gold + faction-scrip) without separate accounts.
- **Chain:** xrpl-mainnet · **XLS:** XLS-33 · **Amendment:** MPTokensV1 · **Enabled:** 2025-10-01 · **Maturity:** production · **Use:** recommended

- **Gotchas:** All config is immutable after create — there is no 'edit the currency' transaction in mid-2026 (XLS-94 still proposed). A non-transferable MPT (tfMPTCanTransfer off) CANNOT have a transfer fee and is only usable issuer<->holder. tfMPTCanClawback and tfMPTCanLock MUST be chosen at create time; you cannot retrofit clawback or freeze onto an already-minted MPT, so an anti-exploit recall lever must be opted in up front. Decide AssetScale carefully: integer-only math means scale defines your smallest spendable unit forever.

### Per-holder owner reserve as a multi-currency design budget · `concept` · ● live ✓
Every distinct token a PLAYER holds costs them owner reserve: each trust-line (RippleState) and each MPToken object is one ledger object at the current 0.2 XRP per-object reserve. A 'currency per faction / per dungeon / per season' design therefore charges the player real, locked XRP that scales linearly with the number of token types — the silent constraint that should bound multi-currency ambition. Design few, meaningful currencies (premium + earned, maybe one event currency) rather than a sprawling currency zoo, and account for who funds the reserve (player wallet vs studio-sponsored accounts).
- **Chain:** xrpl-mainnet · **Maturity:** production · **Use:** recommended
- **Key fields / API:** Owner reserve currently 0.2 XRP per owned object; base account reserve currently 1 XRP; each IOU trust line = 1 object; each MPToken = 1 object; reserves are XRP LOCKED (released when the object is deleted), not spent; reserve values are themselves amendment-tunable
- **Gotchas:** Reserve is charged to the HOLDER, not the issuer, so a free-to-play game that hands out 8 currencies forces every player to lock ~1.6 XRP just to hold them — a real onboarding tax. Reserve amounts have changed via amendment historically (do not hardcode 0.2 XRP — read the current fee/reserve from server_state). Authorizing an MPT with RequireAuth still creates a zero-balance MPToken object that costs reserve. Sponsored/abstracted-account designs can shift this cost to the studio but add custody and operational burden.

- **Sources:** [Reserves](https://xrpl.org/docs/concepts/accounts/reserves) — Each ledger object an account owns (including trust lines and MPToken objects) increases its owner reserve by the per-object reserve (0.2 XRP currently); reserves are tunable by amendment. ; [Multi-Purpose Tokens (concepts) - holder objects](https://xrpl.org/docs/concepts/tokens/fungible-tokens/multi-purpose-tokens) — Each holder's MPT balance is tracked as an MPToken object in the holder's owner directory, consuming reserve like a trust line.

### Two-currency design: premium MPT + earned IOU · `pattern` · ● live ✓
The canonical XRPL game-economy pattern in mid-2026 splits hard and soft money across the two primitives that fit each best. Premium/hard currency = a capped MPT with tfMPTCanClawback and (optionally) tfMPTRequireAuth — scarce, recallable on exploit, allow-listed if regulated. Earned/soft currency = an uncapped IOU (or an uncapped-by-policy MPT) — mint-on-demand for rewards, freely sinkable, DEX/AMM-tradeable today. This mirrors the dual-currency model proven in live-service games (a bought currency you protect hard, an earned currency that flows) while respecting each XRPL primitive's strengths.
- **Chain:** xrpl-mainnet · **Maturity:** production · **Use:** recommended
- **Key fields / API:** Premium: MPTokenIssuanceCreate with MaximumAmount cap + tfMPTCanClawback + tfMPTCanLock (+ tfMPTRequireAuth if gated) + tfMPTCanTransfer policy; Earned: IOU with asfAllowTrustlineClawback set pre-issue + freeze flags + lsfDefaultRipple decision; budget 0.2 XRP holder reserve PER currency held
- **Gotchas:** Two currencies = two holder objects = ~0.4 XRP player reserve minimum; do not multiply beyond what the economy needs. Keep premium currency NON-tradeable on DEX (or note MPT DEX is not live yet) if you want to prevent secondary markets for bought gems; conversely a tradeable earned currency invites RMT — pair with clawback/freeze policy. Decide transferability per currency: a soulbound premium currency uses tfMPTCanTransfer off (and then cannot carry a transfer fee). Document the immutable MPT choices since they cannot be changed after launch.
- **Build-focus tracks:** [game-economies](track-game-economies.md)
- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed | net-check: mainnet-live | currency=current | MPT offers controlled issuance while IOU supports uncapped supply.
- **Sources:** [Multi-Purpose Tokens (concepts)](https://xrpl.org/docs/concepts/tokens/fungible-tokens/multi-purpose-tokens) — MPT supports per-issuance flags (CanTransfer, CanClawback, CanLock, RequireAuth) and a MaximumAmount cap, suited to controlled/loyalty tokens; one account can issue many distinct MPTs. ; [Trust Line Tokens](https://xrpl.org/docs/concepts/tokens/fungible-tokens/trust-line-tokens) — Trust-line IOUs have no supply cap and mature DEX/AMM support, fitting freely-minted soft currency.

### Deep Freeze · `amendment` · ● live ✓
Deep Freeze extends individual trust-line freeze so a frozen holder can no longer RECEIVE the token either — closing the gap where standard freeze still allowed incoming balance. It affects payments, offers, the DEX, and AMM interactions. The issuer must apply a standard freeze before enacting a deep freeze.

- **Gotchas:** You cannot deep-freeze a line that is not already standard-frozen, and you must clear deep freeze before clearing the standard freeze. Applies to issued tokens only (not XRP). Reaches into DEX/AMM so deep-frozen balances become fully inert for trading — useful for hard compliance holds but blunt for ordinary disputes.

### Transfer Fees (TransferRate) · `concept` · ● live ✓
Issuers of trust-line tokens can charge a transfer fee when holders move the token among themselves. - **Chain:** xrpl-mainnet · **Maturity:** stable · **Use:** situational

### MPT transfer fee vs IOU TransferRate as a currency sink · `concept` · ● live ✓

### Anti-RMT & compliance levers (clawback, freeze, RequireAuth allow-listing) · `pattern` · · n/a ✓

RequireAuth: issuer flag; holders need explicit authorization (TrustSet authorize / MPTokenAuthorize approval) before holding. ### Sink implementation (crafting costs, fee burns, redemption to issuer) · `pattern` · · n/a ✓
How currency LEAVES the economy -- the half most studios under-build. Three on-ledger sink mechanics: (1) REDEEM-TO-ISSUER: a Payment from player back to the issuing account effectively removes the tokens from circulation (the issuer's own balance is not a circulating supply); this is the cleanest crafting/shop sink -- player pays crafting cost to the issuer and the currency is retired. (2) NATIVE TRANSFER-FEE BURN on every secondary trade (MPT TransferFee / IOU TransferRate), a passive always-on sink. (3) XRP GAS BURN: every transaction destroys ~10 drops of XRP, a tiny structural sink on activity. There is NO on-chain hook to auto-burn on a game event, so crafting/shop sinks are your server sending the player's spend back to the issuer (or to a no-key burn/black-hole address).
- **Chain:** xrpl-mainnet · **Maturity:** production · **Use:** live
- **Key fields / API:** Redeem sink: Payment Account=player -> Destination=issuer (tokens retired from circulation; transfer-fee-exempt on the issuer leg). Passive sink: MPT TransferFee / IOU TransferRate burn on P2P trades. Structural sink: ~10 drops XRP burned per tx. True burn address: a black-holed account (master key disabled, no regular key) for irrevocable removal. Sink magnitude is tuned in server-side cost tables, not on-chain.
- **Gotchas:** Sending currency to the ISSUER reduces circulating supply but the issuer can re-emit it (it is not destroyed); for irreversible burn use a provably-unspendable black-holed address or, for MPT/IOU, rely on the transfer-fee burn which is true destruction. Don't conflate the two when modeling supply. As with faucets there is NO on-chain trigger -- the protocol won't burn on 'crafted an item'; your server must construct the sink Payment. Balance faucet emission against sink drainage explicitly (the faucet-and-sink discipline) or the soft currency inflates regardless of supply cap.

### Treasury management via Token Escrow (XLS-85) for vesting & structured payouts · `pattern` · ● live ✓
Studio treasury and emission control without a smart contract. XLS-85 Token Escrow went live on mainnet 2026-02-12, extending native time-locked / conditional escrow -- previously XRP-only -- to IOU trust-line tokens AND MPTs. For a game economy this gives you: vesting schedules for team/partner currency allocations, escrow-gated emission (lock the season's reward pool and release it on a finish-after time so the faucet cannot over-emit), and structured/scheduled treasury payouts -- all enforced by the ledger. A finish-after-only escrow sits Held until its time passes, then becomes Ready and anyone can EscrowFinish it.
- **Chain:** xrpl-mainnet · **XLS:** XLS-85 · **Amendment:** TokenEscrow · **Enabled:** 2026-02-12 · **Maturity:** production · **Use:** live
- **Key fields / API:** EscrowCreate with Amount as an IOU or MPT (post-XLS-85), FinishAfter (time-based release), optional Condition (crypto-condition). Each escrowed object costs 0.2 XRP owner reserve while active. Held -> Ready (after FinishAfter) -> finished via EscrowFinish; CancelAfter returns funds. Supports stablecoins (e.g. RLUSD) and any on-ledger token.
- **Gotchas:** Each active escrow consumes a 0.2 XRP owner reserve, so escrow is for treasury-scale movements (a few large locks), NOT for per-player micro-vesting (thousands of escrows = thousands of reserves). Escrow is not a general programmable vault -- it is time/condition release only; complex emission curves still need your server to create successive escrows. Verify the token issuer hasn't frozen/clawed the asset, which can interact with escrowed balances.

### Reward distribution at scale (and the Batch XLS-56 gap) · `pattern` · · n/a ✓
The hardest current reality of XRPL game economics: there is NO atomic mass-payout primitive on mainnet in 2026. Batch (XLS-56) -- the intended way to group many inner Payments into one atomic transaction -- was found to have a critical signature-validation flaw (an attacker could execute inner transactions on arbitrary victim accounts without their keys), disclosed 2026-02-19, and rippled 3.1.1 (2026-02-23) marked both Batch and fixBatchInnerSigs UNSUPPORTED so validators cannot enable them. The successor BatchV1_1 is implemented but UNDER REVIEW with no date. Until then, distribute quest rewards and drops by looping INDIVIDUAL Payment transactions from your faucet/issuer account: a server-side sender that manages the account Sequence (or uses Tickets to parallelize), submits N payments, and reconciles results. Each payment is exempt from the transfer fee if it comes from the issuer.
- **Chain:** xrpl-mainnet · **XLS:** XLS-56 · **Amendment:** Batch (disabled); BatchV1_1 (under review) · **Maturity:** experimental · **Use:** blocked
- **Key fields / API:** Current path: N x Payment txs from one funded sender; manage Sequence numbers strictly in order OR pre-allocate Tickets (TicketCreate) to submit out-of-order/in-parallel. Each tx burns ~10 drops of XRP. Issuer-leg payments are transfer-fee-exempt (full reward delivered). Failed Batch hash/details in XLS-0056-batch repo; BatchV1_1 removes the early-exit in signer validation. NO atomic all-or-nothing semantics available in 2026.
- **Gotchas:** Do NOT architect your payout system assuming Batch exists -- it is disabled and may stay so for an unknown period. Looping Payments is NOT atomic: partial failure is possible, so your server must track which recipients succeeded and retry idempotently. Sequence-number contention is the classic footgun for high-throughput payout; use Tickets to avoid serializing every payout behind one Sequence. Throughput is also ledger-paced (~3-4s/ledger, finite tx/ledger), so very large drops are batched over time off-chain, not instant.
