### Cross-currency payments & pathfinding · `pattern` · ● live ✓
Pathfinding finds the most cost-effective route for a payment that converts between currencies, using the XRPL's native decentralized exchange (order books) and Automated Market Makers. A Payment carries a path set (a collection of candidate paths sharing the same start and end currency); a single transaction can combine liquidity across multiple paths and intermediaries. Builders use the ripple_path_find / path_find RPC methods to compute paths off-transaction, then submit with SendMax and the resulting Paths.
- **Chain:** xrpl-mainnet · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** ["SendMax (source currency cap)", "Amount (destination currency target)", "Paths (path set)", "ripple_path_find / path_find RPC methods", "DeliverMin (with tfPartialPayment for slippage tolerance)", "Flags: tfNoRippleDirect, tfLimitQuality"]
- **Gotchas:** ["Liquidity shifts every few ledgers (~3–5s); a path found now may be stale at submission — pathfind close to signing and set SendMax to bound cost.", "rippled is NOT guaranteed to find the cheapest path; confirm results before signing.", "Without trust-line rippling configured correctly, intermediary IOU steps may not flow (No Ripple flag interactions).", "Auto-bridging through XRP can route token-to-token trades; XLS-60d DefaultAutoBridge work affects default bridging behavior."]
- **Build-focus tracks:** [game-economies](track-game-economies.md), [payments](track-payments.md)
- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed | net-check: mainnet-live | currency=current | Cross-currency payments use pathfinding through order books and AMMs, with path sets carried in transactions.
- **Sources:** [Paths (xrpl.org)](https://xrpl.org/docs/concepts/tokens/fungible-tokens/paths) — Paths define how tokens flow through intermediary steps (order books and AMMs) to enable cross-currency payments, and a transaction carries a path set of candidate paths. ; [Path Finding (XRPL Commons Trainings)](https://docs.xrpl-commons.org/xrpl-basics/path-finding) — It is recommended to perform pathfinding separately and confirm results before signing, since the cheapest path changes as new ledgers are validated.

### Destination tags & source tags · `concept` · ● live ✓
Source and destination tags are 32-bit unsigned integers attached to payments (and other transactions like escrows and checks) that let a single receiving address disambiguate among many logical beneficiaries. Exchanges, custodians, and payment processors rely on destination tags to credit the correct customer when many users share one hosted wallet. Accounts can require destination tags via the RequireDest account flag to prevent misrouted deposits.
- **Chain:** xrpl-mainnet · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** ["DestinationTag (32-bit uint)", "SourceTag (32-bit uint)", "Account flag: asfRequireDest / RequireDestTag (tfRequireDestTag in AccountSet)", "X-addresses (encode address + tag together to reduce user error)"]
- **Gotchas:** ["Omitting a required DestinationTag on an account with RequireDest enabled fails the transaction (tecDST_TAG_NEEDED).", "Tags are NOT encrypted or validated by the ledger — they are application-level routing hints; the receiving business must map them.", "A wrong or missing tag to an exchange is the #1 cause of 'lost' deposits; prefer X-addresses to bundle address+tag and avoid copy errors.", "Tags are distinct from InvoiceID — tags route to a beneficiary, InvoiceID references an external order/invoice."]

### Escrow (XRP) — time-based & conditional · `transaction` · ● live ✓
Escrow locks XRP on-ledger to be released only when conditions are met. Three release models exist: time-based (FinishAfter), conditional (a PREIMAGE-SHA-256 crypto-condition whose fulfillment must be supplied), and combination (both). EscrowCreate locks the funds, EscrowFinish releases them to the destination once conditions hold, and EscrowCancel returns them to the sender after CancelAfter expiry. It is trustless, smart-contract-free conditional payment built into the protocol.
- **Chain:** xrpl-mainnet · **Amendment:** Escrow · **Enabled:** 2017-03-31 · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** ["EscrowCreate: Amount, Destination, FinishAfter, CancelAfter, Condition (PREIMAGE-SHA-256), DestinationTag", "EscrowFinish: Owner, OfferSequence, Condition, Fulfillment", "EscrowCancel: Owner, OfferSequence", "ledger object: Escrow"]
- **Gotchas:** ["PREIMAGE-SHA-256 is the ONLY supported crypto-condition type.", "EscrowFinish with a Fulfillment costs an elevated fee proportional to the fulfillment size (anti-spam).", "Release times are granular to ledger close (~3–5s); FinishAfter is 'earliest', not exact.", "An escrow without FinishAfter or Condition is pointless (would be immediately finishable); the ledger requires at least one release mechanism.", "Locked XRP still counts toward the owner's reserve obligations."]
- **Build-focus tracks:** [game-economies](track-game-economies.md), [identity-compliance](track-identity-compliance.md), [payments](track-payments.md)
- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed | net-check: mainnet-live | currency=current | Escrow amendment enables time-based and conditional (PREIMAGE-SHA-256) XRP escrows on mainnet.
- **Sources:** [Escrow (xrpl.org)](https://xrpl.org/docs/concepts/payment-types/escrow) — Escrow supports time-based, conditional (PREIMAGE-SHA-256 the sole supported crypto-condition), and combination release; EscrowCreate locks funds, EscrowFinish releases, EscrowCancel returns them after expiry. ; [Known Amendments (xrpl.org)](https://xrpl.org/resources/known-amendments) — The Escrow amendment enabling conditional and time-based escrows of XRP is enabled on mainnet.

### Channel reserve & XRP-only economics · `concept` · ● live ✓
Each open channel costs the source one owner-reserve item — 0.2 XRP since the 2024-12-02 reserve reduction — locked (not burned) while the channel exists, plus the escrowed Amount which is locked until claimed or returned. Channels are XRP-only on mainnet as of mid-2026: token-enabled PayChan (alongside the token-escrow line that shipped first) remains in spec phase with no activated mainnet amendment. This shapes the build decision: stablecoin/IOU/MPT micropayments cannot stream over a channel today and must use XRP or a different rail.
- **Chain:** xrpl-mainnet · **Amendment:** PayChan · **Enabled:** 2017-03-30 · **Maturity:** battle-tested · **Use:** recommended

### channel_authorize (sign a claim) · `transaction` · ● live ✓
The rippled API method the source uses to produce a claim signature for a given channel and cumulative drops amount, using the channel's key seed/secret. The signature is computed over the canonical claim message — the prefix 'CLM\0' (0x434C4D00) followed by the 32-byte channel ID and the 8-byte big-endian drops amount — with Ed25519 or secp256k1. ### channel_verify (verify a claim signature) · `transaction` · ● live ✓
The receiver-side rippled method that checks whether a claim signature is cryptographically valid for a given channel_id, amount, and public_key, returning signature_verified true/false. Critically it verifies ONLY the signature — it does NOT confirm the channel exists, is funded, or has that much XRP remaining. A safe receiver pairs channel_verify with account_channels to confirm live funding before treating a claim as money in hand.
- **Chain:** xrpl-mainnet · **Amendment:** PayChan · **Enabled:** 2017-03-30 · **Maturity:** battle-tested · **Use:** recommended
- **Key fields / API:** ["channel_id (64-char hex)", "amount (cumulative drops the signature should authorize)", "public_key (channel key, base58 or hex)", "signature (hex)", "Output: signature_verified (boolean)"]

### Off-ledger signed Claim (the micropayment unit) · `concept` · ● live ✓
A Claim is a tiny off-ledger data structure the source signs to authorize a CUMULATIVE total of drops deliverable through a specific channel. Claims never touch the network individually — the source sends them to the receiver over any channel (HTTP, WebSocket, in-band game protocol), the receiver verifies each locally, and only the final/largest claim is settled on-ledger. This 'sign many, settle once' property is the actual micropayment mechanism: throughput scales with signing speed, not ledger consensus.
- **Chain:** xrpl-mainnet · **Amendment:** PayChan · **Enabled:** 2017-03-30 · **Maturity:** battle-tested · **Use:** recommended
- **Key fields / API:** ["Channel ID (32-byte hex of the target channel)", "Authorized amount (cumulative XRP drops total, NOT a per-claim delta)", "Signature (over the canonical claim message, by the channel PublicKey)", "Cumulative semantics: to charge two 10-drop items, claim #1 = 10 drops, claim #2 = 20 drops total"]
- **Gotchas:** ["Amounts are CUMULATIVE, not incremental — a new claim restates the running total; redeeming the largest supersedes all smaller ones.", "Claims carry no expiry of their own; their validity is bounded by the channel's Expiration/CancelAfter and remaining funds.", "A claim can authorize more than the channel currently holds — it only becomes redeemable up to the channel's funded Amount, so receivers MUST cross-check funding (see channel_verify gotcha).", "Off-ledger transport is the integrator's responsibility; there is no protocol-level delivery or ordering guarantee.", "XRP-only: a claim authorizes drops, never tokens."]

### Quality limits & slippage control (tfLimitQuality) · `concept` · ● live ✓
tfLimitQuality (flag 0x00040000) caps the exchange QUALITY (input:output ratio) of every path step a payment consumes: the ledger only takes conversions whose ratio is equal to or better than the implied DeliverMax:SendMax rate. This is the on-chain slippage guard for cross-currency payments — it refuses to fill the payment through expensive path segments rather than burning your whole SendMax on a bad rate. Quality is defined per path; the engine prefers higher-quality (cheaper) paths and tfLimitQuality enforces a hard worst-acceptable bound.
- **Chain:** xrpl-mainnet · **Maturity:** stable · **Use:** live
- **Key fields / API:** tfLimitQuality (0x00040000 / 262144). Reference ratio is DeliverMax:SendMax (the rate you'd accept if the whole tx executed at the cap). Pairs naturally with SendMax (absolute cost cap) and tfPartialPayment+DeliverMin (allow under-delivery at acceptable quality instead of overpaying). tfNoRippleDirect (0x00010000) is the related routing control: skip the default path, use only the supplied Paths.
- **Gotchas:** tfLimitQuality bounds the RATE, not the absolute spend — pair it with SendMax for a hard cost ceiling. Without tfPartialPayment, a quality limit that can't be met just fails the whole tx (tecPATH_PARTIAL / tecPATH_DRY); with tfPartialPayment it delivers less at acceptable quality. The reference ratio is derived from your DeliverMax and SendMax, so those two fields ARE your slippage tolerance — set them deliberately. tfNoRippleDirect is a different lever (route restriction, not price) and is easy to confuse with quality control.

### Anyone-can-finish & owner-reserve mechanics of escrow · `concept` · ● live ✓
Two operating realities of every escrow that change how you build around it. (1) PERMISSION: escrow has no identity gate on completion. Once a time-based escrow is Ready (past FinishAfter), ANY account may submit EscrowFinish; once Expired (past CancelAfter), ANY account may submit EscrowCancel. The submitter only pays the fee — funds always go to the fixed Destination on finish and back to the sender on cancel. There is no FinishFunction / credential-gated finisher today; the access control is the crypto-condition (must hold the fulfillment) and the clock, not WHO signs. (2) RESERVE: each Escrow is one owned ledger object costing the SENDER 0.2 XRP of owner reserve, locked from create until finish/cancel (the reserve was lowered to 0.2 XRP per object on 2024-12-02). These two facts mean release is not automatic (you need a keeper to crank EscrowFinish), recipients should never assume they are the finisher, and high-volume escrow designs must budget real XRP reserve plus a finisher bot.

### Checks (CheckCreate / CheckCash / CheckCancel) — deferred pull payments · `transaction` · ● live ✓
A Check is an authorization to PULL funds, not a transfer and not an escrow. CheckCreate writes a Check ledger object naming the Destination, a SendMax (the cap, in XRP or an issued token), and optional Expiration / DestinationTag / InvoiceID. Crucially, NO funds are set aside at creation — money only moves when the recipient submits CheckCash, and only if the sender still holds the funds and a viable path/trustline exists at cash time (otherwise CheckCash fails and the recipient can retry until Expiration). The recipient cashes with either Amount (exact) or DeliverMin (flexible: deliver at least this, up to SendMax) — never both. This makes Checks the right primitive for studio->player payouts where the player should claim on their own schedule (e.g. battle-pass rewards, tournament prizes) and for sending into a DepositAuth-protected wallet, since CheckCash is receiver-initiated and bypasses the deposit-auth block. - **Gotchas:** Funds are NOT locked — a Check can be unfundable at cash time even though CheckCreate succeeded; never treat CheckCreate success as a guaranteed payout. ### Conditional escrow via PREIMAGE-SHA-256 crypto-condition · `transaction` · ● live ✓
The secret-locked form of escrow: EscrowCreate stores a Condition (a PREIMAGE-SHA-256 crypto-condition), and the escrow can only be finished by an EscrowFinish that supplies a matching Fulfillment — the preimage whose SHA-256 hash, wrapped in the condition encoding, equals the stored Condition. You generate the fulfillment first (a type prefix + arbitrary, usually random bytes), derive the condition (hash + length metadata), and hand only the condition to the ledger at create time; whoever later learns the fulfillment can release the funds (still only to the fixed Destination). PREIMAGE-SHA-256 is the ONLY condition type the ledger supports — there is no on-ledger scripting, multisig-of-conditions, or arbitrary predicate. This is the gate that makes hash-locked / reveal-a-secret flows possible: cross-leg atomicity tricks, claim-on-reveal rewards, and the conditional half of HTLC-style settlement. Conditional escrows MUST also have an expiration so funds can't be locked forever if the secret is never revealed.

### delivered_amount (DeliverMax) — authoritative credited amount · `concept` · ● live ✓
The single most important backend-safety field. A Payment (and CheckCash) can deliver LESS than its Amount — partial payments and flexible cashes are legitimate — so crediting a player from the Amount field is the canonical way to get robbed. The transaction metadata exposes delivered_amount (surfaced as DeliverMax in clio/rippled API v2), the exact currency actually received by the destination. Read it ONLY from a validated ledger result. It is generated on-demand for the API response and is deliberately NOT part of the binary metadata or the metadata hash, so you must request it from rippled/Clio rather than expect it in raw ledger data. For partial payments validated before 2014-01-20 it returns the string 'unavailable' and you must parse AffectedNodes balance deltas instead — not a concern for new payments but worth knowing if you ingest deep history. ### Idempotent submission: sequence + LastLedgerSequence + persisted hash · `pattern` · ● live ✓
XRPL gives you exactly-once semantics for free IF you use the account sequence number correctly. Each account has a strictly increasing Sequence; a transaction with a given (account, sequence) can be applied at most once, so a signed blob can never double-spend even if you submit it ten times. The reliable pattern: (1) fetch current sequence from account_info with ledger_index:validated; (2) set LastLedgerSequence to last-validated + 4 so the tx provably dies if not included by then; (3) persist the tx hash, sequence, LastLedgerSequence, sender, and signed tx_blob BEFORE submitting; (4) submit; (5) confirm by hash via the tx method, accepting only validated:true. If the result is txnNotFound AFTER LastLedgerSequence has passed, the tx is permanently gone — safe to re-sign with the SAME sequence, a fresh LastLedgerSequence, and possibly a higher Fee. The persisted tx hash is also your reconciliation key: credit a player once per validated hash and you can replay your whole pipeline without double-crediting.
- **Chain:** xrpl-mainnet · **Maturity:** battle-tested · **Use:** stable
- **Key fields / API:** Sequence (per-account, from account_info ledger_index:validated); LastLedgerSequence (set to last-validated + 4); persisted: tx hash, tx_blob, Sequence, LastLedgerSequence, sender, validated-ledger index; verify via tx method requiring validated:true; result classes tes/tec/ter/tef/tem.
- **Gotchas:** Result classes decide retry policy: tesSUCCESS = done; tec-class = INCLUDED in a ledger, burned the fee, did nothing else — FINAL failure, record it, do NOT resubmit the same blob (the sequence is consumed); terQUEUED / ter-class = temporary, may apply later, watch it; tef/tem = never entered a ledger, safe to fix and resend. Resubmitting after LastLedgerSequence passes must reuse the SAME sequence or you risk a gap that stalls later txs. A consumed sequence with a tec result means the NEXT payout uses sequence+1 — track this server-side or use Tickets for out-of-order submission. Never key idempotency on your own internal id alone; key on the validated tx hash. Fee escalation: under load a too-low Fee yields terQUEUED or drops — bump Fee on resubmit.
- **Build-focus tracks:** [payments](track-payments.md)
- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed | net-check: mainnet-live | currency=current | Standard idempotent transaction submission pattern using sequence numbers and LastLedgerSequence is correct.
- **Sources:** [Reliable Transaction Submission / XRPL.org](https://xrpl.org/docs/concepts/transactions/reliable-transaction-submission) — Persist tx hash, LastLedgerSequence, sequence and signed tx_blob before submitting; use last-validated+4 for LastLedgerSequence; correct sequence numbers make a transaction processable at most once; on txnNotFound past LastLedgerSequence, resubmit with same sequence and new LastLedgerSequence. ; [Transaction Results / XRPL.org](https://xrpl.org/docs/references/protocol/transactions/transaction-results) — tec-class results are included in ledgers and destroy the transaction cost but do nothing else; ter/tef/tem classes differ in retryability.

### Owner reserve accounting for payment objects (Checks/Escrows/Channels/Preauth) · `concept` · ● live ✓
Every payment-related ledger object the studio's accounts OWN is collateralized by locked XRP it cannot spend until the object is removed. Current mainnet reserves: 1 XRP base reserve per account plus 0.2 XRP owner reserve per owned object. Each outstanding Check, Escrow, PayChannel, DepositPreauth, Offer, trustline, ticket, and signer list increments the owner reserve by 0.2 XRP. This is the hidden cost of a backend that mints many payment objects: a payout system holding 5,000 uncashed Checks has 1,000 XRP locked in reserve; an escrow-heavy quest system locks 0.2 XRP per outstanding escrow. Reserve is RECLAIMED when the object leaves the ledger — cashing/cancelling a Check, finishing/cancelling an Escrow, closing a Channel, removing a trustline. Budget reserve as working capital and run sweepers (CheckCancel on expired checks, EscrowCancel on lapsed escrows) to recover it. Reserve amounts are set by fee voting and can change; verify current values via server_info / server_state at runtime rather than hardcoding.
- **Chain:** xrpl-mainnet · **Maturity:** battle-tested · **Use:** stable
- **Key fields / API:** Base reserve ~1 XRP/account; owner reserve ~0.2 XRP per owned object (Check, Escrow, PayChannel, DepositPreauth, Offer, trustline, ticket, signer list). Read live values from server_info / server_state (reserve_base_xrp, reserve_inc_xrp). NFTs reserve per-page (up to 32 NFTs) not per-token. Some objects (e.g. larger Oracles) count as more than one increment.
- **Gotchas:** Reserve is LOCKED, not spent — it reappears when the object is deleted, but until then it's unspendable, which can starve a hot wallet that's also paying network fees. Hardcoding 0.2/1 XRP is a future bug: reserves are governance-adjustable; fetch reserve_base_xrp and reserve_inc_xrp from server_state. A backend that creates Checks/Escrows faster than it cashes/cancels them will hit account-funding errors (tecINSUFFICIENT_RESERVE) — pre-fund and sweep. Trustlines also reserve (the holder owes it), so a wallet holding many in-game tokens carries reserve too. Don't forget DepositPreauth objects count — per-sender whitelisting has a reserve cost that credential-based auth avoids.

- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed | net-check: mainnet-live | currency=current | Owner reserve accounting for payment objects is accurate and should be read dynamically from server state.
- **Sources:** [Reserves / XRPL.org](https://xrpl.org/docs/concepts/accounts/reserves) — Mainnet base reserve is 1 XRP and the owner reserve is 0.2 XRP per owned object; Checks, Escrows, Payment Channels, Deposit Preauthorizations, Offers, trust lines, tickets and signer lists each count toward the owner reserve; NFTs reserve per page of up to 32. ; [server_state / server_info reserve fields / XRPL.org](https://xrpl.org/docs/references/http-websocket-apis/public-api-methods/server-info-methods/server_state) — Current reserve_base_xrp and reserve_inc_xrp are reported by the server and set by fee voting, so they should be read at runtime rather than hardcoded.

### Partial-payment-safe crediting (delivered_amount / DeliverMax) · `concept` · ● live ✓

### Pathfinding (ripple_path_find / path_find) · `concept` · ● live ✓

### Real-time inflow detection: subscribe streams vs account_tx polling · `service` · ● live ✓
Two complementary mechanisms feed the backend. (1) The subscribe WebSocket method with an accounts:[<hot wallet>] argument pushes a 'transaction' message every time a validated transaction affects that account — this is your real-time deposit webhook. ### tfPartialPayment & the partial-payment exploit · `concept` · ● live ✓
tfPartialPayment (flag 0x00020000) lets a Payment succeed by delivering LESS than DeliverMax rather than failing when full delivery would exceed SendMax. Useful for legitimately clearing the maximum deliverable given available liquidity — but it is the mechanism behind the exploit: an attacker sends a Payment with a huge DeliverMax, tfPartialPayment set, and minimal real delivery; the tx returns tesSUCCESS while delivering near-zero. Any system that credits from DeliverMax/Amount gets robbed. The defense is the delivered_amount rule plus DeliverMin. Understanding both sides (when to send partial vs how to never be fooled by one) is core for a payments studio.
- **Chain:** xrpl-mainnet · **Maturity:** battle-tested · **Use:** live
- **Key fields / API:** tfPartialPayment (0x00020000 / 131072). When set, delivery is reduced instead of the tx failing. Constraint: DeliverMin <= delivered <= DeliverMax, and total source spent <= SendMax. XRP-to-XRP partial payments are forbidden (temBAD_SEND_XRP_PARTIAL). delivered_amount in metadata reveals the true amount.
- **Gotchas:** Two failure modes for the studio: (1) RECEIVING — never credit on DeliverMax; always read delivered_amount. (2) SENDING — only set tfPartialPayment when you genuinely accept under-delivery (e.g. returning funds / sweeping dust); for a normal payout you want full-or-fail, so leave it OFF and let the tx fail rather than silently deliver less. A successful tx result code (tesSUCCESS) says nothing about how much was delivered when this flag is in play. Do not pair tfPartialPayment with a fixed SendMax expecting exact delivery — that's the whole point of the flag being dangerous.

### Vesting / lockup schedule via escrow ladder · `pattern` · ● live ✓

### Batch reward distribution / mass payout (Batch — NOT on mainnet) · `transaction` · ● live
XLS-56 Batch would wrap up to 8 inner transactions (min 2) into one atomic envelope with four execution modes — tfAllOrNothing (all succeed or none), tfOnlyOne (first success wins), tfUntilFailure (apply until first failure), tfIndependent (apply all regardless). The dream use case for a game economy is one mass-payout batch ('credit 50 tournament winners atomically') or an all-or-nothing multi-leg trade. STATUS WARNING (mid-2026): the original Batch and fixBatchInnerSigs amendments were DISABLED in rippled 3.1.1 (2026-02-23) after a Feb-19 disclosure that inner transactions could execute on arbitrary victim accounts without their keys. Both are marked Obsolete / unsupported and CANNOT be voted onto any production network. A corrected BatchV1_1 is under review with NO release date. DO NOT design a shipping payout pipeline that depends on Batch today — use per-payment loops with the partial-payment-safe credit pattern as the mainnet fallback.
