### XRP as native gas token · `concept` · ● live ✓
Unlike most EVM L2s/sidechains that use their own token, the XRPL EVM sidechain uses XRP itself as the native gas (fee) token. XRP is sourced onto the chain by bridging from XRPL mainnet over Axelar, after which it behaves as the chain's native coin (the 'msg.value' / balance asset) and pays for all gas. This keeps the user experience XRP-denominated end to end.
- **Chain:** xrpl-evm-sidechain · **Enabled:** 2025-06-30 · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** Native coin symbol: XRP. Gas paid in XRP. XRP arrives via Axelar bridge from XRPL mainnet; the on-chain native asset is the bridged XRP. Typical transaction cost <$0.01.
- **Gotchas:** You must bridge XRP from XRPL mainnet (or acquire it on the sidechain) BEFORE you can pay gas — a freshly created EVM address has zero balance and cannot transact. Sources sometimes call the bridged asset 'wrapped XRP' / 'eXRP'; on the sidechain it functions as the native gas coin, not an ERC-20 you approve. Decimal handling differs from XRPL drops — EVM uses 18-decimal wei-style accounting.

### Axelar bridge (XRPL ⇄ EVM sidechain) · `service` · ● live ✓
Axelar is the exclusive launch bridge connecting XRPL mainnet to the EVM sidechain and to 80+ other chains. It is a decentralized proof-of-stake validator network that moves XRP, XRPL IOUs and ERC-20 tokens cross-chain. End users typically bridge via the Squid Router widget; developers build cross-chain apps with Axelar's Interchain Token Service (ITS) and General Message Passing (GMP).
- **Chain:** xrpl-evm-sidechain · **Enabled:** 2025-06-30 · **Maturity:** new · **Use:** recommended
- **Key fields / API:** Bridge UI: Squid Router (connect XRPL wallet — XRPL Snap or Crossmark — enter XRP amount + EVM receiver, swap). Axelar primitives: Interchain Token Service (ITS), General Message Passing (GMP). Connects 80+ chains. Bridge live 2025-06-30 (announced at EthCC).
- **Gotchas:** Bridging is a cross-chain operation with finality lag and bridge fees — not instant or free. Axelar is a trust-minimized validator bridge, not the same security model as the L1 itself; treat large transfers accordingly. Wormhole is described as 'incoming' (not yet the primary path). Always confirm the exact ITS token address on the sidechain rather than trusting a symbol.

### Solidity / EVM smart contracts · `concept` · ● live ✓
Full Ethereum Virtual Machine compatibility lets you write, deploy and call Solidity contracts exactly as on Ethereum, using OpenZeppelin libraries and standard tooling. This is the headline reason the sidechain exists: native XRPL has no general-purpose VM, so all Turing-complete on-chain logic (DeFi, complex NFTs, game logic, DAOs) for the XRP ecosystem runs here.
- **Chain:** xrpl-evm-sidechain · **Enabled:** 2025-06-30 · **Maturity:** new · **Use:** recommended
- **Key fields / API:** EVM version: Paris (upgrade to Prague planned). Solidity compiler: solc <= 0.8.24 (moving to 0.8.30). Standard EVM opcodes, ERC-20/721/1155 supported. Migrated from Evmos to Cosmos EVM v0.4.1 (adds ERC-20 mint/burn + newer EIP support). Interact via ethers.js / web3.js.

As a Cosmos EVM chain, some bleeding-edge Ethereum precompiles/opcodes may lag mainnet Ethereum — test before assuming parity. New chain: fewer audited reference contracts and oracles than Ethereum mainnet.

### When to use EVM sidechain vs native XRPL vs Xahau · `pattern` · ● live ✓
A build-decision rule for placing a feature on the right chain. Use the EVM sidechain when you need Turing-complete Solidity, composable DeFi, or to port Ethereum dApps — XRP-denominated but fully programmable. Use native XRPL mainnet for cheap, battle-tested built-in primitives (payments, the native DEX/AMM, XLS-20 NFTs, escrow, multi-sign) without writing a VM contract. Use Xahau when you want lightweight on-ledger automation (Hooks) closer to XRPL's model without a full EVM.
- **Chain:** xrpl-evm-sidechain · **Enabled:** 2025-06-30 · **Maturity:** new · **Use:** recommended
- **Key fields / API:** EVM sidechain (chain xrpl-evm-sidechain, ID 1440000): Solidity/DeFi/complex logic. Native XRPL (xrpl-mainnet): built-in payments, DEX/AMM, XLS-20 NFTs, escrow, low fees, no smart contracts. Xahau: Hooks (lightweight WASM-ish on-ledger logic). Bridge assets between chains via Axelar.
- **Gotchas:** Don't reimplement on the EVM what XRPL already does natively and cheaply (basic payments, DEX, NFTs) just to stay in Solidity — you lose XRPL's free-tier robustness. Conversely, don't expect XRPL mainnet to run arbitrary contracts — it can't, by design. Cross-chain composition means bridge latency/fees and bridge trust. Xahau Hooks are not EVM — different programming model entirely.

### XRPL EVM Sidechain (standalone Cosmos L1) · `concept` · ● live ✓
The XRPL EVM sidechain is a standalone Layer-1 blockchain that runs Ethereum-compatible smart contracts with XRP as the native gas token. It is built on the Cosmos SDK with CometBFT consensus and is a SEPARATE chain from XRPL mainnet — the native XRP Ledger does not and will not run a general-purpose VM, so this is where Solidity/EVM dApps live in the XRP ecosystem. Mainnet went live 2025-06-30; it saw ~1,400 contracts deployed in week one.
- **Chain:** xrpl-evm-sidechain · **Enabled:** 2025-06-30 · **Maturity:** new · **Use:** recommended
- **Key fields / API:** EVM mainnet chain ID 1440000 (hex 0x15f900); Cosmos chain-id xrplevm_1440000-1; testnet chain ID 1449000; devnet 1440002. Native currency symbol XRP. Built by Ripple + Peersyst + Axelar. Standard Ethereum JSON-RPC surface.
- **Gotchas:** It is NOT the XRPL mainnet — different chain ID, different address format (0x EVM addresses, not r-addresses), separate explorer, and assets must be bridged across. Do not assume XLS amendments (XLS-20 NFTs, native DEX, etc.) exist here; those are XRPL-mainnet features. Being a new chain, ecosystem depth and audited infra are still maturing.

### Axelar trust & security model (PoS committee, quadratic voting) · `concept` · ● live ✓
The actual security guarantee behind every XRPL↔EVM movement, and the part most easily glossed over. Axelar is a Tendermint Proof-of-Stake L1 (~70 active validators mid-2026) whose validators/verifiers run light clients or nodes for connected chains and stake AXL. Every cross-chain message must be co-authorized by a weighted-threshold quorum using QUADRATIC VOTING — each validator's vote weight equals the square root of its stake, which caps the influence of large stakers and pushes toward broader collusion requirements. The honest framing for a studio: this is 'an L1's trust model applied to messaging' — strictly weaker than XRPL's own consensus for assets that have crossed, because it adds an external committee you must now also trust to be live and honest. ### callContractWithToken — value + message in one hop · `pattern` · ● live ✓
The GMP variant that delivers a fungible token transfer AND an arbitrary payload to the destination contract in a single cross-chain message. ### General Message Passing (GMP) — cross-chain contract calls · `service` · ● live ✓
The primitive for sending ARBITRARY data and function calls across chains — the heart of any 'native XRPL ownership + EVM game logic' design. From XRPL, you submit a Payment (min 1 drop if no asset moves) to the Axelar Multisig account with Memos carrying the call type, destination chain, target contract address, and an ABI-encoded payload hash (encode with ethers AbiCoder). Axelar verifies and relays; the EVM-side Amplifier Gateway records ContractCallApproved; the relayer triggers execute() on your AxelarExecutable contract, passing commandId, sourceChain ('xrpl'), sourceAddress (the originating r-account), and the ABI payload. This lets an XRPL-side event ('player listed asset', 'player paid entry') drive Solidity game logic without bridging the asset itself — the recommended low-trust pattern. Confirmation is typically a few minutes (bridge-dominated, not block-time-dominated).

### Native XLS-20 ownership + EVM game logic (cross-chain pattern) · `pattern` · ● live ✓

It is the concrete answer to 'native XRPL NFT ownership + EVM-contract game logic'.

### XRP as native gas token (bridged via Axelar) · `concept` · ● live ✓
Unlike most EVM L2s where gas is a distinct token (ETH/MATIC), the XRPL EVM sidechain uses XRP itself as the native gas asset. XRP is moved from the XRP Ledger onto the sidechain through Axelar — the first interoperability provider to connect XRPL EVM — so the gas you spend is bridged XRP. Fees are sub-cent. MetaMask shows XRP as the native balance, a first for XRP in a MetaMask context.
- **Chain:** xrpl-evm-sidechain · **Enabled:** 2025-06-30 · **Maturity:** production · **Use:** live
- **Key fields / API:** Native gas token: XRP; currency symbol: XRP; bridge for gas: Axelar (XRPL <-> XRPL EVM); user-facing bridge UIs: Squid Router (Axelar-powered), Skip Go (Cosmos), Gas.zip (up to $500 XRP from any asset); fee level: ultra-low / sub-cent.
- **Gotchas:** You must bridge XRP onto the sidechain BEFORE you can deploy or transact — a fresh EVM address starts with zero gas even if you hold XRP on the XRP Ledger. The bridged XRP and L1 XRP are not the same balance. Bridge latency and bridge trust assumptions (Axelar validator set) apply. Keep a small XRP buffer for gas separate from contract-held funds.

### XRPL EVM Sidechain (execution layer) · `concept` · ● live ✓
The standalone Layer-1 EVM chain that any bridged value or message lands on. Built by Peersyst on evmOS (Evmos modular stack) atop Cosmos SDK + CometBFT/Tendermint, running a Proof-of-Authority validator set with ~3.5s block time, sub-4-second finality, and ~1000 TPS. It executes standard Solidity / EVM bytecode and ERC-20/721 contracts, with XRP itself as the NATIVE gas token (not a wrapped ERC-20). This is the 'EVM-contract game logic' half of any cross-chain game pattern: mutable state, combat math, marketplaces, and progression live here in Solidity, while canonical scarce assets can stay on XRPL mainnet. Understanding that it is a sovereign chain with its own consensus and its own gas market — not an L2 rollup posting to XRPL — is the precondition for reasoning about the bridge's trust boundary.
