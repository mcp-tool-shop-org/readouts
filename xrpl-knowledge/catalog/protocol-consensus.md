### Account & owner reserves · `concept` · ● live ✓
Every XRPL account must hold a minimum XRP balance: a base reserve (currently 1 XRP) plus an owner reserve (currently 0.2 XRP) for each ledger object the account owns (trust lines, offers, escrows, NFT offers, checks, payment channels, signer lists, tickets, etc.). Reserved XRP cannot be spent but is freed when the corresponding object is removed. Reserve amounts are set by validator fee voting and have been lowered over time (the 1 XRP / 0.2 XRP levels reflect a reduction from the older 10 XRP / 2 XRP regime).
- **Chain:** xrpl-mainnet · **Enabled:** 2024-12-01 · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** reserve_base_xrp (base, ~1 XRP), reserve_inc_xrp / owner reserve (~0.2 XRP per item); total reserve = reserve_base_xrp + (OwnerCount * reserve_inc_xrp); AccountRoot.OwnerCount; API: server_info (validated_ledger.reserve_base_xrp, reserve_inc_xrp), account_info, account_objects. Reserve changes via fee-voting consensus.
- **Gotchas:** Reserve is denominated in XRP and is locked, not lost - it is reclaimable by deleting objects. Funding a brand-new account requires sending at least the base reserve (1 XRP) or the account is never created. Each trust line, offer, and NFT-offer adds owner reserve; apps that spam offers can lock up a user's XRP. NFTs themselves are batched into NFTokenPages (each page, holding up to 32 NFTs, costs one owner reserve, not per-NFT). Always read live reserve values from server_info - do not hardcode, because fee voting can change them.
- **Build-focus tracks:** [game-economies](track-game-economies.md), [identity-compliance](track-identity-compliance.md), [nft-assets](track-nft-assets.md), [payments](track-payments.md)
- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed | net-check: mainnet-live | currency=current | Reserve requirements (1 XRP base + 0.2 XRP per item) are correctly stated and currently enforced.
- **Sources:** [Reserves](https://xrpl.org/docs/concepts/accounts/reserves) — The current Mainnet base reserve is 1 XRP and the owner reserve is 0.2 XRP per item; total reserve = OwnerCount * reserve_inc_xrp + reserve_base_xrp.

### Amendment process (2/3 supermajority, 2-week activation) · `concept` · ● live ✓
Protocol changes ship via amendments, which validators vote on at flag ledgers (every 256th ledger). An amendment that holds more than 80% support among trusted validators for two continuous weeks becomes enabled on mainnet automatically; if support drops below threshold the clock resets. Default votes are baked into each rippled/xrpld release and operators can override them. Servers running software that lacks an enabled amendment become amendment-blocked and stop validating until upgraded. This is the gate that makes every other capability in this lane current-or-not.
- **Chain:** all · **Enabled:** 2017-05-01 · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** Flag ledger = every 256th ledger (~15 min); >80% support for 2 weeks -> enabled; EnableAmendment pseudo-transaction records activation; amendment IDs (sha512half of the amendment name); API: feature, ledger (amendment majorities), Amendments ledger object. Server states: amendment-blocked when behind an enabled amendment.
- **Gotchas:** Voting threshold is effectively a >80% supermajority sustained for two weeks - not a one-time snapshot; a temporary dip resets the timer. An amendment can be in 'majority' but not yet enabled (still inside its two-week window). The process is also a kill-switch: the original Batch and fixBatchInnerSigs amendments were marked unsupported in rippled 3.1.1 (Feb 2026) after a flaw was found during voting, proving amendments can be pulled before activation. Always verify an amendment's ACTUAL on-chain status (feature method / explorer) - do not assume from version notes.
- **Build-focus tracks:** [game-economies](track-game-economies.md), [identity-compliance](track-identity-compliance.md), [nft-assets](track-nft-assets.md), [payments](track-payments.md)
- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed-with-fixes | net-check: mainnet-live | currency=current | fix: Amendment requires >80% support (not 2/3) for two weeks before activation | Amendment process is live but the threshold is 80% not 2/3 as claimed.
- **Sources:** [Amendments](https://xrpl.org/docs/concepts/networks-and-servers/amendments) — An amendment requires more than 80% validator support for two weeks (votes cast at flag ledgers every 256th ledger) before it becomes enabled, and outdated servers become amendment-blocked. ; [XRPL batch amendment security patch blocks mainnet risk](https://en.cryptonomist.ch/2026/02/27/xrpl-batch-amendment-security/) — rippled 3.1.1 (Feb 2026) marked the original Batch and fixBatchInnerSigs amendments unsupported after a vulnerability was found during validator voting.

### Clio API server (history & read scaling) · `service` · ● live ✓
Clio is a read-optimized API server that extracts validated ledger and transaction data from an upstream rippled/xrpld node (via gRPC) and serves it over the same WebSocket/HTTP API, using ~4x less storage than rippled. It does NOT join the P2P network or participate in consensus. Clio is the standard way to serve historical queries, account_tx, and NFT data at scale: multiple Clio instances can share one Cassandra/ScyllaDB dataset, taking read load off validation nodes. Requests needing live/consensus data are transparently forwarded to the upstream rippled.
- **Chain:** xrpl-mainnet · **Enabled:** 2022-10-01 · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** Backed by Cassandra or ScyllaDB; serves account_info, account_tx, account_objects, ledger, tx, nft_info, nft_history, book_offers (read paths); forwards to rippled for: submit, submit_multisigned, fee, ledger_closed, ledger_current, ripple_path_find, manifest, channel_authorize, channel_verify, and ledger_index current/closed or accounts/queue/full flags.
- **Gotchas:** Clio cannot submit transactions or give you the current (unvalidated) ledger from its own store - those forward to rippled, so a Clio-only deployment without a healthy upstream node degrades. Clio serves VALIDATED data only - great for finality, but it lags the absolute tip by design. NFT-specific methods (nft_info, nft_history) are a Clio strength rippled lacks. Make sure your Clio is fed by a node retaining enough history for your queries, or historical lookups return missing-data errors.

- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed | net-check: mainnet-live | currency=current | Clio server is operational on mainnet for historical data access and read scaling.
- **Sources:** [The Clio Server](https://xrpl.org/docs/concepts/networks-and-servers/the-clio-server) — Clio extracts validated data from a rippled server, does not connect to the P2P network, uses Cassandra/ScyllaDB with up to 4x less space, and forwards submit/fee/current-ledger requests to rippled.

### Dynamic NFTs (DynamicNFT / XLS-46) · `amendment` · ● live ✓
DynamicNFT (XLS-46) extends the native XLS-20 NFT system to allow mutable NFTs: the issuer can update an NFToken's URI field after minting, enabling evolving metadata (game state, leveling, dynamic art) without burning and re-minting. It was enabled on mainnet on 2025-06-11. It sits on top of the already-live XLS-20 native NFT primitives (mint, burn, create/accept/cancel offers, broker mode).
- **Chain:** xrpl-mainnet · **XLS:** XLS-46 · **Amendment:** DynamicNFT · **Enabled:** 2025-06-11 · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** Transaction: NFTokenModify (update URI); requires the tfMutable flag set at NFTokenMint time; ledger objects: NFTokenPage, NFTokenOffer; base XLS-20 txns: NFTokenMint, NFTokenBurn, NFTokenCreateOffer, NFTokenAcceptOffer, NFTokenCancelOffer. Only the URI is mutable, not the NFT's identity/issuer/taxon.
- **Gotchas:** Only NFTs minted with the mutable flag can be modified - you cannot retroactively make an existing immutable NFT dynamic. Only the URI (metadata pointer) changes; the on-chain token identity is fixed, so off-chain metadata at that URI must be managed carefully (and is only as trustworthy as its hosting). NFTs are stored in NFTokenPages (up to 32 per page) which affects owner-reserve math. For NFT history/queries at scale use Clio's nft_info/nft_history. Confirm DynamicNFT is enabled on the network you target (it is on mainnet).

### Ledger structure & ledger objects · `concept` · ● live ✓
Each ledger version has three parts: a fixed-size header (ledger index, ledger hash, parent hash, close time, state-data hash, transaction-set hash), the transaction set (transactions applied in canonical order, each with metadata describing its effects), and the state data - a tree of ledger entries (ledger objects) each keyed by a unique 256-bit identifier. Ledgers chain by sequential index back to the genesis ledger; identical hashes guarantee identical contents. Builders read state through ledger objects and write state by submitting transactions.
- **Chain:** all · **Enabled:** 2012-06-01 · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** Ledger object types: AccountRoot, RippleState (trust line), Offer, Escrow, PayChannel, Check, Ticket, SignerList, DepositPreauth, NFTokenPage, NFTokenOffer, AMM, DID, Credential, PermissionedDomain, Oracle, MPTokenIssuance, MPToken, Vault (newer). API: ledger_entry, account_objects, account_info, ledger, ledger_data, ledger_index vs ledger_hash.
- **Gotchas:** Two identification schemes - ledger_index (sequence) vs ledger_hash (content); always pin to validated for finality. Each owned ledger object increases your account's owner reserve. Ledger object IDs are deterministic keylets (hash of type + fields); some pre-fix entries lacked identifying fields (addressed by fixIncludeKeyletFields). account_objects on a busy account may paginate (marker). NFTs live in NFTokenPage objects, not one-object-per-NFT, which affects reserve math.
- **Build-focus tracks:** [game-economies](track-game-economies.md), [identity-compliance](track-identity-compliance.md), [nft-assets](track-nft-assets.md), [payments](track-payments.md)
- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed | net-check: mainnet-live | currency=current | XRPL ledger structure with header, transactions, and state data tree is correctly described and live.
- **Sources:** [Ledger Structure](https://xrpl.org/docs/concepts/ledgers/ledger-structure) — Each ledger has a header, a transaction set, and state data organized as a tree of ledger entries each with a unique 256-bit identifier. ; [Ledger Entry Types](https://xrpl.org/docs/references/protocol/ledger-data/ledger-entry-types) — Ledger entries include AccountRoot, RippleState, Offer, Escrow, NFToken pages, MPTokenIssuance, and other typed objects.

### Multi-Purpose Tokens (MPTokensV1) · `amendment` · ● live ✓
MPTokensV1 (XLS-33) introduced Multi-Purpose Tokens, a compact fungible-token type that is more storage- and reserve-efficient than classic trust-line (IOU) tokens and is optimized for common issuance use cases like stablecoins and tokenized assets. MPTs add new ledger objects (MPTokenIssuance, MPToken) and integrate with the Payment transaction. The amendment was enabled on mainnet on 2025-10-01, and follow-on work (DynamicMPT/XLS-94, MPTokensV2/XLS-82 for DEX integration, ConfidentialTransfer/XLS-96) extends it.
- **Chain:** xrpl-mainnet · **XLS:** XLS-33 · **Amendment:** MPTokensV1 · **Enabled:** 2025-10-01 · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** Transactions: MPTokenIssuanceCreate, MPTokenIssuanceDestroy, MPTokenAuthorize, MPTokenIssuanceSet; ledger objects: MPTokenIssuance, MPToken; fields: MPTokenMetadata, AssetScale, MaximumAmount, TransferFee, flags (CanLock, CanClawback, CanTransfer, RequireAuth); Payment supports MPT amounts. fixMPTDeliveredAmount adds delivered-amount metadata to MPT payments (voting/2026).
- **Gotchas:** MPTs are NOT trust-line tokens - the holder model, metadata, and reserve footprint differ; existing IOU tooling does not transparently apply. MPTokensV1 alone does not give MPTs DEX/AMM trading - that needs MPTokensV2 (XLS-82, still in development as of mid-2026). Direct MPT Payments historically lacked full delivered-amount metadata until fixMPTDeliveredAmount (in voting in 2026) - reconcile carefully. Confidential MPT transfers (XLS-96) are not yet live. Verify which MPT sub-amendments are enabled before relying on them.

### rippled / xrpld core server (v3.2.0 rebrand) · `service` · ● live
rippled is the reference C++ server that runs the XRP Ledger: it participates in the peer-to-peer network, runs consensus, validates ledgers, holds ledger state, and serves the full JSON-RPC/WebSocket API including transaction submission. As of v3.2.0 (targeting June 15 2026) the software is being renamed rippled -> xrpld, decoupling the name from Ripple the company and delivering a 30-40% memory-footprint reduction plus rounding/number-handling fixes. Builders submit transactions and query live/consensus data through a rippled/xrpld node (or an upstream provider's node).
- **Chain:** xrpl-mainnet · **Enabled:** 2026-06-15 · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** JSON-RPC + WebSocket API; methods: submit, submit_multisigned, fee, server_info, server_state, ledger_current, ledger_closed, account_info, account_objects, tx, path_find, ripple_path_find; config rippled.cfg (now xrpld.cfg); modes: validator vs stock/tracking node; online_delete + ledger history retention. Current line: 3.1.x enabled on mainnet; 3.2.0 = rename + perf.
- **Gotchas:** Use a node (or provider) on the right software version or you risk amendment-blocked state and stale features. Full-history nodes are storage-heavy; most operators run with online_delete and keep only recent history - for deep history use Clio or a full-history provider. Submission MUST go to rippled/xrpld (Clio forwards submit/fee to it). The 3.2.0 rename means config/binary names change; CI and tooling referencing 'rippled' should track the 'xrpld' rename. Public clusters (s1/s2) rate-limit; run your own node for production.

### Transaction cost & fee escalation · `concept` · ● live ✓
Every transaction destroys a small amount of XRP as its cost (anti-spam, deflationary). The reference/base cost is 10 drops (0.00001 XRP) for a standard transaction. Under load the open-ledger cost escalates exponentially once a soft per-ledger transaction limit is reached, so transactions that don't meet the open-ledger cost but exceed the local load cost get queued for a later ledger. The actual required fee = base_fee * load_factor / load_base, queried live via the fee API method.
- **Chain:** all · **Enabled:** 2012-06-01 · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** Fee field (in drops, set before signing); reference cost 10 drops; multipliers: SetRegularKey reset = 0 drops, multisigned = 10 * (1 + number of signatures), AccountDelete = 2,000,000 drops (2 XRP), EscrowFinish with fulfillment = 10 * (33 + fulfillment_bytes/16). API: fee (drops.base_fee, drops.open_ledger_fee, queue stats), server_info (load_factor), server_state.
- **Gotchas:** The Fee is destroyed even if the transaction FAILS (tec/tem/tef results still burn the fee on tec; only certain reject codes avoid inclusion). Hardcoding 10 drops breaks during congestion - always query fee and pad. AccountDelete costs 2 XRP and can only run if the account has no blocking objects and meets a sequence-gap rule. Multisign and EscrowFinish-with-fulfillment cost materially more. Queued transactions can expire or be replaced; manage Sequence/LastLedgerSequence carefully.
- **Build-focus tracks:** [game-economies](track-game-economies.md), [nft-assets](track-nft-assets.md), [payments](track-payments.md)
- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed | net-check: mainnet-live | currency=current | Transaction cost mechanism with base fee and escalation under load is accurately described and operational.
- **Sources:** [Transaction Cost](https://xrpl.org/docs/concepts/transactions/transaction-cost) — The reference transaction cost is 10 drops and escalates via the open-ledger cost under load; AccountDelete costs 2,000,000 drops and multisign costs 10 drops per signature.

### Validators & Unique Node List (UNL) · `concept` · ● live ✓
Each XRPL server is configured with a Unique Node List (UNL): the set of validators it trusts not to collude. Only validation votes from UNL members count during consensus; votes from non-UNL validators are ignored. Most operators do not hand-curate a UNL - they subscribe to a published, signed validator list (vl.ripple.com historically, with the network migrating toward an XRPLF-published default UNL in 2025). The UNL is where the network's trust assumptions live: safety depends on UNLs overlapping by a sufficient margin across the network.
- **Chain:** all · **Enabled:** 2012-06-01 · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** validators.txt config (validator_list_sites, validator_list_keys); signed validator list (vl) with manifests; server_info -> validation_quorum; quorum is ~80% of trusted+available validators. API to inspect: validators, validator_list_sites, manifest.
- **Gotchas:** Running your own validator does NOT mean others trust you - you must be added to their UNLs / a published vl to influence consensus. UNLs across the network must overlap (>~90% recommended) or the network can fork. The default-UNL publisher key matters: a 2025 migration changed the canonical publisher; ensure servers trust the current XRPLF list. Validators earn no direct protocol reward (no staking yield); they run for ecosystem reasons.
- **Build-focus tracks:** [identity-compliance](track-identity-compliance.md)
- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed | net-check: mainnet-live | currency=current | UNLs are fundamental to XRPL consensus, with ongoing community management of default lists.
- **Sources:** [Unique Node List (UNL)](https://xrpl.org/docs/concepts/consensus-protocol/unl) — A UNL is a server's list of validators it trusts not to collude, determining which validation votes it counts. ; [Default UNL Migration](https://xrpl.org/blog/2025/default-unl-migration) — The XRPL community migrated the default/published Unique Node List arrangement in 2025.

### XRP Ledger Consensus Protocol (XRP LCP) · `concept` · ● live ✓
XRP LCP is the federated Byzantine agreement protocol that the XRP Ledger uses instead of proof-of-work or proof-of-stake. Its only job is to make trusted validators agree on which set of candidate transactions and their order go into the next ledger; it does not vote on transaction outcomes (those are deterministic given the set). Consensus rounds close a new ledger roughly every 3-5 seconds, and a ledger becomes validated and immutable once a supermajority of a server's trusted validators agree on its hash. Energy-efficient and final-on-validation (no probabilistic confirmations like Bitcoin).
- **Chain:** all · **Enabled:** 2012-06-01 · **Maturity:** stable · **Use:** recommended
- **Key fields / API:** Validated ledgers (build against ledger_index validated, never current/closed for finality); ledger close ~3-5s; consensus rounds operate in deliberation/establish/accept phases; finality = validated (no reorgs of validated ledgers). API: server_info (validated_ledger, complete_ledgers), ledger with ledger_index: validated.

### XRP native asset · `concept` · ● live ✓
XRP is the XRP Ledger's native asset, created at genesis with a fixed maximum supply of 100 billion. ### Negative UNL · `concept` · ● live ✓
The Negative UNL is a liveness feature that lets the network keep validating ledgers during a partial outage. When trusted validators go offline, consensus temporarily reduces the effective quorum by disregarding the unreliable validators, so forward progress continues even with several validators down. Validators are added/removed via UNLModify pseudo-transactions at flag ledgers based on a measured reliability threshold (added below ~50% reliability over the last 256 ledgers, removed above ~80%).
- **Chain:** xrpl-mainnet · **Amendment:** NegativeUNL · **Enabled:** 2021-12-09 · **Maturity:** stable · **Use:** situational
- **Key fields / API:** UNLModify pseudo-transaction; flag ledgers (ledger_index % 256 == 0, ~every 15 min); reliability = % of last 256 ledgers where the validator's vote matched consensus; at most one add and one remove per flag ledger; safeguard: quorum can never drop below 60% of total UNL entries; Negative UNL considered 'full' at 25% of configured validators.
- **Gotchas:** Improves liveness, NOT safety - it does not let a smaller group rewrite history. If MORE than ~20% of validators drop simultaneously, the network may stall on validated ledgers until the Negative UNL adjusts over successive rounds (degrades gracefully for slow 1-2-at-a-time outages, not sudden mass outages). Builders should treat brief validated-ledger gaps during incidents as expected and wait for validated, not panic on current-ledger latency.
- **Build-focus tracks:** [payments](track-payments.md)
- **Verify:** cross-family(deepseek-v3.1:671b)=confirmed | net-check: mainnet-live | currency=current | NegativeUNL amendment is enabled on mainnet and improves network liveness by handling offline validators.
- **Sources:** [Negative UNL](https://xrpl.org/docs/concepts/consensus-protocol/negative-unl) — The Negative UNL improves liveness by letting servers adjust effective UNLs based on which validators are online, and cannot reduce quorum below 60% of total UNL entries.

### Permissioned Domains · `amendment` · ● live ✓
PermissionedDomains creates rule-based, credential-gated environments on the public ledger so institutions can restrict who may participate in certain activity (e.g., permissioned DEX trading or lending) while still using XRPL's shared security and transparency. It builds on the Credentials amendment: a domain defines which credentials are accepted, and participants must hold a matching credential to act inside it. It was enabled on mainnet on 2026-02-04 with more than 91% validator support.
- **Chain:** xrpl-mainnet · **XLS:** XLS-80 · **Amendment:** PermissionedDomains · **Enabled:** 2026-02-04 · **Maturity:** new · **Use:** situational
- **Key fields / API:** Transaction: PermissionedDomainSet, PermissionedDomainDelete; ledger object: PermissionedDomain; references accepted Credential types/issuers; integrates with permissioned DEX (DomainID on Offers) and the Lending Protocol. Depends on Credentials amendment (issuer-signed on-ledger credentials).
- **Gotchas:** Newer amendment (live Feb 2026) - SDK/tooling support is still maturing; verify your client library version. Permissioned domains only constrain activity that is domain-aware (e.g., permissioned offers); they do not make the whole account private. Requires the Credentials primitive to be understood and issued correctly - misconfigured credential acceptance can lock legitimate participants out. fixCleanup3_1_3 (enabled May 2026) shipped fixes touching Permissioned Domains, so build against post-3.1.3 behavior.

### Batch transactions (BatchV1_1 revival) · `amendment` · ◐ pending ✓
Batch (XLS-56) lets a single signed transaction atomically apply multiple inner transactions with modes such as all-or-nothing, only-one, until-failure, and independent. It is a powerful primitive for multi-step game/DeFi actions, but its rollout is a cautionary tale: the original Batch and fixBatchInnerSigs amendments were found to contain a critical signature-bypass flaw (discovered Feb 19 2026 by Cantina AI's Apex tooling) while still in validator voting, and were marked unsupported in the emergency rippled 3.1.1 release (Feb 23 2026). A corrected BatchV1_1 was proposed with stricter authorization and signer-validation guards.
- **Chain:** xrpl-mainnet · **XLS:** XLS-56 · **Amendment:** BatchV1_1 · **Maturity:** experimental · **Use:** avoid
- **Key fields / API:** Transaction: Batch with RawTransactions (inner txns) and BatchTxn fields; flags: tfAllOrNothing, tfOnlyOne, tfUntilFailure, tfIndependent; inner-txn signing rules (the area that was hardened in BatchV1_1). Amendments: Batch + fixBatchInnerSigs (DISABLED/unsupported as of 3.1.1), BatchV1_1 (corrected proposal).
- **Gotchas:** Do NOT build on the original Batch amendment - it is explicitly unsupported as of rippled 3.1.1 and will not activate. Track BatchV1_1 status before relying on atomic batching; as of mid-2026 it is the corrected-but-not-yet-confirmed-enabled successor, so treat as pending/experimental. The flaw was an inner-signature/early-exit authorization bypass - exactly the kind of subtle multi-sig hazard that makes batching risky; wait for the audited, enabled version. This entry exists to stop builders from coding against a withdrawn amendment.
